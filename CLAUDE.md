# GamblingGnomes — Project Conventions

## Tech stack (mirrors ProjectGamble)

- **Unity** with **URP** (`com.unity.render-pipelines.universal`).
- **Netcode for GameObjects** (`com.unity.netcode.gameobjects`) for multiplayer — server-authoritative model.
- **New Input System** (`com.unity.inputsystem`).
- **DOTween** (`Assets/Plugins/Demigiant`) for tweening.
- **Odin Inspector** (`Assets/Plugins/Sirenix`) for inspector tooling — used selectively, not everywhere.
- **Facepunch.Steamworks** (`Assets/Plugins/Facepunch.Steamworks`) for Steam integration.
- **Addressables**, **Timeline**, **Visual Effect Graph**, **Post-processing** as needed.
- C# language version: 9.0.

All of the above packages/plugins have already been installed/copied into this project to match ProjectGamble (`Packages/manifest.json` + `Assets/Plugins/`).

## Folder structure

Follow ProjectGamble's layout:

```
Assets/
  Scripts/
    Game.Runtime/   — all gameplay code (asmdef: Game.Runtime)
    Game.Editor/    — editor-only tooling (asmdef: Game.Editor, includePlatforms: Editor)
  Prefabs/
    UI/             — UI prefabs, with Buttons/ and feature subfolders colocating anim + controller assets
  Scenes/            — Bootstrap.unity (or equivalent) + Gameplay.unity pattern: bootstrap scene loads gameplay
  Fonts/             — one folder per font family
  Textures/
  Materials/
  Configs/           — ScriptableObject data assets
  Resources/         — kept minimal (only assets that must be Resources.Load'ed, e.g. DOTweenSettings)
  Plugins/           — third-party libs dropped in as source/DLL (Demigiant, Sirenix, Facepunch.Steamworks)
  Settings/          — URP assets, Input Actions, volume profiles, Build Profiles
```

Do not scatter scripts outside `Assets/Scripts/`. Do not create per-feature asmdefs — keep the flat two-assembly split (`Game.Runtime` + `Game.Editor`) unless the project grows enough to justify splitting.

## C# code conventions

**Namespaces**: mirror the folder path exactly, rooted at `Game.Runtime` / `Game.Editor` (e.g. a script in `Scripts/Game.Runtime/UI/Poker/` → `namespace Game.Runtime.UI.Poker`).

**Naming**:
- PascalCase for all types; file name matches class name.
- UI `MonoBehaviour`s prefixed `UI` in code (`UIButton`, `UIManager`) — no underscore in the C# identifier.
- Feature/domain prefix for grouping instead of relying only on namespaces (e.g. all poker-specific classes start with `Poker*`).
- Suffixes carry meaning: `*Manager` (singleton-style coordinators), `*Controller` (behavior/logic owner), `*Data` (NetworkBehaviour holding `NetworkVariable`/`NetworkList` state — the "model"), `*Stage` (state-machine step), `*Visual` (presentation-only component), `*Database` (ScriptableObject lookup table), `*Constant`, `*Settings`.
- Interfaces prefixed `I` (`IGameMode`).

**Base types**:
- `NetworkBehaviour` for anything with server-authoritative state.
- Plain `MonoBehaviour` for local/visual-only components.
- `ScriptableObject` (with `[CreateAssetMenu]`) for static config/data assets.
- Structs implementing `INetworkSerializable, IEquatable<T>` for small networked value types (like `CardData`).
- Abstract base classes for pluggable step/ability systems (e.g. a `*Stage` base with `StartStage`/`EndStage`, subclassed per concrete stage; an ability base with lifecycle hooks like `OnInitialize/OnActivateServer/OnActivateClient/OnDeInitialize`).

**Fields & properties**:
- `[SerializeField] private Type _fieldName;` — underscore-prefixed camelCase for private serialized fields.
- `[field: SerializeField] public Type Foo { get; private set; }` for "inspector-set, code-read-only" public members.
- `[HideInInspector] public NetworkVariable<T> Foo = new(...);` — public field (not property) for NGO NetworkVariables, hidden from inspector.
- `[Header("Section Name")]` to group inspector fields logically (e.g. "Player Info", "Game State", "References").
- Constants in PascalCase, not SCREAMING_CASE (`private const int MinimumPlayersToStart = 2;`).
- No regions. No XML doc comments. Comments are rare — only for non-obvious business logic, one line max.

**Patterns**:
- Singleton managers: hand-rolled `public static X Instance { get; private set; }`, set in `Awake()` with a duplicate-destroy guard. No generic `Singleton<T>` base.
- Data/logic split: put networked state in a dedicated `*Data` `NetworkBehaviour` (model), expose it via a `Data` property from the owning controller/stage (logic), keep UI as a separate view that reads `Data` and subscribes to its change events.
- State machines: a list of stage objects + current index, `NextStage()` calling `EndStage()`/`StartStage()` on transition.
- Event-driven sync: plain `event Action`/`event Action<T>`, subscribed in `OnNetworkSpawn`/`OnEnable`, unsubscribed symmetrically in `OnNetworkDespawn`/`OnDisable`. Prefer `NetworkVariable<T>.OnValueChanged` / `NetworkList<T>.OnListChanged` for state→view sync over manual RPC broadcasts of state.
- RPCs: use the modern NGO attribute style `[Rpc(SendTo.Server, ...)]` / `[Rpc(SendTo.Owner, ...)]`, not legacy `[ServerRpc]`/`[ClientRpc]`. Method names keep the `RPC` suffix (`ActivateRPC`, `ReadyRPC`).
- Async: use Unity's native `Awaitable`/`Awaitable<T>`, not UniTask or coroutines, for new async code. Every async operation takes `CancellationToken ct = default` and undoes its own setup on cancel; a temporary handler subscribed inside an awaitable wrapper is unsubscribed on *every* path, cancel included. `async void` is banned except for a Unity/UI event handler, and that handler catches. **A re-entry guard flag is released in `finally`, never on the success path alone** — one throw and the button is dead for the rest of the session (`UIFindLobby`, `UIPauseMenu`, `GameNetworkManager._joiningLobby`). UI handlers pass `destroyCancellationToken`, so an await outliving its object unwinds instead of writing into a corpse.
- Tweens: cache `Tween` references in a field, `.Kill()` before restarting.
- No DI container / service locator. Wire dependencies via `[SerializeField]` inspector refs or static `Instance` singletons.
- **Never resolve a dependency with `FindFirstObjectByType`/`FindAnyObjectByType`/`Camera.main`** (editor tooling excepted) — a dependency arrives serialized, is handed over by its owner's lifecycle (`Initialize(owner)`), or comes from a registry that sets itself up and tears itself down in its own lifecycle (`GameCamera`, `PokerSeat`). A *spawned* prefab is the case that needs the registry: it cannot serialize a reference to the scene it lands in.
- No polling. `Update`/`LateUpdate` is for genuinely continuous work (look smoothing, camera follow) — never for detecting that something changed, and never for `GetComponent`, `Instantiate`, `Find*` or allocation. Cache lookups in `Awake`/`Initialize`.
- Odin Inspector (`[ValueDropdown]`, `[FoldoutGroup]`, etc.) only where plain `[SerializeField]`/`[Header]` can't express the need (dynamic dropdowns, foldout grouping) — not as the default on every class.

## Design principles

Hold code to an industry-standard design bar rather than inventing bespoke structure. When facing a design choice, reach for the solution many teams already converge on; check whether this codebase (or the wider industry) already has the shape for it before writing a new mechanism.

- **SOLID + KISS + DRY.** Split into clear modules that can be reused and assembled, not monoliths.
- **Minimise coupling.** A component that needs a dependency takes it from an event or an injected reference rather than reaching into a concrete singleton — a module that can only work in the one place it grew up in is not reusable.
- **Domain-agnostic mechanism, concrete domain code.** Genericity is a property of the module boundary, not of every line. A reusable mechanism carries no poker/Steam/lobby word in its name or API (`PlayerGlassesController`, `PlayerActionAnimator`, `PlayerSpawnPoint` — the mechanism is the same whatever sits in it). Code built on top of it stays explicit: `DealCardToPlayer`, `CollectBlinds`, `OnChipsWagered` — never `Assign`, `Process`, `OnValueChanged`. **A name must state its purpose on sight; that outranks genericity.** A vague name in domain code is a defect, not an abstraction.
- **Don't over-generalize.** Structural abstraction (interface, type parameter, base hierarchy) costs something: two real uses justify it, one does not. Write the concrete case, and pull the mechanism out when the second caller actually arrives. Duplication twice is a signal, three times is a refactor.
- **Data, logic and visual are three responsibilities, never mixed in one class.** Data owns state (`NetworkVariable`, serialized config) and no behaviour; logic owns rules and transitions and touches no `Renderer`/`Animator`/`Image`/tween; visual renders and animates and never decides a rule or writes authoritative state. Visual *reacts* to data through events and `OnValueChanged` — it never drives. `PokerGameData`/`PokerGameMode`/`PokerVisual` and `PlayerData`/`PlayerController`/`PlayerVisual` are the reference shapes.
- **Downward references only.** `GameModeController` → `PokerGameMode` → `PokerModule`/`PokerStage`; a child never calls up, it raises an `event` the parent listens to. Cross-module talk goes through events or a small shared contract, not a reach into the other module's concrete type.
- **Template method for extension points.** A base class keeps its own step non-virtual and calls a `protected virtual` hook from inside it, so a subclass extends behaviour without the parent ever being edited, and shared work can't be skipped by a subclass that forgets `base.Foo()`:

  ```csharp
  private void Tick(float deltaTime)
  {
      // shared work the base always does
      OnTick(deltaTime);
  }

  protected virtual void OnTick(float deltaTime) { }
  ```

  The outer method carries the invariants (guards, ordering, state flags); the `OnX` hook carries only the subclass's own work. Applies to every extension point, not just tick — `Start`/`End`, `Bind`/`Unbind`, `Enable`/`Disable`. See `PokerStage` (`StartStage`/`OnStartStage`), `UIPokerView` and `PokerVisual` (`OnBind`/`OnUnbind`).
- **Every system has an explicit lifecycle.** Bind and unbind through paired hooks — `OnEnable`/`OnDisable`, `OnNetworkSpawn`/`OnNetworkDespawn`, `OnBind`/`OnUnbind`, or a static `OnInstanceChanged`-style event. Never poll for a dependency in `Update()` and rebind when you notice it changed: that hides the binding in the per-frame path and leaves no single point where the subscription is released, so handlers leak. Unsubscribe in the reverse order of subscribing, and null a reference only after the unsubscribe that needs it.
- **Animate with DOTween, not hand-rolled interpolation.** A per-frame `Vector3.Lerp`/`Quaternion.Slerp` toward a moving target bakes the curve into decay maths and offers no hook for "then do this". A tween makes easing, duration, delay, loops, callbacks and sequences tunable after the fact. Expose duration and `Ease` as `[SerializeField]` so they can be retuned without touching code, and prefer `SetEase` over hand-tuned constants.

## Scenes and lifetimes

Two lifetimes: `Bootstrap.unity` is persistent, `Gameplay_*.unity` is loaded additively and disposable.

- Bootstrap owns the services that outlive a match — `NetworkManager`, `GameNetworkManager`, `SteamController`, `GameCamera` + the Cinemachine brain, `UIManager`'s canvas. Gameplay owns the mode, the table, the seats and the players.
- **Bootstrap code must not reference gameplay types.** Gameplay consumes bootstrap services through their registered instance or an interface, never the other way round.
- Gameplay must survive being unloaded and reloaded without leaking a handler or a static: every `+=` in a spawn/enable hook has its `-=` in the mirrored despawn/disable hook, and every static holding state resets under `[RuntimeInitializeOnLoadMethod]`.
- Never assume gameplay is loaded from bootstrap code; go through the async load path. Scene operations in a networked session go through `NetworkManager.SceneManager`.
- Exactly one `Camera` + `CinemachineBrain` exists, and it lives in bootstrap. Everything else — the player prefab's first-person rigs, any cutscene rig — is a `CinemachineCamera` the brain blends to. Never hand-drive `Camera.transform`.

## Netcode rules

- Server is authoritative for spawn/despawn and for every rule. Owner-write `NetworkVariable`s are for input-shaped state only (look angles, identity).
- **Set `readPerm`/`writePerm` explicitly on every `NetworkVariable`** — never rely on the defaults. See `PokerAbilityModule`, `PlayerManager`.
- **A replicated value has one seeder, and a spawn-time write on another component is an ordering bug.** When a central system takes ownership of a value, delete the local `OnNetworkSpawn` seed in the same change: `PokerBloodExchangeModule` kept `Enabled.Value = _enabledByDefault` after the match config began seeding it, and because module components sit after `PokerGameMode` in the prefab, the stale seed would have run second and silently stomped a pre-scene "off" — an override that only fails for whoever configured it.
- **Saving a prefab that carries a `NetworkObject` auto-appends it to `DefaultNetworkPrefabs` — even when an entry already names the same asset.** Rebuilding `Player_Poker` as a variant left the list with one dead entry (the old root fileID) and one auto-added duplicate; NGO warns about duplicates at every startup. After any save that creates or re-roots a networked prefab, re-point the dead entry and deduplicate by object, then grep the `.asset`.
- Guard server-only work with `IsServer` and owner-only work with `IsOwner` at method entry, not halfway down.
- Don't write a `NetworkVariable` every frame; throttle by a meaningful delta.
- **Subscribe to another object's singleton from `Start`, never `OnEnable`.** Objects in one scene wake in no guaranteed order, so an `OnEnable` reading `GameNetworkManager.Instance` can find null, subscribe to nothing, and never try again — silently deaf for the session, with the symptom appearing only on whichever path happens to lose the race. `UINetworkLoadingBinder` lost it on the host and won it on the client, which read as "loading works for clients only". Pair `Start` with `OnDestroy`, as `UIMainMenu` and `UIPauseMenu` already do.
- **A third-party SDK's callbacks are a singleton too, and subscribing before it is initialised loses them.** `GameNetworkManager` hooked `SteamMatchmaking.OnLobbyCreated` in `OnEnable`, and `SteamController.Awake` is what calls `SteamClient.Init` — two objects in one scene, no guaranteed order. Lose that race and Steam opens the room while `OnLobbyCreated` never arrives, which is where the host is started and the gameplay scene loaded: the lobby exists, the game never begins, and nothing is logged. It now binds from `Start` **and** from `SteamController.OnInitialized`, guarded by a flag so whichever happens first wins and the second is a no-op; `OnDestroy` drops both. `StartHost` also refuses through `OnConnectFailed` when nothing is bound, because a start that cannot possibly finish must say so rather than look like a scene that would not load.
- **Hide a loading screen on `OnLoadComplete` for the local client, not `OnLoadEventCompleted`.** The latter is the server's "everyone is in" and is never raised for a client that arrives through synchronization — which is how anyone joining an existing table gets the scene, so their screen would stay up forever. `OnLoadComplete` fires on both paths and the local client id is what makes it ours; `OnSynchronizeComplete` is the backstop for a client that synchronizes without loading anything. See `UINetworkLoadingBinder`.
- **Handle late join by reading the current value in `OnNetworkSpawn` and snapping to it** — a client that only subscribes to `OnValueChanged` shows nothing until the next change, which for a value set before it joined is never.
- Teardown belongs in `OnNetworkDespawn`, not `OnDestroy`.

## UI structure

- `UIManager` is the single canvas, living in bootstrap and surviving additive gameplay loads. Features never ship a canvas of their own; they `Show` into a layer (`UILayer.Hud` / `Screen` / `Overlay`). The layers exist so an overlay can open without disturbing the HUD beneath it.
- **The `CanvasScaler` lives on the `UIManager` canvas only** — one on a child canvas silently rescales everything under it. Scale With Screen Size, 1920×1080, Match Width Or Height 0.5, which survives both 21:9 and 4:3.
- Full-screen panels anchor `(0,0)`–`(1,1)` with zero offsets; corner HUD anchors to its corner. Anything inside a layout group needs an explicit `LayoutElement` — unconstrained children are the cause of most "looked fine at 1080p" bugs.
- **A frame that gets stretched carries a 9-slice border; a decorated shape does not.** The border lives on the sprite in **Single** mode — Multiple is for cutting several sprites out of one file, not for slicing — and the `Image` must be set to Sliced to use it (`button_Default`/`button_press` at 16, the `time_*` capsules at 16 across and 0 vertically, since only their length changes). Art with a shaped end is the exception: `button_ability_default`'s arrow head has to scale as one piece, and slicing it on a button 38 tall against art drawn at 102 pinches the head — that one stays Simple. `fillAmount` and 9-slice are the same setting, so a progress bar slices its track and leaves the fill Filled.
- **A fan of cards turns about a point below them, never about each card's own middle.** Rotating a card in place splays its top one way and its bottom the other, so the row opens gaps along the bottom edge while overlapping at the top — it reads as skewed tiles, and no amount of tuning the angle fixes it because the shape is wrong. `UIPokerRankingPanel.PlaceOnFan` sits the cards on a circle centred `_communityFanRadius` below the row: they lean away from one shared point, the outer ones ride lower than the middle, and the whole arrangement comes out of a number anybody can picture — how far down a hand holding it would be. Placing them takes the layout group off that row, since a group owns position and would put them straight back in a line; that is allowed here because the count is small, fixed by the rules, and entirely the panel's business.
- **Padding is measured off the art, not off the rect.** `table_ranking`'s rolled bar overhangs the plank at both ends, and a 9-slice keeps that overhang at its authored size however wide the board is stretched — so the usable wood is inset from the `Image` rect by a fixed amount, and a layout group padded to the rect puts its rows on transparency outside the board. Read the inset off the sprite and pad past it; the failure renders as content hanging off the edge of the frame rather than as anything a number in the inspector would warn about.
- **A HUD prefab that only exists at runtime is still previewable, and a UI is not built until it has been looked at.** Instantiate it under a `ScreenSpaceCamera` canvas with the project's scaler in a throwaway additive scene, fill the rows by hand, `ForceRebuildLayoutImmediate`, render the camera to a `RenderTexture` and write a PNG. One render caught three real defects arithmetic had not — "2nd" ellipsised inside a column sized for "1st", a name losing its tail, and rows spilling past the board's edge — and every one of them would have shipped as "it looked right in the hierarchy".
- **UI prefabs split into `Prefabs/UI/Components/` and `Prefabs/UI/Screens/`.** A component is a piece worth reusing — `UI_MenuItem`, `UI_ProgressBar`, `UI_TimerBar`, `UI_SelectionPointer`, `UI_TitleLabel`, `UI_Background`; a screen composes them as nested prefab instances, so restyling every menu entry in the game is one edit to one prefab. A screen root is full-screen `(0,0)`–`(1,1)` with zero offsets and carries its own `CanvasGroup`. **A screen nested inside `UI_Manager` is still a screen** — `Screen_FindLobby`, `Screen_RoomSetting` and `Screen_Pause` were built straight into the manager prefab and so were the one place in the project where a restyle had to be done by hand; they are prefab instances now, like `Screen_MainMenu` and `Screen_Loading` always were.
- **The second time a widget is drawn, it becomes a component prefab — and the thing driving it becomes one component.** Five views each carried their own `Image _timerFill` + `TextMeshProUGUI _timerLabel` and the same two lines of `fillAmount`/`CeilToInt`, on three different sprites: the clocks had visibly drifted apart because nothing tied them together. `UITimerBar` (`SetTime(remaining, normalized)`, mm:ss, urgent colour near zero) plus `UI_TimerBar.prefab` is now the single answer, and the views hand it numbers instead of drawing. A repeated widget left loose does not stay in sync — it just fails to, quietly, one prefab at a time.
- **Swapping a loose object for a prefab instance: resolve the victims before instantiating, and re-point references by search.** The replacement usually wants the old object's name, so a `Find` done *after* it exists hands back the new one to be destroyed. And a serialized field pointing at the old object is not always the one you expected — walk every component's `SerializedObject` for an `objectReferenceValue` equal to the old object and repoint it, rather than naming fields by hand and leaving the ones you did not think of dangling.
- **A list of choices marks its selection once, from the group.** `UISelectionGroup` owns the single pointer and slides it to whatever is chosen; `UISelectionItem` only says where the pointer should aim (`PointerAnchor`, normally the label so the mark lands after the last letter, whatever the word). The item's own look comes from `UIButtonState.Selected`, which outranks `Hovered` — being chosen survives the mouse wandering off, and that is the difference the two states exist to draw.
- **Let uGUI own focus; never hand-roll navigation beside it.** The EventSystem already moves selection with arrows, WASD, d-pad and both sticks, already routes Submit into `Button.onClick`, and already skips entries that are not interactable — a second navigation loop reading its own `Navigate` action does not replace that, it runs *alongside* it and the two fight over what is current. `UISelectionItem` implements `ISelectHandler` and raises `OnPointed` from it, and hover calls `EventSystem.SetSelectedGameObject` rather than marking the item directly, so pointer and keyboard feed one focus. `UISelectionGroup` then only follows that focus and slides its pointer. Consumers subscribe to `OnSelectionChanged` alone and are right for mouse and controller together.
- **A group that hides releases its selection, and remembers it separately.** Keeping `Selected` pointing at the old entry makes the very same entry arriving again look like "nothing changed", so the early-out fires and the button is never re-marked nor the pointer moved — it stays wherever `KillMove` cut the tween, which is how `UISelectionGroup` ended up aiming between two entries. Clear it on disable, stash it in `_lastSelected`, and re-offer it on enable behind `_restoreSelectionOnEnable`, re-checking that it is still active and interactable rather than trusting it.
- **Activating a parent runs its `OnEnable` before its children are switched on.** A list asking which of its items is active during its own `OnEnable` gets "none" on every re-show — it only works on scene load, where everything is activated before any `OnEnable` runs, which is exactly the kind of bug that passes the first test and fails the second. Do the work again on the next frame (`UISelectionGroup.ResnapAfterLayout`) rather than trusting the enable pass.
- **Anything that reads a laid-out rect runs in `CanvasUpdate.PostLayout`, not in `OnEnable` and not a frame later.** Implement `ICanvasElement`, call `CanvasUpdateRegistry.RegisterCanvasElementForLayoutRebuild(this)` when the answer needs recomputing, and do the work in `Rebuild(CanvasUpdate.PostLayout)` — uGUI's own "layout is settled" pass, in the same frame, after every rect has its final size. `UISelectionGroup` resolves its selection and places its pointer there. Reading in `OnEnable` gives a rect of zero (and on a re-show the children are not even active yet); `ForceRebuildLayoutImmediate`, a next-frame retry and a "hide until the rect looks real" guard are each a partial patch for the same missing hook, and each one leaves a case behind. Unregister in `OnDisable`/`OnDestroy`, and re-request from `OnRectTransformDimensionsChange` so a resize or a longer translation re-aims without polling.
- **A layout group nested in another reports its own size; never put a `ContentSizeFitter` on it as well.** The fitter sizes the child from its contents while the parent sizes it from what it reports, and with the parent's `childControl*` off neither ever writes a number — both rows land at `sizeDelta (0,0)` and stack on the same spot, which reads as a broken prefab. Turn the parent's `childControlWidth`/`childControlHeight` **on** and delete the fitter: a `HorizontalLayoutGroup` is already an `ILayoutElement` and answers for itself (`UI_IconCounter` inside `VitalsPanel`).
- **A container that sits inside a layout group carries its own `LayoutElement`.** A plain `RectTransform` reports no preferred size, so the parent gives it none and every child collapses into the same spot — the failure looks like a broken prefab, not like a missing component.
- **A row or column of widgets is an auto-layout group, never hand-placed anchors.** Sizes change, buttons get hidden, translations get longer — a `HorizontalLayoutGroup` with a `LayoutElement` per child reflows for all three, where authored positions leave a hole exactly where the hidden widget sat. `ActionBar`/`CallActionBar` keep their buttons in a stretched `Buttons` row for that reason; only genuinely fixed furniture (a corner label, a timer fill) stays anchored.
- **A screen with several sections splits into one component per section, never one class branching over every widget.** `UIPokerView` subclasses (`UIPokerStagePanel`, `UIPokerActionBar`, `UIPokerRankingPanel`, …) each own their own widgets and bind through `OnBind`/`OnUnbind`; the host only holds the list and fans the refresh out. A new HUD section is a new view plus a list entry, not another branch.
- Widget logic and visual stay split, as everywhere else: `UIButton` holds no `Image`, colour or tween — it resolves `Normal`/`Hovered`/`Pressed`/`Disabled` in that priority order and raises `OnStateChanged(previous, current)`. A `UIButtonVisual` subclass draws the answer: `UIButtonSpriteVisual` swaps the sprite, `UIButtonScaleVisual` tweens the scale, and a third backend is another subclass rather than a branch in an existing one. The base owns the subscription and snaps to the state already standing on enable, so a subclass can neither leak a handler nor appear wearing the wrong one.
- **A button puts itself back to rest after a click, and a redraw is not a transition.** uGUI delivers the pointer release to whoever took the press, so a button whose `OnClick` opened a screen never hears it and is left holding `_pressed` with nothing coming to clear it — the symptom is a button that "sometimes doesn't come back" after a click. `UIButton.ResetState()` clears the held flags and calls `RefreshState(force: true)`, and `Click` calls it unless a key is still down, because holding the key must keep holding the button. The force matters as much as the clear: a visual stranded mid-tween has made no state change, so the plain "nothing changed, nothing to do" guard is the very thing keeping it stuck — the same defect `UIWheelItemView.Bind` was fixed for. `UIButtonVisual` snaps rather than animates when `previous == current`, since a redraw has nothing to travel from. Anything else that takes the pointer away mid-press calls `ResetState()` too.
- **A key bound to a button goes through `UIButton`, and holds it down as long as the key is held.** `UIButtonHotkey` calls `UIButton.Submit()` and sets `IsPressedByKey` from the action's `started`/`canceled` — never the uGUI `Button` underneath, which is an implementation detail nothing should reach past this component for. Firing only the click is the bug worth naming: the handler runs but the button never enters `Pressed`, so a key press does everything except look like one. Bracketing the state from the action rather than timing a flash here is also what makes holding the key hold the button, exactly as a mouse does. The key shown on the face is read from the binding (`GetBindingDisplayString`) rather than typed. A visual that moves the button (`UIButtonOffsetVisual`) measures its offsets from the position captured once in `Awake` — reading the live position on each state change folds the last offset into the rest and walks the button off its authored spot one press at a time.
- **A tint a visual paints at runtime is also authored on the `Image`.** `UIButtonVisual.OnEnable` never runs in edit mode, so a prefab whose colour lives only in `_normalColor` reads white in the editor and in every prefab render — the thing looks broken long before anyone presses Play. Set both (`Button_ActionPad`, `Button_Plate`), and take the tone from the prefab that already has it rather than inventing a second one.
- **A visual that moves the button moves the art, never the `RectTransform` carrying the raycast.** `Button_ActionPad` had `UIButtonOffsetVisual` driving its own root, so pressing it slid the *hit region* down with the picture: the pointer fell outside without the user moving the mouse, uGUI raised `PointerExit`, the button returned to rest, slid back under the cursor, raised `PointerEnter` — and the press animation ended up oscillating instead of returning to idle. The fix is structural: the root keeps the `Image` and the pointer handlers and never moves; a `Content` child holds the art and the label and is what the offset and scale visuals target.
- **A button whose art is not a rectangle narrows its hit area with `UIAlphaHitArea`**, which sets `Image.alphaHitTestMinimumThreshold` (0.1) so the transparent corners stop swallowing clicks — four diamonds packed into a pad otherwise overlap in the gaps nobody drew. This needs **Read/Write enabled** on the sprite's texture, and writing the property *at all* throws without it — so the component checks `texture.isReadable` first and leaves the property alone when it cannot be used, rather than resetting it to zero and tripping the very exception it is avoiding. The raycast `Image` therefore keeps the shaped sprite (tinted fully transparent) while the visible copy lives on `Content`.
- **A `TextureImporter` setting written from a `RunCommand` may not persist** — `importer.isReadable = true; SaveAndReimport()` reported success and the `.meta` on disk still said `isReadable: 0`. Write through `new SerializedObject(importer)`, then `AssetDatabase.WriteImportSettingsIfDirty` + `ImportAsset(ForceUpdate)`, and confirm by reading the `.meta` back rather than trusting the log.
- **A button styled by a visual sets the uGUI `Button`'s Transition to None** — leaving it on Color Tint puts two components on the same `Image`, and the one that wrote last wins.
- **An overlay blends with what the canvas drew *before* it, through the blend state — never by reading the backdrop.** The canvas is Screen Space Overlay, so the UI is drawn straight to the back buffer after URP has finished: there is no grab pass, `_CameraOpaqueTexture` is not bound and would not contain the UI beneath anyway. `UI/Blend` therefore drives `Blend`/`BlendOp` from material properties and `UIBlendShaderGUI` picks the mode, which covers everything separable — Normal, Multiply, Screen, Additive, Subtract, Darken, Lighten. "Behind" means earlier in draw order, so a stroke parented to a button (last sibling of its `Content`, `raycastTarget` **off** or it swallows the click) blends with that button. Photoshop's dst-reading modes — Overlay, Soft Light, Colour Dodge/Burn — are not reachable this way at all and need a render feature copying the colour buffer; don't reach for one without that.
- **`BlendOp Min`/`Max` apply to alpha as well, so a blend mode built on them writes its alpha separately.** Darken's `min(src.a, dst.a)` punches the backdrop's alpha out wherever the overlay is transparent — invisible on the back buffer, and it destroys the image the moment the canvas renders into a `RenderTexture`, which is exactly how a HUD gets previewed here. `UI/Blend` hard-codes the alpha half (`BlendOp [_BlendOp], Add` / `Blend [_SrcBlend] [_DstBlend], One OneMinusSrcAlpha`) because every mode wants the same coverage maths. Prove it by *reading the alpha back* out of the render (`Texture2D.GetPixel(...).a`) — a viewer draws transparent as white, which reads as a blend mode that inverted rather than as an alpha channel that was erased.
- **A blend mode fades through a neutral colour, not through the blend factors.** `Blend DstColor …` ignores a `CanvasGroup` entirely and `BlendOp Min` ignores the factors outright, so a Multiply or Darken overlay would sit at full strength whatever its alpha said — a fade that visibly does nothing. `UI/Blend` lerps the source toward the value that leaves the backdrop alone (`lerp(_BlendNeutral.rgb, color.rgb, color.a)`, black for the factor modes, white for Darken's Min), which is one line and makes alpha, `Image.color` and `CanvasGroup` behave the same across every mode. The neutral is set with the factors as a set, never apart from them.
- **A custom uGUI shader keeps the stencil block and `UNITY_UI_CLIP_RECT`, or it ignores every mask in the project.** `Mask` works through the stencil properties and `RectMask2D` through `_ClipRect`; a shader written from scratch without them renders correctly on its own and then spills outside the first scroll view it is put in. Copy the state block from Unity's `UI-Default` rather than writing it fresh.
- **A shader that Shader Graph can express is built in Shader Graph, never written as code.** The project's own art already works that way (`Lit_Default`, the gnome's cell shading), and a graph is what an artist can open, retune and extend without a compile — a hand-written `.shader` makes every later change a programmer's errand. That includes URP post-processing: a full-screen effect is a **Fullscreen Shader Graph** driven by a `Full Screen Pass Renderer Feature` on the renderer asset, not a hand-rolled pass. Reach for HLSL only where the graph genuinely cannot go — a custom blend state or stencil block, which is why `UI/Blend` is still code.
- **When the overlay has exactly one image behind it, sample both in one shader rather than blending against the framebuffer.** `UI/Blend Overlay` goes on the *base* image — uGUI binds that Image's own sprite to `_MainTex`, so a button swapping art per state keeps working, where a material holding the button as a texture would go stale — and takes the stroke as `_OverlayTex`. Three things follow that the blend state cannot give: the modes that read the destination (Overlay, Soft Light, Colour Dodge/Burn) become available at all, the maths can be done in Photoshop's space, and the effect is masked by the base's own alpha instead of staining whatever else lies under the rect. That last one is usually the complaint: hardware Darken through a child Image spills past the button's silhouette because the blend unit combines with the *whole* framebuffer, and Photoshop's clipping mask has no equivalent there. Reach for `UI/Blend` only when there is no single backdrop texture — a full-screen tint over the HUD and the table.
- **A full-screen effect is a Fullscreen Shader Graph plus a renderer feature that is off until somebody is seeing it.** `Hallucination_Wave.shadergraph` offsets the blit source's UV by `sin(y * Frequency + Time * Speed) * Amplitude` and nothing else; `PokerHallucinationFullscreenEffect` switches the feature on, clones the material so the strength is never written into the asset on disk, and fades that one float from zero — which is why zero of it has to look like nothing at all. A feature left enabled costs a blit every frame for a room nobody is hallucinating in, and `SetActive(false)` is the whole cost of not doing that. Adding one from script needs both halves: `AddObjectToAsset` on the renderer, then `m_RendererFeatures` **and** `m_RendererFeatureMap` (the feature's local file id), or the renderer drops it on the next import. `Game.Runtime` had to reference `Unity.RenderPipelines.Universal.Runtime` to name the type at all. **A screen-space distortion has to taper to nothing at the frame edge**, or it samples outside what was rendered and draws a black band along the side it pushed from: the wave multiplies its offset by `sin(PI * x)`, which is 1 in the middle and 0 at both edges, so nothing is ever asked for off-screen. A `Clamp` on the final UV stays behind it as a net, not as the answer — clamping alone trades the black band for a smear of the edge pixel.
- **A `.shadergraph` is a stream of JSON objects separated by one blank line, so a blank line inside an object splits it.** `MultiJsonInternal.Parse` cuts at the first `\n\n` after each `{`, and the whole import then fails with `JSON parse error: Invalid value` naming nothing — a blank line put inside the graph's edge list for readability was the entire cause. Written by hand, the file is verified by importing it and asking `ShaderUtil.ShaderHasError`, and then by resolving every edge against the slots it names: Shader Graph drops an edge whose slot id does not exist **in silence**, so a graph that compiles is not yet a graph that is connected. Slot ids are per node type (Multiply `A=0 B=1 Out=2`, Sine `In=0 Out=1`, Split `In=0 R=1 G=2 B=3 A=4`, Vector2 `Out=0 X=1 Y=2`, URP Sample Buffer `UV=0 Output=2`).
- **Match Photoshop by blending in gamma, and measure it rather than eyeballing it.** Photoshop blends the 8-bit sRGB values it stores; this project renders Linear, so `LinearToGammaSpace` around the blend and `GammaToLinearSpace` after is what makes the numbers agree. Measured against Photoshop's own formulas: with the conversion every mode lands within 0.002 (half a step of 8-bit), without it Multiply misses by 0.013, Soft Light by 0.079, Overlay by 0.198 and Colour Burn by a full 0.400 — that last one is not a shade off, it is a different picture. Build the comparison by rendering flat patches and reading the pixel back; "looks about right" cannot separate 0.013 from 0.000.
- **Darken and Lighten survive the Linear colour space; Multiply and Screen do not.** The project renders Linear, so hardware blending is done on linear values and a Multiply will not match what the artist saw in Photoshop. `min`/`max` are the exception — the sRGB transfer curve is monotonic, so the same channel wins either way and Darken matches exactly. Worth knowing before retuning art to chase a difference that is the colour space rather than the art.
- **A pad's petals never move and never leave; only their light changes.** Every button on `UIPokerActionPad` stays in its slot and is dimmed when the moment does not allow it — a cluster whose buttons come and go has no shape to learn, and the shape is the entire reason a fixed control scheme exists. The one exception stays the one already written below: a verb the *mode* does not have (`Button_Report` without the ability module) is not here rather than not now. Something that is not one of the street's answers at all — looking at your own cards — sits outside the diamond on its own key rather than being squeezed into it.
- **A button that would change its verb is a second button sharing the slot.** A call the stack cannot cover is not a call with a different price, it is an all-in — a different move, a different name, and a different thing announced to the table. Relabelling one petal makes the pad quietly mean something else while looking identical, which is the one thing a fixed control scheme must never do. `UIPokerActionPad` gives each its own petal and each sends its own action, so the notice announces the move that happened. Where the two would come to the same thing, only the honest one lights: a call costing everything is a shove, so `CanCall` goes dark and All In stays lit; an accusation whose shove adds nothing to the stake is a call, so `UIPokerReportActionPad` darkens All In instead. Name the petal after what actually happens, and the collision resolves itself. Build the second one with `PrefabUtility.InstantiatePrefab` of the same button prefab and copy the first's overrides with `GetPropertyModifications`/`SetPropertyModifications`: `Object.Instantiate` of the sibling drops the link and the copy stops receiving restyles, and re-typing its slot and key by hand is how the two drift apart.
- **Ask whether the street has a question before it posts its price, not after.** `PostOpeningBet` ran first and the "nobody left to act" guard tested `CurrentBet == 0`, so the street's own opening bet made its own guard unreachable: with the table all-in but for one player, the street put a price down and then charged the last player standing for it — money nobody could answer, on a hand whose betting was over. `PokerBettingStage.NothingLeftToAsk` is checked before the price goes down and asks the real question — fewer than two players can act, and whoever is left owes nothing. The cards still turn on every remaining street; only the asking stops, which is what running a board out means.
- **A permission about choosing a move must not refuse a player priced into it.** `_allowAllIn` is off on a call-or-fold street because nobody may *shove* there — but a short stack calling with everything is not moving the price, it is failing to cover one that is already standing, and refusing it leaves folding as the only answer to a call they can actually make. `PokerBettingStage.CanAllIn` accepts it whenever `owed >= chips` regardless of the flag, and the pad lights its petal from that same method so the two cannot drift. Read every action permission for which half it governs: the choice, or the arithmetic.
- **A shove is capped, and the cap does not apply to a call somebody is short of.** `_maximumAllIn` (4) bounds what going all-in *offers*; a player who cannot cover the price already standing still pays everything they hold, because capping that would leave them owing on a hand they meant to answer in full. `PokerBettingStage.AllInAmountFor` decides which of the two it is, and `PokerAbilityModule.MaximumAllIn` does the same for blood in an accusation — scarcer than money, so an uncapped shove there is not a raise but a dare to die.
- **A permission that changes how much of an answer is available is not one that changes the question.** `IsCallOnly` is what hands a street's verbs to the pad rather than the full bar, and folding `_allowAllIn` into it meant turning shoving on silently switched the whole pad off. Raising and checking change what the street is asking; a shove only changes the size of the answer — so it is read per-petal, never as part of deciding which UI owns the street.
- **What the rules forbid is hidden; what the player merely cannot afford is dimmed.** A greyed button says "not now", a missing one says "not here" — `UIPokerActionBar` hides raise/check/all-in on a street that never allows them and only greys what this stack cannot cover, the same way `UIPokerSimultaneousBetBar` hides fold. A stage kind that asks a different question gets its own bar rather than the full one with most of it switched off (`UIPokerCallActionBar`), and each bar decides its own visibility from the running stage so exactly one is ever up.
- **An overlay brings its own pad, and the street's leaves rather than dimming.** The fixed control scheme argument cuts both ways: a pad is learnable *because* the same petal always means the same thing, so a moment that changes both the verbs and the currency — `UIPokerReportActionPad`, answering an accusation in blood — is a different pad, not the same four petals quietly meaning something else. `UIPokerActionPad` therefore hides outright while `OverlayStageId` is set, because two pads up at once is two control schemes up at once and neither is learnable.
- **A second currency gets a second readout, never the same one with a different icon.** The report stakes blood between two players; the hand stakes money among everyone. Sharing one "Pot" line would leave the icon beside it as the only thing saying which — a distinction that survives right up until somebody glances at it. `UIPokerReportPotPanel` is its own view over the module's own `ReportPot`, drawn with the finger, and `UIPokerPotPanel` stands down while an overlay is up for the same reason the street pad does. **A notice offers one method per shape it can take, never one method with a `detail` string.** One feed says "REPORT / Beechef" and "CAUGHT / +3", and those two rows are not the same thing wearing different text: a name is drawn like the name on top of the card, a count is drawn small beside its icon. `UIPokerActionNotice` has `Show` (nothing under the verb), `ShowAmount` (a number and its currency) and `ShowTarget` (another player) — the caller picks the shape and cannot then hand it the wrong-looking content. The target row is cloned from the name label it has to match, so the two stay identical without two sets of type settings being kept in step by hand.
- **A HUD readout is about the player looking at it; the room is read off the room.** `UIPokerHallucinationBar` draws the local player's rate alone, because every rate is already public and `PokerHallucinationTagVisual` writes each one over its own head — a HUD listing four bars would be a second place the same numbers live, kept in step by hand, and it would move the reading off the faces where the guessing game happens. The bar takes its colour from a serialized ladder of `(threshold, colour)`, the same shape `PokerHallucinationTiers` uses, so the rungs stay a number somebody can picture. `UIProgressBar.SetFillColor` is the whole addition it needed: a bar whose value means different things at different heights is still just a bar.
- **A countdown reads whichever clock is actually running, never the one that was.** A turn clock and the stage clock are two different numbers, and a beat where nobody is on the clock — an overlay's own pause — has only the second. Reading `TurnRemaining` there gives a bar frozen at 00:00, which reads as a hung timer rather than as the wrong source. `UIPokerTurnPanel` and `UIPokerReportView` both pick on `Data.HasTurn`, and `WantsTick` accepts either clock or the panel stops updating the moment the turn ends.
- **A countdown is for a wait somebody is being held through, not for a beat that simply passes.** `UIPokerRankingPanel` was given a clock and a cancel button; both are gone. Nothing is being asked of the player there — the board is up for exactly as long as the showdown is, and it goes away because the stage's own timer ran out and cleared the list. A countdown over that says "hurry", and a close button offers to skip something nobody is waiting on, which then needs a dismissed flag, an entry on `UIEscapeStack` and a rule about the next ranking being a new one. Draw a clock where a player has to act before it runs out (`UIPokerTurnPanel`, `UIPokerReportView`); let a beat that passes on its own pass.
- **A transition that exists to hide a change has to actually contain it, and one number says how long.** `PokerHallucinationController` holds `_transitionDuration` and lands the rungs at its midpoint; `UIPokerHallucinationBlink` reads that same property to time the eyelids. Two numbers kept in step by hand would let the room change in front of an open eye, which is the one thing the blink was added to prevent — same shape as the verdict card reading `VerdictDuration` off the stage it belongs to. Logic owns the number, the view reads it. A change arriving mid-blink is folded into the beat already running rather than queued, because the apply reads the rate at the moment it runs and a queue would spend a second blink saying nothing new; the guard is released before the trailing re-check, or a change landing in the second half is lost.
- **`DOTween`'s UI module is not in this project, so a `CanvasGroup` is faded by value.** `DOFade` on a group compiles against `ShortcutExtensions` for `Material` and fails with a message about the wrong receiver type, which reads as a missing using rather than a missing module. `DOTween.To(() => group.alpha, a => group.alpha = a, target, duration)` is the idiom — `UIPokerBlackoutScreen` already carried a comment saying so, and reading it first would have saved the compile.
- **A moment's announcement lasts exactly as long as the moment.** The verdict card reads its lifetime off `PokerReportStage.VerdictDuration`, the same number the pause runs on, so the card cannot outlive the beat or fade before it — one number, not two kept in step. `lifetime` is the whole time on screen and the notice budgets its own fades inside it. An overlay also suppresses the table's `ActionNotice` (`PokerGameMode.SubmitActionRPC` checks `CurrentOverlay`) and announces its own moves instead: the table's prices everything off a change in `Bet`, which an overlay never touches, so it would go out as a bare verb beside the overlay's own card saying it properly.
- **A control that answers to the chair rather than to the moment is its own view — until the state answers for it, and then it is nothing.** `UIPokerCheckPanel` existed because looking at your own cards is not one of the street's answers, so it could not live on the pad that carries them; showing on `IsSeated` alone and greying on `IsInHand && CardCount > 0` was the right shape for a button somebody had to press. It is **deleted** now: the mushroom round picks cards by pointing at them, so "is this player holding cards" is derived from the cards themselves and drives `IsHaveCardOnHand` straight onto the rig. A control that asks for a state the data already answers is a second answer to a settled question, and the two can disagree. The lesson that survives it is the one about *where* such a control goes if one is ever needed again, and the one about **subscribing to `OnHoleCardsChanged` as well as `OnStateChanged`, because folding writes two replicated changes** — the status and the mucked hand — **whose order of arrival is not decided**; `PokerHandPoseController` listens to both for exactly that reason.
- **A button dropped into a layout group needs a row of its own, not just a `LayoutElement`.** `RankingPanel/Panel` runs `childControlWidth`/`childControlHeight` on with `childForceExpandWidth`, so a bare `Button_Plate` collapses to nothing — and the moment it is given a preferred size it is stretched to the full width of the plank instead, which is what `Title` (preferred 700, rendered 1340) already shows happening. The shape to copy is `CommunityRow`: an empty rect carrying the `LayoutElement` for height, with the button centred inside at its authored size. (`CancelRow` was that shape and has since been deleted with the button it held — the lesson is the layout, not the row.)
- **A key bound to a button that is not a single letter needs the badge to auto-size.** `Button_Plate`'s badge is a 30px circle authored at 14pt for one character, and a key like "Esc" needs three characters where the art has room for one. Auto-sizing with the max left at the authored size means a single letter renders exactly as before and only a longer string shrinks — measured by rendering "F", "Esc" and "Enter" through the real prefab, where "Esc" fits and "Enter" still touches the edge at the 7pt floor. (Measured on the ranking board's cancel badge, which has since been deleted; the sizing rule outlives it.)
- **A button's hotkey must not hold an action anything else runs on.** `UIButtonHotkey.OnDisable` calls `Disable()` on the action it points at, and the actions are one asset shared by the whole process — so a close button wired to `UI/Cancel` or `Player/Pause` would switch that key off for every screen in the game the first time it went away. `UIActionKeyLabel` is the safe way to put such a key on a face: it reads the binding string and never enables or disables anything, which is why the ranking board's CANCEL badge names Escape while the key itself is handled elsewhere.
- **Escape is one key with one handler, and what is on screen decides what it means.** Two actions bound to it both fire, so a board dismissed with Escape would pull the pause menu up behind it. `UIEscapeStack` is the seam: anything dismissible pushes while it is up and removes itself when it goes, `UIPauseMenu` calls `DismissTop()` before opening, and the menu is what the key falls through to rather than what it always means. Newest-first, and the handler is taken off the stack *before* it is invoked so a close that re-pushes cannot strand a stale entry.
- **Deleting an action leaves the override that pointed at it behind.** Removing `UIButtonHotkey` from a prefab instance dropped the component but left an `_action` property modification in `m_Modifications` aimed at an asset that no longer exists — invisible at runtime, and exactly the sort of thing that survives a merge. After removing an action or a component that held one, sweep every prefab and scene for `fileID`s under the actions asset's guid that no longer resolve, and strip the modifications with a null `objectReference`.
- **Panels that answer the same question share one slot, and exactly one is ever up.** "What is the table waiting on, and for how long" has one place on screen — bottom centre, a title over a `UITimerBar`. `TurnPanel`, `UI_ReportAimPanel` and `UI_ReportPanel` all take that rect and that style, and each decides its own visibility so the three can never overlap: the turn panel hides whenever `OverlayStageId` is set (an overlay hands out turns of its own, so "X'S TURN" is *true* during an accusation and still the wrong thing to be reading), and the two report panels split on phase. Build them by copying the rect and the layout group off the one that already exists, and instantiate the rows from `UI_TitleLabel`/`UI_TimerBar` with `PrefabUtility.InstantiatePrefab` — `Object.Instantiate` of a sibling silently drops the prefab link, and the copy then stops receiving restyles of the component it was copied from.
- **A beat that asks the whole room one question is its own panel.** `UIPokerReportAimPanel` puts a fixed question and a clock up for everybody while one player looks for a face; `UIPokerReportView` reports the conversation between the two people once a name has been said. Folding both into one label reads as a panel that keeps changing its mind, and the fixed half ends up written into whatever label was nearest — a title stuffed into a `UITimerBar`'s label leaves the timer nowhere to put the seconds.
- **A screen covering a wait owns a minimum visible duration, and the bar spends that hold arriving.** `UILoadingScreen._minimumShownDuration` keeps the screen up even when the load beats it, because one that flashes past reads as a glitch rather than as loading — and `Hide` hands the bar the *remaining* time (`UIProgressBar.SetProgress(value, duration)`) so it travels to full across the hold instead of sitting at 100% waiting to disappear, which reads as a stall. The guarantee lives on the screen, not on the caller: `UINetworkLoadingBinder` reports real progress and asks to hide, and every other caller gets the same floor for free.
- **A screen that hides itself hides a child, never its own GameObject** — anything driving it sits on the root too, and a component on a disabled GameObject never runs `OnEnable`, so it subscribes to nothing and no event can ever wake the screen again. `UILoadingScreen` switched off its own root in `Awake` and took `UINetworkLoadingBinder` down with it: the loading screen was unreachable from the moment the game started, and nothing logged a word. It now toggles a serialized `_content` child and leaves the root alive, holding `CanvasGroup.alpha`/`blocksRaycasts` at zero. The same trap is why a mode's HUD variant *disables* the bars it does not want rather than deleting them — read that rule as the deliberate case and this one as the accident.
- **The cursor is a counted release, and who holds one depends on whether there is anything to point at.** `PlayerController` holds `CursorController.SetBaseLocked(true)` for as long as the player lives and never releases on its own; a screen that needs pointing calls `RequestUnlock`/`ReleaseUnlock` in its own paired hooks, the way `UIPauseMenu` does, and the counter is what lets two overlap without one closing yanking the cursor out of the other. Walking around there is nothing out in the world to click, so nothing releases and the mouse only turns the view. **At the table there is** — five cards lying in front of the player — so `TableCursorController` holds a release for its whole life and gives it back only while the look button is held. That inverts the default deliberately: pointing is the common case there and turning the view is the deliberate one. What must never appear is a *toggle*, which is a second answer to the same question and desyncs the moment a panel is also holding a release. `ReadLookInput` early-outs on `!CursorController.IsLocked`, so a freed cursor stops the view turning for every holder at once rather than each one remembering to.
- **A card is an object on a table, so it is picked by pointing at it, not by a button beside it.** `PokerCardPickController` raycasts from the camera through the cursor and asks the server (`LookAtHoleCardRPC`); a row of UI buttons would be a second place the same five cards exist, kept in step by hand with every animation the real ones play. The cards therefore carry a collider — sized in `PokerCardVisual` from the sprite, because a card only knows how big it is once it has a face, and the prefab has none until the database hands it one at runtime. Pick the **nearest** hit that is one of *our* cards rather than the first: `RaycastNonAlloc` does not sort, and cards on a table overlap on purpose.
- **A card is chosen before it is taken.** `PokerCardLookStage` asks for several cards at once, so `PokerCardPickController` marks a card on the click, unmarks it on a second click, and commits the whole set only when as many are marked as the player is still owed (`ViewableHoleCards` minus what they have already turned). Lifting each card as it was clicked made every click a decision nobody could take back, and it sent the server a half-made mind one slot at a time. The lift is one number decided in one place (`ApplyLift`), with chosen outranking hovered, or a marked card drops back to the table the moment the pointer wanders off it.
- **Only a player who was dealt in has anything to look at.** The pick beat takes the view down to the row of cards, and a player who took a chair mid round has none — so `RefreshStage` asks `IsInHand` before requesting the camera state, or a spectator's view is parked on an empty spot on the table while the round happens above it.
- **A card has two places it can be, and where it is is derived rather than replicated.** `PokerPlayerData.IsHoleCardInHand(slot)` is `!HandRevealed && HasLookedAt(slot)` — lifted off the table until the hand is shown, at which point everything goes back down for the room to read. Both facts are already on the wire, so a third value would only be one more thing to fall out of step. `LookedAtHoleCards` is therefore **Everyone-read**: lifting a card is an act the whole table watches, and the face stays hidden by `IsHoleCardVisible`, which asks `IsOwner`. That is the same public-act/private-grant split the cheat abilities make, and getting it backwards means a pickup animation only its owner can see.
- **The pad's pointer is `VirtualMouseInput`, not a cursor written by hand.** It is the Input System's own answer and it creates a real virtual `Mouse` device, so everything already reading `Pointer.current` — the card picker, uGUI's raycasting — is pointed at by a stick without knowing a stick exists. `UIVirtualCursor` only decides *when* it runs, because on a keyboard the hardware cursor is the pointer and a second arrow drawn beside it is two pointers answering one hand. It subscribes to `InputSchemeController.OnSchemeChanged` from `Start`, never `OnEnable`, for the reason every other static subscription does. A **software** cursor is also what lets `CursorController` go on hiding the hardware one for a pad: the arrow the player sees is a UI Image.
- **Seated and standing are different control schemes, and that is a second look action rather than a rebind.** `Table/Look` puts the pad's left stick on the view because nobody walks at a table and the right stick is needed for the cursor; `PlayerController` reads it in place of `Player/Look` while `_bodyAnchored`. Rebinding the standing action instead would have taken walking away from the pad everywhere, to fix a conflict that only exists in a chair.
- **Locking the cursor takes the pad's pointer away with it, so the look must stop asking about the lock.** `InputSystemUIInputModule` drops every `MouseOrPen` pointer while `Cursor.lockState` is `Locked`, and the pad's cursor is a real `Mouse` — so freeing the stick to look by locking the cursor is the one move that cannot work: it kills hover and clicks in the act of enabling the look. The lock belongs to the mouse alone, and the reason is physical. A mouse is one pointer and has to choose between pointing at the cards and turning the view, which is why `TableCursorController` holds an unlock and gives it back only while the look button is down. A pad has two sticks and needs no choice, so `PlayerController.ReadLookInput` skips the `IsLocked` gate entirely while the scheme is gamepad, and the cursor stays free for the right stick throughout. `CursorController.Apply` already had the other half of it: on a pad the hardware arrow is hidden while the lock stays off, which is exactly what a software cursor wants.
- **A device the game invented is not a device the player is holding.** `VirtualMouseInput` creates a real `Mouse`, so every generic binding matches it: `InputSchemeController` read its events and flipped the scheme back to keyboard the instant the right stick moved the pad's own cursor, which then switched that cursor off — a flip-flop with no error and no log. `SchemeFor` now refuses anything whose `InputDevice.native` is false. The same fact bites the look: `Table/Look` binds `<Mouse>/delta` and `Player/Look` binds `<Pointer>/delta`, both of which the virtual mouse satisfies, so the cursor stick turned the view as well as the pointer. `PlayerController.ReadLookInput` checks `action.activeControl.device is Gamepad` against the scheme and drops anything the player is not actually holding. Reach for `native` and for the active control's device whenever a synthetic device shares a class with a real one; the binding paths cannot tell them apart and never will.
- **A `PassThrough` action performs on release as well as on press, so the callback asks what the button is doing.** `UI/Click` is PassThrough because that is what `InputSystemUIInputModule` wants of it, and every value change raises `performed` — so one click ran `PokerCardPickController`'s pick twice: the press took the card under the cursor and the release took whatever that uncovered. Nothing about it reads as an input problem; it looks like a raycast taking more than it was pointed at. Neither frame-scoped helper covers it — `WasPerformedThisFrame` sees only one half at a time because the press and the release are frames apart, and `WasPressedThisFrame` is unreliable on a PassThrough action, which has no press phase to speak of and reports the release actuation too. The value is the only thing that answers honestly: `if (!context.ReadValueAsButton()) return;`. A frame guard beside it is the *other* defect, not the same one — the action carries a binding per device it answers to and the pad's cursor is a real `Mouse`, so two controls can actuate in one frame. Read the action's **type** before deciding what an event means.
- **An action that drives the virtual cursor must be one the virtual cursor cannot drive back.** `VirtualMouseInput.leftButtonAction` was `Table/PickCard`, which binds `<Mouse>/leftButton` — and the virtual mouse *is* a Mouse, so the action was bound to the very button it was pressing. The result latches: the pad's button starts the action, the pressed virtual button keeps it actuated, releasing the pad raises no cancel, and the button never comes back up. Hover works and nothing can ever be clicked, which reads as a broken UI rather than as a loop. `UIVirtualCursor` builds its own `InputAction` on the pad's south button and hands that over; being in no asset and bound by nothing else is what makes it safe, so this is the rare case where an action must *not* be a pickable `InputActionReference`.
- **Pointing at a card and pointing at a button are one act, so they are one action.** `Table/PickCard` was a second name for `UI/Click` with the same mouse binding, which is how it came to be wired into the virtual cursor and closed the loop above. It is deleted; `PokerCardPickController` takes `UI/Click`. Deleting an action from `.inputactions` is safe only with both checks the rules already demand: capture every `action.id` first and prove none moved (33 kept, 0 moved, 1 removed), and afterwards resolve every `InputActionReference` fileID serialized in any prefab or scene against the reimported asset (30 of 30, the one miss being the `InputActionAsset` itself). Repoint the consumers *before* deleting, while the thing they point at still exists to be found.
- **A pad is given a cursor only where there is something in the world to point at.** `CursorController.IsPointerWanted` is a counted request, the same shape as the unlock beside it, and `TableCursorController` holds one for as long as there is a table. A menu asks for none, so `UIVirtualCursor` draws nothing there and uGUI's own focus runs the screen — an arrow drawn beside a moving selection is two pointers answering one hand, which is the same argument that already keeps it off a keyboard. The lock and this are deliberately different questions: one is whether the hardware arrow is free, the other is whether a pointer is wanted at all.
- **A component on the player runs on every copy of every player, so anything about *this* machine is owner-gated — and ownership is not settled in `OnEnable`.** `TableCursorController` held a cursor unlock and answered the local hold button from each remote player's copy as well as the local one; the counters hid it, since two requests and two releases still balance, and it would have surfaced as the table growing more wrong with every extra chair. It is a `NetworkBehaviour` now and binds from `OnNetworkSpawn` behind `IsOwner`, because a spawned prefab runs `Awake` and `OnEnable` at instantiate and only learns who owns it when it spawns. `OnEnable` still binds behind `IsSpawned && IsOwner` for a switch-off and on afterwards, which `OnNetworkSpawn` cannot cover: it is raised once. Bind and unbind are idempotent behind one flag, or the despawn and the disable that follows it release twice.
- **A hallucination is a ladder of thresholds, and climbing a rung draws from its pool rather than naming an effect.** `PokerHallucinationTiers` is a list of `(threshold, pool)` and nothing else — there is no "tier" type, because a tier was only ever a number with some effects behind it, and a fourth rung is a row in an asset. Effects **stack**: a player at the third rung is wearing all three, so the world gets worse rather than swapping appearance. `PokerHallucinationController` is owner-only, since what somebody is seeing is the one thing at this table that is deliberately not shared. Crossing back down takes a rung off and climbing it again **re-draws** — which is what makes an item that lowers the rate visible, and what stops a player seeing the same room twice.
- **A `ScriptableObject` is config; what runs is an object in the scene.** `PokerHallucinationVolumeEffect` kept its live `Volume` on the asset, and effects are allowed to sit in two pools on purpose — so the lower rung's `End` tore down what the higher rung believed it owned, and one of the two silently did nothing. Cloning the asset per rung fixes the stacking and nothing else: a clone is still invisible, so what a player was actually seeing could only be read out of the controller's dictionary in a debugger. `PokerHallucinationEffect` therefore holds serialized fields and one `Attach`, and `PokerHallucinationEffectBehaviour` holds every field the effect mutates on a child object named for its rung — stacking works by construction because two rungs are two objects, the `Volume` sits on the thing that owns it, and the whole ladder is legible in the hierarchy while it is on screen. A `MonoBehaviour` also brings the lifetime with it: `Stop` is the deliberate way down, `OnDestroy` is the backstop, and an effect that eases out says how long its host must outlive the moment it was taken off (`LingerSeconds`) rather than leaving a tween to be killed with the object carrying it. **Declare the Unity message once, in the base**, and give subclasses a hook (`OnDisposed`) — a subclass redeclaring `OnDestroy` hides the base one and the backstop is silently gone.
- **What an effect acts on is a different asset from what it does.** `PokerHallucinationTarget` resolves a list of transforms and nothing else, and the effects take one — because "make this bigger", "paint this" and "hang something off this" all have to answer the same question first, and that answer is the half a designer actually retunes: one scale effect aimed at a head or at a whole body is two different hallucinations. Splitting it is what keeps the effect count at four for nine authored categories.
- **A prop is asked to wear one of its own looks; it is never handed a model to become.** Swapping the staked cap for a smiling mushroom as a hide-plus-spawn named one prefab, which is the wrong answer for the next kind somebody authors — five mushrooms in the database and the hallucination would show the same face on all of them. `PropVariantController` sits on the prop and owns what each variant means, so `PokerHallucinationVariantEffect` only says *which* (`PropVariant.Smiling`) and each object answers in its own way; a prop that never authored that variant is left as it was rather than being replaced by something generic. Requests are counted like the bone scale and material overrides — last caller wins, dropping one puts back what the caller before it asked for — and `OnVariantChanged` is the seam for a prop whose variant is more than which children are switched on. A look also **replaces a mesh rather than switching a bone off**: hiding `Root_M` to put a mushroom person in its place takes the whole skeleton down and the camera hanging off it with them, and it is the wrong shape for the art that is coming — the artist builds the piece against the same skeleton, so only `sharedMesh` changes hands. `MeshSwap` captures what the renderer was authored with the first time it is taken over, which is the only moment that value is still there to read. The mechanism carries no poker and no hallucination in it: anything that ever asks a prop to look different gets it for nothing, which is why a variant is named after what the prop becomes and never after the rung that asked.
- **An asset cannot name a scene object, so the scene registers what an asset is allowed to ask for.** `PokerHallucinationSceneryTarget` wants "the room", which lives in `Gameplay_Poker` and can never be serialized onto a `ScriptableObject`. `PokerScenery` is a scene component holding named groups and registering itself in its own lifecycle, the shape `PokerSeat` and `GameCamera` already take. The group is a `PokerSceneryGroup` enum rather than a string id, because both halves have to name the same group and only one of them is in the scene: two dropdowns cannot disagree where two typed ids silently never match.
- **A hook handed a plain `Action` can be unsubscribed; one that wraps it in a lambda cannot.** `PokerScenery.OnInstanceChanged` carries no argument for exactly that reason — the first draft was `Action<PokerScenery>` and the target's `Subscribe` wrapped the caller's handler in a closure, which `Unsubscribe` then had no way to find. Every consumer reads `Instance` anyway. When an event exists to be relayed through a generic seam, make its signature the seam's signature.
- **A screen covering a wait blocks input by disabling named action maps, never devices.** `UILoadingScreen._blockedActionMaps` switches `InputSystem.actions`' `Player` map off while it is up and re-enables only what it switched off; the maps are picked from a `[ValueDropdown]` over the project-wide asset, not typed. Devices belong to the whole application — disabling them takes the menus and the cursor with them — and `CanvasGroup.blocksRaycasts` only stops pointer hits, never the gameplay actions running underneath.
- **Cover a wait from the edge that starts it, not from the one that answers.** `OnHostStarted`/`OnLobbyEnter` arrive *after* Steam replies, so a screen hung off them appears once the slow part is already over; `GameNetworkManager` raises `OnConnectStarted` at the click and `OnGameLeaving` before the teardown unloads the scene, and `UINetworkLoadingBinder` covers both. Leaving needs it as badly as joining — a scene unloaded with nothing over it blinks the table out from under the player.
- **Every start must end in an outcome the UI hears.** A screen put up by one event and taken down by another is stuck forever on any path that returns without raising the second — which is why `StartHost` reports its invalid-`SteamClient` guard through `OnConnectFailed` instead of only logging it. Raise the start event *past* the guards, so the only starts announced are the ones that go on to answer, and raise a teardown event only when there is a session to tear down (`if (IsInGame)`) so a no-op `Shutdown` never flashes a screen over nothing.
- **A wait that happens while the game is stopped counts unscaled time.** `Awaitable.WaitForSecondsAsync` and an untagged tween both run on scaled time, so at `timeScale = 0` — which is exactly when a loading screen or a pause menu is up — they never finish. Loop to a `Time.unscaledTime` deadline with `Awaitable.NextFrameAsync(token)`, and mark tweens `SetUpdate(true)` (`UILoadingScreen`, `UIProgressBar`, `UISelectionGroup`).
- **A wheel with fewer items than anchors either repeats them or leaves gaps, and that is a setting, not a default.** `ItemIndexForSlot` wrapping with `% Count` is what fills five anchors with two abilities — the same card drawn three times, which reads as a hand nobody has. `_wrapAround` off makes the strip finite instead: the slot index is left unclamped on purpose, anything outside the list binds empty, and stepping refuses at the ends rather than clamping (clamping spends a step animating the wheel to where it already is). An empty slot is **faded through a `CanvasGroup`, never deactivated** — it is still travelling with the wheel, and switching it off would kill the tween carrying it. `OnBind` is not called with a default nobody asked a subclass to draw; `OnEmpty` is the hook for anything beyond the fade.
- **A list scrolled past a fixed selection is `UIWheelController<T>`.** One view per anchor and no more: stepping recycles the slot leaving one end, re-binds it and snaps it to the other, so a list of any length costs a fixed handful of objects. The first and last anchors sit outside the mask — that is where a slot arrives from, and it is the difference between a wheel turning and items popping in place. Rebuild by re-binding the views it already has, never by destroying and re-instantiating: `Destroy` runs at the end of the frame, so the old set is still drawn underneath the new one for one frame. `UIPokerAbilityWheel`/`UIPokerAbilityWheelPanel` are the concrete pair — the wheel knows nothing about poker, the panel feeds it and sends the RPC.
- **A key shown on a face is read from its binding, never typed.** `UIActionKeyLabel` fills a label from `InputAction.GetBindingDisplayString()`, the same way `UIButtonHotkey` does for a button, so a rebind follows on its own and the face can never name a key the action does not answer to. Size the holder for a word rather than a letter — the string is "Enter", not "E" — and let the label auto-size instead of trusting one hand-picked point size.
- **A selection in a list is drawn as a change of tone, not of size.** A row that swells when chosen makes the whole column shift under the eye every time the wheel turns, and the neighbours move for a reason that has nothing to do with them. `UIPokerAbilityWheelItem` tints its plate and its diamond and leaves every anchor at scale 1; the unselected rows stay readable rather than blank, because the list is what the player is choosing between.
- **A view fed by two network objects subscribes to both, because their order of arrival is not decided.** `Data.Showdown` lives on the table and `HandRevealed` on each player, so a ranking row built from the showdown list and never looked at again drew the winner's hand face down on every screen but their own — the list landed first, which is not the unlucky case but the ordinary one. `UIPokerRankingRow` binds the player it is drawing and redraws on `OnStateChanged`/`OnHoleCardsChanged`; `UIPokerRankingPanel` does the same for `OnCommunityVisibilityChanged`. The tell is a view that is right on the host and wrong on the client: the host writes both values in one call and never has to wait for either.
- **A view asks the replicated stage id which stage is running, never `GameMode.ActiveStage`.** `PokerStageMachine.CurrentStage` is written only by `Next`/`GoTo`, and both are server-only — so on a client `ActiveStage` is null for the whole session and any view gated on it simply never appears. `UIPokerItemWagerBar` was, which read as a wager bar that worked for the host and for nobody else. `GameMode.FindStage(Data.StageId.Value.ToString())` is the client-safe route, and `UIPokerActionBar` was already taking it. The tell is the same one the ranking rows taught: **right on the host, wrong on the client** means a view reading state the host happens to hold locally.
- **A board that reports a hand that is over keeps its own copy of it.** `UIPokerRankingRow` read `PokerPlayerData.HoleCards` live, so the next deal's `ServerResetForHand` emptied a ranking still on screen — a player who left the board up past the countdown watched the cards vanish out of it. It snapshots instead, and the snapshot is refreshed only by a hand that still *has* cards, so the reveal landing after the showdown list still updates it while a later clear cannot erase it. Anything drawing a past moment off live state has the same defect waiting: the moment is over, the state is not.
- **A view that counts across players watches every one of them, not the list they are in.** `UIPokerStartPanel` reads `FundedPlayerCount`, which sums blood and money off each seat's own object, while subscribing only to the phase and to `OnSeatedPlayersChanged` — so a match ending and handing everyone their stake back left the start button dead, because the list had not changed, only what the seats were carrying. It re-subscribes to every seated player's `OnStateChanged` whenever the list changes and drops them all in `OnUnbind`. The symptom names the defect: *standing up and sitting down fixes it* means the only event the view hears is the one about the roster.
- **A view draws its state when it is built, not only when that state changes.** A guard written as "nothing changed, nothing to do" is about transitions, and a slot that has just been created or handed new data has made no transition — it is wearing whatever the prefab was saved with. `UIWheelItemView.Bind` re-applies the selection look on every bind, so a rebuild and a recycle both leave a row correct; the change-guard stays on `SetSelected`, where it belongs, for the animated case. The symptom is the giveaway: "it only looks right after I select it".
- UI reads the mode's `*Data` and the stage's own methods; it never computes a rule of its own and never talks to Netcode directly beyond the mode's public API.

## Inspector (Odin)

**A serialized value that must match something else is picked, never typed.** A hand-typed stage id, scene name or action id is a silent runtime failure; a dropdown cannot be misspelled.

- `[ValueDropdown]` wherever the valid values are knowable; where they live in an asset catalogue, bake them into a `*Database` asset and pick from that, so the list still works in a build and diffs in version control (`PlayerActionAnimationDatabase`, `GameModeDatabase`).
- `[Required]` on any reference whose absence breaks the object at runtime; `[InfoBox]` with a condition to explain a broken setup in place rather than failing later (`GameModeDatabase` flags a scene missing from Build Settings).
- **Where a value may legitimately name something not authored yet, the dropdown offers but does not confine** — `[ValueDropdown(..., AppendNextDrawer = true)]` keeps the text field alongside the list. `PlayerActionAnimationDatabase.StateName` is the case: a gesture is allowed to name an animator state the rigs have not been given yet, because `PlayerActionAnimator` skips a missing one on purpose.
- `[MinValue]`/`[PropertyRange]` on numbers with a real valid range.
- **When the order of a serialized list carries meaning, say so on the field** — `PokerStageSequence._stages` runs in list order, and a reorder is a behaviour change no compiler catches.
- Reference the objects themselves, never string ids kept in sync by hand.
- **A shader's `[Enum(...)]` takes at most seven name/value pairs and fails silently past that** — it logs "Failed to create material drawer" once at import and then draws a bare float, so a nineteen-mode list becomes a number nobody can pick and everybody can mistype. Write a `MaterialPropertyDrawer` instead (`UIBlendModeDrawer`, used as `[UIBlendMode]`), which is the same dropdown with the enum living in C# where it can be read. The enum's order is the shader's branch order and nothing checks that at compile time — say so in both files.
- Odin is inspector UX only: never let an attribute change runtime behaviour.

## Gameplay architecture

Distilled while building the ability system — new features follow these.

- **An act with a length holds its player for exactly that length, and the lockout is the same number as the act.** `PokerAbility.BusySeconds` is virtual so a card whose lean already has a duration answers with that one number instead of carrying a second field beside it; `PokerAbilityModule.IsBusy` is what both the server's refusal and the wheel's greying read, so the two cannot drift. It replicates as `PokerPlayerData.AbilityBusyUntil`, **owner-read** for the same reason the hand is — "somebody is busy" would announce that somebody just played something, and the act itself is the only thing the table is ever supposed to learn. Absolute server time rather than a countdown, so a client arriving mid-trick reads what is left instead of restarting the clock. A busy window ends by a clock running out and raises no event, so it is the rare thing a view has to watch (`UIPokerAbilityWheelPanel.WantsTick`) rather than subscribe to.
- **Public act, private grant.** A cheat ability is two halves: a cosmetic act everyone sees (glasses on, neck stretched across the table) and an owner-read grant only the holder's client learns. The normal and cheat variants of a card share one display name and look identical from outside — the guessing game depends on it. The grant is gated on the public act and reclaimed by its controller the moment the act ends.
- **An ability is a thing you do; calling it a cheat is a different game.** `PokerAbilityModule` deals, holds and spends — `PokerReportModule` runs accusations, and Hold'em is the only preset carrying both. They were one 770-line class, and the tell was that 7 of its 10 consumers touched only the report half. The report asks the ability module one question (`HasPlayedCheat`) through a serialized reference; guilt stays a plain server-side set on the module that watched it happen, because replicating it hands the answer to the players who are supposed to be guessing. Splitting a module is a **rename plus a new small file**, never a surgical delete: `AssetDatabase.MoveAsset` carries the guid, so the prefab's existing component keeps every serialized report setting and becomes the new class, and the clean half is written fresh beside it.
- **Splitting a class splits what it was quietly doing for the other half.** Handing out each hand's report charges rode inside the ability *deal* — `data.ReportsLeft.Value = _reportsPerRound` sat in the middle of the dealing loop — so moving the deal out left nobody granting them: the first hand could be reported on and no later one could, with nothing logged. After lifting a method out, read what the *rest* of the old method was writing, not only what the new one needs. A shared helper is the other half of the same problem: `IsStageAllowed` was private to the old class and now belongs on `PokerModule`, because two modules asking "am I awake right now" must not answer it twice.
- **An inventory that persists and one dealt fresh are one flag apart.** `PokerAbilityModule._clearHandEachRound` on is Hold'em's hand-per-hand deal; off carries unspent cards forward, which is what an item a player is stockpiling has to do. `_abilitiesPerLoss` hands one to every loser at the settlement — through `PokerTableUtility.FeedFromWinner`, because *who lost* is a question only the settlement has answered, and a stage hook would have to work it out again. Folders are paid too: coming last is the round's own reward, and compensating only the eaters punishes folding twice. `GiveServer` is the single door into a hand so `_handLimit` cannot be walked past by whichever caller forgets it, and a full hand refuses **silently** — saying so out loud would tell the table somebody is holding a full hand.
- **A cheat is only worth anything while the table cannot see it happen, so it must not disturb what they are watching.** `ServerReplaceHoleCards` writes each slot rather than clearing the list and refilling it: a clear-and-add is what a *deal* looks like on the wire, and `PokerHandVisual` plays it as one — every card torn down and the replacements flipped in one at a time, on every screen at the table. Writing the slots raises `Value` changes instead, which a hand nobody may see reads as no change at all, because a face-down back before and a face-down back after are the same card. The honest half of such a card must also fail the same way the cheat does: `PokerAbilityRedrawHand` spends itself and plays the shuffle even when the deck is too thin to swap anything, since a card identifiable by what did *not* happen is identifiable.
- **An act with a delayed effect waits on the lifetime of something that can die, not on the asset that describes it.** The redraw lands after the hands come back down — cards swapped in mid-air swap where nobody is looking, and being looked at is the whole point. A `ScriptableObject` has no lifetime of its own, so the wait carries `PokerGameMode.destroyCancellationToken` and the cards are drawn at the *end* of it, never the start, so a cancel has nothing to undo. `async Awaitable` left unawaited rather than `async void`, so a throw still has somewhere to go.
- **Props stay cosmetic.** Generic player pieces (`PlayerGlassesController`, `PlayerHeadStretchController`, `PlayerActionAnimator`) live in `Game.Runtime.Player`, replicate only the act itself, and carry no game meaning. What the act means belongs to a mode-side controller (`PokerBoardPeekController`, `PokerPeekController`) that owns the grant `NetworkVariable` and installs the rule that reads it. Never put per-ability state on shared data (`PokerPlayerData`, `PokerGameData`).
- **Feature components sit on named child GameObjects** of the player prefab, not piled on the root. `Player_Poker` groups its own half by what each piece is about — `Cards` (hand visual, card picking, revealed cards, the holding pose), `Items` (the plate), `Hallucination`, `Body`, `Table` — while `PokerPlayerData` and `PokerPlayer` stay on the root, because they are the model and its owner and everything else addresses the player through them. **`[RequireComponent]` is what stops this, and it is usually the wrong assertion**: `[RequireComponent(typeof(PokerPlayerData))]` says the data must be on the *same object*, so moving the component would have Unity add a second `PokerPlayerData` — a second copy of a NetworkBehaviour on one NetworkObject. Take the attribute off and let the fallback search the object instead (`GetComponentInParent`), which is the rule below about searching from the `NetworkObject` down rather than assuming one shared GameObject. Move with `AddComponent` + `EditorUtility.CopySerialized`, re-point references by sweeping every `SerializedObject` for the old component, and destroy the originals **last** — a reference resolved after they are gone reads back null with nothing left to map from. Verify by diffing the complete type-and-path list against a baseline taken before the move, and by counting: a type appearing twice is a copy left behind.
- **Sight granted and sight owed are different questions, and only the first is worth drawing.** `IsHandVisible` covers "may this client see it at all" — which is true for the owner and for everyone at a showdown. `IsHandVisibleByGrant` is the narrow one: an ability handed this client a look it was not owed. `PokerRevealedCardsVisual` lays those cards out over the player's head where they can actually be read, because a gnome's fist is edge on to everybody but its owner and turning it face up grants sight of something still unreadable. It hangs off the **player root, never the head bone** — the bones are Maya-style so "flat and face up" authored against `Head_M` is ninety degrees off, and a head that goes travelling would take the cards with it. Driving it off the rule rather than off the ability means anything that ever grants a look gets the display for nothing.
- **Where something goes is a transform in the prefab, not a bone plus an offset in code.** "Above the head" as a height and a euler is two numbers to guess at, guess at again for the second thing that needs the same spot, and re-guess whenever the rig changes — and on these Maya-style bones the euler is wrong before it is even tried. `Player_Poker` carries `RevealedCards` and `PeekLookPoint` as real children, dragged into place in the scene view; `PokerRevealedCardsVisual` parents its cards to the first and `PlayerLookTarget` offers the second. Two transforms rather than one, so where the head parks and where the cards lie can be tuned apart.
- **What a player is holding up to be looked at outranks the bone somebody aimed at.** `IPlayerLookPoint` is the seam: the neck is a generic prop and must not know what cards are, so the target offers a pose and the stretch falls back to its configured bone when nothing is on offer. The offer is **unconditional** — a peek that granted nothing must still park the head in the same place, or the honest and cheating halves of the card arrive differently and the bluff is readable from across the table.
- **The neck travels a curve, and a Bézier's parameter is not its arc length.** `PlayerHeadStretchController` lays a cubic from the shoulders to the reach pose — an arch of an authored height square to the straight line, with both handles as fractions of the chord so one set of numbers describes the shape at any distance. The head arrives wearing the pose's own rotation rather than whatever the curve was heading for, so the arch is free to come down onto the target the way a neck reaching over something does. Stepping `t` evenly to place the joints is the trap: measured on a real reach it gave gaps of 0.66 / 0.87 / 0.37, so the joint nearest the head was crammed into less than half the spacing of the one at the shoulders — precisely where the curve bends onto the gaze, which is precisely where a neck must not bunch. A 24-sample cumulative-length table mapping arc back to `t` brings that to 0.6308 / 0.6333 / 0.6314, a spread of 0.4%. Chord distances between the placed joints still vary by a third, and that is the curve bending rather than an error — measure arc, not the straight line, or the good answer looks like the bad one.
- **A stretching chain spreads its joints evenly along the path, never in the proportions the skeleton was built with.** The gnome's seven neck joints sit in the first **46%** of the neck and the single segment from the last of them to `Head_M` takes the other **54%** — so honouring rest proportions crowded every joint into the near half of the arch and handed the whole descent to one bone: three quarters of a metre of dead straight neck running into the head, a curve for the first half and a rod for the second. `PlayerHeadStretchController.MeasureRestChain` gives each joint `i / count` instead, which puts the apex on the middle joint (measured: 0 / 0.204 / 0.286 / **0.299** / 0.271 / 0.212 / 0.122 / 0, arc gaps within 0.13%). A chain being pulled apart is not holding its proportions anyway; how far each segment is pulled is a choice, and sharing the bend equally is the only one that cannot leave an unjointed run wherever a rig happened to put a long bone. `_restLength` is still measured, for the reach clamp.
- **Read the rig's own numbers before deciding a curve is wrong.** "The middle of the neck does not lift" sounds like a bug in the curve maths and was a bug in the *sampling* — the arch was exact and the joints were simply all in the wrong half of it. Printing each bone's parameter and its height above the chord named the cause in one run; looking at the shape in Play mode could only have confirmed the symptom.
- **Every joint gets its own aim off the tangent where it sits, and the animated rotation is what gets turned.** One shared delta for the whole chain — what the straight-line version used — reads as beads threaded on a wire once the path curves. `Quaternion.FromToRotation(restDirection, tangent) * animatedRotation` per bone keeps the twist the clip put into the neck instead of flattening it out. Read every bone's animated position *and* rotation before writing any of them: moving a bone drags its children, so after the first write the rest no longer report where the animation put them — and those same rest positions are what the weight blends back toward, which is why they are read every frame rather than cached.
- **A shape control the artist types a number into must produce that number, and one control owns each thing.** "How high does the neck arch" was being decided twice: `_curveOutHandle` pushed the outgoing control point along the neck's rest direction — which points almost straight up out of the shoulders — so on a reach across the table it was almost entirely arch, and `_curveHeight` was a small correction added on top. Measured on a 1.4m reach: **height 0 requested still arched 0.29m**, and asking for 0.30 delivered 0.50. `PlayerHeadStretchController.BuildCurve` now keeps only each handle's component *along the chord* and gives the whole square-on rise to the height, lifted perpendicular to the straight line rather than along the player's up so it means the same on a flat reach and one angled upward. The handles are left saying how gently the curve eases off that line, which is what a handle is for.
- **A cubic whose handles are pushed square to its chord by 4H/3 is exactly the parabola of height H.** The perpendicular profile of a cubic Bézier with both handles offset by d is 3t(1−t)d, so d = 4H/3 makes it 4H·t(1−t) — peak H at the halfway point, to float precision (measured: requested 0.15/0.30/0.60, peaked 0.1500/0.3000/0.6000, worst deviation from the ideal parabola 0.00000). Lifting by H itself arches to three quarters of what the inspector says, which is the kind of error that gets "fixed" by retuning the number instead of the factor.
- **Where a head arrives and which way it faces are one authoring decision, so they are one transform.** `IPlayerLookPoint.TryGetLookPose` hands back a position *and* a rotation, and `PlayerHeadStretchController` travels straight to it and slerps onto it — no orbit pitch, no yaw off the target's facing, no standoff distance, none of which anybody could picture without pressing Play. The gizmo's blue axis is the gaze; turn it in the scene view until the cards read. Splitting the two leaves the facing to be reconstructed in code from the position, and on a head that arrives *at* the point it came to look at, `LookRotation` toward that point is a zero vector — the aim silently falls back to the animated pose and the peek stares at nothing. Offset the pose by the camera's own `localPosition`/`localRotation` when placing the bone: the pose says where the *eye* belongs, and the camera trails the bone it hangs off.
- **Visibility is a display rule.** Cards replicate to everyone; who may look is decided client-side through provider hooks (`PokerPlayerData.AddHandVisibilityProvider`, `PokerGameData.AddCommunityVisibilityProvider`) plus a `Notify*RulesChanged` event the views listen to. The rule is the only thing hiding the data — a deliberate trade, made once.
- **Visibility is asked per card, not per hand.** `PokerPlayerData.IsHoleCardVisible(slot)` is what views call; `IsHandVisible` survives only as the whole-hand shorthand. A round that deals five and lets the holder turn three is the case that breaks the old shape, and it breaks it *for the owner* — everyone else is still told exactly what they always were. `PokerHandVisual` therefore keeps a bitmask of which slots it has drawn face up rather than one `_shownFaceUp` flag, because a single flag can only ever say "the whole hand" and a change-guard built on it would miss a second card being turned. A table that sets no limit reduces to the old behaviour exactly, which is what keeps Hold'em untouched.
- **What a player may look at is a rule the server enforces, and what they *did* look at is theirs alone.** `LookedAtHoleCards` is a bitmask replicated **owner-read** — which cards somebody dared to turn is as private as what they say about them — and `LookAtHoleCardRPC` is asked of the server rather than decided locally, because a client that lied about the limit would be reading a card the round says it may not. `ViewableHoleCards` is stamped by `PokerDealStage` **before** the cards go out: the view redraws on the list changing, so a limit written afterwards arrives one event too late and the whole hand flashes face up first.
- **Two rigs, one act.** The owner renders `Gnome_HandOnly`, everyone else `Gnome_rig`. Bone positions come from `PlayerBoneRig`/`PlayerRigController` (`RenderedRig`, `RenderedHead`), never per-feature name lookups. Replicated acts play on whichever rig each client renders, so every seat sees the same thing.
- **The four gnome models under `Player.prefab`'s `Models` node are prefab instances of their FBX, so an art update arrives on its own — but only what lives *in* the model does.** They were plain GameObject copies until they were converted, and two rounds of art updates had reached nothing: the prefab still carried `Neck7_M`/`Head_M` and no beard chains while `Gnome_Model_Rig.fbx` had renamed them and added two mesh pieces per hand. Nothing warns about that — an out-of-date skeleton is a real skeleton and animates fine. Keep them as instances, and a bone added or renamed by the artist propagates by itself. What does **not** propagate is anything the prefab holds *about* the model: `PlayerVisual._bodyMeshRenderers`/`_handOnlyBodyMeshRenderers` and `PlayerFingerVisual._fingers` are lists of renderers, so a mesh piece the artist adds turns up in the hierarchy and in nobody's list — and a renderer `PlayerVisual` does not hold is one the owner/remote rig split cannot switch off, which renders as a piece of body floating in front of the first-person camera. Look at those lists whenever the model gains a piece; `PlayerFingerBinder` re-binds the finger half by name.
- **A Generic avatar binds a clip to bones by transform path, so a clip must be exported against the rig it will play on — rename a bone and every curve under it binds to nothing.** `Gnome_Model_RigAvatar` is Generic (`isHuman=False`), and `Gnome_Model_Rig.fbx` is the reference for what the bones are called: the model updates itself into `Player.prefab` because the four `Models` nodes are instances of it, and the animation FBXs under `Assets/Art/Character/Gnome/Anim/` have to follow by being re-exported. When they lagged behind — the model had renamed `Neck7_M`→`Neck_M` and `Head_M`→`Head1_M` — **20 of 83 curve paths per clip bound to nothing**: the whole neck chain, the head, the beard and the ears. Nothing is logged, and it does not present as a missing animation. It presents as a camera bug, because `PlayerController.ApplyLookTo` multiplies onto whatever is already on the bone and relies on the Animator putting the rotation back: measured in Play mode, writing 30° into `Head1_M` twice read back as **60°** while `Shoulder_L` was pinned to its animated value both times. So the view spun while seated (the look drives the head there) and stayed wherever it had got to after standing up, with nothing able to restore it. Two things follow. **A model updating itself is only half the update** — the clips are a second asset built on the same skeleton and they do not follow on their own. And a rig that is "not animated" is diagnosed by *writing into a bone and seeing whether it comes back*, never by looking at it. Until that re-export lands, `GnomeAnimationBoneRemapper` bridges the gap by renaming the paths in `OnPostprocessAnimation` — it is a temporary shim, it is recomputed at every import and persisted nowhere, and the day the clips come back exported against the current rig it stops matching anything and should be deleted.
- **Swapping a rig means re-pointing before deleting, and mapping the roots by hand.** Two things bite in that order: destroy the old objects first and every serialized reference reads back as null with nothing left to map from, so the repoint pass finds zero; and rename the replacement before building the name map and the rig root never matches itself, quietly dropping the Animator and bone rig hanging off it. Take a null baseline of the prefab first — half of what looks broken afterwards was already null by design, the way `PlayerBoneRig` resolves its bones by name at runtime. A prefab instance also refuses to give its children away, so unpack it before lifting hand-placed props like the camera or the glasses off the old head bone.
- **A skinned mesh deforms from its bone array in *index* order, so a rig swap that keeps every bone and loses the order melts the model silently.** `bones[i]` is what `sharedMesh.bindposes[i]` belongs to; rebuilding that array from a fresh hierarchy walk after re-parenting gives a correct-looking set in a scrambled order, and every bone then reads perfect in the inspector while the mesh renders as a spike of flesh. `Player_Poker` and `Player` both arrived that way from the rig update: `Gnome_rig/.../body` had all 103 slots wrong and `Gnome_Outfit_1/OutFit` 102, while the eight finger meshes, the head and the whole hand-only rig were untouched — so **the defect only existed on the rig nobody sees of themselves**, which is why it survived being looked at. Diagnose by comparing the renderer's bone *names in order* against the renderer in the model asset that owns the same `sharedMesh` (match on the mesh asset, never on its name — two rigs here both ship a mesh called `body`); repair with `Assets → Player → Repair Skin Bones`, which reorders the transforms the renderer already holds rather than searching the hierarchy, so a prefab carrying two skeletons under identical bone names cannot be re-bound to the wrong one. `BoneRemapper` maps by name index-for-index and therefore preserves a scramble rather than causing or curing it.
- **Rebuilding a prefab as a variant keeps its guid but kills its fileIDs, and a variant cannot reparent or delete what it inherits.** `Player_Poker` is a variant of `Player` now: everything generic — the `Offset` camera pivots (a reparent, so it had to land in the base), `PlayerBoneRig`, `PlayerRigController`, `PlayerColorVisual`, `AimTarget`, the glasses and the five feature children — was absorbed into the base first, and the variant adds only `Poker*` components, its own anchors, and overrides. Both hats live in the base and **active flags are the seam**: `Cone_Hat` on for Sandbox, `Non_Gnome` on for Poker, because a variant may not delete an inherited child. Transplant components with `EditorUtility.CopySerialized` plus a path-based reference remap between the identical hierarchies, save the variant to the same path so the `.meta` guid survives, then re-point everything that held the old root fileIDs (network prefab list, scene `PlayerManager`) and verify by instantiating the result and reading the load-bearing refs back.
- **Rebuild a prefab from the object itself, and verify by diffing the whole component list — never from a summary of it.** `Player_Poker` lost its `Fingers` node in the variant rebuild because the transplant worked off an exploration write-up that listed eight root children where the prefab had nine, and the verification pass only re-read the components it had set out to copy: everything it checked was green, and the one thing nobody thought to check was gone. Enumerate the source with `GetComponentsInChildren<Component>(true)` at the moment of the rebuild, and afterwards compare the *complete* type-and-path list of before against after — anything present only in the old one is a drop. Blindness is the normal case, not the unlucky one: a visual that never runs renders as a hand that simply never loses a finger, a bone rig nobody reads renders as nothing at all, and neither logs a word.
- **A rig rendered in a preview scene proves nothing.** `PrefabUtility.InstantiatePrefab` into `NewPreviewScene` runs no `Awake`, so `PlayerVisual` has neither picked a rig nor rebound the outfits: both skeletons and both outfits draw at once, over each other, and the result looks exactly like the broken skinning it is being used to rule out — the first render of `Player_Poker` and the one taken from `git HEAD` were pixel-identical *and* both wrong. Judge a rig in Play mode against the source FBX instantiated beside it under the same `Animator_Gnome`; the side-by-side is what named the defect in one frame.
- **What tells players apart replicates as an index, never as the thing itself.** `PlayerData.ColorIndex` is a number; `PlayerColorDatabase` turns it into a colour on each client. The palette is then an asset that restyles without a word of it reaching the network, and two clients cannot be looking at different colours for the same player. The pool of indices belongs to whoever owns spawn-to-teardown — `PlayerManager` claims the **lowest free** one and gives it back on disconnect, so a player who leaves mid-game leaves a hole the next arrival walks into rather than pushing everyone further down a palette that eventually wraps. Count the claims; do not derive the index from a position in the player list, which renumbers everybody the moment one of them leaves.
- **A tint painted at runtime needs a shader that has the property, and a `MaterialPropertyBlock` will not tell you it does not.** The gnome's outfit is a Shader Graph whose only colour input is a *texture* (`_Base_Color:Texture`) — a block writing `_BaseColor` there is a silent no-op that looks exactly like a broken subscription. Check `Material.HasProperty` before choosing the mechanism; `Cone_Hat` is URP/Simple Lit and does have `_BaseColor`, which is why the hat is what gets coloured. Author that material on the renderer in the prefab too, even though `PlayerVisual.ApplySkin` assigns it at runtime, so edit mode is not showing a different hat from the one that runs. A block is the right tool once the property exists: it is per-renderer, instances no material, and survives `ApplySkin` replacing the list underneath it.
- **A rig is however many meshes the artist cut it into.** The gnome arrives as a body, a head and a piece per finger, so hiding "the body" for the owner means hiding all of them — `PlayerVisual` holds arrays, and one renderer left behind is a head floating where the owner should see nothing.
- **A part of the body that can be lost is switched off as a GameObject, never as a renderer.** `PlayerVisual` owns `renderer.enabled` — that is the owner/remote rig split — and rewrites `sharedMaterials` on every skin change, so a finger taken off through either is handed back the next time one of them runs. `PlayerFingerVisual` calls `SetActive(false)` on the pieces instead, which composes with both rather than racing them. One finger is a *list* of objects, not one: the gnome carries `Body/HandCut_L/Index_L` on the full body rig and again on the hand-only rig, and a piece left out is a finger only its owner keeps.
- **Blood is drawn on the body, and the two counts are authored to line up.** The gnome has eight finger meshes and `Player_Poker`'s `_startingHealth`/`_maxHealth` are eight, so one point of blood is one finger and a table reads how badly somebody has been caught without looking at the HUD. `PokerBloodFingerVisual` counts what is gone off the *damage* (`MaxHealth - Health`) rather than off the blood left, so a player at full health is whole whatever the two numbers are tuned to — mapping the other way leaves a player who has lost nothing missing fingers the moment the ceiling is raised. Nothing new replicates: health already does, and the visual reads the current value in `OnNetworkSpawn` for a late join. The mechanism carries no poker in it — `PlayerFingerVisual` is handed a count — so anything else that ever costs a finger gets the display for free.
- **One-shot gestures go through `PlayerActionAnimator`**: ids in `PlayerActionIds`, mapping in `PlayerActionAnimationDatabase`, states on the animator's `Gestures` layer. Missing states are skipped silently, so triggers can land before the art does. Poses and locomotion stay on the base layer with `PlayerSeatController`.
- **An act that lasts as long as a decision is a bool on its own controller, never a gesture.** `PlayerActionAnimator` fires and forgets: its clip ends when the clip ends, which is the wrong length for an arm held out across the table while somebody makes their mind up. A held act is a replicated bool driving a bool parameter on both rigs — `PlayerHandPeekController`, `PlayerPointController` — and the state it drives is left **without an exit transition**, because a non-looping Unity state clamps on its last frame. That is the pose being *held*, where looping the clip would replay the raise over and over. The three-clip shape is the whole idiom: a one-shot to start it (`_Report`), a state that arrives and stays (`_Point`), and a state the falling bool leaves through (`_PointExit`).
- **The outline lives on the thing that already owns every renderer.** `PlayerVisual` holds both rigs, knows which one this client draws, and is what a skin is hung on — so a replicated `Outlined` bool belongs there too. Only the full body rig is lit: a glow on the owner's own hands marks them to nobody. Do not reach into `Interaction` for this — that outline answers to the crosshair and this one to the table; they are separate systems that happen to share a shader.
- **An extra material pass is added to what a renderer is already wearing, never rebuilt out of the skin.** Hanging the outline as part of `ApplySkin` looks like the tidy "one path decides what a renderer wears" answer and is the bug: `ApplyMaterial` skips a renderer whose skin slot is empty, so any mesh the skin does not name is a mesh the outline can never reach — and on a rig cut into ten pieces, one unlit piece reads as the whole outline being broken. Read `sharedMaterials`, append or drop the pass, write it back; then have `ApplySkin` re-hang it afterwards, because assigning a material replaces the whole list.
- **Two things must never write the same bone at once.** The look composes onto whatever is on the bone (`AngleAxis(yaw) * AngleAxis(pitch) * localRotation`) and the neck stretch replaces it outright, so with both running the result is whichever wrote last and the look spends the stretch multiplying into a pose the Animator never meant. `PlayerHeadStretchController` calls `PlayerController.SetLookSuspended` for as long as it is stretching — released **when the weight is home**, not when the target cleared, or the retract's last frames are fought over — and hands it back in `OnNetworkDespawn`, where there is no later frame to do it in.
- **Never add or remove an input device from inside an input callback.** `InputSchemeController` raises `OnSchemeChanged` from `InputSystem.onEvent`, and `UIVirtualCursor` answered it by toggling `VirtualMouseInput.enabled` — which adds or removes a real `VirtualMouse` device. Doing that mid-callback tears the device out from under an action that is still delivering: `Table/PickCard` binds `/Mouse/leftButton` *and* `/VirtualMouse/leftButton`, so releasing the real mouse ran `VirtualMouseInput.OnButtonActionTriggered`, which queried a control whose device had just been removed and threw `InvalidOperationException`. The throw takes the rest of that callback list with it, and the symptom nobody would trace back is *the UI no longer accepting clicks*. `UIVirtualCursor` defers to the next frame through `Awaitable.NextFrameAsync(destroyCancellationToken)` and collapses several changes into one apply, because the apply reads the scheme when it runs.
- **A guard that lets `Awake` return early owes every later method a matching guard.** `PokerGameMode.Awake` destroys a duplicate table and returns *before* building `_stageMachine`, but `Destroy` is deferred to the end of the frame and NGO spawns a scene object regardless of whether its component is enabled — so `Update` and `OnNetworkSpawn` both ran on an object with none of the state they assume, and a hundred identical `NullReferenceException`s a second buried whatever the real problem was. The duplicate now warns once, switches itself off, and `Update`/`OnNetworkSpawn`/`Stages` each ask for the machine before using it. Read every early return in a lifecycle hook and ask which fields it skipped, then guard the methods that need them; a stack that stops at your own `Update` line is usually a field the constructor path never reached.
- **A bone taken over is handed back on the taker's terms, not taken away from the player.** Suspending the look so the stretch can aim the head is only half of it: a first person view the player cannot turn is a cutscene, not a peek. The taker writes its pose and then calls `PlayerController.ComposeLookOnto(bone)`, which multiplies the player's own yaw and pitch onto whatever it just wrote — one write on the bone, in the right order, instead of two racing. Two details are the whole thing: the angles are measured from a **baseline the act carries**, or arriving at the cards jumps the view by however far the player already happened to be looking; and the axes come from the **camera's** frame rather than the character's, because on this Maya-style rig the head bone's own right is a quarter turn off the way the camera is pointing and pitching around it sends the view sideways. `ApplyLook` records what it was given even on the frames it does not apply, so a remote peer that only ever knows interpolated angles still has something to measure.
- **A baseline something replicated is measured against is part of the act, not a note each client takes.** `PlayerHeadStretchController.LookBaseline` is a server-written `NetworkVariable` captured in `ServerStretchTo`, alongside the `Target` that starts the lean. Capturing it locally instead — each client noting the look angles at the moment *its own* copy of the act got going — looks equivalent and is not: the clients start at different times and off differently-interpolated values, so every screen ends up with a different zero and the turn the player is making drifts away from the turn everybody else watches. The symptom reads as "it only rotates on my machine", which sends you hunting for a replication bug in a value that was replicating all along.
- **The Animator puts rotations back, never positions — so anything that *moves* a bone must put it back itself.** "The Animator rewrites the bone every frame, so a driver that stops driving is back under the clip" is only true for rotation: the clips carry rotation curves and a root position, and nothing else. `PlayerHeadStretchController` spreads the neck by writing bone **positions**, and those had no authored pose to be restored to — the neck stayed stretched forever, which reads as a camera stuck across the table rather than as a bone never coming home. Cache each bone's rest `localPosition` once when the chain is built (a skeleton's bone lengths never change) and write it back at the top of every `LateUpdate`, before reading the animated pose: that both ends the lean and stops each frame's stretch compounding on the displaced result of the last one. Keep drawing while the retract tween runs, too, or "ease home" is a snap with a tween nobody sees.
- **It writes scale too, over the whole skeleton, and every one of those curves is a constant.** Measured across the gnome set: 10 of 11 clips carry 249 scale curves each, 83 bones times three channels, and not one of them varies — they are all a flat 1. So the clips express no scale intent whatever, and yet a resize written straight onto a bone is erased on the very next frame, which reads as an effect that simply does not work rather than as one being overwritten. `PlayerBoneScaleController` writes in `LateUpdate` after the Animator and before the brain samples, since a scaled head carries the camera hanging off it. It writes **rest times the multiplier**, never the value it reads back: rest is captured once when a bone is first claimed, so a bone the clips do *not* animate cannot fold its own last write into the next one. Check what a clip actually animates before deciding a driver is fighting it — the curve count named this in one run, where Play mode could only have shown that nothing happened.
- **A tween's per-frame callback is a per-frame path, so it does no lookups.** `PokerHallucinationScaleEffect` resolved its target into transforms and then called `GetComponentInParent` for each of them on every tick of the growth tween. Caching the bone and its controller together as one pair at resolve time is the whole fix, and the shape generalises: whatever a callback needs, bind it when the set is resolved, because the set changing is an event you already have.
- **One writer of `sharedMaterials`, and the composition lives where the renderers do.** Assigning a material replaces the whole array, so a hallucination painting a body directly would be wiped by the next accusation hanging the outline, and the outline would be wiped by the next repaint. `PlayerVisual` therefore composes skin, override and outline in one pass and exposes `SetMaterialOverride`; `PlayerMaterialOverrideController` holds the *requests* and resolves which one wins, because how many callers there are is a question `PlayerVisual` has no business knowing. Split the two whenever several systems want to change one thing: one place decides the final value, another place decides whose turn it is.
- **Anything posing a bone the camera hangs off runs between `PlayerController` (order 0) and the Cinemachine brain (order 100).** The Animator restores bones every frame, so a LateUpdate write after the brain's sample is not a frame late — it is never seen at all.
- **What the view is doing is a state per object, not a row in a list.** States differ in *behaviour*, not configuration — `PlayerCameraFreeflyState` hands the look back to the player and raises nothing, `PlayerCameraVirtualCameraState` makes an authored shot live and aims it — so each is a subclass of `PlayerCameraState` on its own child under `Cameras`, and adding one is a new script and a new object rather than another branch in the controller. `Enter`/`Exit` are non-virtual and own the invariants; `OnEnter`/`OnExit`/`OnRetarget` are what a subclass fills in. `PlayerCameraController` only decides *which*, from a stack of requests — the shape `UIEscapeStack` and the cursor's counted release already take, so a card being picked while a focus is up unwinds in any order. Callers hold a handle rather than a name: a state released by name is released by whoever asked last, not by whoever holds it.
- **Freefly is the absence of a shot, not one of them.** The player is already looking through the camera on whichever rig this client renders, and which rig that is stays `PlayerVisual`'s business — naming it in the camera states would mean picking one of the two, and the owner renders the other. So the base state raises nothing and only hands the look back. A shot is made live by enabling the `CinemachineCamera` **component**, never by switching its GameObject off: the state that has to switch it back on lives on that same object. And it must be disabled rather than left at priority zero, because every enabled vcam is a candidate and the rig's own also sits at the default — a tie the brain may break either way, which reads as the view occasionally starting out pointed at nothing.
- **Suspending the look and disabling it are two different things, and a camera state wants the second.** `PlayerController.SetLookSuspended` hands the *bone* over and deliberately keeps reading input, because a first person view the player cannot turn is a cutscene rather than a peek — `PlayerHeadStretchController` relies on exactly that. A shot that has taken the view somewhere else needs `SetLookInputDisabled`: left reading, `ReadLookInput` goes on writing `_lookYaw` and `_pitch`, which replicate — so every other client watches the head turn while the owner sees nothing move, and the view snaps to wherever they had turned the moment the state lets go. The tell was the report: *"can't control the camera, but the head still rotates"*.
- **A shot that should start from the player's own view is locked to the eye, not authored at a height.** The first version put the focus cameras on a node placed at the eye's position *in the prefab* — a standing bind pose — and the gnome plays the game sitting down, so the shot framed the floor. `PlayerCameraVirtualCameraState._lockToEye` points the camera's `TrackingTarget` at `PlayerRigController.RenderedCamera` and a `CinemachineHardLockToTarget` puts it there, so the shot begins exactly where the player is already looking from and only swings onto its target. A transform authored at a fixed local height is a guess about a pose; the rendered eye is the pose.
- **The look aims a different bone per mode, not per rig, and composes onto the animation rather than replacing it.** On their feet the look drives `Chest_M`, which parents both the neck chain and the two scapulae — so a player looking down lowers their hands with their gaze instead of craning a head off a body that never moved. Anchored in a seat it drives `Head_M` alone: the chair already decided how the body sits, and swinging the whole torso to read the table throws that pose away. Each rig therefore supplies both bones (`_bodyLookTransform`/`_headLookTransform` and their `_owner*` twins) and `ActiveLookTransform` picks on `_bodyAnchored`. Nothing needs undoing when the answer changes — the Animator rewrites both bones every frame, so the one that stops being driven is back under the clip on the next one (measured: switching modes left zero residue). Both are written as `AngleAxis(yaw) * AngleAxis(pitch) * localRotation`, reading whatever the Animator just put there, because every clip in the set poses the chest and a write that replaced it would leave the gnome bolt upright. The axes are derived from the bone's parent *each frame* for the same reason: that parent is itself animated, so a pair cached at spawn has the aim drift off level as the torso moves under it.
- **The camera hangs off the head bone and must stay there** — `PlayerHeadStretchController` walks the neck chain up to the head bone and the camera is somewhere below it, so a head sent across the table takes the view with it; moving the camera out from under that bone would kill the peek. `AlignCameraToBody` squares it against its *own* parent rather than assuming it hangs off the look bone.
- **Drive the bone the mesh is skinned to, and let the camera ride along below it — never the pivot the camera happens to hang off.** `PlayerRigController.RenderedHead` took `camera.parent`, and this rig is `Head_M/Offset/Camera`, so the whole neck stretch was aiming **`Offset`**: a node carrying nothing but the eye. Both halves of the failure follow from that one line, and neither points at it. The head *mesh* was left to `Head_M`, which sat in the chain and so took the curve's **tangent** at its own arc offset instead of the pose's rotation — the head arrived pitched along the arc rather than facing the cards, which reads as a permanent droop. And `ComposeLookOnto` was handed `Offset` too, so the player's own turn moved the camera and nothing else: correct from inside their eyes, a head frozen mid-lean from every other seat at the table. Prefer the named bone (`GetBone(PlayerBone.Head)`) and keep the camera's parent only as the fallback; then warn when the camera is *not* a descendant of that bone, since that is the rig this cannot work on. The tell to recognise is the pair — **"it looks right to me but nobody else sees it move"** is a write landing on something only the viewer is attached to.
- **Unwind a camera offset through the bone being driven, not through the camera's own parent.** `eyeRotation * Inverse(camera.localRotation)` is only the right answer when the camera is the bone's direct child; with a pivot in between, `localRotation`/`localPosition` describe where the camera sits *on the pivot* and say nothing about where it sits on the head. Measure it live against the bone — `Inverse(head.rotation) * camera.rotation` and `Inverse(head.rotation) * (camera.position - head.position)` — which is rotation-only, so it survives a rig that is not at unit scale, and which cannot go stale when `AlignCameraToBody` writes its squaring at spawn in an order this component may not assume.
- **Put a bone's *position* back every frame, but its *rotation* only when the act is over.** `PlayerHeadStretchController.RestoreChain` restored both, and since it runs at the top of `LateUpdate` — after the Animator has written the frame's rotations and before anything reads them — it was handing the blend a bind pose to start from instead of the pose the clip was holding. Position genuinely has nothing else to restore it; rotation does, and it already ran.
- **The host holds the button, not a hand.** `PokerGameMode.CanStartMatch` counts the funded players and lets the host's own seat count as company even when they have gone under: nothing revives a player between matches unless the idle stage is told to, so a table whose host is unconscious had no way back at all — the one player who can press start was the one the count refused. Pressing it does not bring them round; the deal marks them out of the running like anybody else and they watch the match they started. Keep it separate from `CanDealAnotherHand`, which is the same count asked about *dealing* and must go on refusing.
- **Author the camera's facing in the prefab as well as correcting it at runtime.** This rig's bones are Maya-style — `Head_M`'s forward is world +X while the character faces +Z — so a camera left at `0,0,0` aims ninety degrees off the body, and only `AlignCameraToBody` at spawn hides it. A prefab that lies about where its camera looks costs an afternoon before anyone thinks to press Play. Bake `Quaternion.Inverse(parent.rotation) * root.rotation` into the authored `localRotation` so edit mode and play mode agree.
- **Every rig sharing a set of clips needs the shared avatar, and the one nobody renders loses it quietly.** `Gnome_HandOnly`'s Animator came out of the rig swap with `m_Avatar` null while `Gnome_rig` kept `Gnome_Model_RigAvatar`, so the owner's own hands could not play a single clip — and with no head and no body on that rig, nothing on screen looked wrong. The giveaway was a first person camera that measured *perfectly* still over fifty seconds of idle: an animation that never moves is not a calm animation, it is one that is not running. Check `avatar` on every Animator after a rig swap, not just the one you can see.
- **"Where does yaw go" and "which bone does the look aim" are two questions, not one bool.** `_bodyAnchored` answered both for as long as there were only two cases, and came apart on the third: an accuser pointing across the table is still held by their chair — yaw still goes to the bone rather than swivelling the body out of its pose — and yet aims from the chest, because the whole torso is in the act. No reading of "anchored" produces that. The anchor stays a bool about the body being held; the bone is a named `PlayerLookMode`, with `SetLookModeOverride`/`ClearLookModeOverride` for an act that wants a say while it lasts. **The override is released, never set back to a remembered value** — what the look should aim at once the arm comes down is the seat's business, and the seat is the one that knows whether there is still a chair. Set on every peer, like the anchor and for the same reason: a pointing player's torso turns on everyone else's screen too.
- **Seated, the look yaw turns the look bone; standing, it turns the character.** `PlayerController.ApplyLookConstraint(..., keepBodyAnchored: true)` is what a seat asks for: the chair decided where the character faces, so yaw goes to `_lookYaw` on whichever bone the mode is aiming and the body is left where it was put. Standing yaw needs no replication of its own because it rides the body's NetworkTransform — look-bone yaw has nothing to ride, so it replicates like pitch, with the same history and interpolation. Both modes read the same `SeatPose.YawLimits` and the same `AllowRotation`: a pose that forbids turning forbids turning the head too.
- **A mode is a branch inside the controller, not a second controller.** Splitting seated and standing into two `NetworkBehaviour`s looks tidy until you notice NGO binds `NetworkVariable`s to the behaviour that declares them: two components means two replicated pitches, and swapping between them snaps every remote head to the other one's last value and throws away the interpolation buffer that was smoothing it. `AlignCameraToBody` and the owner/remote rig choice are rig knowledge, needed by both, so they would be duplicated as well. What actually differs between sitting and standing is one line — where yaw goes.
- **Stages reached by reference rather than by sequence** (overlays, module-pushed stages) must be declared in `PokerModule.CollectReferencedStages`, so every peer clones them at build time — clients look running stages up by id. Overlays exit with `PopOverlay`, never `FinishStage`.
- **A mode's HUD is a variant of the shared HUD prefab, never a copy of it.** `UI_Poker_AbilityMode` inherits every widget from `UI_Poker` and only switches off the bars its streets never ask for (`ActionBar`, `BetBar`) — a copy would stop receiving fixes made to the original. Switching a bar off rather than deleting it is deliberate: a disabled view never runs `OnEnable`, so it subscribes to nothing, and turning raises back on for a mode is one toggle.
- **A module gated on stage references is a second place the sequence is named.** `PokerAbilityModule._abilityStages`/`_reportStages` say which stages their windows open in, and an *empty* list means every stage — so a list still pointing at the previous preset's stages turns the ability game silently off rather than on. Swapping a mode's sequence means re-pointing every module list in the same change.
- **Numbers the UI offers are the stage's own methods** (`StakeCeiling`, `ClampBet`, …): server clamps and bar sliders call the same code, so a client can never offer what the server will refuse. The same goes for *which* actions are offered — a new permission on a stage (`AllowRaise`) is read by the bar in the same change that adds it, or the button stays lit on a move the server rejects.
- **A turn on a clock must always end, whatever the rules refuse.** The timeout action is a preference, not a guarantee: a street that forbids checking, an action a short stack cannot make, any rule saying the polite answer is unavailable — and a refused action leaves the turn expired, so the tick fires again next frame and the table waits forever on somebody who has already stopped answering. `PokerBettingStage` takes the refusal and folds, which nothing can refuse. Silence itself defaults to **calling** rather than folding (`_timeoutFolds` off): a player who says nothing is usually reading the table, not leaving it, and throwing away a hand they never chose to throw is the harshest reading of a pause.
- **One number decides whether a step is on a clock at all, and a step with no clock draws no bar.** `PokerItemWagerStage._turnDuration` at zero or less runs no countdown and no timeout: the table simply waits, which is what a wager the players are meant to take their time over needs. Set a duration and the timeout and the bar both come back together — two behaviours from one field rather than a visibility toggle beside a hidden deadline that could disagree with it. `PokerGameData.HasTurnClock` is what a view reads to decide, because `TurnRemaining` already answers 0 for an unclocked turn and a bar drawn at 00:00 reads as a hung timer rather than as no timer.
- **The fallback for an expired turn is a ladder, and folding is only ever its last rung.** One preferred action and then straight to fold is a coin toss dressed up as a rule: `_allowCheckWhenNoBet: 0` on a call-or-fold street meant every player who owed nothing had their check refused and was folded for going quiet, on a street whose whole design was that you cannot be made to leave it. `PokerBettingStage.OnTickStage` tries call, then the all-in they are short of, then check, then `PassSquareTurn` — a player who **owes nothing is already square with the street and it has nothing left to ask them**, so the turn is simply marked answered. Each rung is gated by the method the pad lights that petal from (`CanCall`), so a silence makes the move the player was actually being offered and the table hears it by the right name. The all-in rung is the priced-in case only: putting somebody all-in on their behalf because they went quiet is a decision nobody made. A permission that exists to govern a *choice* (you may not tap the table instead of paying) must not be re-read as a punishment for a silence.
- **An event that changes no rule is a replicated flag on a module, never a stage.** `PokerBlackoutModule` puts the lights out once a hand at a moment nobody is given: the turn keeps running, the clock keeps counting, nothing is asked differently — so it is a `NetworkVariable<bool>` every client draws for itself, and `UIPokerBlackoutScreen` owns entirely what the dark looks like. Push a stage only when the *question* changes. Every stage gets its own shot at it: the moment is picked as the stage opens and the odds are not rolled until that moment arrives, so *when* and *whether* stay two questions — a street that ends early simply never had its roll, and one that rolls and misses stays lit rather than trying again. The schedule is a list of stage assets with a chance each, picked rather than named, so a street can be made dangerous and the deal left alone. The screen is a panel over the whole HUD rather than the scene's lights switched off, because half of what a player is reading is drawn on the canvas and "everything goes dark" has to include it; it never takes the pointer, since the hand carries on underneath and the pad is still being pressed by players who simply cannot see it.
- **"The stage started" is too late for a rule about what a player is carrying.** `PokerDealStage` takes its ante inside `StartStage`, so a module listening on `OnStageStarted` hears about it after the money is gone — a player down to their last coin paid the ante with it and was put all in on the spot, staked out of a hand before being dealt into it. `PokerStageMachine` raises `OnStageStarting` before `StartStage` for that, and `PokerBloodExchangeModule` sells its blood there. Two things have to move with the hook. `CanAct` is always false at that moment, because nobody is `Active` until the hand has started — seated and alive is the question being asked. And "is the purse empty" is the wrong test when a cost is about to land: `PokerStage.UpfrontCostPerPlayer` (the deal's seat cost, zero everywhere else) is what the player is priced against, so the sale fires on `Chips - upfront <= 0` and catches somebody holding exactly the ante. With no cost coming it reduces to the old condition, so one line serves the street and the deal. It sells once and not in a loop, so a seat cost worth more than one sale still leaves them short — deliberately, since bleeding somebody repeatedly for one hand is not a decision anybody made.
- **A guard copied from a street that bets *after* the deal is wrong on one that wagers *before* it.** `PokerItemWagerStage` opened with `CountInHand(...) <= 1` — the same test `PokerBettingStage` uses — but the first wager runs before any card is dealt, so nobody is `Active` and the count reads zero: the street declared the hand over and jumped to its `_handOverStage`, which is the reveal. The table then span, because the reveal ends the match and drops back to the waiting room, which starts the wager again. `CanWager` asks the question that is actually being asked here — **seated and conscious**, with folding the only thing that removes somebody afterwards — and it is what opening, advancing, finishing and `HandleAction` all read. This is the same trap already written down for `OnStageStarting`: `CanAct` and `IsInHand` are answers about a hand in progress, and any step that runs outside one has to ask something else.
- **A screen meant to cover the HUD is the *last* sibling, and nothing in the inspector says otherwise.** uGUI draws later siblings on top, so a full-screen panel sitting near the front of the list is drawn *under* every widget added after it — and since it still covers the 3D table, it looks like it is working right up until somebody notices the pot readout shining through the dark. `UI_Poker/DrunkScreen` is placed with `SetAsLastSibling` for that reason. Found in passing: `BlackoutScreen` sits at sibling index **1 of 19** while its own comment says it covers the HUD as well as the table — it does not, and has not since the widgets after it were added.
- **A second thing a card leaves behind is a second replicated value on the same controller, not a second component.** `PokerDrinkController` holds both what a round of drinks costs the drinker (`DrunkUntil`) and what it hands the cheat (`ExposedTarget`), because each player has exactly one of each and splitting them would put two NetworkBehaviours on the player to keep in step. Both are **owner-read** and for the same reason: being drunk is drawn on the drinker's own screen alone, so nobody can look across the table and see who was left sober — which is the only thing separating this cheat from its honest twin.
- **A house rule about what a player can answer with hangs off the turn, not the deal.** `PokerModule.OnTurnBegan` is raised from `PokerGameMode.BeginTurn` *after* the turn is on the table, so a module changing what somebody is carrying is answering a question they can already see being asked. `PokerBloodExchangeModule` sells a broke player a stake in blood there — a rate written as two plain integers (`_bloodSpent`, `_moneyGained`) rather than one float nobody can picture, a floor it will not take them below, and a replicated `Enabled` so the table can play without it. It skips an overlay's turns by checking `CurrentOverlay`, because those are already staked in blood and charging again would take a second payment for one moment.
- **A rule variant is another asset, not another class.** `PokerBettingStage` covers a call-or-fold street through `_openingBet` and `_allowRaise` rather than a subclass; the turn loop, pause/resume, timeout and hand-over handling are written once. Reach for a new `*Stage` class only when the *shape* of the step differs, not its numbers or its permissions.
- **A move made by looking is aimed on the owner's client and named on the server.** Only the accuser's machine can see through their eyes, so `PokerReportAimController` reads the aim from the same bone the camera hangs off, in `LateUpdate` after the look has been written, and sends the answer up **only when it changes** — never per frame, and never outside the window the phase says is open. The server decides whether whoever they landed on can be accused at all, and is the one that lights them up, so every seat watches the same finger travel. What is picked is then locked from the server's copy, not from the client's claim at the moment it matters. The cast asks `PokerAbilityModule.CanBeReported` about every body it passes through rather than taking the nearest player: anybody not in this hand is free to walk around the room while it is played, and one of them standing between the accuser and the table was stopping the finger on somebody the server would have refused anyway. Size the hit buffer for everyone the cast can pass through, not for everyone it can accuse — a full buffer drops the rest of the list in silence, which reads as the table not being there at all.
- **A server RPC that refuses says which gate refused it.** A request the UI already decided to offer, dropped by a stack of guards that all `return` in silence, is indistinguishable from a button that is not wired, a prefab field left null and a stage that was never pushed — and each of those sends you looking somewhere else. `PokerAbilityModule.ReportRPC` names its gate (`RefuseReport`), and a setup that cannot possibly work — no action animator, no point controller, an overlay opening with nothing to judge — warns rather than skipping quietly. Reserve the silent skip for things deliberately allowed to be missing, like an animator state the art has not landed yet.
- **A `CharacterController` is not a hit volume — it only exists on the client that drives it.** `PlayerController` enables it for the owner alone (it stays off in the prefab so it cannot overwrite the spawn position the server sent), which means on any given machine *every other player has no collider at all* and no cast can ever find them. Anything that needs to point at a player — an aim, a targeted ability, a hover — needs its own always-present volume: `AimTarget`, a trigger `SphereCollider` hung on the body rig's `Chest_M` so it follows whatever pose the seat put them in, answering casts and pushing nothing. A trigger also stays out of the interaction scan's way, which ignores triggers when testing for obstruction.
- **A cast that finds nothing is diagnosed by drawing it, never by replacing it.** A sphere cast looking for a player fails in several ways that look identical from the outside — the eye sits inside its own `CharacterController` so our own body is always the first hit, the radius may be too small to reach a face across the table, the collider may not cover the seated body, the layer mask may exclude it. Swapping the mechanism for something that cannot miss hides which one it was. `PokerReportAimController` carries `_drawDebugRays` (green for the aim, yellow for a player that lost, **magenta for our own body**, red for scenery, plus the sphere drawn where it ends up) and `_logAimChanges`, which writes the hit list once per change rather than once per frame. Draw it first; the picture names the cause in one frame.
- **A step whose UI asks a different question is a replicated phase, not something inferred from the turn.** `PokerReportPhase` says whether the table is aiming, answering or hearing the verdict; reading that off `CurrentTurnClientId` works right up until a fourth step exists, and then every consumer is subtly wrong at once. The turn still says *who* moves — the phase says *what they are being asked*.
- **Being out of the game is asked at `IsAlive`, and being dealt into the next hand at `PokerGameMode.CanBeDealtIn` — never at the five places that used to ask both by hand.** `IsAlive` is `HallucinationRate < MaxHallucination` and nothing else: blood is still tracked, still staked by an accusation and still drawn on the body, but running out of it is not what ends a player. `CanBeDealtIn` adds the purse, and only where the table plays for one. The deal marks the unconscious `Dead` **before** it asks about money, because being out outranks being broke, and `FundedPlayerCount` counts through the same predicate so a table of corpses cannot start a hand. They keep the chair and watch.
- **Whether the table plays for money at all is a property of the table, not a branch at each gate.** `PokerRuleSettings.PlaysForMoney` off means an empty purse decides nothing: a player is dealt in for as long as they are conscious. That is one asset per variant rather than a condition repeated at `FundedPlayerCount`, `RotateDealer`, `DealHoleCards`, `PokerWaitingStage` and `IsCommittedToMatch` — where it *had* been repeated, and where a mode that stopped using chips would otherwise have marked every player `Busted` before the first card and never dealt a hand. The old `MinimumMoneyToSit` went with it: a stake nobody can meet is the deal's question, and the door stopped asking questions when chairs stopped being chosen.
- **Hallucination is its own currency and does not touch blood.** `PokerPlayerData.HallucinationRate` climbs 0→100 and reaching the ceiling is elimination; `Health` stays the blood that fingers are drawn from and that an accusation is staked in. Mapping one onto the other looks tidy and is the trap — the finger display counts *damage* against `MaxHealth`, so borrowing it would make a player at full blood lose fingers to a mouthful of mushrooms. Both are public, because the round's two real decisions (what to wager, who to feed the Colorful cap) are choices about who is closest to going under.
- **A mushroom effect asset is one object for every kind, because the kind arrives as a parameter.** `PokerItemEffect.ConsumeServer(gameMode, eater, itemType)` hands the kind in, so `PokerItemHallucinationEffect` can ask whether this eater has met it before (`PokerPlayerData.EatenItemTypes`, a bitmask, public and lasting the whole match) and charge the larger gain if not — one asset, four caps, and the price is data rather than four near-identical assets to keep in step. A kind with no bit of its own (the plain chip, anything past the mask) must read as *never eaten*, so an unconfigured table charges the full gain rather than silently handing out the discount forever.
- **How something ended is one value, and only one ending is allowed to say what was in the hand.** `PokerReportResult.Outcome` is `Dropped`/`Conceded`/`Judged` rather than a `Called` bool the UI then reads amounts alongside — three states inferred from two fields is how "the accuser backed down" came out on screen as an **INNOCENT** card, publishing the exact thing they had just paid not to find out. `WasCheater` means nothing unless the outcome is `Judged`, and the feed returns early on `Conceded`: the fold that caused it is the whole announcement. Backing down also skips the judging pause outright — that pause is the table getting ready to be told something, and holding everyone there only promises a verdict that is never coming.
- **An accusation costs the loser; it never pays the winner.** Being right about a cheat is worth not having been wrong, and nothing else: `ResolveReportServer` hands the winner back exactly what *they* staked (`_accuserPaid` or `_accusedPaid`) and the loser's stake is simply gone. Paying out the pot would make pointing at people a way to *gain* blood, and a table where guessing right feeds you is all accusation and no poker. `ReportPot` stays as the readout of what is at risk; nothing is ever won from it, and the verdict announces what the loser lost rather than what the pot held.
- **A stake is paid as it is offered; only the verdict waits.** Staking *is* the act, so the pot grows on the button press — a pot that fills once the result is in makes every answer look like it did nothing, and the pause afterwards is a wait for a verdict, not a wait for the money. `PokerAbilityModule.CommitReportBloodServer` tracks each side against what it has already put in, so a call after a shove pays only the difference and a second call pays nothing; the resolve then only decides where the pot goes. Because the blood really did leave, an accusation that drops has to hand it back — `DropReportServer` refunds both sides.
- **Two currencies means every stake says which one it is.** The hand is played for money (`PlayerData.Money`, `ServerPlaceBet`); an accusation is paid for in blood (`PokerPlayerData.Health`, `ServerChangeHealth`), and never touches the pot or `Bet`/`TotalBet` — a report that moved chips would leave the accused unable to call the street they were mid-way through. A stake is taken as it is committed and handed back if the thing it was staked on never happens (`DropReportServer`), so there is no path where blood leaves a player for nothing.
- **The pot is a scalar and a ledger, and one class writes both or they drift.** `PokerGameData.Pot` stays what every rule computes with; `PokerGameData.PotItems` is its itemised twin — one `PokerBetItem` (owner, street, type index) per unit staked, so the pot is queryable and a unit can one day carry an identity of its own (a marked chip, a mushroom) by its `ItemTypeIndex` without touching the betting arithmetic. Every write to either goes through `PokerTableUtility` (`CollectBets`, `CollectDealCost`, `ForfeitBet`, `ResetPot`, `SettlePots`) — the seat-release sweep used to add to `Pot` from `PokerGameMode` directly, which is exactly the second writer that makes a mirrored value silently wrong.
- **The wallet is itemised the same way the pot is, and a stake spends the front of it.** `PokerPlayerData.StakeItems` holds one type per unit of `PlayerData.Money`, drawn from `PokerItemDatabase` **as money enters the wallet** and re-synced by the server on every change of the scalar, whoever moved it — so a deposit that bypasses poker code still gets typed. Bets take from the front (auto-FIFO, never a choice), travel as `_committedItemTypes` while they stand as `Bet`, and hand their types to the pot ledger at collect. The mode stamps the database onto each body beside the starting stats; a new source re-types the whole wallet (the body self-seeded plain chips at spawn), guarded on an actual change so a roster refresh cannot re-deal what a player is holding. No database wired means every unit is `PlainChip` (index 0) and the money game is unchanged.
- **A settlement nobody selects is a branch that only ages.** `PokerSettlement.LoserEatsPot` was the plate-feeding case and no preset in the project ever chose it: it kept `SettleByEating`, an `_eaters` buffer and `PokerTableUtility.FeedPot` alive in the one place a hand pays out, and `FeedPot` was still calling `ConsumeServer` straight from the settlement — the exact shape the "a round's consequence is a beat" rule replaced everywhere else. So the dead path was also the wrong path, and the only thing keeping it honest would have been a preset that used it. It is deleted; `LosersEatWinnersWager` keeps its explicit `= 2` and the gap at 1 stays, because a preset stores this as an integer and renumbering would quietly make the mushroom round settle like poker. Read the presets before deciding a branch is load-bearing — `FindAssets("t:...")` and print the serialized value, which also proves nothing moved afterwards.
- **A stake with no size still has a size the table sets.** A player wagering chooses only the *kind*; how many caps that puts up is `PokerItemWagerStage._itemsPerWager`, a serialized number. The two are different questions and keeping them apart is what lets the stake be retuned without the pad, the bar or the server learning a new shape — nothing in the UI changes when it moves from one to three.
- **A kind that can be fed to somebody is not necessarily a kind that can be wagered.** `PokerItemDatabase.Entry.Wagerable` is off for the Colorful cap, and both the random draw and `PokerItemWagerStage.IsWagerable` read it — so it can never be dealt into a wallet, offered by the bar, or accepted by the server. One flag on the data rather than a special case at each of the three places that would otherwise have to remember it by index.
- **How a hand pays out is an enum, never a pair of bools.** `PokerSettlement` is `WinnerTakesPot` and `LosersEatWinnersWager` (a third, `LoserEatsPot`, was carried unused for a while and is gone); two bools would let a preset switch both on and leave the order they are read in deciding the game. The third case is `PokerTableUtility.FeedFromWinner`, where every loser swallows a **full copy** of what the winner put up rather than a share — aiming a kind at the whole table is the entire point of choosing one — and a player who folded eats only their own opening cap, which is what folding costs. The losers' own caps are simply gone; as with the report, winning is worth not having lost and nothing more.
- **The winner names the victim, in public, and cannot decline.** `PokerColorfulPickStage` gives a turn to one player and takes a seat index through `PokerActionType.Target` — the amount carries an identity rather than a size, the same trick the wager plays. Declining would be declined whenever they are ahead, which is always, so the mechanism would switch itself off; the timeout feeds it to the winner themselves, because a silence must not be a way to aim it. Naming yourself is allowed on purpose: being fed a cap is not only a punishment, and a card that rewards eating one has somewhere to live. Somebody already at the ceiling cannot be chosen — feeding them is a move with no consequence at all.
- **Going under is written as the ceiling, not as a flag.** `PokerItemColorfulEffect` adds its gain, rolls against the **new** rate, and on a bad roll writes `MaxHallucination` — so `IsAlive` stays the one question anything asks, and a later sobering could still bring them back. Measured in Play mode: from 40% + a 10% gain, 92 of 200 rolls fainted against an expected ~100.
- **Money that must not read as a bet never goes through `PlaceBet`.** `Bet`/`TotalBet` are what "is the street square" and the side-pot layers are computed from, so a seat cost paid at the deal goes straight to the pot via `ServerPayIntoPot`/`CollectDealCost` — put it in front of the player instead and they arrive at the next street already square, and are never asked to call.
- **A stake with no size rides the action's `amount` as an identity, not a quantity.** A mushroom wager is one cap and never a sum, so `PokerActionType.Wager` carries the kind's database index where a bet would carry chips — `PokerGameMode.SubmitActionRPC(action, amount)` needed no second RPC, and `PokerItemWagerStage.IsWagerable` is what both the bar and the server size the offer through. Nothing about it touches `Bet`/`TotalBet`, because "is the street square" is a question a round of this kind never asks.
- **The pot ledger is the record of who staked what; a copy on the player is a copy the deal wipes.** A round that wagers *before* it deals puts `PokerDealStage` in the middle of itself, and the deal calls `ServerResetForHand` on every player — so a `WageredTypes` list on `PokerPlayerData` lost the first wager halfway through every round. `PokerBetItem` already stamps `OwnerClientId` and `ItemTypeIndex`, so the ledger answers "what did the winner put up" without a second seeder to keep in step. The same ordering is why `PokerDealStage._clearPotOnDeal` exists: the deal is where a Hold'em hand starts, and only there is wiping the plate the right thing.
- **A serialized field added after an asset was created deserializes to its C# initializer, so a new toggle silently gives every existing asset the old behaviour — including assets created earlier in the same session.** `_clearPotOnDeal = true` is what Hold'em needs and is exactly wrong for the mushroom deal, which had been written to disk minutes before the field existed. Nothing warns: the asset is valid, the value is plausible, and the failure is a first wager quietly wiped. After adding a field, set it explicitly on every asset that wants the non-default and **grep the `.asset`** — `LoadAssetAtPath` will happily report the initializer as though somebody had chosen it.
- **A chair is handed out, not chosen — and the mechanism that seats a player has one entry point whoever decides.** `PokerSeat.CanInteract`/`CanStand` both answer false: the server seats whoever arrives at the lowest free chair (`PokerGameMode.ServerSeatArrivals`) and nobody leaves while they are at the table. Walking up to a chair was one of two callers, so `SeatInteractable.SeatServer` is what both go through — deleting the interaction would have taken Sandbox's seats with it, and re-implementing the seating beside it would have been the second copy to keep in step. A player arriving mid-hand is still seated at once and is `Waiting` until the next deal, because every seat-order helper (`NextPlayer`, `IsBettingComplete`, `CountInHand`, `ReopenAction`) filters on `CanAct`/`IsInHand` rather than on being in the list. The money gate that used to guard the chair went with the choosing: a stake nobody can meet is the deal's question, not the door's.
- **How many chairs the table is laid with is replicated, and the layout is arithmetic every client repeats.** `PokerGameData.ActiveSeatCount` is written once by the server from the lobby size; `PokerSeatRingVisual` spaces that many chairs evenly around the table and switches the rest off. The chairs are **moved, never spawned** — a scene `NetworkObject` created at runtime comes up with `GlobalObjectIdHash = 0` and never spawns at all — and the count is table state rather than each client reading its own copy of the lobby, because chairs standing in different places on different screens is a desync with nothing to warn anyone. Facing still comes from the chair's own position, so the ring cannot reintroduce the hand-typed yaws that once left four seats pointing 12° off. The radius is measured in `Awake` off serialized references, before anything has been moved: measuring later reads chairs this component has already placed.
- **A component that hides objects holds them serialized, and keys on their authored index — never on a spawn-order registry.** `PokerSeat.All` fills in `OnNetworkSpawn`, so it is in *spawn* order, not `SeatIndex` order, and a chair switched off before it spawns never joins it at all. Laying the ring from that registry while `PokerGameMode` handed chairs out from its own `SeatIndex`-sorted list meant the two disagreed about which chairs existed: a table of six came up with four registered seats numbered 1, 2, 4, 5, and players were seated in chairs that had been switched off. Both now read `seat.SeatIndex` and the ring holds its own `_seats` list, so a hidden chair is still reachable and the two answers are the same by construction. **Edit-mode arithmetic cannot catch this** — 45 geometry checks passed on the broken version, and one Play mode run named it in a single log line.
- **Chairs are filled across the table, not around it.** `PokerGameMode.SpreadSeatIndex` interleaves the two halves of the ring — at four chairs the order is 1, 3, 2, 4 — so two players sit opposite rather than elbow to elbow with half the table empty. The formula takes the **larger** half first when the count is odd (`(count + 1) / 2`, not `count / 2`): at three chairs the naive version sends two arrivals to the same seat and never uses the third, which reads as a player who simply fails to sit down. Only even tables ship today, so that case would have hidden until somebody laid a five-chair table — check a fill order by asserting it visits every chair exactly once at every count, not by looking at the one you use.
- **How many chairs a table is laid with belongs to the table, not the lobby.** `PokerRuleSettings.SeatCount` is what `ServerLayTable` reads; how many people a *room* admits and how many can sit at *this* table are different questions and only the second is a rule. The room screen no longer offers either — `UIRoomSetting._fixedMaxPlayers` is a serialized number and the input field that used to set it is switched off in `Awake`, because a control that ignores what you type into it is worse than no control.
- **A device the game invented is not a device the player is holding.** `VirtualMouseInput` creates a real `Mouse`, so every generic binding matches it: `InputSchemeController` read its events and flipped the scheme back to keyboard the instant the right stick moved the pad's own cursor, which then switched that cursor off — a flip-flop with no error and no log. `SchemeFor` now refuses anything whose `InputDevice.native` is false. The same fact bites the look: `Table/Look` binds `<Mouse>/delta` and `Player/Look` binds `<Pointer>/delta`, both of which the virtual mouse satisfies, so the cursor stick turned the view as well as the pointer. `PlayerController.ReadLookInput` checks `action.activeControl.device is Gamepad` against the scheme and drops anything the player is not actually holding. Reach for `native` and for the active control's device whenever a synthetic device shares a class with a real one; the binding paths cannot tell them apart and never will.
- **Being collected into a match commits a player to the match, not to the hand.** Folding is a decision about these cards; if it also let them stand up with the stake still on them, folding would be the way out of the game. `PokerGameMode.IsCommittedToMatch` releases a player only when they have nothing left to play with — the same `IsAlive && Chips > 0` the deal counts to decide who is still in the running — plus the two cases that were never a commitment: still holding cards (all in included, since a stack at zero is not a way out while the money is in the pot), and `Waiting`, which is somebody who took a free chair mid-hand and was never dealt in.
- **Folding is putting the cards down, and that is three things that must not come apart** — the status the rules read, the cards themselves, and the pose the holder is in. `PokerPlayer.ServerFold` does all three, because the five paths that fold a player (a street, a simultaneous street, its timeout, a caught cheat, a departure) each used to do only the first, so a mucked hand stayed in front of its owner and a player caught mid-peek went on studying cards they no longer held. Mucking is a `HoleCards.Clear()` — the opposite of `ServerReplaceHoleCards`, which writes slots precisely so a cheat does *not* read as a deal — and dropping `IsPeeking` is what plays the cards going face down, since the bool drives the animator on both rigs.
- **A hand ending and a match ending are two different events, and only one of them is worth announcing.** A match runs itself out over as many hands as the table can still deal: `PokerShowdownStage` asks `PokerGameMode.CanDealAnotherHand` — the same funded-player count the host's start button is gated on — and deals straight into `_nextHandStage`, so the ranking *is* the ceremony between hands and nobody presses anything. `EndHand` puts the cards, the turn and the modules' round away; `EndGame` is that plus `Phase = Finished`. Keeping the phase out of `EndHand` is the point: a beat of `Finished` mid-match unlocks every chair and reads on each screen as the match being over. The match ends only when one player is left who can still be dealt in, and `PokerWaitingStage` is where the stats go back — the one stage that is only ever arrived at with the previous match already finished.
- **What a match is played with resets; what a hand is played with resets more often.** Blood and money carry from hand to hand — losing the last of either is exactly how a player stops being dealt in — so `ServerResetForMatch` is separate from `ServerResetForHand`, and each class owns its own half: `PlayerData.ServerResetToStart` for the purse, `PokerPlayerData.ServerResetHealthToStart` for the blood. Reaching across to set another component's starting value from here would be a second place to keep in step. Author the starting amount *and* its ceiling to agree — `_startingHealth` left at the C# default over a prefab whose `_maxHealth` was tuned down shows one number in the inspector and clamps to another at runtime.
- **The idle table is where a *match* ends — a round passing through it is not one.** `PokerWaitingStage` put blood, money, hallucination and every served item back on arrival, which is right when the table has been played out and wrong the moment a round loops back through it between hands: everything the players spent the round accumulating went to zero the instant the start button appeared. `_resetMatchStats` is the seam, on for a table that only reaches idle when it is over and off for a round that comes back here each time. Whenever a stage is reused for a second meaning, read what it *does* against both.
- **What may be reached for is opened by the beat that asks, and closed when it ends.** `PokerCardVisual.Pickupable` is set across the hand by `PokerHandVisual.SetPickupable` when the look stage opens and cleared when it closes, and a card already up in the hand is never flagged — so a card stops lifting under the cursor the moment it is taken, rather than hovering for a pick the server would refuse. The camera is held the same way: the shot is requested for the **whole stage** aimed at the seat's card anchor, not per pick aimed at a card. A card is a thing that moves, so a shot held on one would be dragged along by the very pickup it is meant to be framing.
- **A handler unsubscribed by the very act it is meant to survive goes deaf after the first one.** `PokerCardPickController` dropped its `StageId` subscription inside `HandlePick` — a stray line that landed there rather than in the despawn hook — so picking up one card stopped the controller ever hearing the stage change again: the beat opened and never closed, the camera never came back to free flight, and picking stayed open. It watches the id in the `Update` it already runs instead, comparing the raw `FixedString32Bytes` and acting only when it moves. That also closes the real hazard the subscription carried: it had to be taken in `OnNetworkSpawn`, and the table's `Data` may not have spawned by then — binding to nothing there is silent, and the symptom is the same beat that opens and never closes.
- **A per-hand reset must not sweep what another system owns, or that system's setting is a lie.** `PokerPlayerData.ServerResetForHand` cleared `AbilityIds`, so `PokerAbilityModule._clearHandEachRound` set to *off* did nothing at all: the module carried the stockpile forward and the player's own reset emptied it a moment later. Nothing warned — both writes were correct in isolation, and the symptom was an item that vanished between rounds for no visible reason. The inventory belongs to the module that deals it; the hand reset keeps only what a *hand* owns (cards, bets, who has acted), and `ServerResetForMatch` still empties the stockpile because a stockpile belongs to the match it was built up in. Whenever a flag says "keep this", grep for every other place that clears it.
- **A lifecycle hook must be named after the moment that raises it, or every implementer is quietly wrong.** `PokerGameMode.EndHand` raised `OnGameEnded` on every module — so a module that meant to keep something across hands was emptied at the end of each one, and `PokerAbilityModule._clearHandEachRound` set to *off* did nothing whatever. The names now say what they mean: `EndHand` raises `OnHandEnded`, `EndGame` raises `OnMatchEnded` after it. Renaming a hook is not cosmetic — it is how the four implementers get to notice which moment they were actually subscribing to. Beware of testing such a fix through the method you happen to know: calling `ServerResetForHand` directly passed while the real `EndHand` path still wiped the stockpile.
- **A stage sequence wraps to its own first entry, so the last stage must name where the round goes.** `PokerStageMachine` resets its index to 0 at the end of the list, and entry 0 is the waiting room — a table whose final stage just calls `FinishStage()` needs the host to press start after every hand. `PokerColorfulPickStage._nextStage` names the first wager instead. `PokerShowdownStage` is the shape to copy: `_nextHandStage` while the match can continue, `_idleStage` when it cannot, and it calls `EndGame` on that second path — which is also why a showdown left with an empty `_nextHandStage` ends the *match* after every hand rather than falling through to the next stage.
- **A deal that sits in the middle of a round must not rotate the button.** `PokerDealStage.RotateDealer` runs where a Hold'em hand starts, which is the right place there and the wrong place in a round that wagers *before* it deals: the mushroom round's two wagers sit either side of the deal, so the button moved between them and the second wager walked the table in a different order from the first — at two players it read as the order simply flipping. `_rotateDealerOnDeal` is off for that preset, the same shape as `_clearPotOnDeal`. Read every "this is where a hand begins" step in a sequence that begins somewhere else.
- **Where a card lies on the table is a transform in the chair, not the chair itself.** `PokerSeat.CardAnchor` fell back to `SitAnchor` — a point on the *floor* at the player's feet, since a player root is at the feet — so five cards were dealt into the gnome's ankles and no raycast could ever reach them. `Seat_PokerChair` now carries a real `CardAnchor` child on the table top, lying flat with the card's face up and its top pointing away from whoever is sitting there. A fallback that resolves to a plausible transform is worse than a null one: nothing warned, and the cards were "dealt" every hand.
- **A row of cards lying flat steps its depth the way the anchor points, not the way a fan does.** `PokerHandVisual.RowPosition` reused the fan's `-slot * _depthStep`, and the table anchor's forward is *up* — so each later card sank a step into the table and three of five ended up under the surface. Positive is also what a hand dealt onto a table looks like: the card put down later rests on the ones already there.
- **Everybody answering at once is a stage, not something bolted onto the turn before it.** `PokerCardLookStage` is the beat where every player turns their own cards over; nobody holds a turn, and the step ends when the last of them has spent their looks. Folding it into the wager that precedes it would leave one turn ending on two unrelated answers — which cap, and which cards. It offers a `_duration` and ships with it off, which is the table's call and worth knowing the hazard of: with no clock, a player who deliberately turns fewer cards than they may holds the whole table forever, so this eventually needs a way to say "done".
- **A change-guard covering two questions needs two masks, and what it redraws is the difference — not the whole thing.** `PokerHandVisual.HandleStateChanged` guarded on the face-up mask alone, so turning a card over redrew its face and never re-laid the hand out — the card came up face up and stayed lying on the table, which is the entire pickup nobody could see. Which cards are *face up* and which are *up in the hand* are different questions with different answers (a showdown puts a revealed hand back down), so each has its own mask and either changing re-lays the hand. Then the redraw itself has to be the XOR: re-setting every card played the flip on all five when one was turned. A guard answers "did anything change"; what gets redrawn is "which one". Both masks clear in `ClearCards`, or the first card of the next hand reads as no change at all.
- **The same XOR decides what is redrawn *and* what is animated; a re-layout tweens only what actually moved.** `PokerHandVisual.Layout` took one `animate` flag for the whole hand, so picking a card up re-placed all five with a tween — and `PokerCardVisual.PlaceAt` adds a `sin` arc to whatever it animates, an arc that exists so a card *leaving* the table rises off it rather than grinding through it. The four cards merely closing the gap therefore jumped into the air and settled again every time one was taken. `Layout(int animateMask)` takes the same difference the face redraw already takes (`inHand ^ _shownInHandMask`), so the card that changed hands travels and the rest slide to their new slot with no arc; a late-join rebuild passes `0`, because a hand being shown as it already stands has nothing to travel from. Whenever a view re-places a whole group after one member changed, ask which of them actually moved — an animation is a statement that something happened, and playing it on everything says it about the wrong things.
- **Everything authored about a place at the table belongs to the chair.** `PokerSeat` holds `CardAnchor` and `ItemAnchor`, both flat transforms on the table in front of that seat, and `PokerItemPotVisual` looks the spot up from the item's own `OwnerClientId` rather than laying the pot out around the table's middle. Two things follow. A stake lands in front of whoever put it up, which is the only thing the table is actually reading during a wager. And retuning where anything sits is one edit to one chair prefab that reaches every seat — the table visual owns none of it, so a second mode with a different table needs no second layout.
- **The plate is an object on the table when a stake has no size.** `PokerItemPotVisual` reads `PotItems` — the ledger `PokerTableUtility` already writes beside the scalar, so there is no second seeder and a late join replicates the plate as it stands — and puts a cap down on an authored spot with a drop tween. Preset spots rather than computed positions, for the same reason the seat ring measures its radius off serialized references: a layout on a table is something to be looked at.
- **A round's consequence is a beat, not a line in the settlement.** `PokerTableUtility.ServeFromWinner` and `PokerColorfulPickStage` used to call `ConsumeServer` where they decided who owed what, so every effect in the round landed in the same frame behind the ranking board and the whole point of the game happened where nobody could see it. They *serve* now — `PokerPlayerData.PendingItems`, Everyone-read — and `PokerItemConsumeStage` walks the seats swallowing one cap at a time with a gesture and a bite duration. The plate is also what the visual draws, so a cap comes off the list as it goes down rather than after: a cap still drawn that nobody is going to eat is worse than no cap at all. Deciding a cost and paying it are two moments whenever the paying is worth watching.
- **A `*Data` class owns state; a verb with a decision in it is a controller.** `PokerPlayerData` had grown to 735 lines and 26 server methods, which is every rule the round has piled onto the model. `PokerPlayerItemController` is the first piece off it: the plate (`Pending`), the record of what has been met (`ConsumedTypes`) and the one decision that reads both — a kind you have swallowed before costs the smaller gain — because the record is what sets the price and a record kept elsewhere is a second value to keep in step with the eating that writes it. It lands on the `Items` child beside the plate visual, and `PokerPlayer.Items` is how everything reaches it, the same way `ActionAnimator` is reached. The clusters still on the data — the hole cards, the stake wallet, the vitals — come off the same way.
- **When art has not decided what a moment looks like, the moment is an asset.** `PokerItemArrival` is a `ScriptableObject` with one method, and `PokerItemDropArrival` / `PokerItemFlyArrival` are two answers to it: put down in front of you, or handed across from whoever staked it. The visual owns *where* an item ends up and the arrival owns only *how it gets there*, which is what lets the layout be retuned without touching the animation and the animation be replaced without touching the layout. The source it travels from is the last winner's own place, read off `LastWinnerClientId` rather than replicated again — and an arrival handed no source falls back to appearing in place, so "they were already mine" is not drawn as a handover.
- **A flag a rig needs is named after what it means, not after the first thing that set it.** `Animator_Gnome`'s `Sit` / `Sit_FlipUp` / `Sit_Peek` / `Sit_FlipDown` are hands on the table, picking cards up, holding them, putting them down — that is *holding cards*, and `IsPeekingCards` named one caller of it. Renamed to `IsHaveCardOnHand` and driven from the cards themselves (`PokerHandPoseController`), which is why the check button could go: a control asking for a pose the state already answers is a second answer to a settled question, and the two can disagree.
- **Named animator flags replicate through one controller, not one component per pose.** `PlayerAnimatorStateController` holds a server-written `NetworkList<PlayerAnimatorState>` and puts every flag on both rigs, applying the whole set in `OnNetworkSpawn` so a client arriving mid-hand is not waiting for a change that already happened. `ServerSetBool` is idempotent — a caller may write the same answer on every state change without growing the list — and a parameter the controller does not have is skipped in silence, so a pose can be driven before the art lands. What any flag *means* stays with whoever writes it: this piece carries no poker.
- **Before adding a replicated fact, check whether one already implies it.** `PokerPlayerData.HandOnTable` was added so the second wager could put every hand back down while keeping the faces private — and it was wrong twice over. It was a second value covering ground `HandRevealed` already covers (`IsHoleCardInHand` is derived from it, so a revealed hand is by definition not being held), and the moment it was meant to serve turned out not to exist: laying the hands down mid-wager read at the table as *everybody suddenly putting their cards face down*, because the body animation for "no longer holding cards" is exactly that. It is deleted, and `PokerCardRevealStage` does the whole job with one write — `ServerRevealHand` on every hand still in it, which turns the faces up for the room and drops the cards onto the table in the same change. The tell was the bug report: a feature nobody asked for, describing itself in the one animation the rig had for it.
- **Turning the cards over for the room is a beat, and it happens before anybody is told who won.** `PokerCardRevealStage` sits between the last wager and the showdown: every hand still in it goes face up on the table and the table is given `_duration` to read them, because the ranking board answers the question the cards have only just asked. Folding is how a hand leaves before that — `PokerPlayer.ServerFold` discards outright (`HoleCards.Clear()`), so a folder has nothing left to turn over and the reveal skips them on `IsInHand` without a second condition about folding.
- **Adding a stage to a sequence is only half the wiring — every `_handOverStage` that jumps past it is the other half.** `PokerCardRevealStage` went in after the second wager and still never ran, because a street that ends early jumps to its own named stage rather than following the list: `PokerItemWagerStage._handOverStage` pointed at the showdown, which reveals nothing when one player is left (`ResolveContenders` skips `ServerRevealHand` at `inHand <= 1`). The cards therefore stayed face down on exactly the path the round takes most often while testing — a solo table, where the wager ends the moment it opens. Whenever a stage is inserted, grep the preset for every reference that names a stage *by hand* and decide which of them should now go through the new one.
- **A step that runs before the cards exist cannot hand over to a showdown.** `PokerItemWagerStage._handOverStage` is where a street goes when fewer than two players can still act, and on the *first* wager — which runs before the deal — that pointed at the reveal: a table that could not raise two wagerers jumped into the showdown of a hand nobody had been dealt, and published a ranking for it. It goes to the waiting room instead, which is what "there is no hand here" actually means. Read every named exit against *when* its stage runs, not only against what the stage is called.
- **A board that a countdown is running on comes down when the countdown does.** `UIPokerRankingPanel` hides on the showdown list emptying, and the only thing that emptied it was the next `PokerDealStage` — fine for Hold'em, wrong for a round whose deal is in the middle of itself, where the board then sat over the settlement, the pick and the eating. `PokerShowdownStage.FinishShowdown` clears `Data.Showdown` as it hands over, so the beat owns its own board.
- **Furniture is measured, not guessed — and "in front of the chair" is a number about the table.** The seats ring at 1.15–1.177 and the table is a circle of radius 0.795 with its top at 0.423, so a card anchor 0.30 in front of the chair put the hand at 0.850: past the rim, floating in the air between the players. Read the table's own `Renderer.bounds` and place against it (cards at 0.45 → 0.718, staked items at 0.65 → 0.50), the same discipline the seat ring already uses for its radius.
- **A sprite is read from its own -Z, so an anchor that lays one face up points its −Z at the ceiling.** `PokerCardVisual` says so in a comment at the top of the file, and the seat's `CardAnchor` was authored pointing +Z up anyway — which laid every hand face **down** against the wood, and then sent the hover lift (which travels −Z for exactly the same reason) straight down into the table. Two bug reports, one rotation: `Quaternion.Euler(90, 0, 0)` in seat space puts the anchor's forward at the floor, so the card's face is up and its top points at the middle of the table, which is the way round the sitter reads it. Prove it by measuring `-pivot.forward` and checking it is world up — `FaceUp == true` is about which *sprite* is assigned and says nothing about which way the card is pointing. An item anchor is the opposite case and stays upright (identity): a prop stands on the table and is dropped along its own +Y.
- **`EndGame` is the cleanup choke point.** It sweeps every registered player's cards, not only the seated — whoever left a seat mid-hand is outside every stage's reset sweep.

## Asset naming conventions

- Prefabs: `UI_` prefix for UI prefabs (`UI_Screen_<Name>` for full-screen panels, `UI_<Name>` for components). No prefix for gameplay prefabs. `Button_` prefix for button prefabs.
- Animation clips: `Animation_<StateName>.anim`. Animator controllers: `Animator_<Context>.controller` / `.overrideController`. Keep these colocated with the prefab they belong to.
- Scenes: short PascalCase purpose names (`Bootstrap.unity`, `Gameplay_Poker.unity`).
- ScriptableObject assets: PascalCase matching the class name.
- **A font family is a folder holding its faces and their TMP assets** (`Fonts/Skranji/Skranji-Regular.ttf` + `Skranji-Regular SDF.asset`). Font assets are **Dynamic** so a glyph nobody pre-baked — an accent in a Steam name — is rasterised on demand instead of drawing a box, and the bold face is wired into the regular asset's weight table so `<b>` uses the real cut. Created by script, the atlas texture and material must be added to the asset with `AddObjectToAsset`; loose, the asset loads with a broken material.
- **A display font carries `LiberationSans SDF - Fallback` in its fallback table**, so a glyph it was never cut for — a Vietnamese accent, a symbol in a Steam name — comes out in the default face instead of a box. Reach for that asset rather than `LiberationSans SDF`: the plain one is Static with 250 baked characters, the `- Fallback` one is Dynamic over the same TTF and rasterises whatever is asked of it. The project's own strings stay English; the fallback is there for names it does not control.
- **A piece of the world that carries behaviour is a prefab — model, components and its authored anchors together** (`Seat_PokerChair.prefab`, `GameMode_Poker.prefab`, `PokerTableVisual.prefab`), never a scene object assembled by hand. Retuning where cards land is then one prefab edit that reaches every seat; the scene only places instances and sets what differs per instance.
- A spawn point sits where the spawned prefab's *root* belongs, not where the character ends up — player roots are at the feet, so a seat's point stays on the floor and the sitting animation supplies the height.
- **A prop's collider is fitted from its mesh's *local* bounds, never from a world-axis box you compute yourself.** The environment FBXs are Z-up exports and sit in the scene at `rot x=270`, so the mesh's local Y is the world's Z — a `BoxCollider` whose `size` is taken from `Renderer.bounds` is authored in the wrong axis order and comes out lying on its side. `center`/`size` from `MeshFilter.sharedMesh.bounds` are already in the collider's own local space, and the transform's rotation and scale then apply for free. Nothing warns about the wrong one: a box of plausible dimensions in the wrong orientation reads as correct in the inspector and surfaces only as a player walking through one face of a crate and bouncing off thin air beside it. Verify by comparing `Collider.bounds` against `Renderer.bounds` — both are world AABBs, so a correct box matches to within a couple of centimetres (`Gameplay_Poker`'s room props: 36 of 36).
- **An environment prop carries its collider from the model importer, not from a box fitted by hand in the scene.** `addColliders` on the FBX gives every instance a `MeshCollider` that follows the actual geometry, arrives with the model, and needs no scene override — the perimeter `Bounds/Wall_*` boxes and the seat prefabs are the only hand-authored colliders left in `Gameplay_Poker`. Turning that flag on over a scene that was already fitted with primitives is where it bites, in two silent ways found together. Every prop that had a box keeps it **and** gains the mesh one, so the room runs two colliders per object with nothing complaining; and a prop whose auto `MeshCollider` a previous pass had *removed as an override* gains nothing at all, because the flag was already on and the removal outranks it — 13 barrels sat with only their box while the other 23 props sat with both. Fixing it is one pass: revert the removed-component overrides, then delete every `BoxCollider` that is an added-component override on an FBX instance (`PrefabUtility.IsAddedComponentOverride` is what separates those from the walls and the chairs, which are not prefab instances). Two older lessons survive for anything still fitted by hand: a box is built from `MeshFilter.sharedMesh.bounds`, never from `Renderer.bounds` — these FBXs are Z-up exports sitting at `rot x=270`, so a box sized from world bounds comes out lying on its side and reads as correct in the inspector; and what is worth colliding at all is read off the `CharacterController` (`height 0.647`, `stepOffset 0.30`), since a prop whose bottom sits above ~0.70 cannot be reached and one under the step offset is walked over regardless.
- **Measure a seated fit with the Animator running, never with `AnimationClip.SampleAnimation`.** The two disagree, and the difference is the whole answer: `SampleAnimation` writes only the clip's curve paths, so a root node the curves do not name stays at its bind pose, while the Animator also writes the generic avatar's root node from the clip's root motion settings. On the gnome sit clips that is a 17cm lift — `Root_M` local Y `0.2825` under the Animator against `0.1788` sampled — so a chair fitted from a sampled pose leaves the character floating in play. Sample only to read a clip's authoring intent; take every number that furniture is built from out of Play mode.
- **A seat's facing is derived from where it stands, never typed.** `Gameplay_Poker`'s six chairs carried hand-typed yaws off a clean hexagon (0/60/120/180/240/300) while four of them actually sat at ring angles `±47.735°`/`±132.265°` and a radius of `1.1769` rather than `1.15` — so those four faced `12.265°` away from the table and the sitter's hands landed skew on it. The two on the Z axis happened to be right, which is exactly why it survived: half the table looked fine. Compute the yaw as `Atan2(-x, -z)` from the seat's own position and the error cannot be introduced again. The pose itself was never at fault — the wrists measure `(∓0.5290, 0.4232, 0.0249)` in the character's own frame, symmetric to four decimal places, so any skew on the table is the seat's angle and nothing else.
- **A component that recomputes a layout has to be able to stand down, or hand-authoring it is impossible.** `PokerSeatRingVisual.Place` writes every chair's position *and* rotation on `OnEnable`, so a designer who squares the chairs up in the scene and turns the model to taste watches all of it snap back the moment they press Play, with nothing logged and nothing in the inspector to explain it. `_placeSeats` off leaves each chair exactly where the scene put it and keeps only the hide-and-show half, which is the half that answers to a replicated count. The cost is real and is the reason it stays on by default: a table laid for two then seats them at adjacent corners of a square rather than opposite each other, which is the whole reason the ring exists.
- **A model that is turned wrong is fixed in its own prefab, not corrected in whatever code aims it.** The first answer here was a `_facingOffset` on the ring visual, turned onto the derived facing — and it put the same angle in two places, left the seat transform lying about which way the chair looks, and would have gone stale the moment the art was re-exported. The chair's own child carries the correction inside `Seat_PokerChair`, so the seat root goes on meaning "square to the table" everywhere that reads it — the card and item anchors included.
- **Re-authoring the chairs redefines the ring, because the radius is measured off them.** `_radius` at zero averages the distance of every serialized chair, so trimming a six-chair hexagon to four and squaring them up sets the radius to whatever was authored. Carrying the old average across (the four survivors measured `1.1634302`, so the square was laid at exactly that) keeps play mode unmoved by what was meant to be a tidy-up of the scene view; picking a rounder number would have shifted every seat relative to a table nobody re-measured.
- **An Animator on a rig whose renderers are all disabled freezes.** `PlayerVisual` switches off the body rig for the owner and the hand-only rig for everyone else, and the default `CullUpdateTransforms` then stops writing that rig's transforms entirely — its bones hold whatever pose they were last given. It reads as a rig that animates correctly, because the stale pose is a real pose. Set `AlwaysAnimate` on any rig that is hidden but still has to be measured, drive a prop, or feed a bone lookup.
- **Fix "this object is switched off" in the prefab that owns it, never with a scene override.** `Screen_Loading` was inactive inside `UI_Manager.prefab`, and the scene was carrying an `m_IsActive` override to switch it back on — so the loading screen worked only for as long as that one override survived, and it did not. Set it in the prefab and revert the override (`PrefabUtility.RevertPropertyOverride`) so the scene stops disagreeing; an override that merely repairs the prefab is a bug waiting for the next merge.
- **A scene re-serialized by the editor is not automatically noise — read whose prefab the guid belongs to before reverting it.** Discarding `Bootstrap.unity` after a rebase threw away an `m_IsActive: 1` override on the `UI_Manager` instance that was switching `Screen_Loading` on, and the loading screen went dead again with nothing to explain it. Map the guid to its `.meta` first (`grep -rl <guid> Assets --include=*.meta`); a `git checkout` of a scene is a content change, not a cleanup.
- **A scene instance's override beats the prefab, so check the scene before believing a prefab edit landed.** `Gameplay_Poker`'s `GameMode_Poker` instance overrides `_sequence`, which means the preset the match actually runs is the scene's, not the prefab's — change one and the other silently keeps deciding. Same for any serialized value a designer has touched in the scene.
- **`SetDirty` + `AssetDatabase.SaveAssets()` is not a write.** Two `PokerShowdownStage` presets took a `SerializedObject` edit, reported the new value back correctly, and were still unchanged in the `.asset` on disk — `SaveAssets` flushed nothing and said nothing. `AssetDatabase.SaveAssetIfDirty(asset)` wrote them. Same lesson as the prefab saves below, with a different API doing the lying: name the asset you mean, then grep the file.
- **"Read it back from disk" means the file, not `LoadAssetAtPath`.** That returns the *in-memory* asset, so a verification pass built on it happily reports the change you just made even when the write never reached the file — three separate fixes read back green and were all still absent from the `.prefab` on disk. The tell was in the console, not the tool result: `Asset Database is set to Read Only, but it has found out-of-date assets`, with `SaveAsPrefabAsset` returning `false` and `SaveAsPrefabAsset` on an instance returning `null`, neither of them logging a reason. Check `git diff` or `grep` the asset file itself, and treat a `false`/`null` from a save API as a hard stop rather than something to retry through. `PrefabUtility.SavePrefabAsset(go, out var ok)` on the asset loaded in place succeeded where the `LoadPrefabContents`/`SaveAsPrefabAsset` round trip did not. That route is not reliable either — it returned `false` twice in one session on a prefab it had just saved, again with nothing logged. When both save APIs refuse, write the value into the `.prefab` YAML directly and `ImportAsset(ForceUpdate)`, then read it back through `SerializedObject`: the file is the source of truth and the editor will pick up an honest edit to it.
- **A prefab edit is not done until it is read back from disk.** `SaveAsPrefabAsset` returned without complaint on an edit that deleted a child, and the child was still there on the next load — the failure only surfaced later as a missing script on the object that was supposed to be gone. Use the `out bool` overload, then `LoadAssetAtPath` again and check the thing you changed; the same lesson `Screen_Loading` and the button tints already taught, now with the save itself lying.
- **A PNG under `Assets/Textures/**` imports as a Sprite because a Preset says so, not because anyone remembered.** `Assets/Settings/Presets/UISprite.preset` carries the settings the project's UI art already uses — Sprite/Single, no mipmaps, Clamp, Tight, 100 PPU, Uncompressed, alpha as transparency — and it is registered in the Preset Manager against `glob:"Assets/Textures/**"`. The filter is the whole point and must not be widened to all textures: `Assets/Art/**/Texture` is full of 3D material maps that have to keep arriving as Textures with mipmaps and Repeat. Build the preset from a throwaway seed PNG rather than from an existing sprite, or that sprite's own 9-slice border becomes everyone's default. Verify it the only way that means anything — import a fresh PNG into each of the two places and read the importer back.
- **Move assets with `AssetDatabase.MoveAsset`, never by moving files on disk** — it carries the `.meta` and the GUID, so references survive. After a batch move, open the affected prefabs and scenes and check for null materials and missing scripts.
- **Renaming a serialized *field* silently drops its value, even when the guid survives the file rename.** `AssetDatabase.MoveAsset` carried every script's guid through the Mushroom→Item rename, so no prefab lost a component and nothing logged a word — but `_mushroomDatabase`, `_mushroomAnchor` and `_capPrefab` were still the keys in the YAML, and Unity would have deserialized the renamed fields as null the first time each prefab was saved. The failure is a table with no database, chairs with no item spot and a pot that draws nothing, all of them looking like features that were never wired. After renaming a field, grep every `.prefab`, `.unity` and `.asset` for the **old key** and rewrite it in place; the check is that the property reads back non-null through `SerializedObject`, not that the component is still there.
- **A mechanism is renamed when the game outgrows the one thing it was built for, and prose is not part of the rename.** `PokerMushroom*` became `PokerItem*` — database, effect, wager stage, consume stage, pot and plate visuals, `PendingItems`, `ServerQueueItem`, `WagerItem`, `PokerSeat.ItemAnchor` — because a stake is an index into a catalogue and nothing in any of it knows what a mushroom is. The comments still say cap and mushroom where they describe *this* game, which is the same split the naming rule already asks for: domain-agnostic mechanism, concrete domain code. What tells two stakes apart is a prefab per entry (`PokerItemDatabase.Entry.WorldPrefab`), never a tint on one shared model — a colour is how a placeholder distinguishes things, not how a game does.

## Editor settings that affect how you write code

- **Domain Reload is disabled** (Scene Reload only). Static fields, static events, and singleton `Instance` properties survive between Play sessions. Every class holding static state must reset it via `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` — see `SteamController`, `GameNetworkManager`, `GameModeController`, `UIManager`. A `static event` is the dangerous one: reset it to `null` there rather than trusting `OnDisable`, or it keeps handlers pointing at objects destroyed two play sessions ago. `static readonly` constants are exempt.
- **Auto Refresh is disabled.** After writing scripts outside the Editor, trigger `AssetDatabase.Refresh()` manually before expecting a recompile.
- **A `ProjectSettings/*.asset` written through an API lives in memory until the project is saved.** `Preset.SetDefaultPresetsForType` reported the new entry back correctly through `GetDefaultPresetsForType` while `PresetManager.asset` on disk still read `m_DefaultPresets: {}` — the same lie `SetDirty` + `SaveAssets` tells about prefabs, with a different API. Follow it with `AssetDatabase.SaveAssets()` **and** `ExecuteMenuItem("File/Save Project")`, then grep the file.
- **`AssetDatabase.DeleteAsset` is refused inside a `RunCommand`** ("User interactions are not supported"), and it aborts the whole script before anything runs — so a command that deletes halfway through silently does none of its earlier work either. Do the deletion from the shell (`.png` *and* `.meta`) and keep the command to the parts the Editor has to do.
- **A `RunCommand` cannot import a *new* asset, and it reports success either way.** Writing three new `.cs` files and calling `AssetDatabase.Refresh`/`ImportAsset` logged no error, and `AssetPathToGUID` even handed back a fresh guid for each — while no `.meta` reached disk, `LoadAssetAtPath<MonoScript>` stayed null, `FindAssets` returned **0**, and every compile failed with CS0246 against a file sitting right there in the folder. The tell is that pair: a path that resolves to a guid but finds nothing. Editing an *existing* tracked file works fine, which is why this only bites when a feature adds its first new script. `AllowAutoRefresh()` is not the fix and is actively harmful — it decrements a counter the project keeps at zero and the editor then asserts `m_DisallowAutoRefresh >= 0` on every refresh until it is paired back. New files need a real import from the editor itself (focus it, or Ctrl+R with Auto Refresh off), so plan on handing that step to whoever is at the machine rather than reporting the code as compiled.
- **Make a folder with `AssetDatabase.CreateFolder`, and never with `Directory.CreateDirectory` + `Refresh`.** The refresh does not take effect inside the `RunCommand` that asked for it, so the folder exists on disk and not in the database — and then every write into it fails *quietly*: `SaveAsPrefabAsset` returned `false` for six prefabs in a row and `CreateAsset` left the object null, which surfaced later as an `ArgumentException` from a `SerializedObject` built on it rather than as anything naming the folder. Materials into the same missing folder appeared to succeed. Create the folder in its own command, check `IsValidFolder` before writing, and reload the asset from its path after `CreateAsset` rather than keeping the instance you passed in.
- **Check which editor the Unity connection is attached to before trusting a single write.** An MPPM virtual player runs with `-readonly`, so through it `SaveAsPrefabAsset` returns `false`, `SaveAssets` flushes nothing, and `AssetDatabase.IsOpenForEdit` is `false` for every asset in the project — the whole session reads as a string of silent no-ops, and the edits look correct right up until the file on disk is checked. `Application.dataPath` names it outright: the main editor answers `<project>/Assets`, a virtual player answers `<project>/Library/VP/mppm*/Assets`. Read that first and re-point the connection at the main editor rather than diagnosing each failed write; the "Asset Database is set to Read Only" console line is the same fact arriving too late.
- **Deleting a script fails the compile with CS2001 against an MPPM mirror until that virtual player's build cache is cleared.** The mirror's `Assets` is a symlink, so the file is already gone there — what is stale is `Library/VP/mppm*/Library/Bee` and the generated `.csproj`, and the main editor's own clean rebuild never reaches them. Delete those two, then `RequestScriptCompilation(CleanBuildCache)`. Closing the virtual player also works but throws away a running test session, so clear the cache first.
- **UI uses TextMeshPro**, never legacy `UnityEngine.UI.Text` — `TextMeshProUGUI`, `TMP_InputField`, `TMP_Dropdown`, and `TMP_Text` in code.
- **Input uses `InputActionReference` serialized fields**, never string lookups like `_playerInput.actions["Look"]` — see `PlayerController`.
- **A mouse reports a delta and a stick reports a position, so they are integrated differently or the pad crawls.** Mouse delta is already a per-frame amount and must never be scaled by `deltaTime`; a stick says how far it is being held, which is a rate and means nothing until multiplied by the frame length and a degrees-per-second speed. Worse, a `Value` action only raises `performed` when its value *changes*, so a stick held at full deflection stops reporting entirely — the view turns about a degree and stops. `PlayerController.ReadLookInput` is therefore polled from `Update` (look is the continuous work the no-polling rule already exempts) and branches on `InputSchemeController.IsGamepad`, with `_lookSensitivityX/Y` for the mouse and `_gamepadLookSpeedX/Y` plus an exponent for the stick. The symptom reads as "controller sensitivity is too low", which sends you tuning a number that was never the problem.
- **Which device is in hand is `InputSchemeController`, driven by `InputSystem.onEvent` and not by `onActionChange`.** `onActionChange` only speaks for actions that are enabled and bound, so a pad button pressed on a street where nothing is listening would never switch the scheme and every badge on screen would keep naming a key nobody is using. Filter events through `EnumerateChangedControls(device, 0.15f)` — a stick at rest still streams state and a mouse reports jitter, so an unfiltered event is not evidence anyone touched anything — and early-out when the device already matches, which is almost every event.
- **Every binding carries its control scheme, or masking silently blanks the UI.** `GetBindingDisplayString(InputBinding.MaskByGroup(...))` is what makes a badge name the device in hand, and a binding whose `groups` is empty matches no mask and comes back as an empty string. The whole `Table` map was authored that way, so adding the mask would have blanked all nine key badges on the action pad at once. Assign the groups in the same change that introduces the mask. Composites are the exception worth knowing: `Move`'s WASD composite returns empty under a keyboard mask, so a "WASD to move" hint cannot be read this way.
- **A "nothing changed" guard has to be told that a rebind is a change.** `PlayerInteractionController.RefreshPrompt` early-outs when the action name matches what is already shown, and the name does not move when the device does — so the prompt would go on naming a keyboard after the player picked up a pad. Clear the remembered value before refreshing, the same defect `UIButton.ResetState` and `UIWheelItemView.Bind` were fixed for.
- **Two `RuntimeInitializeOnLoadMethod(SubsystemRegistration)` methods run in an undefined order, so never subscribe to another static's event from one.** `CursorController` listening for `InputSchemeController.OnSchemeChanged` from its own reset would be wiped whenever the other reset ran second and set the event to null. Reset in `SubsystemRegistration`, subscribe in `AfterSceneLoad`, which always runs after every reset.
- **Editing `.inputactions` from script: write `asset.ToJson()` and then prove the action ids did not move.** Prefabs reference `InputActionReference` sub-assets whose fileIDs come from the action ids, so an id that changes silently detaches every serialized reference in the project. Capture `action.id` for every action before the edit, reimport, and compare — 30 of 30 unchanged is the check, not "it looked fine in the inspector".
- **Never call `AssetDatabase.Refresh(ImportAssetOptions.ForceUpdate)`; refresh plainly, or import the one asset you wrote.** A whole-project force reimport re-serializes assets nobody touched, and the damage lands where a serialized value is *resolved* rather than stored — an `InputActionProperty` re-binds itself by name to whichever `InputActionReference` sub-asset the fresh import handed out. `UI_Manager`'s `VirtualMouseInput` came back with its left button moved from `Table/PickCard` to `UI/Click`, and `UI/Click` is bound to the real mouse: every click then pressed the *virtual* mouse's button, `Pointer.current` became the virtual cursor sitting somewhere else, and the press landed on nothing. The report was "clicking the UI does nothing", which points at the UI and not at an import three commands earlier. Two anchor overrides were flattened in the same pass. Plain `AssetDatabase.Refresh()` picks up new scripts perfectly well; when a specific asset needs rereading, name it with `ImportAsset(path)`.
- **`.inputactions` ships two `InputActionReference` sub-assets per action, so a fileID resolves by luck.** Measured on `InputSystem_Actions`: 68 references for 34 actions, every name appearing twice, and a force reimport does not collapse them. So `-5630367516989439448` is `Table/PickCard` in one set and was something else in the other, which is why a prefab pointing at a fileID can silently come to mean a different action. Diagnose by loading every sub-asset and printing name against `TryGetGUIDAndLocalFileIdentifier`, never by reading the fileID in the YAML and assuming it still means what it meant.
- Scene-placed `NetworkObject`s created programmatically get `GlobalObjectIdHash = 0` and fail to spawn. If that happens, remove and re-add the `NetworkObject` component on the saved scene object to regenerate it.

## Rules

1. Keep the two-assembly split (`Game.Runtime`, `Game.Editor`); don't introduce new asmdefs without a real modularity need.
2. Server-authoritative by default — any gameplay state that must be consistent across clients lives in a `NetworkBehaviour`/`NetworkVariable`, not in a locally-mutated field trusted from the client.
3. No XML doc comments or comment blocks; let naming carry the meaning.
4. Follow SOLID, KISS and DRY; prefer industry-standard patterns over bespoke structure, and keep modules loosely coupled and reusable.
5. Extend through `protected virtual OnX` hooks called from a non-virtual base method — never edit a parent class to accommodate a subclass. Never make a Unity message (`Awake`, `Update`, `OnDestroy`) `virtual`: a subclass forgetting `base.Awake()` is a recurring, silent bug.
6. Every system binds and unbinds through explicit paired lifecycle hooks; never poll for a dependency in `Update()`.
7. Animate with DOTween tweens, not hand-rolled `Lerp`/`Slerp` stepped in `Update()`.
8. Never resolve a dependency by searching the scene (`FindFirstObjectByType`, `FindAnyObjectByType`, `Camera.main`) — serialize it, be handed it, or register it.
9. Name a mechanism domain-agnostically and domain code explicitly; the name must state its purpose on sight. Don't abstract until a second real use exists.
10. A serialized value that must match something else is picked from a dropdown, never typed.

## Maintaining this file

**Write the rule down in the same change that establishes it.** A convention agreed only in chat is gone by the next session — these rules are where the project remembers.

A rule earns its place when either is true: **it repeats** (the same correction or the same shape has come up twice — don't wait for a third), or **it matters** (getting it wrong causes a silent failure, a leak, or a bug that is hard to trace back, even if it happened once). A one-off decision with no consequence stays in the code.

When adding one: put it in the section it belongs to instead of appending a new one, cite the file in this repo that demonstrates it, and fix any existing rule it contradicts. A rule that disagrees with the code is worse than no rule, because it will be trusted.
