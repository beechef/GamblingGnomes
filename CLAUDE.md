# GamblingGnomes — Project Conventions

## Tech stack (mirrors ProjectGamble)

- **Unity** with **URP** (`com.unity.render-pipelines.universal`).
- **Netcode for GameObjects** (`com.unity.netcode.gameobjects`) for multiplayer — server-authoritative model.
- **New Input System** (`com.unity.inputsystem`).
- **DOTween** (`Assets/Plugins/Demigiant`) for tweening.
- **Odin Inspector** (`Assets/Plugins/Sirenix`) for inspector tooling — used selectively, not everywhere.
- **Facepunch.Steamworks** (`Assets/Plugins/Facepunch.Steamworks`) for Steam integration.
- **Addressables**, **Timeline**, **Visual Effect Graph**, **Post-processing** as needed.
- C# language version: 9.0.

All of the above packages/plugins have already been installed/copied into this project to match ProjectGamble (`Packages/manifest.json` + `Assets/Plugins/`).

## Folder structure

Follow ProjectGamble's layout:

```
Assets/
  Scripts/
    Game.Runtime/   — all gameplay code (asmdef: Game.Runtime)
    Game.Editor/    — editor-only tooling (asmdef: Game.Editor, includePlatforms: Editor)
  Prefabs/
    UI/             — UI prefabs, with Buttons/ and feature subfolders colocating anim + controller assets
  Scenes/            — Bootstrap.unity (or equivalent) + Gameplay.unity pattern: bootstrap scene loads gameplay
  Fonts/             — one folder per font family
  Textures/
  Materials/
  Configs/           — ScriptableObject data assets
  Resources/         — kept minimal (only assets that must be Resources.Load'ed, e.g. DOTweenSettings)
  Plugins/           — third-party libs dropped in as source/DLL (Demigiant, Sirenix, Facepunch.Steamworks)
  Settings/          — URP assets, Input Actions, volume profiles, Build Profiles
```

Do not scatter scripts outside `Assets/Scripts/`. Do not create per-feature asmdefs — keep the flat two-assembly split (`Game.Runtime` + `Game.Editor`) unless the project grows enough to justify splitting.

## C# code conventions

**Namespaces**: mirror the folder path exactly, rooted at `Game.Runtime` / `Game.Editor` (e.g. a script in `Scripts/Game.Runtime/UI/Poker/` → `namespace Game.Runtime.UI.Poker`).

**Naming**:
- PascalCase for all types; file name matches class name.
- UI `MonoBehaviour`s prefixed `UI` in code (`UIButton`, `UIManager`) — no underscore in the C# identifier.
- Feature/domain prefix for grouping instead of relying only on namespaces (e.g. all poker-specific classes start with `Poker*`).
- Suffixes carry meaning: `*Manager` (singleton-style coordinators), `*Controller` (behavior/logic owner), `*Data` (NetworkBehaviour holding `NetworkVariable`/`NetworkList` state — the "model"), `*Stage` (state-machine step), `*Visual` (presentation-only component), `*Database` (ScriptableObject lookup table), `*Constant`, `*Settings`.
- Interfaces prefixed `I` (`IGameMode`).

**Base types**:
- `NetworkBehaviour` for anything with server-authoritative state.
- Plain `MonoBehaviour` for local/visual-only components.
- `ScriptableObject` (with `[CreateAssetMenu]`) for static config/data assets.
- Structs implementing `INetworkSerializable, IEquatable<T>` for small networked value types (like `CardData`).
- Abstract base classes for pluggable step/ability systems (e.g. a `*Stage` base with `StartStage`/`EndStage`, subclassed per concrete stage; an ability base with lifecycle hooks like `OnInitialize/OnActivateServer/OnActivateClient/OnDeInitialize`).

**Fields & properties**:
- `[SerializeField] private Type _fieldName;` — underscore-prefixed camelCase for private serialized fields.
- `[field: SerializeField] public Type Foo { get; private set; }` for "inspector-set, code-read-only" public members.
- `[HideInInspector] public NetworkVariable<T> Foo = new(...);` — public field (not property) for NGO NetworkVariables, hidden from inspector.
- `[Header("Section Name")]` to group inspector fields logically (e.g. "Player Info", "Game State", "References").
- Constants in PascalCase, not SCREAMING_CASE (`private const int MinimumPlayersToStart = 2;`).
- No regions. No XML doc comments. Comments are rare — only for non-obvious business logic, one line max.

**Patterns**:
- Singleton managers: hand-rolled `public static X Instance { get; private set; }`, set in `Awake()` with a duplicate-destroy guard. No generic `Singleton<T>` base.
- Data/logic split: put networked state in a dedicated `*Data` `NetworkBehaviour` (model), expose it via a `Data` property from the owning controller/stage (logic), keep UI as a separate view that reads `Data` and subscribes to its change events.
- State machines: a list of stage objects + current index, `NextStage()` calling `EndStage()`/`StartStage()` on transition.
- Event-driven sync: plain `event Action`/`event Action<T>`, subscribed in `OnNetworkSpawn`/`OnEnable`, unsubscribed symmetrically in `OnNetworkDespawn`/`OnDisable`. Prefer `NetworkVariable<T>.OnValueChanged` / `NetworkList<T>.OnListChanged` for state→view sync over manual RPC broadcasts of state.
- RPCs: use the modern NGO attribute style `[Rpc(SendTo.Server, ...)]` / `[Rpc(SendTo.Owner, ...)]`, not legacy `[ServerRpc]`/`[ClientRpc]`. Method names keep the `RPC` suffix (`ActivateRPC`, `ReadyRPC`).
- Async: use Unity's native `Awaitable`/`Awaitable<T>`, not UniTask or coroutines, for new async code. Every async operation takes `CancellationToken ct = default` and undoes its own setup on cancel; a temporary handler subscribed inside an awaitable wrapper is unsubscribed on *every* path, cancel included. `async void` is banned except for a Unity/UI event handler, and that handler catches. **A re-entry guard flag is released in `finally`, never on the success path alone** — one throw and the button is dead for the rest of the session (`UIFindLobby`, `UIPauseMenu`, `GameNetworkManager._joiningLobby`). UI handlers pass `destroyCancellationToken`, so an await outliving its object unwinds instead of writing into a corpse.
- Tweens: cache `Tween` references in a field, `.Kill()` before restarting.
- No DI container / service locator. Wire dependencies via `[SerializeField]` inspector refs or static `Instance` singletons.
- **Never resolve a dependency with `FindFirstObjectByType`/`FindAnyObjectByType`/`Camera.main`** (editor tooling excepted) — a dependency arrives serialized, is handed over by its owner's lifecycle (`Initialize(owner)`), or comes from a registry that sets itself up and tears itself down in its own lifecycle (`GameCamera`, `PokerSeat`). A *spawned* prefab is the case that needs the registry: it cannot serialize a reference to the scene it lands in.
- No polling. `Update`/`LateUpdate` is for genuinely continuous work (look smoothing, camera follow) — never for detecting that something changed, and never for `GetComponent`, `Instantiate`, `Find*` or allocation. Cache lookups in `Awake`/`Initialize`.
- Odin Inspector (`[ValueDropdown]`, `[FoldoutGroup]`, etc.) only where plain `[SerializeField]`/`[Header]` can't express the need (dynamic dropdowns, foldout grouping) — not as the default on every class.

## Design principles

Hold code to an industry-standard design bar rather than inventing bespoke structure. When facing a design choice, reach for the solution many teams already converge on; check whether this codebase (or the wider industry) already has the shape for it before writing a new mechanism.

- **SOLID + KISS + DRY.** Split into clear modules that can be reused and assembled, not monoliths.
- **Minimise coupling.** A component that needs a dependency takes it from an event or an injected reference rather than reaching into a concrete singleton — a module that can only work in the one place it grew up in is not reusable.
- **Domain-agnostic mechanism, concrete domain code.** Genericity is a property of the module boundary, not of every line. A reusable mechanism carries no poker/Steam/lobby word in its name or API (`PlayerBoneScaleController`, `PlayerActionAnimator`, `PlayerSpawnPoint` — the mechanism is the same whatever sits in it). Code built on top of it stays explicit: `DealCardToPlayer`, `SwapPotToLosers`, `OnPotItemsChanged` — never `Assign`, `Process`, `OnValueChanged`. **A name must state its purpose on sight; that outranks genericity.** A vague name in domain code is a defect, not an abstraction.
- **Don't over-generalize.** Structural abstraction (interface, type parameter, base hierarchy) costs something: two real uses justify it, one does not. Write the concrete case, and pull the mechanism out when the second caller actually arrives. Duplication twice is a signal, three times is a refactor.
- **Data, logic and visual are three responsibilities, never mixed in one class.** Data owns state (`NetworkVariable`, serialized config) and no behaviour; logic owns rules and transitions and touches no `Renderer`/`Animator`/`Image`/tween; visual renders and animates and never decides a rule or writes authoritative state. Visual *reacts* to data through events and `OnValueChanged` — it never drives. `PokerGameData`/`PokerGameMode`/`PokerVisual` and `PlayerData`/`PlayerController`/`PlayerVisual` are the reference shapes.
- **Downward references only.** `GameModeController` → `PokerGameMode` → `PokerModule`/`PokerStage`; a child never calls up, it raises an `event` the parent listens to. Cross-module talk goes through events or a small shared contract, not a reach into the other module's concrete type.
- **Template method for extension points.** A base class keeps its own step non-virtual and calls a `protected virtual` hook from inside it, so a subclass extends behaviour without the parent ever being edited, and shared work can't be skipped by a subclass that forgets `base.Foo()`:

  ```csharp
  private void Tick(float deltaTime)
  {
      // shared work the base always does
      OnTick(deltaTime);
  }

  protected virtual void OnTick(float deltaTime) { }
  ```

  The outer method carries the invariants (guards, ordering, state flags); the `OnX` hook carries only the subclass's own work. Applies to every extension point, not just tick — `Start`/`End`, `Bind`/`Unbind`, `Enable`/`Disable`. See `PokerStage` (`StartStage`/`OnStartStage`), `UIPokerView` and `PokerVisual` (`OnBind`/`OnUnbind`).
- **Every system has an explicit lifecycle.** Bind and unbind through paired hooks — `OnEnable`/`OnDisable`, `OnNetworkSpawn`/`OnNetworkDespawn`, `OnBind`/`OnUnbind`, or a static `OnInstanceChanged`-style event. Never poll for a dependency in `Update()` and rebind when you notice it changed: that hides the binding in the per-frame path and leaves no single point where the subscription is released, so handlers leak. Unsubscribe in the reverse order of subscribing, and null a reference only after the unsubscribe that needs it.
- **Animate with DOTween, not hand-rolled interpolation.** A per-frame `Vector3.Lerp`/`Quaternion.Slerp` toward a moving target bakes the curve into decay maths and offers no hook for "then do this". A tween makes easing, duration, delay, loops, callbacks and sequences tunable after the fact. Expose duration and `Ease` as `[SerializeField]` so they can be retuned without touching code, and prefer `SetEase` over hand-tuned constants.

## Scenes and lifetimes

Two lifetimes: `Bootstrap.unity` is persistent, `Gameplay_*.unity` is loaded additively and disposable.

- Bootstrap owns the services that outlive a match — `NetworkManager`, `GameNetworkManager`, `SteamController`, `GameCamera` + the Cinemachine brain, `UIManager`'s canvas. Gameplay owns the mode, the table, the seats and the players.
- **Bootstrap code must not reference gameplay types.** Gameplay consumes bootstrap services through their registered instance or an interface, never the other way round.
- Gameplay must survive being unloaded and reloaded without leaking a handler or a static: every `+=` in a spawn/enable hook has its `-=` in the mirrored despawn/disable hook, and every static holding state resets under `[RuntimeInitializeOnLoadMethod]`.
- Never assume gameplay is loaded from bootstrap code; go through the async load path. Scene operations in a networked session go through `NetworkManager.SceneManager`.
- Exactly one **base** `Camera` + `CinemachineBrain` exists, and it lives in bootstrap. Everything else — the player prefab's first-person rigs, any cutscene rig — is a `CinemachineCamera` the brain blends to. Never hand-drive `Camera.transform`. The one other `Camera` is `Bootstrap/UICamera`, an URP **Overlay** camera in the base camera's stack; it draws the UI and nothing else, and has no brain.

## Netcode rules

- Server is authoritative for spawn/despawn and for every rule. Owner-write `NetworkVariable`s are for input-shaped state only (look angles, identity).
- **Set `readPerm`/`writePerm` explicitly on every `NetworkVariable`** — never rely on the defaults. See `PlayerManager`.
- **A replicated value has one seeder, and a spawn-time write on another component is an ordering bug.** When a central system takes ownership of a value, delete the local `OnNetworkSpawn` seed in the same change: the blood exchange module (`PokerBloodExchangeModule`, since deleted) kept `Enabled.Value = _enabledByDefault` after the match config began seeding it, and because module components sit after `PokerGameMode` in the prefab, the stale seed would have run second and silently stomped a pre-scene "off" — an override that only fails for whoever configured it.
- **Saving a prefab that carries a `NetworkObject` auto-appends it to `DefaultNetworkPrefabs` — even when an entry already names the same asset.** Rebuilding `Player_Poker` as a variant left the list with one dead entry (the old root fileID) and one auto-added duplicate; NGO warns about duplicates at every startup. After any save that creates or re-roots a networked prefab, re-point the dead entry and deduplicate by object, then grep the `.asset`.
- Guard server-only work with `IsServer` and owner-only work with `IsOwner` at method entry, not halfway down.
- Don't write a `NetworkVariable` every frame; throttle by a meaningful delta.
- **Subscribe to another object's singleton from `Start`, never `OnEnable`.** Objects in one scene wake in no guaranteed order, so an `OnEnable` reading `GameNetworkManager.Instance` can find null, subscribe to nothing, and never try again — silently deaf for the session, with the symptom appearing only on whichever path happens to lose the race. `UINetworkLoadingBinder` lost it on the host and won it on the client, which read as "loading works for clients only". Pair `Start` with `OnDestroy`, as `UIMainMenu` and `UIPauseMenu` already do.
- **A third-party SDK's callbacks are a singleton too, and subscribing before it is initialised loses them.** `GameNetworkManager` hooked `SteamMatchmaking.OnLobbyCreated` in `OnEnable`, and `SteamController.Awake` is what calls `SteamClient.Init` — two objects in one scene, no guaranteed order. Lose that race and Steam opens the room while `OnLobbyCreated` never arrives, which is where the host is started and the gameplay scene loaded: the lobby exists, the game never begins, and nothing is logged. It now binds from `Start` **and** from `SteamController.OnInitialized`, guarded by a flag so whichever happens first wins and the second is a no-op; `OnDestroy` drops both. `StartHost` also refuses through `OnConnectFailed` when nothing is bound, because a start that cannot possibly finish must say so rather than look like a scene that would not load.
- **Hide a loading screen on `OnLoadComplete` for the local client, not `OnLoadEventCompleted`.** The latter is the server's "everyone is in" and is never raised for a client that arrives through synchronization — which is how anyone joining an existing table gets the scene, so their screen would stay up forever. `OnLoadComplete` fires on both paths and the local client id is what makes it ours; `OnSynchronizeComplete` is the backstop for a client that synchronizes without loading anything. See `UINetworkLoadingBinder`.
- **Handle late join by reading the current value in `OnNetworkSpawn` and snapping to it** — a client that only subscribes to `OnValueChanged` shows nothing until the next change, which for a value set before it joined is never.
- Teardown belongs in `OnNetworkDespawn`, not `OnDestroy`.

## UI structure

- `UIManager` is the single canvas, living in bootstrap and surviving additive gameplay loads. **It is Screen Space - Camera, rendered by `UICamera`, so 3D models can be put on the UI**: `UICamera` is an Overlay camera stacked on the base `Camera`, parked at `(0, 5000, 0)` so nothing in the world is ever in front of it, culling only the `UI` layer, clearing depth (a model on the UI never intersects the table), with post-processing, shadows and AA off and `UI_Renderer` (index 1 in both `PC_RPAsset` and `Mobile_RPAsset`, a copy of `PC_Renderer` with **no renderer features**) so SSAO and the hallucination wave never touch the HUD, as they never did while it was an overlay canvas. The canvas's mode and plane distance (100, inside the camera's far 200) live in `UI_Manager.prefab`; its `worldCamera` is the one scene override on the instance, because a prefab cannot reference a scene camera. **Everything shown through `UIManager` is on the `UI` layer** — every prefab under `Prefabs/UI` was moved there (most sat on Default) — and a canvas object on another layer is not culled by `UICamera` and draws nowhere, with nothing logged. World-space canvases over heads stay on `UI` too: the base camera culls Everything, and `UICamera` is 5000 units away from them. Measured in Play mode: the main menu draws, and switching `UICamera` off leaves only the skybox, so the whole HUD really is on the overlay camera. Features never ship a canvas of their own; they `Show` into a layer (`UILayer.Hud` / `Screen` / `Overlay`). The layers exist so an overlay can open without disturbing the HUD beneath it.
- **The `CanvasScaler` lives on the `UIManager` canvas only** — one on a child canvas silently rescales everything under it. Scale With Screen Size, 1920×1080, Match Width Or Height 0.5, which survives both 21:9 and 4:3.
- Full-screen panels anchor `(0,0)`–`(1,1)` with zero offsets; corner HUD anchors to its corner. Anything inside a layout group needs an explicit `LayoutElement` — unconstrained children are the cause of most "looked fine at 1080p" bugs.
- **A frame that gets stretched carries a 9-slice border; a decorated shape does not.** The border lives on the sprite in **Single** mode — Multiple is for cutting several sprites out of one file, not for slicing — and the `Image` must be set to Sliced to use it (`button_Default`/`button_press` at 16, the `time_*` capsules at 16 across and 0 vertically, since only their length changes). Art with a shaped end is the exception: `button_ability_default`'s arrow head has to scale as one piece, and slicing it on a button 38 tall against art drawn at 102 pinches the head — that one stays Simple. `fillAmount` and 9-slice are the same setting, so a progress bar slices its track and leaves the fill Filled.
- **A fan of cards turns about a point below them, never about each card's own middle.** Rotating a card in place splays its top one way and its bottom the other, so the row opens gaps along the bottom edge while overlapping at the top — it reads as skewed tiles, and no amount of tuning the angle fixes it because the shape is wrong. The ranking board's community row (`UIPokerRankingPanel.PlaceOnFan`, since deleted with the community cards) sat its cards on a circle centred `_communityFanRadius` below the row: they leaned away from one shared point, the outer ones rode lower than the middle, and the whole arrangement came out of a number anybody can picture — how far down a hand holding it would be. Placing them took the layout group off that row, since a group owns position and would put them straight back in a line; that was allowed because the count was small, fixed by the rules, and entirely the panel's business. **`PokerCardFanVisual` is the same arrangement in the world and had the same defect**, which is the reason this rule is worth reading twice: it slid each card sideways by a spacing and then turned it in place, and it looked like a fan that needed its angle tuning. It turns about a shared pivot `_pivotDrop` card-heights below the cards now, and there is no spacing left — the whole spread comes from `_fanAngle`, because that is what a fan is. A drop of 0.5 puts the pivot on each card's own bottom edge, which is how a hand held in a fist opens; further down is a gentler arc. Measured at 20° across five cards: tops at ±0.0558 with 0.0261 between neighbours against a card 0.0616 wide, and every bottom edge meeting at the pivot.
- **Padding is measured off the art, not off the rect.** `table_ranking`'s rolled bar overhangs the plank at both ends, and a 9-slice keeps that overhang at its authored size however wide the board is stretched — so the usable wood is inset from the `Image` rect by a fixed amount, and a layout group padded to the rect puts its rows on transparency outside the board. Read the inset off the sprite and pad past it; the failure renders as content hanging off the edge of the frame rather than as anything a number in the inspector would warn about.
- **A HUD prefab that only exists at runtime is still previewable, and a UI is not built until it has been looked at.** Instantiate it under a `ScreenSpaceCamera` canvas with the project's scaler in a throwaway additive scene, fill the rows by hand, `ForceRebuildLayoutImmediate`, render the camera to a `RenderTexture` and write a PNG. One render caught three real defects arithmetic had not — "2nd" ellipsised inside a column sized for "1st", a name losing its tail, and rows spilling past the board's edge — and every one of them would have shipped as "it looked right in the hierarchy".
- **UI prefabs split into `Prefabs/UI/Components/` and `Prefabs/UI/Screens/`.** A component is a piece worth reusing — `UI_MenuItem`, `UI_ProgressBar`, `UI_TimerBar`, `UI_SelectionPointer`, `UI_TitleLabel`, `UI_Background`; a screen composes them as nested prefab instances, so restyling every menu entry in the game is one edit to one prefab. A screen root is full-screen `(0,0)`–`(1,1)` with zero offsets and carries its own `CanvasGroup`. **A screen nested inside `UI_Manager` is still a screen** — `Screen_FindLobby`, `Screen_RoomSetting` and `Screen_Pause` were built straight into the manager prefab and so were the one place in the project where a restyle had to be done by hand; they are prefab instances now, like `Screen_MainMenu` and `Screen_Loading` always were. **A HUD panel is a prefab too, under `Prefabs/UI/Panels/`**: every section of `UI_Poker` (`UI_HallucinationBar`, `UI_TurnPanel`, `UI_RankingPanel`, `UI_MushroomWagerBar`, `UI_HandHelper`, …) is a nested instance, and a panel owns everything it references — `Button_Help` moved under `HandHelper` for that reason, since a panel pointing at a sibling outside itself is a reference the panel asset cannot hold. **A list item is never an inactive template kept inside the list**: `RungTemplate`, `EatenTemplate` and `KindTemplate` became `UI_HallucinationRung`, `UI_ConsumedItemIcon` and `UI_PokerBetKind` under `Components/`, referenced as `_*Prefab`, so the item is edited once and there is no hidden object for every copy of the list to carry (the one exception is `TMP_Dropdown`'s `Template`, which the dropdown requires as a child). Converting was `SaveAsPrefabAssetAndConnect` per child inside `LoadPrefabContents`, checked by diffing the full type-and-path component list before and after — only the templates and `Button_Help`'s path differed, and the variant and `Player_Poker` followed with nothing missing. **A list built at runtime can still be looked at in the editor**: `UIPokerHandRankingList` has an Odin **Build Preview** / **Clear Preview** button that instantiates linked row prefabs under the container with Undo, and `_rebuildAtRuntime` decides whether opening the board re-binds from the database (on) or shows the saved preview as it is (off); rows already under the container are adopted in `Awake`, so a rebuild never adds a second set.
- **The second time a widget is drawn, it becomes a component prefab — and the thing driving it becomes one component.** Five views each carried their own `Image _timerFill` + `TextMeshProUGUI _timerLabel` and the same two lines of `fillAmount`/`CeilToInt`, on three different sprites: the clocks had visibly drifted apart because nothing tied them together. `UITimerBar` (`SetTime(remaining, normalized)`, mm:ss, urgent colour near zero) plus `UI_TimerBar.prefab` is now the single answer, and the views hand it numbers instead of drawing. A repeated widget left loose does not stay in sync — it just fails to, quietly, one prefab at a time.
- **Swapping a loose object for a prefab instance: resolve the victims before instantiating, and re-point references by search.** The replacement usually wants the old object's name, so a `Find` done *after* it exists hands back the new one to be destroyed. And a serialized field pointing at the old object is not always the one you expected — walk every component's `SerializedObject` for an `objectReferenceValue` equal to the old object and repoint it, rather than naming fields by hand and leaving the ones you did not think of dangling.
- **A list of choices marks its selection once, from the group.** `UISelectionGroup` owns the single pointer and slides it to whatever is chosen; `UISelectionItem` only says where the pointer should aim (`PointerAnchor`, normally the label so the mark lands after the last letter, whatever the word). The item's own look comes from `UIButtonState.Selected`, which outranks `Hovered` — being chosen survives the mouse wandering off, and that is the difference the two states exist to draw.
- **Let uGUI own focus; never hand-roll navigation beside it.** The EventSystem already moves selection with arrows, WASD, d-pad and both sticks, already routes Submit into `Button.onClick`, and already skips entries that are not interactable — a second navigation loop reading its own `Navigate` action does not replace that, it runs *alongside* it and the two fight over what is current. `UISelectionItem` implements `ISelectHandler` and raises `OnPointed` from it, and hover calls `EventSystem.SetSelectedGameObject` rather than marking the item directly, so pointer and keyboard feed one focus. `UISelectionGroup` then only follows that focus and slides its pointer. Consumers subscribe to `OnSelectionChanged` alone and are right for mouse and controller together.
- **A group that hides releases its selection, and remembers it separately.** Keeping `Selected` pointing at the old entry makes the very same entry arriving again look like "nothing changed", so the early-out fires and the button is never re-marked nor the pointer moved — it stays wherever `KillMove` cut the tween, which is how `UISelectionGroup` ended up aiming between two entries. Clear it on disable, stash it in `_lastSelected`, and re-offer it on enable behind `_restoreSelectionOnEnable`, re-checking that it is still active and interactable rather than trusting it.
- **Activating a parent runs its `OnEnable` before its children are switched on.** A list asking which of its items is active during its own `OnEnable` gets "none" on every re-show — it only works on scene load, where everything is activated before any `OnEnable` runs, which is exactly the kind of bug that passes the first test and fails the second. Do the work again on the next frame (`UISelectionGroup.ResnapAfterLayout`) rather than trusting the enable pass.
- **Anything that reads a laid-out rect runs in `CanvasUpdate.PostLayout`, not in `OnEnable` and not a frame later.** Implement `ICanvasElement`, call `CanvasUpdateRegistry.RegisterCanvasElementForLayoutRebuild(this)` when the answer needs recomputing, and do the work in `Rebuild(CanvasUpdate.PostLayout)` — uGUI's own "layout is settled" pass, in the same frame, after every rect has its final size. `UISelectionGroup` resolves its selection and places its pointer there. Reading in `OnEnable` gives a rect of zero (and on a re-show the children are not even active yet); `ForceRebuildLayoutImmediate`, a next-frame retry and a "hide until the rect looks real" guard are each a partial patch for the same missing hook, and each one leaves a case behind. Unregister in `OnDisable`/`OnDestroy`, and re-request from `OnRectTransformDimensionsChange` so a resize or a longer translation re-aims without polling.
- **A layout group nested in another reports its own size; never put a `ContentSizeFitter` on it as well.** The fitter sizes the child from its contents while the parent sizes it from what it reports, and with the parent's `childControl*` off neither ever writes a number — both rows land at `sizeDelta (0,0)` and stack on the same spot, which reads as a broken prefab. Turn the parent's `childControlWidth`/`childControlHeight` **on** and delete the fitter: a `HorizontalLayoutGroup` is already an `ILayoutElement` and answers for itself (`UI_IconCounter` inside `VitalsPanel`).
- **A container that sits inside a layout group carries its own `LayoutElement`.** A plain `RectTransform` reports no preferred size, so the parent gives it none and every child collapses into the same spot — the failure looks like a broken prefab, not like a missing component.
- **A row or column of widgets is an auto-layout group, never hand-placed anchors.** Sizes change, buttons get hidden, translations get longer — a `HorizontalLayoutGroup` with a `LayoutElement` per child reflows for all three, where authored positions leave a hole exactly where the hidden widget sat. the old money-street `ActionBar`/`CallActionBar` kept their buttons in a stretched `Buttons` row for that reason; only genuinely fixed furniture (a corner label, a timer fill) stays anchored.
- **A screen with several sections splits into one component per section, never one class branching over every widget.** `UIPokerView` subclasses (`UIPokerTurnPanel`, `UIPokerRankingPanel`, …) each own their own widgets and bind through `OnBind`/`OnUnbind`; the host only holds the list and fans the refresh out. A new HUD section is a new view plus a list entry, not another branch.
- Widget logic and visual stay split, as everywhere else: `UIButton` holds no `Image`, colour or tween — it resolves `Normal`/`Hovered`/`Pressed`/`Disabled` in that priority order and raises `OnStateChanged(previous, current)`. A `UIButtonVisual` subclass draws the answer: `UIButtonSpriteVisual` swaps the sprite, `UIButtonScaleVisual` tweens the scale, `UIButtonOffsetVisual` slides it and `UIButtonRotationVisual` tilts it about Z (both composing onto a rest pose captured once in `Awake`), `UIButtonCanvasGroupVisual` fades the whole button through one `CanvasGroup` (alpha only — `interactable`/`blocksRaycasts` are the button's rule to decide, not the drawing's), and a further backend is another subclass rather than a branch in an existing one. A subclass never declares `Reset` itself — the base's `Reset` is what finds the `UIButton`, and a `Reset` on the subclass **hides** it, so the button reference is silently never filled (`UIButtonScaleVisual`, `UIButtonOffsetVisual`, `UIButtonLabelVisual` and `UIButtonSpriteVisual` all did). It fills its own references in the `protected virtual OnReset` the base calls from there, which is the same template-method shape as `OnApply`. That lookup is `GetComponentInParent`, so a visual is free to sit on a child of the button — or on another object entirely, with the reference dragged in — which is how a press moves the art without dragging the raycast rect with it. The base owns the subscription and snaps to the state already standing on enable, so a subclass can neither leak a handler nor appear wearing the wrong one.
- **A button is its state, not its art, so a visual can draw on any object — a 3D model included.** `UIModelView` puts a prefab on the UI (the overlay `UICamera` renders the `UI` layer, see the canvas rule), scales it uniformly into one authored box (`_bounds`, in UI units, drawn as a gizmo) so prefabs made at different sizes all come out the size the box says, hangs it as `Root` (brought half the box in front of the canvas plane, and what visuals turn) → `Tilt` (`_pivot`, the lean) → model, centred on `Tilt` in all three axes. Visuals target `Root`, never the model, since the model is replaced per bind: `UIButtonSpinVisual` turns `Root` 360° about the upright Y at `_degreesPerSecond`, while the picker authors `Tilt` at −20° about Z — a cap turning bolt upright looks the same at every angle and the spin reads as nothing, and leaning the thing that turns would only spin it about its own lean. The fit is measured in `Tilt`'s space, so neither the lean nor the spin changes the box while hovered/selected/pressed (one incremental DOTween loop, back to rest by the shortest way), and `UIButtonOutlineVisual` hangs `UI_ModelOutline.mat` on every renderer under it through `PropMaterialOverrideController`. The outline **is** the highlight — the picker's 2D glow was removed. Three things measured the hard way. **Centre the model and move the pivot**: pushing the model off its pivot to sit in front of the canvas made it orbit the pivot instead of turning in place. **Measure only what is drawn**: the caps carry switched-off eyes (a `PropVariant`), and counting them pulled the centre 9 units off the spin axis. **Never measure through world space up there**: `UICamera` sits 5000 units up, and a model at unit scale under a 0.11-scale canvas is a few thousandths of a unit across, inside float32 precision — `Renderer.bounds`, `Renderer.localBounds` and `worldToLocal * localToWorld` all gave a different, wrong fit per button (1600, 1458, 1482 for a cap whose true fit is 1466.667). The box is built from `sharedMesh.bounds` through the local TRS chain between renderer and pivot, and is exact and identical for every button. **A model shown on the HUD is the world prefab itself, never a UI copy of it.** The bet picker draws `PokerItemDatabase.Entry.WorldPrefab` — the very prefab the pot spawns — and `UIPokerBetKindButton` announces the instance on `PokerItemCapRegistry` like any cap on the table, so whatever a hallucination does to the caps (the smiling variant, a repaint) reaches the picker as well, and refits the box on `PropVariantController.OnVariantChanged` since a look can switch pieces on. **The UI paint is authored on the prop, not on a copy of it.** `PropUIMaterials` sits on each `Mushroom_*` prefab and lists, per renderer (the switched-off eyes included), the material each slot wears on the UI — URP/Unlit `*_UI.mat`, so a cap on the HUD reads the same over any room; `UIModelView` calls `SetIsUI(true)` on the instance as it arrives, **before anything claims a renderer**, so `PropMaterialOverrideController` captures the UI paint as the authored array and the outline and every hallucination layer onto it (measured: `[Mushroom_Green_UI, UI_ModelOutline]` under the outline, `[Mushroom_Green_UI]` after it, the asset untouched). Per prop rather than one project-wide map, because every kind of item will want materials of its own. A `Mushroom_*_UI` prefab variant was the first answer and was deleted: a second prefab is a second thing no hallucination, script or art change ever reaches.

 **No light is added for UI models**: a directional light on the `UI` culling mask is still a directional light to URP, and with no `RenderSettings.sun` in `Gameplay_Poker` the brightest one becomes the world's main light. **A visual subclass never declares `OnDisable`**: the base's private one unsubscribes from the button and a subclass declaring its own hides it; undo work goes in `protected virtual OnDisabled`, the same shape as `Reset`/`OnReset`.
- **A button puts itself back to rest after a click, and a redraw is not a transition.** uGUI delivers the pointer release to whoever took the press, so a button whose `OnClick` opened a screen never hears it and is left holding `_pressed` with nothing coming to clear it — the symptom is a button that "sometimes doesn't come back" after a click. `UIButton.ResetState()` clears the held flags and calls `RefreshState(force: true)`, and `Click` calls it unless a key is still down, because holding the key must keep holding the button. The force matters as much as the clear: a visual stranded mid-tween has made no state change, so the plain "nothing changed, nothing to do" guard is the very thing keeping it stuck — the same defect the old ability wheel's `UIWheelItemView.Bind` was fixed for. `UIButtonVisual` snaps rather than animates when `previous == current`, since a redraw has nothing to travel from. Anything else that takes the pointer away mid-press calls `ResetState()` too.
- **A click is held for the length of its own animation before the handler runs.** Most handlers hide, replace or destroy the button they were raised from, and uGUI raises `onClick` on the same frame as the release — so the press the player just made is drawn for zero frames, and the button reads as unresponsive at exactly the moment it responded. `UIButton._clickDelay` (0.1s) waits before `OnClick`, and the wait is **unscaled** through `AwaitableUtility.WaitUnscaledAsync`, because a pause menu at `timeScale` 0 is where half of these buttons live and a scaled wait there never ends. Three things it has to do: a re-entry guard released in `finally`, or one throw leaves the button dead for the session; the conditions re-asked on the far side (`this`, `isActiveAndEnabled`, `IsInteractable`), since a button switched off mid-wait must not go on to fire; and zero meaning *no* wait rather than a frame of one, so a button that must answer instantly can say so.
- **A key bound to a button goes through `UIButton`, and holds it down as long as the key is held.** `UIButtonHotkey` calls `UIButton.Submit()` and sets `IsPressedByKey` from the action's `started`/`canceled` — never the uGUI `Button` underneath, which is an implementation detail nothing should reach past this component for. Firing only the click is the bug worth naming: the handler runs but the button never enters `Pressed`, so a key press does everything except look like one. Bracketing the state from the action rather than timing a flash here is also what makes holding the key hold the button, exactly as a mouse does. The key shown on the face is read from the binding (`GetBindingDisplayString`) rather than typed. A visual that moves the button (`UIButtonOffsetVisual`) measures its offsets from the position captured once in `Awake` — reading the live position on each state change folds the last offset into the rest and walks the button off its authored spot one press at a time.
- **A tint a visual paints at runtime is also authored on the `Image`.** `UIButtonVisual.OnEnable` never runs in edit mode, so a prefab whose colour lives only in `_normalColor` reads white in the editor and in every prefab render — the thing looks broken long before anyone presses Play. Set both (`Button_ActionPad`, `Button_Plate`), and take the tone from the prefab that already has it rather than inventing a second one.
- **A visual that moves the button moves the art, never the `RectTransform` carrying the raycast.** `Button_ActionPad` had `UIButtonOffsetVisual` driving its own root, so pressing it slid the *hit region* down with the picture: the pointer fell outside without the user moving the mouse, uGUI raised `PointerExit`, the button returned to rest, slid back under the cursor, raised `PointerEnter` — and the press animation ended up oscillating instead of returning to idle. The fix is structural: the root keeps the `Image` and the pointer handlers and never moves; a `Content` child holds the art and the label and is what the offset and scale visuals target.
- **A button whose art is not a rectangle narrows its hit area with `UIAlphaHitArea`**, which sets `Image.alphaHitTestMinimumThreshold` (0.1) so the transparent corners stop swallowing clicks — four diamonds packed into a pad otherwise overlap in the gaps nobody drew. This needs **Read/Write enabled** on the sprite's texture, and writing the property *at all* throws without it — so the component checks `texture.isReadable` first and leaves the property alone when it cannot be used, rather than resetting it to zero and tripping the very exception it is avoiding. The raycast `Image` therefore keeps the shaped sprite (tinted fully transparent) while the visible copy lives on `Content`.
- **A `TextureImporter` setting written from a `RunCommand` may not persist** — `importer.isReadable = true; SaveAndReimport()` reported success and the `.meta` on disk still said `isReadable: 0`. Write through `new SerializedObject(importer)`, then `AssetDatabase.WriteImportSettingsIfDirty` + `ImportAsset(ForceUpdate)`, and confirm by reading the `.meta` back rather than trusting the log.
- **A button styled by a visual sets the uGUI `Button`'s Transition to None** — leaving it on Color Tint puts two components on the same `Image`, and the one that wrote last wins.
- **An overlay blends with what the canvas drew *before* it, through the blend state — never by reading the backdrop.** The UI is drawn by the overlay `UICamera` after the base camera has finished, on a renderer with no features: there is no grab pass, `_CameraOpaqueTexture` is not bound and would not contain the UI beneath anyway. `UI/Blend` therefore drives `Blend`/`BlendOp` from material properties and `UIBlendShaderGUI` picks the mode, which covers everything separable — Normal, Multiply, Screen, Additive, Subtract, Darken, Lighten. "Behind" means earlier in draw order, so a stroke parented to a button (last sibling of its `Content`, `raycastTarget` **off** or it swallows the click) blends with that button. Photoshop's dst-reading modes — Overlay, Soft Light, Colour Dodge/Burn — are not reachable this way at all and need a render feature copying the colour buffer; don't reach for one without that.
- **`BlendOp Min`/`Max` apply to alpha as well, so a blend mode built on them writes its alpha separately.** Darken's `min(src.a, dst.a)` punches the backdrop's alpha out wherever the overlay is transparent — invisible on the back buffer, and it destroys the image the moment the canvas renders into a `RenderTexture`, which is exactly how a HUD gets previewed here. `UI/Blend` hard-codes the alpha half (`BlendOp [_BlendOp], Add` / `Blend [_SrcBlend] [_DstBlend], One OneMinusSrcAlpha`) because every mode wants the same coverage maths. Prove it by *reading the alpha back* out of the render (`Texture2D.GetPixel(...).a`) — a viewer draws transparent as white, which reads as a blend mode that inverted rather than as an alpha channel that was erased.
- **A blend mode fades through a neutral colour, not through the blend factors.** `Blend DstColor …` ignores a `CanvasGroup` entirely and `BlendOp Min` ignores the factors outright, so a Multiply or Darken overlay would sit at full strength whatever its alpha said — a fade that visibly does nothing. `UI/Blend` lerps the source toward the value that leaves the backdrop alone (`lerp(_BlendNeutral.rgb, color.rgb, color.a)`, black for the factor modes, white for Darken's Min), which is one line and makes alpha, `Image.color` and `CanvasGroup` behave the same across every mode. The neutral is set with the factors as a set, never apart from them.
- **A custom uGUI shader keeps the stencil block and `UNITY_UI_CLIP_RECT`, or it ignores every mask in the project.** `Mask` works through the stencil properties and `RectMask2D` through `_ClipRect`; a shader written from scratch without them renders correctly on its own and then spills outside the first scroll view it is put in. Copy the state block from Unity's `UI-Default` rather than writing it fresh.
- **A shader that Shader Graph can express is built in Shader Graph, never written as code.** The project's own art already works that way (`Lit_Default`, the gnome's cell shading), and a graph is what an artist can open, retune and extend without a compile — a hand-written `.shader` makes every later change a programmer's errand. That includes URP post-processing: a full-screen effect is a **Fullscreen Shader Graph** driven by a `Full Screen Pass Renderer Feature` on the renderer asset, not a hand-rolled pass. Reach for HLSL only where the graph genuinely cannot go — a custom blend state or stencil block, which is why `UI/Blend` is still code.
- **When the overlay has exactly one image behind it, sample both in one shader rather than blending against the framebuffer.** `UI/Blend Overlay` goes on the *base* image — uGUI binds that Image's own sprite to `_MainTex`, so a button swapping art per state keeps working, where a material holding the button as a texture would go stale — and takes the stroke as `_OverlayTex`. Three things follow that the blend state cannot give: the modes that read the destination (Overlay, Soft Light, Colour Dodge/Burn) become available at all, the maths can be done in Photoshop's space, and the effect is masked by the base's own alpha instead of staining whatever else lies under the rect. That last one is usually the complaint: hardware Darken through a child Image spills past the button's silhouette because the blend unit combines with the *whole* framebuffer, and Photoshop's clipping mask has no equivalent there. Reach for `UI/Blend` only when there is no single backdrop texture — a full-screen tint over the HUD and the table.
- **A full-screen effect is a Fullscreen Shader Graph plus a renderer feature that is off until somebody is seeing it.** `Hallucination_Wave.shadergraph` offsets the blit source's UV by `sin(y * Frequency + Time * Speed) * Amplitude` and nothing else; `PokerHallucinationFullscreenEffect` switches the feature on, clones the material so the strength is never written into the asset on disk, and fades that one float from zero — which is why zero of it has to look like nothing at all. A feature left enabled costs a blit every frame for a room nobody is hallucinating in, and `SetActive(false)` is the whole cost of not doing that. Adding one from script needs both halves: `AddObjectToAsset` on the renderer, then `m_RendererFeatures` **and** `m_RendererFeatureMap` (the feature's local file id), or the renderer drops it on the next import. `Game.Runtime` had to reference `Unity.RenderPipelines.Universal.Runtime` to name the type at all. **A screen-space distortion has to taper to nothing at the frame edge**, or it samples outside what was rendered and draws a black band along the side it pushed from: the wave multiplies its offset by `sin(PI * x)`, which is 1 in the middle and 0 at both edges, so nothing is ever asked for off-screen. A `Clamp` on the final UV stays behind it as a net, not as the answer — clamping alone trades the black band for a smear of the edge pixel. The third layer is a **zoom**: `lerp(uv, 0.5, _EdgeInset)` pulls the whole sampled rectangle in by 2% before the clamp, so the frame the player sees is the middle of what was rendered and the offset has somewhere to push into even at the very edge. One `Lerp` toward the centre rather than a scale about it, because a lerp needs no divide and its parameter reads as the inset itself.
- **A `.shadergraph` is a stream of JSON objects separated by one blank line, so a blank line inside an object splits it.** `MultiJsonInternal.Parse` cuts at the first `\n\n` after each `{`, and the whole import then fails with `JSON parse error: Invalid value` naming nothing — a blank line put inside the graph's edge list for readability was the entire cause. Written by hand, the file is verified by importing it and asking `ShaderUtil.ShaderHasError`, and then by resolving every edge against the slots it names: Shader Graph drops an edge whose slot id does not exist **in silence**, so a graph that compiles is not yet a graph that is connected. Slot ids are per node type (Multiply `A=0 B=1 Out=2`, Sine `In=0 Out=1`, Split `In=0 R=1 G=2 B=3 A=4`, Vector2 `Out=0 X=1 Y=2`, URP Sample Buffer `UV=0 Output=2`).
- **A card is a quad, not a sprite, because a `SpriteRenderer` draws one material and silently keeps the rest.** Assigning it a second material stores the array — `sharedMaterials.Length` reads 2 — and renders slot 0 alone, so every effect hanging a pass on a card would have been a no-op nobody could see. `Card_Poker` is **one** `MeshRenderer` on Unity's built-in Cube, flattened to the card's thickness, and `Card_Face.shadergraph` draws both sides of it: `_BaseMap` on the face whose object-space normal points down −Z (the side the card is read from), `_BackMap` on everything else, chosen by `step(0, normal.z)` into a `lerp` — so the thin edges wear the back. Both pictures are set per renderer through one `MaterialPropertyBlock`. It used to be two quads (and then two cubes) back to back, one renderer per side: that is two transparent objects the per-object distance sort has to order against each other and against every neighbour in a fan, and a coplanar pair z-fights at the seam. One box with two textures has neither problem, and `_BaseMap` stays the front's name so `Card_Wave`'s Replace still samples the picture it bends. The card art went with it: five sliced sheets became 54 single textures, so the mesh's own UVs are the whole card and there is no atlas rectangle to carry — a tiling and offset that has to be right on every card and is wrong in silence when it is not. Two quads back to back also need **thickness**: coplanar at the same depth they z-fight, and with backface culling the pair reads as a card flickering between its own front and back — so each face sits half a card either side of the middle. That thickness has to fit **between its neighbours**, because the groups step each card along the anchor's forward and a step shorter than the card is deep is two cards intersecting (`_depthStep` 0.005 against a card 0.002 thick). `PokerCardFanVisual` was authored at **0.001** and every pair in the hand was therefore interpenetrating — which reads as cards fighting over the same pixels rather than as a stack, and is easy to blame on the fan angle. Check that number against the card's own thickness on every group, and note that the direction of the step is about **which way that group's anchor points**, never about which arrangement it is: the row on the table steps positive and the fan in the hand steps the other way, because the hand anchor is turned about Y. Which side ends up on top is **not** a matter of taste or of the anchor, and I got it wrong twice by treating it as one: a card's face reads down its own `-Z`, so whoever is looking at the faces stands on the anchor's `-Z` side, and nearer the viewer is *negative*. In a hand the later card must overlap the one to its left, so it steps negative — that is what leaves every card showing the top corner its rank is printed in, which is the whole reason a fan is fanned. Stepping positive buries each card behind the one before it and reads as a hand dealt in the wrong order. And the angle has to be wide enough for the overlap to leave that corner showing: measured against a card 0.0616 wide, 20° leaves 48% of a card visible with three in hand and 42% with five, 28° leaves 66% and 51%. **All of it is authored in the prefab, none of it computed at runtime**: every card in the deck is the same size, so the quad scale, the two face offsets and the hit box are values somebody can look at and tune, and the code only says which picture goes on which face. The runtime version of this was three fields and two helper methods deriving numbers that never varied — and it is where the collider came out at the sprite's own scale, and later at twice the card's, because a derivation has somewhere to be wrong and a serialized value does not. Two things the conversion moves that nothing warns about: the quad now carries the card's size in its own `localScale`, so `ResizeCollider` measures against the **pivot** or it counts that size twice (measured: 0.0550 × 0.1092 against a card of 0.0625 × 0.0881); and the sprite is still the thing that knows how big a card is, so it is kept rather than read back off a renderer that no longer holds one. Prove a conversion like this by rendering before and after and comparing the pixels, not the inspector.
- **Hand-authoring a Shader Graph: the slot type is part of the node, and the wrong one leaves the node on its own default.** `MultiplyNode` takes `DynamicValueMaterialSlot` (it accepts matrices) while `AddNode` takes `DynamicVectorMaterialSlot`; feeding Multiply a vector slot dropped the value and left B at the node's own default of **2**, a shader wrong by a factor of four with nothing saying the slot had not taken. And a `DynamicValueMaterialSlot` promoted to a vector reads the matrix's **first row**, not its diagonal — `e00/e01/e02` — so a diagonal-only 0.5 came out as `float3(0.5, 0, 0)`. Neither shows up as an import error: the graph loads, the shader compiles, and the maths is quietly wrong. Read the generated pass (`ShaderUtil.GetShaderData(shader).GetSubshader(0).GetPass(0).SourceCode`) and check every constant and every operand by eye. Generate the file from **C#**, not a shell script: the JSON is full of quotes and `$`, and a bash heredoc mangles both in ways that surface as "JSON parse error" naming nothing.
- **Match Photoshop by blending in gamma, and measure it rather than eyeballing it.** Photoshop blends the 8-bit sRGB values it stores; this project renders Linear, so `LinearToGammaSpace` around the blend and `GammaToLinearSpace` after is what makes the numbers agree. Measured against Photoshop's own formulas: with the conversion every mode lands within 0.002 (half a step of 8-bit), without it Multiply misses by 0.013, Soft Light by 0.079, Overlay by 0.198 and Colour Burn by a full 0.400 — that last one is not a shade off, it is a different picture. Build the comparison by rendering flat patches and reading the pixel back; "looks about right" cannot separate 0.013 from 0.000.
- **Darken and Lighten survive the Linear colour space; Multiply and Screen do not.** The project renders Linear, so hardware blending is done on linear values and a Multiply will not match what the artist saw in Photoshop. `min`/`max` are the exception — the sRGB transfer curve is monotonic, so the same channel wins either way and Darken matches exactly. Worth knowing before retuning art to chase a difference that is the colour space rather than the art.
- **Screens that answer one moment are panels of one `UIPanelStateGroup`, and the view that decides stays on an object the group never switches off.** The wager turn is a menu (`ActionMenu`: BET, ITEMS, FOLD) and the picker BET opens (`BetPicker`: a cloud of kinds, the cost of the one under the pointer, "CHOOSE A SHROOM TO BET"); `UIPokerItemWagerBar` sits on `MushroomWagerBar` itself, shows the menu on the local wager turn, swaps to the picker on BET and hides both when the turn ends, while `UIPanelStateGroup.Show` guarantees the two are never up together. **An overlay panel animates both ways, and the group waits for it**: a panel carrying a `UIPopInVisual` (on itself or its art, found once in `Awake`) pops in on `SetActive(true)` and is switched off only in the callback of `UIPopInVisual.Hide`, which fades it out with `blocksRaycasts`/`interactable` off so a click cannot land on a screen already dismissed; a panel brought back mid-fade is switched off and on to replay the pop-in, and a panel without one still just switches. Measured in Play mode: showing the picker left the menu active, hiding and non-raycastable while the cloud faded in from 0, and the menu was switched off (alpha and raycasts restored) once its fade ended; `HideAll` did the same to the picker. A transition is only as good as its `CanvasGroup` — `Cloud` shipped without one, because it was added through `GetComponent() ?? AddComponent()`, and a missing component in edit mode is Unity's fake null, which `??` does not see, so the picker had never faded in either. Use `if (!component)` before adding, and read the reference back. Putting the deciding component on a panel is the `UILoadingScreen` trap again — it would switch itself off and never hear the next turn. The picker quotes the price from the kind's own effect (`PokerItemEffect.PreviewHallucinationGain`, the call the eating beat charges with), steps back through `UIEscapeStack`, and each kind is a `UIButton` whose root keeps the hit area while `Content` swells and a 3D cap (see the 3D button rule) spins and outlines. The kinds are a `UISelectionGroup` handed its runtime-built entries through `SetItems`, with `_followHoverOnMouse` **off**: the first kind is marked the moment the picker opens, for mouse and pad alike — with it on (a mouse marking only what it hovers) a pad picked up over a picker with nothing focused had nowhere for the first arrow press to start from, so the d-pad did nothing; the mouse still re-marks whatever it hovers, and the pad starts on the first kind, walks the row with d-pad/stick through uGUI navigation (Horizontal) and confirms with Submit — the cost follows `OnSelectionChanged`, the wager `OnSubmitted`, so both devices share one path. Confirming also has a face: `Button_Choose` is a `Button_Plate` with its icon off and **no `UIButtonHotkey`** — its key is `UI/Submit`, which the EventSystem runs on, so the badge is a `UIActionKeyLabel` instead; clicking it confirms the marked kind and it greys while nothing is marked. `UI/Submit` was a single `*/{Submit}` binding, which displays as "Enter" under *every* mask, so it is now `<Gamepad>/buttonSouth` (Gamepad, same binding id) plus `<Keyboard>/enter` (Keyboard&Mouse) — a generic usage binding cannot name a key per device. The cloud pops in through `UIPopInVisual` on its own `OnEnable` (scale from 0.6, OutBack, fade), on the art rather than on a layout-placed rect. ITEMS is built and switched off until it does something. The four keys are `Table/Bet` (A / X), `Items` (S / Y), `Fold` (D / A) and `Help` (Q / Select); the money streets' `Report`, `Call`, `AllIn` and `Ability*` actions were deleted because they held exactly those keys — measured before and after: 0 surviving action ids moved, and all 24 `InputActionReference`s in prefabs and scenes still resolve.
- **A reference board asks the rules for its content; it never keeps a copy of them.** `UIPokerHandHelper` (HELPER, `Table/Help`) opens a paper board listing every hand in `PokerHandDatabase` best first — each row (`UI_PokerHandRow`) calls the hand's own `GetName`/`GetDescription`/`GetExampleCards`, authored on the hand asset (`_description`, `_exampleCards` as rank + named `CardSuit`), so a hand added to the table turns up on the board with nothing else edited, and a hand that is not in the database is not drawn (`PokerHandRoyalFlush`, tier 9, is a straight flush whose high card is the ace). The sample cards overlap in a `HorizontalLayoutGroup` with **negative spacing** and `reverseArrangement`: the first card is the *last* sibling, so it lands leftmost and draws on top, and a hand with fewer cards simply switches the rest off and stays right-aligned. The helper sits on an always-active `HandHelper` and toggles a `Panel` child, closing through `UIEscapeStack`; the board grows out of the corner the button is in because its **pivot** is bottom-left and `UIPopInVisual` only scales; closing plays the pop-in backwards (`UIPopInVisual._popOut`: shrinks toward the same pivot with InBack while it fades) through `UIPopInVisual.Hide(onHidden)`; while the board is open the wager bar steps aside (`UIPokerItemWagerBar._handHelper`, listening to `UIPokerHandHelper.OnOpenChanged`, which is raised when the board is asked to go rather than when its fade ends) and closing it lands back on the menu, since the picker was put away with everything else, and the panel is switched off only in that callback, since a switched-off object draws no fade — a board reopened mid-fade is switched off and on again, which cancels the fade and replays the pop-in, and `IsOpen` is false while it fades so the button reopens rather than closing twice — where a pop grows from is the target's pivot, authored on the prefab, never an offset computed in code. Measured by render: the first layout put a 34pt name in a column 286 wide and ellipsised "Straight" and "Four of a Kind", and a two-line description pushed the name out of the row entirely — the cure was a narrower card fan (50 wide, -30) and a name with its own `LayoutElement` height; and a text column with `childForceExpandWidth` off sizes a wrapping description to its own preferred width, so it broke after two words until the column was forced to fill. All board text is Lacquer (title 48, name 40, description 14).
- **What the rules forbid is hidden; what the player merely cannot afford is dimmed.** A greyed button says "not now", a missing one says "not here" — the old money streets' `UIPokerActionBar` hid raise/check/all-in on a street that never allowed them and only greyed what the stack could not cover, the same way `UIPokerSimultaneousBetBar` hid fold (all since deleted). A stage kind that asks a different question gets its own bar rather than the full one with most of it switched off, and each bar decides its own visibility from the running stage so exactly one is ever up.
- **A second currency gets a second readout, never the same one with a different icon.** The old accusation staked blood between two players while the hand staked money among everyone. Sharing one "Pot" line would have left the icon beside it as the only thing saying which — a distinction that survives right up until somebody glances at it — so the report had its own pot view (`UIPokerReportPotPanel`, since deleted with it), and `UIPokerPotPanel` stood down while that overlay was up. **A notice offers one method per shape it can take, never one method with a `detail` string.** One feed said "REPORT / Beechef" and "CAUGHT / +3", and those two rows are not the same thing wearing different text: a name is drawn like the name on top of the card, a count is drawn small beside its icon. `UIPokerActionNotice` has `Show` (nothing under the verb), `ShowAmount` (a number and its currency) and `ShowTarget` (another player) — the caller picks the shape and cannot then hand it the wrong-looking content. The target row is cloned from the name label it has to match, so the two stay identical without two sets of type settings being kept in step by hand.
- **A HUD readout is about the player looking at it; the room is read off the room.** `UIPokerHallucinationBar` draws the local player's rate alone, because every rate is already public and `PokerHallucinationTagVisual` writes each one over its own head — a HUD listing four bars would be a second place the same numbers live, kept in step by hand, and it would move the reading off the faces where the guessing game happens. The bar takes its colour from a serialized ladder of `(threshold, colour)`, the same shape `PokerHallucinationTiers` uses, so the rungs stay a number somebody can picture. `UIProgressBar.SetFillColor` is the whole addition it needed: a bar whose value means different things at different heights is still just a bar. It is also **down while the table waits** (`Phase == Waiting`): nothing has been eaten and nothing can be, so the HUD meter is shown only once a match starts — while the heads' meters stay up throughout, since those are another view and read the room.
- **A countdown reads whichever clock is actually running, never the one that was.** A turn clock and the stage clock are two different numbers, and a beat where nobody holds a turn — `PokerCardLookStage`, where everyone answers at once — has only the second. Reading `TurnRemaining` there gives a bar frozen at 00:00, which reads as a hung timer rather than as the wrong source. `UIPokerTurnPanel` shows on `HasTurn || HasStageTimer` and picks its source on `Data.HasTurn` (as the deleted `UIPokerReportView` did), and `WantsTick` accepts either clock or the panel stops updating the moment the turn ends.
- **A countdown is for a wait somebody is being held through, not for a beat that simply passes.** `UIPokerRankingPanel` was given a clock and a cancel button; both are gone. Nothing is being asked of the player there — the board is up for exactly as long as the showdown is, and it goes away because the stage's own timer ran out and cleared the list. A countdown over that says "hurry", and a close button offers to skip something nobody is waiting on, which then needs a dismissed flag, an entry on `UIEscapeStack` and a rule about the next ranking being a new one. Draw a clock where a player has to act before it runs out (`UIPokerTurnPanel`); let a beat that passes on its own pass.
- **A transition that exists to hide a change has to actually contain it, and one number says how long.** `PokerHallucinationController` holds `_transitionDuration` and `_applyPoint` (0–1, default 0.5) and lands the rungs at `ApplyDelay`; `UIPokerHallucinationBlink` closes over `ApplyDelay` and opens over the rest, so the eye is fully shut on the frame the effects switch whatever point is authored. **What the switch sets off must not add a delay of its own**: `PokerRoomController` once waited half of its own `_transitionDuration` (0.5 in the scene) after being asked, so the room changed 0.25 s after the blink's shut point — with the eye already open. The room swaps at once now; the caller is what hides it. Two numbers kept in step by hand would let the room change in front of an open eye, which is the one thing the blink was added to prevent. Logic owns the number, the view reads it. A change arriving mid-blink is folded into the beat already running rather than queued, because the apply reads the rate at the moment it runs and a queue would spend a second blink saying nothing new; the guard is released before the trailing re-check, or a change landing in the second half is lost.
- **`DOTween`'s UI module is not in this project, so a `CanvasGroup` is faded by value.** `DOFade` on a group compiles against `ShortcutExtensions` for `Material` and fails with a message about the wrong receiver type, which reads as a missing using rather than a missing module. `DOTween.To(() => group.alpha, a => group.alpha = a, target, duration)` is the idiom — the blackout screen (`UIPokerBlackoutScreen`, since deleted) carried a comment saying so, and reading it first would have saved the compile.
- **A moment's announcement lasts exactly as long as the moment.** The old accusation's verdict card read its lifetime off the report stage's `VerdictDuration`, the same number the pause ran on, so the card could not outlive the beat or fade before it — one number, not two kept in step. `lifetime` is the whole time on screen and the notice budgets its own fades inside it.
- **A control that answers to the chair rather than to the moment is its own view — until the state answers for it, and then it is nothing.** `UIPokerCheckPanel` existed because looking at your own cards is not one of the street's answers, so it could not live on the pad that carries them; showing on `IsSeated` alone and greying on `IsInHand && CardCount > 0` was the right shape for a button somebody had to press. It is **deleted** now: the mushroom round picks cards by pointing at them, so "is this player holding cards" is derived from the cards themselves and drives `IsHaveCardOnHand` straight onto the rig. A control that asks for a state the data already answers is a second answer to a settled question, and the two can disagree. The lesson that survives it is the one about *where* such a control goes if one is ever needed again, and the one about **subscribing to `OnHoleCardsChanged` as well as `OnStateChanged`, because the cards and the status are two replicated values whose order of arrival is not decided** (a deal writes the list and then `Active`); `PokerHandPoseController` listens to both for exactly that reason.
- **A button dropped into a layout group needs a row of its own, not just a `LayoutElement`.** `RankingPanel/Panel` runs `childControlWidth`/`childControlHeight` on with `childForceExpandWidth`, so a bare `Button_Plate` collapses to nothing — and the moment it is given a preferred size it is stretched to the full width of the plank instead, which is what `Title` (preferred 700, rendered 1340) already shows happening. The shape to copy was `CommunityRow`: an empty rect carrying the `LayoutElement` for height, with the button centred inside at its authored size. (`CommunityRow` and `CancelRow` were both that shape and have since been deleted with what they held — the lesson is the layout, not the row.)
- **A key bound to a button that is not a single letter needs the badge to auto-size.** `Button_Plate`'s badge is a 30px circle authored at 14pt for one character, and a key like "Esc" needs three characters where the art has room for one. Auto-sizing with the max left at the authored size means a single letter renders exactly as before and only a longer string shrinks — measured by rendering "F", "Esc" and "Enter" through the real prefab, where "Esc" fits and "Enter" still touches the edge at the 7pt floor. (Measured on the ranking board's cancel badge, which has since been deleted; the sizing rule outlives it.)
- **A button's hotkey must not hold an action anything else runs on.** `UIButtonHotkey.OnDisable` calls `Disable()` on the action it points at, and the actions are one asset shared by the whole process — so a close button wired to `UI/Cancel` or `Player/Pause` would switch that key off for every screen in the game the first time it went away. `UIActionKeyLabel` is the safe way to put such a key on a face: it reads the binding string and never enables or disables anything, which is why the ranking board's CANCEL badge named Escape while the key itself was handled elsewhere.
- **Escape is one key with one handler, and what is on screen decides what it means.** Two actions bound to it both fire, so a board dismissed with Escape would pull the pause menu up behind it. `UIEscapeStack` is the seam: anything dismissible pushes while it is up and removes itself when it goes, `UIPauseMenu` calls `DismissTop()` before opening, and the menu is what the key falls through to rather than what it always means. Newest-first, and the handler is taken off the stack *before* it is invoked so a close that re-pushes cannot strand a stale entry.
- **Deleting an action leaves the override that pointed at it behind.** Removing `UIButtonHotkey` from a prefab instance dropped the component but left an `_action` property modification in `m_Modifications` aimed at an asset that no longer exists — invisible at runtime, and exactly the sort of thing that survives a merge. After removing an action or a component that held one, sweep every prefab and scene for `fileID`s under the actions asset's guid that no longer resolve, and strip the modifications with a null `objectReference`.
- **Panels that answer the same question share one slot, and exactly one is ever up.** "What is the table waiting on, and for how long" has one place on screen — bottom centre, a title over a `UITimerBar`. `TurnPanel` takes that rect and that style — as the accusation's `UI_ReportAimPanel` and `UI_ReportPanel` did before they were deleted — and each panel sharing it decides its own visibility so none can overlap: the turn panel used to hide whenever `OverlayStageId` was set (an overlay handed out turns of its own, so "X'S TURN" was *true* during an accusation and still the wrong thing to be reading); overlays are since deleted and it now shows on `HasTurn || HasStageTimer`. Build them by copying the rect and the layout group off the one that already exists, and instantiate the rows from `UI_TitleLabel`/`UI_TimerBar` with `PrefabUtility.InstantiatePrefab` — `Object.Instantiate` of a sibling silently drops the prefab link, and the copy then stops receiving restyles of the component it was copied from.
- **A screen covering a wait owns a minimum visible duration, and the bar spends that hold arriving.** `UILoadingScreen._minimumShownDuration` keeps the screen up even when the load beats it, because one that flashes past reads as a glitch rather than as loading — and `Hide` hands the bar the *remaining* time (`UIProgressBar.SetProgress(value, duration)`) so it travels to full across the hold instead of sitting at 100% waiting to disappear, which reads as a stall. The guarantee lives on the screen, not on the caller: `UINetworkLoadingBinder` reports real progress and asks to hide, and every other caller gets the same floor for free.
- **A screen that hides itself hides a child, never its own GameObject** — anything driving it sits on the root too, and a component on a disabled GameObject never runs `OnEnable`, so it subscribes to nothing and no event can ever wake the screen again. `UILoadingScreen` switched off its own root in `Awake` and took `UINetworkLoadingBinder` down with it: the loading screen was unreachable from the moment the game started, and nothing logged a word. It now toggles a serialized `_content` child and leaves the root alive, holding `CanvasGroup.alpha`/`blocksRaycasts` at zero. The same trap is why a mode's HUD variant *disables* the bars it does not want rather than deleting them — read that rule as the deliberate case and this one as the accident.
- **The cursor is a counted release, and who holds one depends on whether there is anything to point at.** `PlayerController` holds `CursorController.SetBaseLocked(true)` for as long as the player lives and never releases on its own; a screen that needs pointing calls `RequestUnlock`/`ReleaseUnlock` in its own paired hooks, the way `UIPauseMenu` does, and the counter is what lets two overlap without one closing yanking the cursor out of the other. Walking around there is nothing out in the world to click, so nothing releases and the mouse only turns the view. **At the table there is** — five cards lying in front of the player — so `TableCursorController` holds a release for its whole life and gives it back only while the look button is held. That inverts the default deliberately: pointing is the common case there and turning the view is the deliberate one. What must never appear is a *toggle*, which is a second answer to the same question and desyncs the moment a panel is also holding a release. `ReadLookInput` early-outs on `!CursorController.IsLocked`, so a freed cursor stops the view turning for every holder at once rather than each one remembering to.
- **A card is an object on a table, so it is picked by pointing at it, not by a button beside it.** `PokerCardPickController` raycasts from the camera through the cursor and asks the server (`LookAtHoleCardRPC`); a row of UI buttons would be a second place the same five cards exist, kept in step by hand with every animation the real ones play. The cards therefore carry a collider — sized in `PokerCardVisual` from the sprite, because a card only knows how big it is once it has a face, and the prefab has none until the database hands it one at runtime. Pick the **nearest** hit that is one of *our* cards rather than the first: `RaycastNonAlloc` does not sort, and cards on a table overlap on purpose.
- **A card that lifts under the cursor moves its art, never the collider — and one writer owns how high the art sits.** `PokerCardVisual.SetLift` moved the root, and the `BoxCollider` sat on `Pivot` below it, so hovering a card near its own edge raised the hit box out from under the pointer: unhovered, dropped back under it, hovered again — a card flickering several times a second, which reads as a raycast problem rather than as a hit region that moved. The same structural answer `Button_ActionPad` already needed: the root carries the collider and only moves when the card genuinely travels, while the lift and the flip move `Pivot` beneath it. That in turn means the flip's arc and the hover lift are two tweens writing one `localPosition`, so they are summed into `ApplyArtHeight` instead — two tweens on one property is not a compromise, it is whichever ticked last. Thickening the collider to cover the lift is the tempting one-liner and is wrong: a box standing taller than the card shadows the card behind it at grazing angles, which is exactly the edge case being fixed. **Moving a collider to another object moves its numbers into another scale** — `Pivot` is at `0.07` because that is what shrinks the sprite to a card, and a box sized from `sprite.bounds` read straight across on the root came out fourteen times too big and swallowed the table. `ResizeCollider` converts by the ratio of the two `lossyScale`s rather than by the constant, which also cancels whatever scale the anchor above adds, and it is measured — instantiate the prefab in a preview scene, call `SetCard`, and compare `Collider.bounds` against `Renderer.bounds`, both world AABBs, which agreed to 0.06 × 0.09.
- **An anchor built from the rendered rig is re-checked, never cached once — ownership is not settled when a view wakes.** Picking up is the hands slapping the table and the cards flying up to be held in the hand, so `PokerCardFanVisual.ResolveAnchor` parents the fan's holder to the rendered rig's `HandLeft` bone (`_handBone`, at `_handLocalPosition (0.0657, -0.08, 0.034)` and `_handLocalEuler (0, 180, 0)`). That lookup goes through `PlayerRigController.RenderedRig`, which is `IsOwner ? handOnly : fullBody` — so a holder built the first time anybody asked and kept forever, if that first call lands before the object has spawned, is pinned to the *body* rig's hand for the rest of the session. The host and a client reach that first call at different moments, so it comes out right on one machine and wrong on the other — the tell that sends you hunting for a replication bug in a lookup that never replicated anything. It keeps the holder and re-parents it whenever the bone changes, because the cards hang off it and a fresh one would leave them on a corpse. (A root-level `Player_Poker/HeldCards` anchor was tried in its place and reverted.) **A card takes its new parent when it lands, never when it is told to move.** `PokerCardVisual.PlaceAt` used to reparent at the call, so a card waiting out `_pickUpDelay` was already a child of a hand that was moving and rode it before it ever took off, instead of lying still on the table. `ArcTween` flies in world space — start read on its first frame, destination read off the parent every frame, since the hand it is flying to is animating — and `Land` reparents at the end, so neither the wait nor the flight is carried by the rig.
- **The cards are transparent, so the depth *step* is what decides the draw order — not the depth buffer, and not anything the layout maths does.** `Card_Face` is URP Unlit Transparent with `ZWrite` off at queue 3000, so nothing writes depth and URP orders the faces per object by the distance from the camera to each bounds centre. The z positions still decide it, but only through that distance, and in a fan the stagger runs along the way the cards *face* — close to square with the way they are looked at — so it projects onto the view as a fraction of itself. Too small a `_depthStep` leaves a near tie, and a tie breaks on the order the renderers happened to be registered in, which is not the same on a host as on a client: the same hand drawn in two different orders with every transform correct. The hand fan runs at 0.03 for that reason, against a card 0.002 thick. **Diagnose this class of report by reconstructing the group's frame from the transforms themselves** — the axis of the rotation between two fanned cards *is* the group's depth axis, so projecting the positions onto it gives the real spacing where world coordinates give nothing. That is what separates "laid out wrong" from "drawn in the wrong order", and the two need opposite fixes: measured on a hand that looked broken, the layout was exact (28.00° a step, 0.0206 across, 0.0099 in depth) and only the draw order was at stake.
- **An arrangement asks the card how big it is; it never carries its own copy of the number.** `PokerCardFanVisual` had `_fanRadius: 0.0434` typed on it — half a card's height, transcribed by hand, and already 0.0006 out. `PokerCardVisual.Size` reads it off the face quad (Unity's Quad mesh is 1×1, so its lossy scale *is* its size, divided back out of the card's own scale so the answer is in the units a parent places it in — measured `(0.0625, 0.0881)`, matching the authored hit box exactly). `PokerCardGroupVisual.CardSize` asks whichever card the group is holding, and the fan keeps only `_pivotDrop`, a *fraction* of that height. Resize the deck in its prefab and every arrangement follows; a distance authored on the layout side is the one that quietly keeps the old shape, and nothing warns because a fan of the wrong radius is still a fan. `PokerCardRowVisual` was the one still carrying a centre-to-centre `_spacing` (0.1), and the new card art (231×304 against 88×124) widened the face box to 0.1004 — five cards overlapping on one plane at a depth step of zero. It serializes `_gap` now and steps by `CardSize.x + _gap`. **The face box is authored against the art's aspect**: `Card_Poker/Face` is the sprite's size in units (`0.9422 × 1.24` at 100 PPU), so new art of another shape means re-authoring that scale and the root `BoxCollider` with it, or every face is drawn squashed with nothing warning.
- **Where cards are laid out is a group, and a card being picked up moves between two of them.** `PokerHandVisual` owned both the slots and both arrangements, so "row on the table" and "fan in the hand" were two branches inside one `Layout` with a shared slot counter, a shared anchor lookup and a bitmask deciding which of the two each card took. `PokerCardGroupVisual` is the seam: it holds the cards it has been given, resolves its own anchor and answers `SlotPosition`/`SlotRotation`, and `PokerCardRowVisual`/`PokerCardFanVisual` are the two arrangements — a third is a third subclass, not a third branch. The hand visual keeps what only it can know (which slot holds which card, which faces are up, what a raycast may pick) and hands a card over when `IsHoleCardInHand` changes. Two things the group must own or the old defects come back: it takes a card **at its place in the deal** rather than at the end, so picking the third card up first does not put it at the front of the fan; and only the card that just arrived travels, because `PlaceAt` arcs whatever it animates and the rest are only being put right where they lie. **Whether a group closes up around a card that left is the arrangement's choice**, through `SlotOf(index)`/`SlotCount`: the fan does (its place among the cards held, out of how many are held), while `PokerCardRowVisual` keeps every card on the place it was dealt into, out of the whole hand (`OrderAt`, `_data.CardCount`). A row that closed up slid the cards left behind across the wood while the picked ones were still lying there waiting their turn to fly — measured 0.053 apart against a card 0.100 wide — and a card put back down now returns to exactly its own spot. **Cards arriving together leave one after another, and a card in the air is never snapped.** A pick of three commits in one frame, and each `Add` re-laid the group with the others non-animated — so every card but the last was snapped into the fan mid-flight, and the ones that did fly went the same path at the same moment, two transparent faces close enough to draw through each other the whole way. `PokerHandVisual.HandlePresentationChanged` sees every card that changed hands in one change, and gives each `_handOverStagger` (0.15) for every moved card **in a higher slot** — rightmost first — passing it through `PokerCardGroupVisual.Add(..., delay)`; the group only arranges. **That only works because a pick is one replicated write.** `PokerCardPickController.Commit` used to send `LookAtHoleCardRPC` once per card, so the host heard one change per card in the order the player had marked them while a client heard the set as one — and two view-side patches in a row (counting arrivals per frame, then ranking them per frame) were guesses at reassembling a decision the wire had already broken up. Right on the client, wrong on the host was the tell both times. `LookAtHoleCardsRPC(int slots)` takes the whole set, refuses it whole with the gate named, writes `LookedAtHoleCards` once and plays the gesture once. **When the view needs to know what happened together, send it together; never let the view infer a batch from timing.** And the set **leaves its group before any of it arrives**: handed over one card at a time, the first `Remove` re-laid the row that still held the rest of the set and snapped them sideways across the table before their turn (measured with the real `PokerCardRowVisual`/`PokerCardFanVisual`: slots 2 and 1 had moved at the instant of the handover while their flights still landed staggered, which is why landing times alone could not show it). A pass that removes them one by one has the same defect, because every `Remove` re-lays the group and the group still holds the movers not yet taken — measured again after the first attempt at this fix, slots 4 and 2 still snapped while only the last one out held still. `PokerHandVisual.LeaveGroup` therefore calls `PokerCardGroupVisual.Remove(card, layout: false)` for every mover, each group is laid out **once** when the set is out, and only then does `HandOver` give each its turn — and `PokerCardVisual.PlaceAt` keeps a card that is waiting its turn or still travelling on its way to wherever it now belongs instead of landing it. The wait is the same `_departAt` a deal uses (the later of the two wins), so the flip waits with it, and a chosen card keeps its lift while it waits and brings it down over the flight rather than dropping onto the wood before it takes off (measured: three cards committed in one frame left at 0.012 / 0.087 / 0.166 s and landed at 0.372 / 0.456 / 0.535, the third held its 0.015 lift through the wait, and a place at rest still snapped). **The stagger is spent lying on the table, and the flight goes straight to the hand.** The wait sits *before* the travel in the card's sequence, so a card holds where it lay until its turn and then flies one unbroken path. Leading the depth axis ahead of the rest of the path to keep each card in its own layer was tried and taken out: the card lurched along Z first and then crawled the remaining distance, which reads as it hanging in the air partway to the hand — the stagger appearing mid-flight instead of on the table. Measured on the straight path: three cards committed together held on the table with their lift until 0.011 / 0.153 / 0.304 s, rightmost first, landed at 0.378 / 0.522 / 0.673, never moved away from their slot once they had left, and no pair's depth order inverted in flight — the 0.15 stagger alone keeps them apart. **The flight waits for the hand, and the wait is measured off the animator, never guessed.** The pose (`IsHaveCardOnHand`) and the move come off the same replicated change, so both clocks start together and `PokerHandVisual._pickUpDelay`/`_putDownDelay` only have to cover the transition plus the clip's contact frame (the stagger is added on top). Measured with `Animator_Gnome` driven by hand from `Sit` (`Animator.Play("Sit")`, then `Update(1/48)` steps — the rig never reaches `Sit` from a bare prefab because the seat plays it, and a sample taken there reads a still idle): picking up, the right hand comes down onto the cards at 0.50–0.56 s and lifts them to 0.875 s while the left — the fan's `HandLeft` — rises to hold, so a card leaves the table at **0.5**; putting down, the right hand reaches the table at 0.75 s and a card flies for `_moveDuration` 0.4, so it leaves the hand at **0.35** to land on the contact. Re-measure both when `Anim_CamBaiLen` changes — `Animation_Sit_FlipDown` is built from it.
- **A dealt card comes off the deck in the middle of the table, in seat order, and waits there for its turn.** `PokerDeckVisual` sits on `PokerTableVisual/Deck` (a `Card_Poker` instance thickened into a stack, plus a `Top` transform where each card starts) and registers itself, because the hands asking are on spawned players. `PokerHandVisual.AddCard` hands every *animated* add to `Deal`, which puts the card on `Top` and gives it a wait. **What the deal looks like is a `PokerDealController` on the `Deck` object**, and another deal is another subclass dropped into `PokerDeckVisual._controller` — nothing else changes. The deck answers *whose turn* (`PokerDealTurn`: the card's slot, the seat's place in seat order — how many `InMatch` players sit at a lower `SeatIndex`, counted among `InMatch` players only so an empty chair takes no turn, and how many are being dealt); the controller answers *how long it waits* (`DelayFor`) and *how it flies* (`Travel`, a tween from where the card lies to its slot in the parent's space). `PokerDealArcController` is the dealer's deal — one card each before anyone gets a second, tossed in an arc through the same `PokerCardVisual.ArcTween` the table-to-hand move uses. The turn is worked out from replicated seats rather than from the order the adds arrive — a host hears one player's whole hand before the next player's, and a client in any order at all. The wait and the controller live on the card (`PokerCardVisual._departAt`/`_deal`) until it lands, and **every `PlaceAt` and `Flip` honours them, animated or not**: a group re-lays every card each time one arrives, and a non-animated place mid-deal would snap the card out of the deck ahead of its turn or cut its throw short (measured: three cards re-placed that way left at 0.014 / 0.102 / 0.204 s and landed at 0.381 / 0.483 / 0.588, the visible one began its flip the frame it left, and a place after landing snapped as normal). The card wraps the controller's tween in a sequence of its own for the wait and the final landing rather than setting a callback on it, so a controller is free to hang its own. A late join passes `animate` false and is placed straight in its slot. The whole deal has to fit inside the deal stage's duration, or the next beat opens with cards in the air — `PokerStage_Deal5` runs 2 s for four players by five cards at the arc controller's 0.1.
- **An event is named after what changed, not after the object it changed on.** `PokerPlayerData.OnStateChanged` was raised by nine different values, so every view drawing a hand woke on every chip that moved and then asked whether anything it cared about had changed — the answer was almost always no, and a subscription that says nothing about what the handler does is one nobody can read. `OnHoleCardPresentationChanged` carries the three values `IsHoleCardVisible` and `IsHoleCardInHand` are built from — `LookedAtHoleCards`, `HandRevealed` and the visibility rules — and `PokerHandVisual`, `PokerHandPoseController` and `UIPokerRankingRow` take that instead. `HandRevealed` raises **both**, because turning the hand over is how the cards read *and* a fact about the hand being over. `OnStateChanged` keeps what is genuinely "anything about this player": the bars and panels reading status, seat and turn. The split follows the ones already there for the same reason — `OnHealthChanged`, `OnHallucinationChanged` — and the test for a new one is whether a consumer would have to re-derive what it was called for.
- **A player is picked by pointing at them too, and what is outlined is exactly what the click commits.** `UIPokerColorfulPickBar` was a row of name buttons — a second place the players at the table existed, kept in step by hand, asking the winner to read a list at the one moment the whole room is watching faces. It survives as **one** button carrying the winner's own name, because yourself is the one choice the world cannot offer: your body is under your own eye and hidden from you, so the raycast skips it outright and naming yourself is a click on your name instead. `PokerColorfulPickController` raycasts through the cursor onto `AimTarget` (the trigger every body carries for exactly this) and outlines whoever is under it; the click sends the seat of the player *already outlined* rather than casting again, so the thing the winner saw lit is the thing they chose. Who may be hovered is asked of the stage's own `PokerColorfulPickStage.CanBeFed`, the method the server refuses with, so nothing can be lit that a click would then be refused on. Two details carry over from card picking and the old accusation aim: the stage is resolved only when the stage id, the overlay or the turn has moved, because `FixedString.ToString()` on every frame is an allocation on the per-frame path; and **your own body is the answer only when nothing else is** — it sits just under the eye, so a ray to somebody across the table can pass through it, while pointing down at yourself with nobody behind is how the winner names themselves, which the rules allow. The hover is **local**: `PlayerVisual.SetLocalOutlined` is ORed with the replicated `Outlined` rather than writing it, because a cursor passing over somebody is not a move the table needs to see — the choice is, and the server announces that — and a replicated hover would be a message per twitch of the mouse. ORed, not overwritten, so a replicated outline and a cursor passing over the same body cannot switch each other off. One consequence worth knowing: hovering yourself lights nothing on your own screen, because the outline is hung on the body rig and the owner renders the hand-only one.
- **A card is chosen before it is taken.** `PokerCardLookStage` asks for several cards at once, so `PokerCardPickController` marks a card on the click, unmarks it on a second click, and commits the whole set only when as many are marked as the player is still owed (`ViewableHoleCards` minus what they have already turned). Lifting each card as it was clicked made every click a decision nobody could take back, and it sent the server a half-made mind one slot at a time. The lift is one number decided in one place (`ApplyLift`), with chosen outranking hovered, or a marked card drops back to the table the moment the pointer wanders off it.
- **Only a player who was dealt in has anything of their own to look at.** A shot down at the row of cards, or at the spot a staked cap lands, is about *this* player's place in the round — and somebody who took a chair mid match has neither, so the shot would park their view on an empty patch of table while the round happened above it. `PokerStageCameraController` refuses `OwnCards`/`OwnItems` on `!InMatch` and lets the beat fall to free flight; `InMatch` rather than `IsInHand`, because the first wager runs before the deal and nobody is in a hand yet. Everything about the *table* — the wide shot, watching whoever is on the clock — a viewer gets exactly as everyone else does, which is the whole point of being one.
- **A card has two places it can be, and where it is is derived rather than replicated.** `PokerPlayerData.IsHoleCardInHand(slot)` is `!HandRevealed && HasLookedAt(slot)` — lifted off the table until the hand is shown, at which point everything goes back down for the room to read. Both facts are already on the wire, so a third value would only be one more thing to fall out of step. `LookedAtHoleCards` is therefore **Everyone-read**: lifting a card is an act the whole table watches, and the face stays hidden by `IsHoleCardVisible`, which asks `IsOwner`. That is the same public-act/private-grant split the old cheat abilities made, and getting it backwards means a pickup animation only its owner can see.
- **The pad's pointer is `VirtualMouseInput`, not a cursor written by hand.** It is the Input System's own answer and it creates a real virtual `Mouse` device, so everything already reading `Pointer.current` — the card picker, uGUI's raycasting — is pointed at by a stick without knowing a stick exists. `UIVirtualCursor` only decides *when* it runs, because on a keyboard the hardware cursor is the pointer and a second arrow drawn beside it is two pointers answering one hand. It subscribes to `InputSchemeController.OnSchemeChanged` from `Start`, never `OnEnable`, for the reason every other static subscription does. A **software** cursor is also what lets `CursorController` go on hiding the hardware one for a pad: the arrow the player sees is a UI Image.
- **Seated and standing are different control schemes, and that is a second look action rather than a rebind.** `Table/Look` puts the pad's left stick on the view because nobody walks at a table and the right stick is needed for the cursor; `PlayerController` reads it in place of `Player/Look` while `_bodyAnchored`. Rebinding the standing action instead would have taken walking away from the pad everywhere, to fix a conflict that only exists in a chair.
- **Locking the cursor takes the pad's pointer away with it, so the look must stop asking about the lock.** `InputSystemUIInputModule` drops every `MouseOrPen` pointer while `Cursor.lockState` is `Locked`, and the pad's cursor is a real `Mouse` — so freeing the stick to look by locking the cursor is the one move that cannot work: it kills hover and clicks in the act of enabling the look. The lock belongs to the mouse alone, and the reason is physical. A mouse is one pointer and has to choose between pointing at the cards and turning the view, which is why `TableCursorController` holds an unlock and gives it back only while the look button is down. A pad has two sticks and needs no choice, so `PlayerController.ReadLookInput` skips the `IsLocked` gate entirely while the scheme is gamepad, and the cursor stays free for the right stick throughout. `CursorController.Apply` already had the other half of it: on a pad the hardware arrow is hidden while the lock stays off, which is exactly what a software cursor wants.
- **A device the game invented is not a device the player is holding.** `VirtualMouseInput` creates a real `Mouse`, so every generic binding matches it: `InputSchemeController` read its events and flipped the scheme back to keyboard the instant the right stick moved the pad's own cursor, which then switched that cursor off — a flip-flop with no error and no log. `SchemeFor` now refuses anything whose `InputDevice.native` is false. The same fact bites the look: `Table/Look` binds `<Mouse>/delta` and `Player/Look` binds `<Pointer>/delta`, both of which the virtual mouse satisfies, so the cursor stick turned the view as well as the pointer. `PlayerController.ReadLookInput` checks `action.activeControl.device is Gamepad` against the scheme and drops anything the player is not actually holding. Reach for `native` and for the active control's device whenever a synthetic device shares a class with a real one; the binding paths cannot tell them apart and never will.
- **A `PassThrough` action performs on release as well as on press, so the callback asks what the button is doing.** `UI/Click` is PassThrough because that is what `InputSystemUIInputModule` wants of it, and every value change raises `performed` — so one click ran `PokerCardPickController`'s pick twice: the press took the card under the cursor and the release took whatever that uncovered. Nothing about it reads as an input problem; it looks like a raycast taking more than it was pointed at. Neither frame-scoped helper covers it — `WasPerformedThisFrame` sees only one half at a time because the press and the release are frames apart, and `WasPressedThisFrame` is unreliable on a PassThrough action, which has no press phase to speak of and reports the release actuation too. The value is the only thing that answers honestly: `if (!context.ReadValueAsButton()) return;`. A frame guard beside it is the *other* defect, not the same one — the action carries a binding per device it answers to and the pad's cursor is a real `Mouse`, so two controls can actuate in one frame. Read the action's **type** before deciding what an event means.
- **An action that drives the virtual cursor must be one the virtual cursor cannot drive back.** `VirtualMouseInput.leftButtonAction` was `Table/PickCard`, which binds `<Mouse>/leftButton` — and the virtual mouse *is* a Mouse, so the action was bound to the very button it was pressing. The result latches: the pad's button starts the action, the pressed virtual button keeps it actuated, releasing the pad raises no cancel, and the button never comes back up. Hover works and nothing can ever be clicked, which reads as a broken UI rather than as a loop. `UIVirtualCursor` builds its own `InputAction` on the pad's south button and hands that over; being in no asset and bound by nothing else is what makes it safe, so this is the rare case where an action must *not* be a pickable `InputActionReference`.
- **Pointing at a card and pointing at a button are one act, so they are one action.** `Table/PickCard` was a second name for `UI/Click` with the same mouse binding, which is how it came to be wired into the virtual cursor and closed the loop above. It is deleted; `PokerCardPickController` takes `UI/Click`. Deleting an action from `.inputactions` is safe only with both checks the rules already demand: capture every `action.id` first and prove none moved (33 kept, 0 moved, 1 removed), and afterwards resolve every `InputActionReference` fileID serialized in any prefab or scene against the reimported asset (30 of 30, the one miss being the `InputActionAsset` itself). Repoint the consumers *before* deleting, while the thing they point at still exists to be found.
- **A pad is given a cursor only where there is something in the world to point at.** `CursorController.IsPointerWanted` is a counted request, the same shape as the unlock beside it, and `TableCursorController` holds one for as long as there is a table. A menu asks for none, so `UIVirtualCursor` draws nothing there and uGUI's own focus runs the screen — an arrow drawn beside a moving selection is two pointers answering one hand, which is the same argument that already keeps it off a keyboard. The lock and this are deliberately different questions: one is whether the hardware arrow is free, the other is whether a pointer is wanted at all.
- **A component on the player runs on every copy of every player, so anything about *this* machine is owner-gated — and ownership is not settled in `OnEnable`.** `TableCursorController` held a cursor unlock and answered the local hold button from each remote player's copy as well as the local one; the counters hid it, since two requests and two releases still balance, and it would have surfaced as the table growing more wrong with every extra chair. It is a `NetworkBehaviour` now and binds from `OnNetworkSpawn` behind `IsOwner`, because a spawned prefab runs `Awake` and `OnEnable` at instantiate and only learns who owns it when it spawns. `OnEnable` still binds behind `IsSpawned && IsOwner` for a switch-off and on afterwards, which `OnNetworkSpawn` cannot cover: it is raised once. Bind and unbind are idempotent behind one flag, or the despawn and the disable that follows it release twice.
- **A hallucination is a ladder of thresholds, and climbing a rung draws from its pool rather than naming an effect.** `PokerHallucinationTiers` is a list of `(threshold, pool, drawCount)` and nothing else — there is no "tier" type, because a tier was only ever a number with some effects behind it, and a fourth rung is a row in an asset. How many of the pool a rung draws is the rung's own number, and a draw is a partial shuffle so the same effect can never come up twice in one climb — stacking a thing on itself is at best nothing and at worst two callers fighting over one bone. Effects **stack**: a player at the third rung is wearing everything all three rungs drew, so the world gets worse rather than swapping appearance. `PokerHallucinationController` is owner-only, since what somebody is seeing is the one thing at this table that is deliberately not shared. Crossing back down takes a rung off and climbing it again **re-draws** — which is what makes an item that lowers the rate visible, and what stops a player seeing the same room twice.
- **An effect asset in no rung is an effect that never runs, and nothing says so.** `Hallucination_MushroomPeople` was authored, targeted and correct, and sat in no pool of either tiers asset for as long as it had existed — the model swap the round is named after had simply never been drawn. Authoring an effect and putting it in a ladder are two steps, and only the first one leaves anything to look at. Two more things to read while there: `Player_Poker` points at `PokerHallucinationTiers_Sample`, not at `PokerHallucinationTiers`, so the ladder somebody is editing is not necessarily the ladder that runs; and a rung whose `_drawCount` is at least its pool size draws the whole pool every time, which is a fixed set wearing the shape of a draw. Check both by printing every rung's pool through `SerializedObject` rather than by opening the inspector.
- **A `ScriptableObject` is config; what runs is an object in the scene.** `PokerHallucinationVolumeEffect` kept its live `Volume` on the asset, and effects are allowed to sit in two pools on purpose — so the lower rung's `End` tore down what the higher rung believed it owned, and one of the two silently did nothing. Cloning the asset per rung fixes the stacking and nothing else: a clone is still invisible, so what a player was actually seeing could only be read out of the controller's dictionary in a debugger. `PokerHallucinationEffect` therefore holds serialized fields and one `Attach`, and `PokerHallucinationEffectBehaviour` holds every field the effect mutates on a child object named for its rung — stacking works by construction because two rungs are two objects, the `Volume` sits on the thing that owns it, and the whole ladder is legible in the hierarchy while it is on screen. A `MonoBehaviour` also brings the lifetime with it: `Stop` is the deliberate way down, `OnDestroy` is the backstop, and an effect that eases out says how long its host must outlive the moment it was taken off (`LingerSeconds`) rather than leaving a tween to be killed with the object carrying it. **Declare the Unity message once, in the base**, and give subclasses a hook (`OnDisposed`) — a subclass redeclaring `OnDestroy` hides the base one and the backstop is silently gone.
- **What an effect acts on is a different asset from what it does.** `PokerHallucinationTarget` resolves a list of transforms and nothing else, and the effects take one — because "make this bigger", "paint this" and "hang something off this" all have to answer the same question first, and that answer is the half a designer actually retunes: one scale effect aimed at a head or at a whole body is two different hallucinations. Splitting it is what keeps the effect count at four for nine authored categories.
- **A prop is asked to wear one of its own looks; it is never handed a model to become.** Swapping the staked cap for a smiling mushroom as a hide-plus-spawn named one prefab, which is the wrong answer for the next kind somebody authors — five mushrooms in the database and the hallucination would show the same face on all of them. `PropVariantController` sits on the prop and owns what each variant means, so `PokerHallucinationVariantEffect` only says *which* (`PropVariant.Smiling`) and each object answers in its own way; a prop that never authored that variant is left as it was rather than being replaced by something generic. Requests are counted like the material overrides — last caller wins, dropping one puts back what the caller before it asked for (the bone scale composes instead, see below) — and `OnVariantChanged` is the seam for a prop whose variant is more than which children are switched on. A look also **replaces a mesh rather than switching a bone off**: hiding `Root_M` to put a mushroom person in its place takes the whole skeleton down and the camera hanging off it with them, and it is the wrong shape for the art that is coming — the artist builds the piece against the same skeleton, so only `sharedMesh` changes hands. `MeshSwap` captures what the renderer was authored with the first time it is taken over, which is the only moment that value is still there to read. The mechanism carries no poker and no hallucination in it: anything that ever asks a prop to look different gets it for nothing, which is why a variant is named after what the prop becomes and never after the rung that asked.
- **An asset cannot name a scene object, so the scene registers what an asset is allowed to ask for.** `PokerHallucinationSceneryTarget` wants "the room", which lives in `Gameplay_Poker` and can never be serialized onto a `ScriptableObject`. `PokerScenery` is a scene component holding named groups and registering itself in its own lifecycle, the shape `PokerSeat` and `GameCamera` already take. The group is a `PokerSceneryGroup` enum rather than a string id, because both halves have to name the same group and only one of them is in the scene: two dropdowns cannot disagree where two typed ids silently never match.
- **A room is authored in the scene and switched on, never spawned from a prefab.** `Hallucination_WaterRoom` grew a prefab under the room, which is one copy of one room: it carries its own lighting and its own placement, it cannot be laid out against the table it is replacing, and every further room would be another prefab to keep in step with the first. `PokerRoomController` lives in the scene beside the rooms, holds a list of `(PokerRoomVariant, objects)`, and `PokerHallucinationRoomEffect` names which — the same split as `PropVariantController`, where the asset says *which* look and the thing wearing it owns what that means. It registers itself the way `PokerScenery` and `PokerSeat` do, counts its requests so two effects wanting a room unwind in any order, and swaps **at once** — it used to carry a transition of its own, which stacked on top of the blink's and landed the room after the eye had opened (see the blink rule) — and `OnRoomChanged` is the seam for a room that is more than objects being switched on. It has no target, unlike every other effect here — there is one room, and a resolver would be answering a question with one answer. Changing an asset's type in place keeps its guid, so every ladder pointing at it survives: rewrite `m_Script`, reimport, and check the pool entries resolve rather than trusting it.
- **A distortion redraws its subject; only a tint can sit on top.** `Card_Wave` is the fullscreen wave aimed at one card — `sin(uv.y * Frequency + Time * Speed) * Amplitude`, tapered by `sin(PI * x)` so it never asks for a pixel off the card, with a `Clamp` behind it as a net — and it samples `_BaseMap` at the offset UV. That is only possible because the picture arrives through the renderer's `MaterialPropertyBlock`, which applies to every slot: a material that *replaces* the card's is still handed the card it belongs to. So the wave is Replace and the rainbow is Add, and the rule is the shape of the effect rather than a preference — a pass drawn on top cannot bend what is underneath it, and an added rippled copy would show both the bent card and the straight one. **And the tint has to be drawn after the thing it tints, which the material array does not decide.** `PropMaterialOverrideController` always writes `[Wave, Rainbow]`, but Unity sorts a renderer's passes by render queue, and at the same queue two transparent passes on one renderer tie — a lone card in a preview happened to draw the rainbow last, and at the table the wave came out last and painted the whole card over it. `Card_Rainbow.mat` sits at **3001** and the wave stays at 3000 with every other card face, so the replaced card still sorts among its neighbours and the tint is simply a pass after all of them. The cost is that a tint on a card at the back of a fan draws over the card in front of it where they overlap — the rainbow samples no texture, so it had no card-shaped alpha to lose anyway.
- **An added pass on the card must not name a texture property the card itself writes.** `PokerCardVisual` puts the face in a `MaterialPropertyBlock` as `_BaseMap`, and **a block applies to every material slot on the renderer** — so a `PropPaintMode.Add` material built on URP/Unlit, whose own texture is also `_BaseMap`, has its picture replaced by the card's face and draws the card over itself. Nothing warns: the material is valid, the pass runs, the render is simply unchanged, which reads as a material that never got added. `Card_Pattern.mat` is `Sprites/Default` keyed on `_MainTex` for exactly that reason, and any further overlay picks a property nothing else writes. The same block is why `Card_Wave` can be a Replace and still get the right card (it is *handed* the picture), so the two cases pull in opposite directions and the property name is what separates them. Prove an overlay by rendering the card with and without the pass and comparing the pixels — the failure is invisible in the inspector, where both materials look correctly configured.
- **A URP material's render queue is recomputed from `_QueueOffset`, so writing `renderQueue` alone is silently reverted.** Setting `mat.renderQueue = 3001` on a URP/Lit or URP/Unlit material reads back 3000 after the import: URP's validation derives the queue from the surface type plus that float. Set `_QueueOffset` and the queue together. This is not academic — `Card_Rainbow.mat` had been sitting at **3000** ever since, tied with every card face and breaking on registration order, which is the exact defect the rule above about the rainbow sorting after the wave was written to fix. It was authored as 3001, and the write was silently reverted by this. A queue a rule claims is a queue worth measuring: read `Material.renderQueue` back rather than trusting either the rule or the inspector.
- **An added material is a pass on the end, and it is not the same operation as a repaint.** `PropPaintMode` splits them: Replace fills every slot, which is what a body reading as made of something else wants; Add appends one material to what the renderer already wears, which is the only way a card keeps its rank readable underneath. Add also refuses the `PlayerMaterialOverrideController` route on purpose: that controller resolves one *winning* material and hands it to `PlayerVisual`, which has no way to say "and this one as well", so an added pass going through it would silently become a replacement.
- **What a renderer was authored with is captured once, by the renderer, and never by each caller.** `PokerHallucinationMaterialBehaviour` used to read `sharedMaterials`, keep its own copy and put that copy back — which is correct for one painter and wrong the moment there are two, and the ladder allows two on purpose since an effect may sit in more than one rung's pool. The second painter captures *the first one's paint* as though it were the original, and then the release order decides the outcome: measured, releasing the Replace first leaves the card wearing `[Wave]` forever while releasing the Add first happens to come out clean. Nothing warns, and it only appears on the rung combination somebody happens to draw. `PropMaterialOverrideController.Claim(renderer)` adds itself to the renderer's own object the first time anybody paints it — the only moment the authored array is still there to read — and from then on it is the single writer: the last Replace wins (two repaints on one thing is a conflict somebody authored, not a blend anybody asked for) and every Add is hung on afterwards, so both release orders end at the authored array. Claimed rather than serialized, because what gets painted is a card dealt this round; and a caller holds the *controller*, checking it still exists before clearing, since the card it lived on is destroyed between hands.
- **A hook handed a plain `Action` can be unsubscribed; one that wraps it in a lambda cannot.** `PokerScenery.OnInstanceChanged` carries no argument for exactly that reason — the first draft was `Action<PokerScenery>` and the target's `Subscribe` wrapped the caller's handler in a closure, which `Unsubscribe` then had no way to find. Every consumer reads `Instance` anyway. When an event exists to be relayed through a generic seam, make its signature the seam's signature.
- **A screen covering a wait blocks input by disabling named action maps, never devices.** `UILoadingScreen._blockedActionMaps` switches `InputSystem.actions`' `Player` map off while it is up and re-enables only what it switched off; the maps are picked from a `[ValueDropdown]` over the project-wide asset, not typed. Devices belong to the whole application — disabling them takes the menus and the cursor with them — and `CanvasGroup.blocksRaycasts` only stops pointer hits, never the gameplay actions running underneath.
- **Cover a wait from the edge that starts it, not from the one that answers.** `OnHostStarted`/`OnLobbyEnter` arrive *after* Steam replies, so a screen hung off them appears once the slow part is already over; `GameNetworkManager` raises `OnConnectStarted` at the click and `OnGameLeaving` before the teardown unloads the scene, and `UINetworkLoadingBinder` covers both. Leaving needs it as badly as joining — a scene unloaded with nothing over it blinks the table out from under the player.
- **Every start must end in an outcome the UI hears.** A screen put up by one event and taken down by another is stuck forever on any path that returns without raising the second — which is why `StartHost` reports its invalid-`SteamClient` guard through `OnConnectFailed` instead of only logging it. Raise the start event *past* the guards, so the only starts announced are the ones that go on to answer, and raise a teardown event only when there is a session to tear down (`if (IsInGame)`) so a no-op `Shutdown` never flashes a screen over nothing.
- **A wait that happens while the game is stopped counts unscaled time.** `Awaitable.WaitForSecondsAsync` and an untagged tween both run on scaled time, so at `timeScale = 0` — which is exactly when a loading screen or a pause menu is up — they never finish. Loop to a `Time.unscaledTime` deadline with `Awaitable.NextFrameAsync(token)`, and mark tweens `SetUpdate(true)` (`UILoadingScreen`, `UIProgressBar`, `UISelectionGroup`).
- **A list rebuilds by re-binding the views it already has, never by destroying and re-instantiating.** `Destroy` runs at the end of the frame, so the old set is still drawn underneath the new one for one frame. The ability wheel (`UIWheelController<T>`, since deleted) kept one view per anchor for that reason, recycling the slot leaving one end and snapping it to the other, so a list of any length cost a fixed handful of objects.
- **A key shown on a face is read from its binding, never typed.** `UIActionKeyLabel` fills a label from `InputAction.GetBindingDisplayString()`, the same way `UIButtonHotkey` does for a button, so a rebind follows on its own and the face can never name a key the action does not answer to. Size the holder for a word rather than a letter — the string is "Enter", not "E" — and let the label auto-size instead of trusting one hand-picked point size.
- **A selection in a list is drawn as a change of tone, not of size.** A row that swells when chosen makes the whole column shift under the eye every time the wheel turns, and the neighbours move for a reason that has nothing to do with them. The ability wheel's `UIPokerAbilityWheelItem` (since deleted) tinted its plate and its diamond and left every anchor at scale 1; the unselected rows stay readable rather than blank, because the list is what the player is choosing between.
- **A view fed by two network objects subscribes to both, because their order of arrival is not decided.** `Data.Showdown` lives on the table and `HandRevealed` on each player, so a ranking row built from the showdown list and never looked at again drew the winner's hand face down on every screen but their own — the list landed first, which is not the unlucky case but the ordinary one. `UIPokerRankingRow` binds the player it is drawing and redraws on `OnStateChanged`/`OnHoleCardsChanged` (the panel did the same for the community board's visibility, since deleted with the community cards). The tell is a view that is right on the host and wrong on the client: the host writes both values in one call and never has to wait for either.
- **A view asks the replicated stage id which stage is running, never `GameMode.CurrentStage`.** `PokerStageMachine.CurrentStage` is written only by `Next`/`GoTo`, and both are server-only — so on a client `CurrentStage` (and the `ActiveStage` it replaced) is null for the whole session and any view gated on it simply never appears. `UIPokerItemWagerBar` was, which read as a wager bar that worked for the host and for nobody else. `GameMode.FindStage(Data.StageId.Value.ToString())` is the client-safe route. The tell is the same one the ranking rows taught: **right on the host, wrong on the client** means a view reading state the host happens to hold locally.
- **A board that reports a hand that is over keeps its own copy of it.** `UIPokerRankingRow` read `PokerPlayerData.HoleCards` live, so the next deal's `ServerResetForHand` emptied a ranking still on screen — a player who left the board up past the countdown watched the cards vanish out of it. It snapshots instead, and the snapshot is refreshed only by a hand that still *has* cards, so the reveal landing after the showdown list still updates it while a later clear cannot erase it. Anything drawing a past moment off live state has the same defect waiting: the moment is over, the state is not.
- **A view that counts across players watches every one of them, not the list they are in.** `UIPokerStartPanel` reads `DealablePlayerCount` (once `FundedPlayerCount`), which asks each seat's own object whether it can be dealt in, while subscribing only to the phase and to `OnSeatedPlayersChanged` — so a match ending and putting everyone's stats back left the start button dead, because the list had not changed, only what the seats were carrying. It re-subscribes to every seated player's `OnStateChanged` whenever the list changes and drops them all in `OnUnbind`. The symptom names the defect: *standing up and sitting down fixes it* means the only event the view hears is the one about the roster.
- **A view draws its state when it is built, not only when that state changes.** A guard written as "nothing changed, nothing to do" is about transitions, and a slot that has just been created or handed new data has made no transition — it is wearing whatever the prefab was saved with. The old ability wheel's `UIWheelItemView.Bind` re-applied the selection look on every bind, so a rebuild and a recycle both left a row correct; the change-guard stayed on `SetSelected`, where it belongs, for the animated case. The symptom is the giveaway: "it only looks right after I select it".
- UI reads the mode's `*Data` and the stage's own methods; it never computes a rule of its own and never talks to Netcode directly beyond the mode's public API.

## Inspector (Odin)

**A serialized value that must match something else is picked, never typed.** A hand-typed stage id, scene name or action id is a silent runtime failure; a dropdown cannot be misspelled.

- `[ValueDropdown]` wherever the valid values are knowable; where they live in an asset catalogue, bake them into a `*Database` asset and pick from that, so the list still works in a build and diffs in version control (`PlayerActionAnimationDatabase`, `GameModeDatabase`).
- `[Required]` on any reference whose absence breaks the object at runtime; `[InfoBox]` with a condition to explain a broken setup in place rather than failing later (`GameModeDatabase` flags a scene missing from Build Settings).
- **Where a value may legitimately name something not authored yet, the dropdown offers but does not confine** — `[ValueDropdown(..., AppendNextDrawer = true)]` keeps the text field alongside the list. `PlayerActionAnimationDatabase.StateName` is the case: a gesture is allowed to name an animator state the rigs have not been given yet, because `PlayerActionAnimator` skips a missing one on purpose.
- `[MinValue]`/`[PropertyRange]` on numbers with a real valid range.
- **When the order of a serialized list carries meaning, say so on the field** — `PokerStageSequence._stages` runs in list order, and a reorder is a behaviour change no compiler catches.
- Reference the objects themselves, never string ids kept in sync by hand.
- **A shader's `[Enum(...)]` takes at most seven name/value pairs and fails silently past that** — it logs "Failed to create material drawer" once at import and then draws a bare float, so a nineteen-mode list becomes a number nobody can pick and everybody can mistype. Write a `MaterialPropertyDrawer` instead (`UIBlendModeDrawer`, used as `[UIBlendMode]`), which is the same dropdown with the enum living in C# where it can be read. The enum's order is the shader's branch order and nothing checks that at compile time — say so in both files.
- Odin is inspector UX only: never let an attribute change runtime behaviour.

## Gameplay architecture

Distilled while building the ability system — new features follow these.

- **An ability is a thing you do; calling it a cheat is a different game.** The ability module (deal, hold, spend) and the report module (accusations) — `PokerAbilityModule` and `PokerReportModule`, both since deleted — were once one 770-line class, and the tell was that 7 of its 10 consumers touched only the report half. Splitting a module is a **rename plus a new small file**, never a surgical delete: `AssetDatabase.MoveAsset` carries the guid, so the prefab's existing component keeps every serialized report setting and becomes the new class, and the clean half is written fresh beside it.
- **Splitting a class splits what it was quietly doing for the other half.** Handing out each hand's report charges rode inside the ability *deal* — `data.ReportsLeft.Value = _reportsPerRound` (a field since deleted with the report) sat in the middle of the dealing loop — so moving the deal out left nobody granting them: the first hand could be reported on and no later one could, with nothing logged. After lifting a method out, read what the *rest* of the old method was writing, not only what the new one needs. A shared helper is the other half of the same problem: `IsStageAllowed` was private to the old class and now belongs on `PokerModule`, because two modules asking "am I awake right now" must not answer it twice.
- **Replacing what a replicated list holds writes each slot; it never clears and refills.** A clear-and-add is what a *deal* looks like on the wire, and `PokerHandVisual` plays it as one — every card torn down and the replacements flipped in one at a time, on every screen at the table. Writing the slots raises `Value` changes instead, which a hand nobody may see reads as no change at all, because a face-down back before and a face-down back after are the same card. The old redraw cheat's `ServerReplaceHoleCards` (since deleted) was written that way for exactly this reason.
- **An act with a delayed effect waits on the lifetime of something that can die, not on the asset that describes it.** The old redraw card (since deleted) landed after the hands came back down — cards swapped in mid-air swap where nobody is looking, and being looked at is the whole point. A `ScriptableObject` has no lifetime of its own, so the wait carried `PokerGameMode.destroyCancellationToken` and the cards are drawn at the *end* of it, never the start, so a cancel has nothing to undo. `async Awaitable` left unawaited rather than `async void`, so a throw still has somewhere to go.
- **Props stay cosmetic.** Generic player pieces (`PlayerActionAnimator`, `PlayerAnimatorStateController`, `PlayerBoneScaleController`) live in `Game.Runtime.Player`, replicate only the act itself, and carry no game meaning. What the act means belongs to a mode-side controller that owns any grant `NetworkVariable` and installs the rule that reads it — the deleted peek cheats split exactly that way (`PlayerGlassesController`/`PlayerHeadStretchController` for the act, `PokerBoardPeekController`/`PokerPeekController` for the grant). Never put per-feature state on shared data (`PokerPlayerData`, `PokerGameData`).
- **Feature components sit on named child GameObjects** of the player prefab, not piled on the root. `Player_Poker` groups its own half by what each piece is about — `Cards` (hand visual, card picking, the holding pose), `Items` (what has been eaten), `Hallucination`, `Body`, `Table` — while `PokerPlayerData` and `PokerPlayer` stay on the root, because they are the model and its owner and everything else addresses the player through them. **`[RequireComponent]` is what stops this, and it is usually the wrong assertion**: `[RequireComponent(typeof(PokerPlayerData))]` says the data must be on the *same object*, so moving the component would have Unity add a second `PokerPlayerData` — a second copy of a NetworkBehaviour on one NetworkObject. Take the attribute off and let the fallback search the object instead (`GetComponentInParent`), which is the rule below about searching from the `NetworkObject` down rather than assuming one shared GameObject. Move with `AddComponent` + `EditorUtility.CopySerialized`, re-point references by sweeping every `SerializedObject` for the old component, and destroy the originals **last** — a reference resolved after they are gone reads back null with nothing left to map from. Verify by diffing the complete type-and-path list against a baseline taken before the move, and by counting: a type appearing twice is a copy left behind.
- **A bone and a feature component are on two branches that never meet, so `GetComponentInParent` from a bone finds neither.** Bones live under `Models/Gnome_rig/…` and the feature components sit on named children of the player root — `BoneScale`, `MaterialOverride` — so a walk up from `Head` passes the root and returns null every single time. `PokerHallucinationScaleBehaviour` and `PokerHallucinationMaterialBehaviour` both did that, and both **skipped in silence**: the effects resolved their targets, spawned their objects, ran their tweens and moved nothing, for as long as they had existed. Nothing was wrong in any asset — the scale effect had its target, its scope and its multiplier, and the ladder was drawing it. `PlayerRigController.FindOnBody<T>` is the seam, because that component is the one that sits on the root itself: up to the body, then down. And the lookup **warns when it fails**, which is the difference between a minute and a session — a body with no scale controller is a setup that cannot possibly work, and the silent-skip exemption is only for things deliberately allowed to be missing. Prove a hierarchy claim by asking the prefab (`GetComponentInParent` against `FindOnBody`, printed side by side), never by reading the transform paths and reasoning about them. **The same walk finds the body above anything that merely hangs under a player** — cards lie under the player holding them — so `FindOnBody` answers "whose body is this in", not "is this a body". `Hallucination_CardWave` (a Replace) took the body route from each card and repainted the whole gnome with the card shader while the cards stayed plain. Which route a thing takes is the *target's* statement: `PokerHallucinationTarget.ResolvesBodies` is true on `PokerHallucinationPlayerTarget` alone, and `PokerHallucinationMaterialBehaviour` only asks for a body when it is.
- **Where something goes is a transform in the prefab, not a bone plus an offset in code.** "Above the head" as a height and a euler is two numbers to guess at, guess at again for the second thing that needs the same spot, and re-guess whenever the rig changes — and on these Maya-style bones the euler is wrong before it is even tried. The peek cheats carried `RevealedCards` and `PeekLookPoint` as real children of `Player_Poker`, dragged into place in the scene view (both went with them). The same goes for furniture on the table: `PokerTurnArrowVisual` used to write the arrow's position every aim from a `_height` above the table's root, and the number on the prefab (0.35) had drifted below the wood (`BanTron` tops out at 0.4231), so the pointer turned inside the table. It only **turns** the arrow now; `PokerTableVisual/PokerTurnArrow/Arrow` sits at local y 0.425 in the prefab — the measured top plus 2 mm so the flat sprite cannot z-fight the wood — and moving it is a drag in the scene view, not a field to guess at.
- **Visibility is a display rule.** Cards replicate to everyone; who may look is decided client-side through a provider hook (`PokerPlayerData.AddHandVisibilityProvider`; the community board's twin went with the community cards) plus a `Notify*RulesChanged` event the views listen to. The rule is the only thing hiding the data — a deliberate trade, made once.
- **Visibility is asked per card, not per hand.** `PokerPlayerData.IsHoleCardVisible(slot)` is what views call; `IsHandVisible` survives only as the whole-hand shorthand. A round that deals five and lets the holder turn three is the case that breaks the old shape, and it breaks it *for the owner* — everyone else is still told exactly what they always were. `PokerHandVisual` therefore keeps a bitmask of which slots it has drawn face up rather than one `_shownFaceUp` flag, because a single flag can only ever say "the whole hand" and a change-guard built on it would miss a second card being turned. A table that sets no limit reduces to the whole-hand behaviour exactly.
- **What a player may look at is a rule the server enforces.** `LookedAtHoleCards` is a bitmask replicated **Everyone-read**, because lifting a card is an act the whole table watches (see the rule on where a card is), while its face stays hidden by `IsHoleCardVisible` — and `LookAtHoleCardsRPC` is asked of the server rather than decided locally, because a client that lied about the limit would be reading a card the round says it may not. `ViewableHoleCards` is stamped by `PokerDealStage` **before** the cards go out: the view redraws on the list changing, so a limit written afterwards arrives one event too late and the whole hand flashes face up first.
- **Two rigs, one act.** The owner renders `Gnome_HandOnly`, everyone else `Gnome_rig`. Bone positions come from `PlayerBoneRig`/`PlayerRigController` (`RenderedRig`, `RenderedHead`), never per-feature name lookups. **That includes authored points that are not bones** — a prop's hold point is `PlayerBone.HoldRight`, bound by reference on both rigs — and **the rig itself never searches by name at runtime**: `BoneName` is an editor hint that `OnValidate` turns into a reference. `PokerItemCarryController` used `Wrist_R.Find("CapHold")`, and when `CapHold` moved under the new `POT_attach_R` bone that `Find` (direct children only) quietly returned null, fell through to `Cup_R` (also moved) and glued every carried cap to the wrist origin — a cap floating off the hand, with nothing logged. A reference follows the object wherever the rig re-parents it. New values go on the **end** of `PlayerBone`, since a binding serializes the number. Replicated acts play on whichever rig each client renders, so every seat sees the same thing.
- **The four gnome models under `Player.prefab`'s `Models` node are prefab instances of their FBX, so an art update arrives on its own — but only what lives *in* the model does.** They were plain GameObject copies until they were converted, and two rounds of art updates had reached nothing: the prefab still carried `Neck7_M`/`Head_M` and no beard chains while `Gnome_Model_Rig.fbx` had renamed them and added two mesh pieces per hand. Nothing warns about that — an out-of-date skeleton is a real skeleton and animates fine. Keep them as instances, and a bone added or renamed by the artist propagates by itself. What does **not** propagate is anything the prefab holds *about* the model: `PlayerVisual._slots` is a list of renderers (and each `PlayerModel` a list of meshes per slot) and `PlayerFingerVisual._fingers` a list of bones, so a mesh piece the artist adds turns up in the hierarchy and in nobody's list — and a renderer `PlayerVisual` does not hold is one the owner/remote rig split cannot switch off, which renders as a piece of body floating in front of the first-person camera. Look at those lists whenever the model changes; `PlayerFingerBinder` re-binds the finger half by name. **An object hung on a bone of an FBX instance is attached by that bone's fileID, and the importer derives it from the bone's *path*** — so renaming one bone orphans everything hung on it *and on every bone below it*, even ones whose own names did not change. The update that took `Head1_M` back to `Head_M` threw the camera `Offset`s, both pairs of glasses, both hats and the mushroom head off the skeleton onto the instance root, and `HeadEnd_M`'s `Non_Gnome` with them. `PrefabUtility.GetAddedGameObjects` lists them, and one that sits directly under the model root is orphaned. **Re-seat an orphan by its old pose, never by its old numbers**: the local position and rotation were authored against the old bone's axes, and a renamed bone is usually a re-exported one whose axes turned too. Extract the previous FBX from git into a scratch folder (with a fresh guid in its `.meta`), take `delta = Inverse(newBone rotation) × oldBone rotation` in model space, and multiply the orphan's local position and rotation by it — measured: the glasses kept on their old local numbers under the new head sat 0.280 from the eyes, i.e. behind the head.
- **A Generic avatar binds a clip to bones by transform path, so a clip must be exported against the rig it will play on — rename a bone and every curve under it binds to nothing.** `Gnome_Model_RigAvatar` is Generic (`isHuman=False`), and `Gnome_Model_Rig.fbx` is the reference for what the bones are called: the model updates itself into `Player.prefab` because the four `Models` nodes are instances of it, and the animation FBXs under `Assets/Art/Character/Gnome/Anim/` have to follow by being re-exported. When they lagged behind — the model had renamed `Neck7_M`→`Neck_M` and `Head_M`→`Head1_M` — **20 of 83 curve paths per clip bound to nothing**: the whole neck chain, the head, the beard and the ears. Nothing is logged, and it does not present as a missing animation. It presents as a camera bug, because `PlayerController.ApplyLookTo` multiplies onto whatever is already on the bone and relies on the Animator putting the rotation back: measured in Play mode, writing 30° into `Head1_M` twice read back as **60°** while `Shoulder_L` was pinned to its animated value both times. So the view spun while seated (the look drives the head there) and stayed wherever it had got to after standing up, with nothing able to restore it. Two things follow. **A model updating itself is only half the update** — the clips are a second asset built on the same skeleton and they do not follow on their own. And a rig that is "not animated" is diagnosed by *writing into a bone and seeing whether it comes back*, never by looking at it. `GnomeAnimationBoneRemapper` bridged that gap by renaming paths in `OnPostprocessAnimation`, and it is **deleted**: the next update re-exported the clips against a rig whose head was `Head_M` again, and a shim renaming `Head_M`→`Head1_M` then broke clips that had arrived correct — 31 of 97 paths in every clip bound to nothing, the head and everything under it. **A compatibility shim has a condition under which it becomes the bug; delete it in the change that meets that condition**, and re-import the assets it touched, since its edits live in the import result. **An animation update can replace the clip set rather than re-export it, and a controller holds a clip by the fileID of a sub-asset inside its FBX** — so a take that is deleted or renamed leaves every state that used it holding a dangling motion. Nothing is logged, a scan of the prefab finds nothing (the reference lives in the `.controller`), and the rig simply stops moving: `GetCurrentAnimatorClipInfo` comes back empty and every bone measures 0° over seconds. `f8155d4` deleted the whole `Gnome_*` set and shipped `Anim_*`, and nine states of `Animator_Gnome` went dangling at once. Scan controllers alongside prefabs (`state.motion == null` while `m_Motion` still carries an id), and read the clip each state used out of the *previous* controller in git before choosing a replacement — the mapping is a design call, not a rename. Where it landed: `_Idle`/`Sit` → `Anim_IdleLoop`, `Sit_FlipUp` → `Anim_CamBaiLen`, `Sit_Peek` → `Anim_CamBaiIdle`, `Sit_FlipDown` → `Assets/Prefabs/Animation_Sit_FlipDown.anim`, which is `Anim_CamBaiLen` with its keys reversed and **must be rebuilt when that clip changes** (a negative state speed would start a non-looping clip at its first frame and clamp there); `_ShuffleCards`/`_Report`/`_Point`/`_PointExit` were left empty for art (the report's three have since been removed with it), which `PlayerActionAnimator` already skips; `_Bet`, `_Fold → _FoldLoop` and `_ConsumeItem` are new gesture states for ids the game was already calling (`ConsumeItem` needed its database row). New FBX takes arrive with loop off, so an idle or a hold has `loopTime` set on its importer. Measured in Play mode afterwards: idle plays `Anim_IdleLoop` on both rigs, `IsHaveCardOnHand` on runs `Anim_CamBaiLen` into `Anim_CamBaiIdle` and off runs `Animation_Sit_FlipDown` back into the idle, `_Bet` returns to `Empty` and `_Fold` settles in `_FoldLoop`. **A bone that does not move under a clip that is playing is not yet a binding bug — measure the clip before the rig.** The head read 0.00° over seconds of idle, which is what the `Head1_M` defect looked like; sampling the curves showed every clip in the new set holds the head and chest perfectly still (0.00°) while the wrists travel (`Anim_CamBaiLen` 56.7°, `Anim_Bet` 35.6°), so the stillness was the art and the paths were bound. The check that settles it is the one the `Head1_M` rule already names: 30° written into `Head_M` on both rigs and into `NeckPart2_M` read back 0.00° one animated frame later, against 30.00° left on the unanimated `Offset` beside it.
- **Swapping a rig means re-pointing before deleting, and mapping the roots by hand.** Two things bite in that order: destroy the old objects first and every serialized reference reads back as null with nothing left to map from, so the repoint pass finds zero; and rename the replacement before building the name map and the rig root never matches itself, quietly dropping the Animator and bone rig hanging off it. Take a null baseline of the prefab first — half of what looks broken afterwards was already null by design, the way `PlayerBoneRig` resolves its bones by name at runtime. A prefab instance also refuses to give its children away, so unpack it before lifting hand-placed props like the camera or the glasses off the old head bone.
- **A skinned mesh deforms from its bone array in *index* order, so a rig swap that keeps every bone and loses the order melts the model silently.** `bones[i]` is what `sharedMesh.bindposes[i]` belongs to; rebuilding that array from a fresh hierarchy walk after re-parenting gives a correct-looking set in a scrambled order, and every bone then reads perfect in the inspector while the mesh renders as a spike of flesh. `Player_Poker` and `Player` both arrived that way from the rig update: `Gnome_rig/.../body` had all 103 slots wrong and `Gnome_Outfit_1/OutFit` 102, while the eight finger meshes, the head and the whole hand-only rig were untouched — so **the defect only existed on the rig nobody sees of themselves**, which is why it survived being looked at. Diagnose by comparing the renderer's bone *names in order* against the renderer in the model asset that owns the same `sharedMesh` (match on the mesh asset, never on its name — two rigs here both ship a mesh called `body`); repair with `Assets → Player → Repair Skin Bones`, which reorders the transforms the renderer already holds rather than searching the hierarchy, so a prefab carrying two skeletons under identical bone names cannot be re-bound to the wrong one. `BoneRemapper` maps by name index-for-index and therefore preserves a scramble rather than causing or curing it.
- **Rebuilding a prefab as a variant keeps its guid but kills its fileIDs, and a variant cannot reparent or delete what it inherits.** `Player_Poker` is a variant of `Player` now: everything generic — the `Offset` camera pivots (a reparent, so it had to land in the base), `PlayerBoneRig`, `PlayerRigController`, `PlayerColorVisual`, `AimTarget`, the glasses and the five feature children — was absorbed into the base first, and the variant adds only `Poker*` components, its own anchors, and overrides. Both hats live in the base and **active flags are the seam**: `Cone_Hat` was on for the since-deleted Sandbox, `Non_Gnome` is on for Poker, because a variant may not delete an inherited child. Transplant components with `EditorUtility.CopySerialized` plus a path-based reference remap between the identical hierarchies, save the variant to the same path so the `.meta` guid survives, then re-point everything that held the old root fileIDs (network prefab list, scene `PlayerManager`) and verify by instantiating the result and reading the load-bearing refs back.
- **Rebuild a prefab from the object itself, and verify by diffing the whole component list — never from a summary of it.** `Player_Poker` lost its `Fingers` node in the variant rebuild because the transplant worked off an exploration write-up that listed eight root children where the prefab had nine, and the verification pass only re-read the components it had set out to copy: everything it checked was green, and the one thing nobody thought to check was gone. Enumerate the source with `GetComponentsInChildren<Component>(true)` at the moment of the rebuild, and afterwards compare the *complete* type-and-path list of before against after — anything present only in the old one is a drop. Blindness is the normal case, not the unlucky one: a visual that never runs renders as a hand that simply never loses a finger, a bone rig nobody reads renders as nothing at all, and neither logs a word.
- **A rig rendered in a preview scene proves nothing.** `PrefabUtility.InstantiatePrefab` into `NewPreviewScene` runs no `Awake`, so `PlayerVisual` has neither picked a rig nor rebound the outfits: both skeletons and both outfits draw at once, over each other, and the result looks exactly like the broken skinning it is being used to rule out — the first render of `Player_Poker` and the one taken from `git HEAD` were pixel-identical *and* both wrong. Judge a rig in Play mode against the source FBX instantiated beside it under the same `Animator_Gnome`; the side-by-side is what named the defect in one frame.
- **What tells players apart replicates as an index, never as the thing itself.** `PlayerData.ColorIndex` is a number; `PlayerColorDatabase` turns it into a colour on each client. The palette is then an asset that restyles without a word of it reaching the network, and two clients cannot be looking at different colours for the same player. The pool of indices belongs to whoever owns spawn-to-teardown — `PlayerManager` claims the **lowest free** one and gives it back on disconnect, so a player who leaves mid-game leaves a hole the next arrival walks into rather than pushing everyone further down a palette that eventually wraps. Count the claims; do not derive the index from a position in the player list, which renumbers everybody the moment one of them leaves.
- **A tint painted at runtime needs a shader that has the property, and a `MaterialPropertyBlock` will not tell you it does not.** The gnome's outfit is a Shader Graph whose only colour input is a *texture* (`_Base_Color:Texture`) — a block writing `_BaseColor` there is a silent no-op that looks exactly like a broken subscription. Check `Material.HasProperty` before choosing the mechanism; `Cone_Hat` is URP/Simple Lit and does have `_BaseColor`, which is why the hat is what gets coloured. Author that material on the renderer in the prefab too, even though `PlayerVisual.ApplySkin` assigns it at runtime, so edit mode is not showing a different hat from the one that runs. A block is the right tool once the property exists: it is per-renderer, instances no material, and survives `ApplySkin` replacing the list underneath it.
- **A rig is however many meshes the artist cut it into.** The gnome arrives as a body and a head (`body_Gnome`, `Dau_gnome`) and its hand-only rig as one mesh, so hiding "the body" for the owner means hiding all of them — `PlayerVisual` holds arrays, and one renderer left behind is a head floating where the owner should see nothing. **A piece that wears its own texture is its own slot**: the head is `PlayerSlot.Head`, because painting one body material over every body renderer puts the body's texture on the face. The Cartoon look of `PlayerModel_Gnome` is whatever the FBX already wears (`Cell_body_Cartton`, `Cell_Dau_Cartton`, `Cell_Outfit_Cartton`, `Cone_Hat` for the tintable hat) — a default that differs from the model's own materials is a second look nobody chose, applied the moment the player spawns. **Retiring a material means three sweeps, not one**: the skin, the FBX importers' external remaps (entries for material names the model no longer has stay in the `.meta` and keep the old asset alive), and prefab-instance overrides on renderers the rig update removed — `PrefabUtility.RemoveUnusedOverrides` clears the last kind, which `Player.prefab` was carrying nine of (the old material on the finger meshes and the outfit, among 357 dead modifications in all) for renderers that no longer exist.
- **What a player is drawn as is three answers, and a `PlayerModel` asset resolves all of them into a mesh per slot and a material per submesh of it.** The **model** is the body (`PlayerModel_Gnome`, `PlayerModel_Mushroom`, `PlayerModel_GnomeMushroomHead`) — local for now, the prefab's `_defaultModel` unless something asks otherwise; the **outfit** is a `PlayerOutfitId`, replicated and server-written, looked up *by id* so a model without that outfit dresses in its own first one (an empty list wears nothing, which is Mushroom); the **version** (`PlayerLookVersion`: Cartoon, Realistic) is local, and a version or slot a model never authored is painted as in Cartoon (the realistic gnome has no hat material, so the tintable `Cone_Hat` material stays). A caller names the model or the version, **never meshes or materials** — so a character added later answers every request already written. **Switching a model never touches a bone.** Every model is exported against the one skeleton (`Gnome_BodyNam` measured: same 116 bones in the same order, bindposes identical), so `PlayerVisual` only writes `sharedMesh` onto renderers it already has, one per `PlayerSlot` (`Body`, `Head`, `Outfit`, `Hat`, `HandBody`, `HandOutfit`) — and the camera `Offset`, the glasses, `AimTarget`, the look bones, the fingers and every other thing hung on the rig never learn a switch happened. That is the whole reason for the shape: the alternative (a rig per model) meant re-seating eight systems' bone references per character, which is exactly what the last rig update showed going wrong. A slot the model leaves empty is hidden; a mesh skinned to a different bone count is warned about rather than left to melt. Requests go through `PlayerAppearanceController` (the `Appearance` child): one stack per axis, last caller wins, and it hands `PlayerVisual.SetModelOverride`/`SetVersion` the winner; a hallucination's material override still outranks both. **A look paints every submesh, and the material list is rebuilt to the mesh's size.** `PlayerModel.Paint` holds one material per submesh in submesh order; a submesh a version leaves empty takes Cartoon's for that same index, and `PlayerVisual.WriteMaterials` writes an array exactly `subMeshCount` long — assigning a single material only ever reached slot 0, so a two-material mesh kept the previous model's second material and a hallucination painted half a body. A look whose count disagrees with the mesh is flagged in the `PlayerModel` inspector rather than discovered on screen. **Where the player's colour is worn is the model's data** (`PlayerModel.Tints`: slot + submesh + shader property), read by `PlayerColorVisual` on every `OnAppearanceChanged` — Gnome wears it on `Hat` via `_BaseColor`, Mushroom nowhere yet, and art moving it is an asset edit. Effects: `PokerHallucinationModelEffect` (`Hallucination_MushroomPeople`, `Hallucination_MushroomHeads`) and `PokerHallucinationLookVersionEffect` (`Hallucination_RealisticPlayers`) share `PokerHallucinationAppearanceBehaviour`, which reaches the controller through `FindOnBody` and only for a target whose `ResolvesBodies` is true.
- **A part of the body that can be lost is collapsed at its bone, never switched off as a renderer.** `PlayerVisual` owns `renderer.enabled` — that is the owner/remote rig split — and rewrites `sharedMaterials` on every skin change, so a finger taken off through either is handed back the next time one of them runs. The fingers used to be meshes of their own and were switched off as GameObjects; the model is one skinned mesh per rig now, with the fingers as bones, so `PlayerFingerVisual` adds a zero **multiply** to the finger's joint through `PlayerBoneScaleController` — the joint and every bone below it pull their vertices into a point, and the segment before it is left as the stump (`PlayerFingerBinder` binds the second joint, `…Finger2_L/R`). Through that controller and not by writing the scale here, because the Animator rewrites every bone's scale each frame and it is the one writer that runs afterwards; a hallucination resizing the same hand composes with a lost finger rather than fighting it. One finger is still a *list*: the joint on the full body rig and again on the hand-only rig, or a finger is lost only to the players who are not its owner.
- **Blood is drawn on the body, and the two counts are authored to line up.** The gnome has eight fingers to lose and `Player_Poker`'s `_startingHealth`/`_maxHealth` are eight, so one point of blood is one finger and a table reads how badly somebody has been hurt without looking at the HUD. `PokerBloodFingerVisual` counts what is gone off the *damage* (`MaxHealth - Health`) rather than off the blood left, so a player at full health is whole whatever the two numbers are tuned to — mapping the other way leaves a player who has lost nothing missing fingers the moment the ceiling is raised. Nothing new replicates: health already does, and the visual reads the current value in `OnNetworkSpawn` for a late join. The mechanism carries no poker in it — `PlayerFingerVisual` is handed a count — so anything else that ever costs a finger gets the display for free.
- **One-shot gestures go through `PlayerActionAnimator`**: ids in `PlayerActionIds`, mapping in `PlayerActionAnimationDatabase`, states on the animator's `Gestures` layer. Missing states are skipped silently, so triggers can land before the art does. Poses and locomotion stay on the base layer with `PlayerSeatController`. **One act done two ways is still one id.** An entry's `AlternateWhen`/`AlternateStateName` plays another state while a bool on that rig's own animator is on — `Bet` becomes `_BetHoldingCards` while `IsHaveCardOnHand` is on — so the stage names the act and the pose it is made from picks the clip; a caller choosing between two ids would be a second copy of a condition the rig already holds. Anything timed against the clip (`PokerItemPotVisual`'s grab and release frames) picks its numbers off the same fact (`PokerPlayerData.IsHoldingCards`, which the flag is written from), and each clip gets its own pair.
- **An effect that belongs to a moment of an animation is a cue on the clip, kept apart from the model, and the preview spawns it through the very call the game does.** Unity has no Anim Notify: an Animation Event lives in the FBX's import settings, is invisible when scrubbing, calls a method by name, and on this project would fire on both rigs at once. `AnimationVfxCueDatabase` holds `(clip, frame, prefab, bone, offset, lifetime)` rows in an asset of its own, so re-exporting the animation cannot lose an effect and retuning one reimports nothing. The trigger is a real animation event, **installed from the database** rather than authored: `AnimationVfxCueDatabase.InstallEvents` puts one event per cue on its clip when an `AnimationVfxPlayer` wakes, so timing, loops and crossfades are the animator's own and nothing polls. It changes only the clip in memory (an FBX's clips are never written back), and it strips its own previous events first, because with domain reload off a clip keeps them from the last Play session and installing again must not stack a second copy. Each event carries `DontRequireReceiver`, or every other animator playing that clip without a player logs a missing receiver each time the frame passes. They are **taken off again on `Application.quitting`** (which the editor raises on leaving Play mode): a clip keeps runtime events in memory after the session, and an `.anim` edited in the Animation window afterwards would save them into the file. `clip.events =` is refused outside Play mode ("use AnimationUtility"), so the edit-mode side of that goes through `AnimationUtility.SetAnimationEvents` under `#if UNITY_EDITOR`. Two more traps from the move to one player per animator: `[RequireComponent(typeof(Animator))]` makes Unity **add an Animator** to any object already carrying the old component the moment the prefab loads — delete the old holder in the same pass — and a cue past the clip's end is clamped onto its last frame (`Gnome_Report` is 10 frames at 24 fps). **Verified in Play mode, not assumed**: `Assets/Tests/AnimationVfx/AnimationVfxTest.prefab` (the model, a one-state controller on `Gnome_ShuffleCard`, a player and its own test database with one cue at frame 20 on `Wrist_R`) is instantiated during Play and its animator stepped by hand with `animator.Update(dt)` — frame 19.5 has no effect, 20.5 has exactly one parented to `Wrist_R` at zero distance, running to the end adds none, a replay adds a second, and the same instance with its renderers off spawns nothing; after leaving Play no clip still carries the event. Events installed in `Awake`, after the animator has already bound, do fire — no `Rebind` needed. Enter Play on the scene that is open rather than through `playModeStartScene`: with a dirty scene that path can raise a save dialog, which is modal and stalls the editor. One `AnimationVfxPlayer` per animator, **on the animator's own object**, because that is where Unity delivers the event — `Models/Gnome_rig` and `Models/Gnome_HandOnly` each carry one, and a player ignores its event unless its rig has an enabled renderer, so the owner's hands and the body everyone else sees never double an effect. `Tools > Animation VFX Preview` scrubs the clip in edit mode through `AnimationMode` with a driver of its own (the Animation window's sampling, so closing it hands the pose back and dirties nothing), spawns through `AnimationVfxCue.Spawn` — the same method the player calls — and simulates each `VisualEffect` forward to the scrubbed time. Cue by **clip**, not by gesture id: the clip is the thing being previewed, and anything that plays it, a gesture or a seat pose, then gets the effect. Bones are named rather than referenced, because the two rigs carry the same skeleton under the same names and one cue has to land on whichever is drawn.
- **A marker is an animation event written into the clip asset itself — never installed at runtime.** For an FBX take that is the take's events in the model importer (`ModelImporterClipAnimation.events`, normalized time over the take's frame range, saved in the `.fbx.meta`); for a project-owned `.anim` it is `AnimationUtility.SetAnimationEvents`. Every marker calls `PlayerAnimationEventRelay.OnAnimationCueEvent` with the cue's **name in the string parameter** and `messageOptions` DontRequireReceiver. The import settings survive an artist re-exporting the FBX as long as the take keeps its name, and the events are visible on the clip — which is what `AnimationMarkerDatabase` (since **deleted**, with `AnimationMarkers_Player`) hid: it wrote them into clips in memory on `Awake`, so what a clip raised could only be learned from a second asset, a row missing there was a cue that silently never fired (`ImpactShake` shook nothing for exactly that reason), and nothing about the clip said so. Writing a take's events through the importer when `clipAnimations` is empty goes through `defaultClipAnimations`; check afterwards that the controller's motions kept their fileIDs (they did: `Anim_Impact` stayed `7838699852346251955`). Measured in Play mode after the move, no database anywhere: `BetGrab` f14, `BetRelease` f26, `EatGrab` f2, `EatSwallow` f27, `EatShake` f84, `ImpactShake` f1. A release belongs on the frame the hand is *at* the spot; `PokerItemCarryController` takes its grab and release from there instead of counting seconds, so a second clip carries its own frames and needs no field anywhere. Two things the event route makes you do by hand. The event is delivered **only to components on the animator's own GameObject**, so a listener on a feature child (`Items`) can never be called — a relay sits on each rig and raises a C# event, which is also where the **drawn-rig gate** has to go, since both rigs play the clip and an ungated pair fires everything twice. And **a cue that never arrives must not strand what was waiting for it**: the carried cap is hidden at the moment it is staked, so a clip missing its events would leave it invisible for the rest of the hand — a timeout puts it on the table, and it is a backstop rather than a delay anybody tunes.
- **A contact frame is measured inside the clip that will carry the marker, never across the transition that reaches it.** The three card waits were 0.5 / 0.35 / 0.52 seconds "counted from the change that starts the pose", and every one of them was measured from `Sit` through a blend — so none is a frame in the clip it describes, and `Anim_Show`'s 0.52 is longer than the whole 0.50 s clip. Sampled clip-locally instead (`clip.SampleAnimation(rigRoot, t)` on the **animator's own object**, or every curve path resolves to nothing and the rig reads its bind pose at every frame), `Anim_CamBaiLen` has no downward reach in it at all: the seated pose already has the hands on the table, so the right wrist is at its lowest on **frame 0** and only rises. `CardPickUp` is frame 3, because the card flies for `_moveDuration` 0.4 s ≈ 10 frames and the left wrist — the fan's own anchor — settles into its holding pose at frame 13. And `Anim_Show` animates the right wrist **not at all** (a flat 0.4366, the bind value, across all 12 frames), which is worth knowing before hunting for a frame in it — a clip that holds a bone perfectly still is either art that is not finished or a beat that lives on other bones.
- **The runtime install half of a clip-cue database now has one user.** `AnimationCueDatabase` owns stripping its own events, `DontRequireReceiver`, the `Application.quitting` cleanup and the edit-mode-versus-play write; `AnimationVfxCueDatabase` is the only subclass left since markers moved onto the clips, so the base is a candidate to fold back in (or to move VFX cues onto the clips the same way) the next time it is touched.
- **Every animation in the art checklist is wired to the moment that already happens, and each one's timing is measured off `Animator_Gnome`, never guessed.** Measure by instantiating `Player_Poker`, `Animator.Play("Sit")` (the seat plays it, so a bare prefab never reaches it), then `SetBool`/`CrossFade` and step `Update(1/48)` while logging wrists and head — the numbers below came out of exactly that. What lands where:
  - **Seated fidgets** are `PlayerIdleVariation` on `Player/Animation`: local, never replicated (set dressing), firing the `IdleVariation` trigger every 6–12 s only while a rig is *in* `Sit` or `Sit_Peek`, so the trigger can never latch and fire later mid-gesture. `Sit → Sit_IdleRandom` (`Anim_IdleRandom`), `Sit_Peek → Sit_PeekRandom` (`Anim_CamBaiIdleRandom`).

The hand slams down at 0.52 s, so `PokerHandVisual._showDelay` 0.15 lands a 0.4 s flight on it.
  - **Betting a cap** plays `Bet` from `PokerItemWagerStage`, and `PokerItemPotVisual` carries every cap staked on a wager street (`Phase` `FirstWager`/`SecondWager`; a settlement or Colorful serve is stamped with another phase and still drops) in the staker's `HandRight` on whichever rig this client draws: hidden until `_betGrabDelay` 0.6 (the hand at its lowest, 0.625 s), held until `_betReleaseDelay` 1.4 (put down in front, 1.375 s), then slid to its seat slot. One sequence targeting the cap's transform, so a clear kills it, and `Relayout` skips carried caps.
  - **Eating** stays sequential: one `ConsumeItem` gesture per mouthful of `_itemsPerBite` (1) caps, `_biteDuration` = `Anim_AnNam`'s 5 s so the next bite never cuts it. The cap itself rides the hand — `PokerItemPotVisual` hands it to the eater's `PokerItemCarryController.Consume`, which takes it at `EatGrab` (frame 2) and is rid of it at `EatSwallow` (frame 27, where the wrist is nearest the head), the same hold a wager uses with a different ending. **A grab cue can fire before the cap it grabs has arrived**: the consume stage plays the gesture and then takes the cap off the ledger, those replicate separately, and `EatGrab` is only 83 ms into its clip — so a client hearing the gesture first passed the cue with nothing to carry and the cap sat on the table until it vanished at the swallow. `PokerItemCarryController` remembers when each cue last fired and grabs at once when a carry begins within `_lateCueWindow` (0.5 s) of its grab cue; measured in Play mode, a cap handed over 0.2 s into `_ConsumeItem` was parented to `CapHold` on arrival and swallowed at 1.13 s (frame 27). Any cue near the start of a clip that waits on replicated data needs the same catch-up.
  - **One mouthful is three beats in a row, never two of them at once: it goes down, the hit plays, and only then does the world change.** `Impact` used to be fired in the same frame as the effect and the wait was `Mathf.Max(blink, _impactDuration)` — so the room changed *through* the hit, which is the one beat the round is played for. The blink is started by the rate moving, so putting the hit first means **holding the rate back**: `PokerItemConsumeStage` takes the caps off the ledger at the bite (that is what the visual plays as the mouthful), keeps them in `_pendingItems`, and does not call `ConsumeServer` until the impact is over. Whether an impact is owed at all is asked of the effects first through `PokerItemEffect.PreviewHallucinationGain` — **exact rather than predicted**, because the only thing a price turns on is a record nothing has written yet, which is why the "never predict the rate" rule does not forbid it. Anything decided by **chance stays outside the preview**: a Colorful roll that goes to the ceiling is a death, and that has its own pose and wants no hit in front of it. Each beat is a step through `OnTickStage` rather than a duration added to the one before, so nothing can overlap; the rate is still read either side of the apply, because the roll can have moved it further than any preview could say.
  - **Going under** is `IsDead` from `PokerDeathPoseController` on the animator's own **`Death` layer** (override, weight 1): `Empty → _Die` holds the clip's last frame, back to `Empty` when the rate drops. Its own layer, because a gesture cross-fade on `Gestures` (the deal's `Idle`) would otherwise interrupt it and an AnyState return would replay the whole death. `PokerDeathVisual` collapses the **full body rig's** head at `_headVanishDelay` 1.8 (the burst after the shaking, 1.75–1.94 s) through `PlayerBoneScaleController` — never the hand-only rig's, which the owner's camera hangs off — with `_vanishEffect` empty until the smoke VFX lands; a late join is headless at once.
  - **Winner** plays `Laugh` at the showdown (no state yet: `Anim_Smile` binds 0 paths under its `Govannom` root and must be re-exported). **The Colorful pick is chosen first and acted after**: `Serve(target, chooser)` plays `SnapFingers` (`Anim_BungTay`) and `ServerSetFocus(target)` only for a real choice — a timeout is not one — after `ClearTurn` (which drops the focus) and before the stage can finish.
  - The gesture database holds only ids with a state: `Fold`, `Bet`, `Laugh`, `Idle`, `ConsumeItem`, `Impact`, `SnapFingers`. Report's `_Report`/`_Point`/`_PointExit` and the clip-less rows went; code still calling a removed id is skipped in silence, as before.
- **An act that lasts as long as a decision is a bool on its own controller, never a gesture.** `PlayerActionAnimator` fires and forgets: its clip ends when the clip ends, which is the wrong length for an arm held out across the table while somebody makes their mind up. A held act is a replicated bool driving a bool parameter on both rigs (`PlayerAnimatorStateController` today; the deleted `PlayerHandPeekController`/`PlayerPointController` were the first cases), and the state it drives is left **without an exit transition**, because a non-looping Unity state clamps on its last frame. That is the pose being *held*, where looping the clip would replay the raise over and over. The three-clip shape is the whole idiom: a one-shot to start it, a state that arrives and stays, and a state the falling bool leaves through — the old pointing pose was `_Report` → `_Point` → `_PointExit`.
- **A cue-plus-timeout pair is only a cue if the timeout outlasts the clip.** `PokerColorfulPickStage` waits for `SnapServe` before the cap is put down and falls back on `_serveCueTimeout`; that was first authored at 1.5 s against a 1.75 s `Anim_BungTay`, so the backstop would have fired **every single time** and the marker would never once have decided anything. Nothing warns: the cap still arrives, at a plausible moment, and the cue looks wired. Set the timeout from the clip's own length plus a margin, and read the clip rather than guessing at it.
- **A held pose goes on its own layer, and where that layer sits is the whole design.** `IsSmiling` drives `_Smile` on a layer at **index 2** of `Animator_Gnome` — `Base → Gestures → Smile → Death` — and **where it sits is decided by what already names a layer number, not by taste**. Every row of `PlayerActionAnimationDatabase` carries `Layer = 1`, so inserting the new layer at index 1 pushed `Gestures` to 2 and silently played every gesture in the game — Bet, Fold, ConsumeItem, Impact, SnapFingers — on a layer that has none of those states. Nothing logged: `PlayerActionAnimator` skips a missing state on purpose, so the whole gesture set simply stopped, and it surfaced as one bug report about a wager that had lost its animation. **Adding an animator layer renumbers every layer after it; grep for what names an index before choosing where it goes.** Appending was the other wrong answer, because `Death` must stay last or a corpse smiles. A held celebration also **loops**, or the clip clamps on its last frame and reads as the rig having broken; new FBX takes arrive with `loopTime` off. And the parameter's name lives in exactly one place — `PokerWinnerPoseController` — because two stages raise and drop it, and a string typed in both is how a rename moves only half of them. **A flag raised by one beat and dropped by another is stuck on every path that skips the second** — the same defect the "every start must end in an outcome" rule names for screens. The showdown raises the smile and the Colorful pick drops it the moment a name is settled (the clock choosing counts, and so does the stage ending with nobody able to be fed), but a match that cannot deal another hand goes from the showdown straight to the idle stage and never reaches the pick, so the last hand's winner would have smiled through the lobby and into the next match. `PokerWaitingStage` drops it too, beside the pot it already clears for exactly that reason. Whenever something is dropped by a later beat, read every exit of the beat that raised it.
- **A reaction only the person it happened to should feel is owner-gated, and the cue cannot do that for you.** A marker is raised by whichever rig *this machine draws*, so a body being watched across the table raises it on every client at once — without a gate, everybody feels the hit that landed on somebody else. `PlayerCameraShake` binds from `OnNetworkSpawn` behind `IsOwner` (a spawned prefab does not know who owns it in `Awake`), keeps `OnEnable` behind `IsSpawned && IsOwner` for a switch off and on afterwards, and is idempotent behind one flag so a despawn and the disable following it cannot unbind twice. The shake itself is a **Cinemachine impulse** heard by a `CinemachineImpulseListener` on `FirstPersonCamera` — never a key on a bone, because the camera rides the look and not the rig; the listener living on the shot the player looks through is a second reason nobody else feels it. **What a shake feels like is a `PlayerCameraShakePreset`**: a 6D `NoiseSettings` signal (position and rotation), a strength, a frequency and an attack/duration/decay envelope, played as a *Legacy*-type impulse so the noise keeps moving the view for as long as the envelope is open. The default impulse source was the wrong tool — a single bump curve along one axis, so a stronger "hit" was only a bigger lurch. Two traps in the API: a running Legacy impulse **reads its definition live every frame**, so each preset gets its own `CinemachineImpulseDefinition` on the player (a shared one makes every running shake adopt whichever preset played last), and events are **pooled**, so a held reference is only still ours while it carries the signal we gave it. A cue raised again while its shake runs (a looping clip) cancels the old event into its decay and starts a new one — measured in Play mode, `CameraShake_Smile` retriggered mid-run held a steady 0.5° / 2.7 mm with no spike, and `CameraShake_Impact` peaked at 3.1° / 16 mm and was gone by 1.1 s. **A shake's start and length are read off the head in the clip, never picked by feel**: sample `Head_M`'s angular speed frame by frame (`clip.SampleAnimation` on the animator's own object) and put the marker where it turns violent and the envelope's attack + duration + decay where it settles. Measured: `Anim_Impact` rattles from frame 1, hardest through 48 and gone by 98 (`ImpactShake` @1, 1 + 46 + 50 frames); `Anim_AnNam`'s shudder is frames 84–109, peaking near 900°/s at 95 (`EatShake` @84, 1 + 11 + 13 frames) — which is not `EatSwallow` @27, the frame the cap disappears, so the shake has a marker of its own. `CameraShakeNoise_6D` is Cinemachine's "6D Shake" with position ×0.1 and rotation ×6: the package preset is authored for handheld vcam noise, and at a gain that makes its rotation felt its position throws the camera a metre. **A marker on a looping clip fires on every loop**, which is what a held pose wants: `SmileShake` at frame 0 of `Anim_Smile` gives the winner a light knock each 2.75 s chuckle for as long as the smile holds, with nothing counting time. And **a cue is only real once the clip carries it** — `ImpactShake` was wired into the shake list and described as done while no clip raised it, so the hit shook nothing; grep the `.fbx.meta`/`.anim` for the cue name whenever a listener is added for one.
- **The outline lives on the thing that already owns every renderer.** `PlayerVisual` holds both rigs, knows which one this client draws, and is what a skin is hung on — so a replicated `Outlined` bool belongs there too. Every slot wears it, the hand-only rig included: lighting the body alone was written when a glow on your own hands told you nothing, and once the pass is authored in the prefab that becomes two lists — what the renderers carry and what the code re-hangs — which drift apart in silence. One list, and the owner sees themselves lit when the table is pointing at them. Do not reach into `Interaction` for this — that outline answers to the crosshair and this one to the table; they are separate systems that happen to share a shader.
- **A stroke hung on an opaque body belongs before the transparent range, not in it.** `Interactable_Outline.shader` is tagged `Queue = Transparent`, so `Player_Outline_Always.mat` sat at **3000 — the same queue as `Card_Face`** — and with `ZWrite Off` on both, nothing writes depth and the only thing separating them is the per-object distance sort. In first person the arm's bounds reach nearer the camera than the cards it is holding, so the hand's black stroke was drawn *over* the player's own hand of cards. The outline is part of a body that is opaque and does write depth, so it is put at **2900**: after the body it rims, before every card. Set it on the material, never on the shader — `Interactable_Outline.mat` shares that shader and answers to the crosshair rather than to the table, and it stays at 3000. This is the third time one render queue has been the whole bug (`Card_Rainbow` tied with the faces, the pattern pass tied with them too): whenever two transparent passes must have a fixed order, **say the order with the queue** and never leave it to the sort.
- **An extra material pass is added to what a renderer is already wearing, never rebuilt out of the skin.** Hanging the outline as part of `ApplySkin` looks like the tidy "one path decides what a renderer wears" answer and is the bug: `ApplyMaterial` skips a renderer whose skin slot is empty, so any mesh the skin does not name is a mesh the outline can never reach — and on a rig cut into ten pieces, one unlit piece reads as the whole outline being broken. Read `sharedMaterials`, append the pass, write it back; then have `ApplySkin` re-hang it afterwards, because assigning a material replaces the whole list. **The pass is worn all the time and the state is its colour**, not whether it is there: `PlayerVisual` paints `_idleOutlineColor` (clear) or `_outlineColor` on the one runtime clone, so being picked out costs a `SetColor` rather than rebuilding the array on every renderer of the body — and the lit look stops depending on a pass that has to be re-hung after each repaint to exist at all. `Player_Outline_Always.mat` is authored clear **and hung on every renderer in the prefab**, for the reason the UI tint rule gives: what runs and what the prefab shows must agree, and a pass that only exists at runtime is one nobody can see is missing. The cost is a transparent pass drawn per part even for a body nobody is pointing at, which is what makes this the shape for a handful of players and not for a crowd.
- **Never add or remove an input device from inside an input callback.** `InputSchemeController` raises `OnSchemeChanged` from `InputSystem.onEvent`, and `UIVirtualCursor` answered it by toggling `VirtualMouseInput.enabled` — which adds or removes a real `VirtualMouse` device. Doing that mid-callback tears the device out from under an action that is still delivering: `Table/PickCard` binds `/Mouse/leftButton` *and* `/VirtualMouse/leftButton`, so releasing the real mouse ran `VirtualMouseInput.OnButtonActionTriggered`, which queried a control whose device had just been removed and threw `InvalidOperationException`. The throw takes the rest of that callback list with it, and the symptom nobody would trace back is *the UI no longer accepting clicks*. `UIVirtualCursor` defers to the next frame through `Awaitable.NextFrameAsync(destroyCancellationToken)` and collapses several changes into one apply, because the apply reads the scheme when it runs.
- **A guard that lets `Awake` return early owes every later method a matching guard.** `PokerGameMode.Awake` destroys a duplicate table and returns *before* building `_stageMachine`, but `Destroy` is deferred to the end of the frame and NGO spawns a scene object regardless of whether its component is enabled — so `Update` and `OnNetworkSpawn` both ran on an object with none of the state they assume, and a hundred identical `NullReferenceException`s a second buried whatever the real problem was. The duplicate now warns once, switches itself off, and `Update`/`OnNetworkSpawn`/`Stages` each ask for the machine before using it. Read every early return in a lifecycle hook and ask which fields it skipped, then guard the methods that need them; a stack that stops at your own `Update` line is usually a field the constructor path never reached.
- **The Animator puts rotations back, never positions — so anything that *moves* a bone must put it back itself.** "The Animator rewrites the bone every frame, so a driver that stops driving is back under the clip" is only true for rotation: the clips carry rotation curves and a root position, and nothing else. The neck-stretch peek (`PlayerHeadStretchController`, since deleted) spread the neck by writing bone **positions**, and those had no authored pose to be restored to — the neck stayed stretched forever, which reads as a camera stuck across the table rather than as a bone never coming home. Cache each bone's rest `localPosition` once when the chain is built (a skeleton's bone lengths never change) and write it back at the top of every `LateUpdate`, before reading the animated pose: that both ends the lean and stops each frame's stretch compounding on the displaced result of the last one. Keep drawing while the retract tween runs, too, or "ease home" is a snap with a tween nobody sees.
- **It writes scale too, over the whole skeleton, and every one of those curves is a constant.** Measured across the gnome set: 10 of 11 clips carry 249 scale curves each, 83 bones times three channels, and not one of them varies — they are all a flat 1. So the clips express no scale intent whatever, and yet a resize written straight onto a bone is erased on the very next frame, which reads as an effect that simply does not work rather than as one being overwritten. `PlayerBoneScaleController` writes in `LateUpdate` after the Animator and before the brain samples, since a scaled head carries the camera hanging off it. It writes **rest times the multiplier**, never the value it reads back: rest is captured once when a bone is first claimed, so a bone the clips do *not* animate cannot fold its own last write into the next one. Check what a clip actually animates before deciding a driver is fighting it — the curve count named this in one run, where Play mode could only have shown that nothing happened.
- **Where several effects can want one thing at once, they compose through modifiers — last-caller-wins is the wrong default for a value that has arithmetic.** `PlayerBoneScaleController` kept one entry per caller and wrote each of them in turn, so whoever sat last in the list won: a shrink drawn while a swell was running did not fight it, it silently *erased* it and handed back a body that had never been swollen — two effects the hallucination ladder is free to draw together. Every bone is now a **stack of its own** — a base (its authored scale) and a list of modifiers — built the first time that bone is modified and thrown away with the last modifier on it, so a rig nobody is scaling holds no state and its `LateUpdate` returns on the first line. The frame is rebuilt from that base rather than from the value read back, so a bone the clips do not animate cannot compound its own last write. `Add` hands the caller a live `PlayerBoneScaleModifier` it keeps and writes into, rather than a `Set(handle, bone, value)` that searches for its own entry on every tick of a tween: a growth is then a field write, and two calls are two modifiers rather than one replacing the other. Two properties are what make it usable: multiplies are gathered apart from adds (`base × ∏mul + ∑add`), so **the result does not depend on the order the modifiers arrived in** — two effects registering either way round give the same bone; and a mode carries its own neutral, so a fade-in travels from 1 for a multiply and from 0 for an add, the same argument the `UI/Blend` neutral already makes. The value is a `Vector3` throughout, so a head can be made tall without being made wide. Prove it in edit mode against a base that is not 1 (`x2` then `x0.5` must return the *authored* scale, not `Vector3.one`) — a bug that only shows on a bone the artist did not leave at unit scale is one no amount of reading finds — and prove the stack appears and disappears with its modifiers, since a bone left tracked after the last one is dropped is a bone nothing will ever put back.
- **A shape the artist sculpted into the mesh is pushed by name through `PlayerBlendShapeController`, never by index onto the renderer.** `PlayerVisual` is the one writer of what each slot draws, and assigning `sharedMesh` **resets every blend shape weight on that renderer to zero** and re-numbers the shapes behind it — so a weight written straight onto the renderer is silently taken off by the next model, outfit or version change, and an index captured against one mesh means something else on the next. The controller resolves the name across whichever meshes carry it (both rigs, so it does not matter which one this client draws), re-resolves on `OnAppearanceChanged`, and composes its modifiers the way the bone scale stack does — two effects pushing one shape **add up** rather than the last one deciding. It is the same shape of thing as `PlayerBoneScaleController` with one difference worth knowing: the Animator is not a competitor here, because **no clip in the set carries a blend shape curve** (measured: 0 of 17), where every one of them writes scale over the whole skeleton. Measured in Play mode on `Player_Poker`: `outfit_nomal` index 0 at rest 0, 100+30 resolves 130 and renders clamped to 100, dropping one leaves the other standing, and dropping the last puts the shape back to its authored 0 and takes the stack with it.
- **A look the artist shipped as a blend shape is not a `PropVariant`.** `Hallucination_Breasts` was authored as a variant effect aimed at the bodies, and `Player_Poker` carried a `PropVariantController` with no `Breasts` look in it — so the asset resolved, the controller was found, and nothing happened, for as long as it had existed. A variant switches children on or hands a renderer another mesh; there is no second mesh here, only `blendShape.outfit_mocvu` on `outfit_nomal`. The asset was converted in place (`m_Script` rewritten, guid kept, so every rung pointing at it survives) to `PokerHallucinationBlendShapeEffect`. Read what the art actually shipped before picking which mechanism is meant to carry it — both answers resolve, and only one of them moves anything.
- **A tween's per-frame callback is a per-frame path, so it does no lookups.** `PokerHallucinationScaleEffect` resolved its target into transforms and then called `GetComponentInParent` for each of them on every tick of the growth tween. Caching the bone and its controller together as one pair at resolve time is the whole fix, and the shape generalises: whatever a callback needs, bind it when the set is resolved, because the set changing is an event you already have.
- **One writer of `sharedMaterials`, and the composition lives where the renderers do.** Assigning a material replaces the whole array, so a hallucination painting a body directly would be wiped by the next time the outline is hung, and the outline would be wiped by the next repaint. `PlayerVisual` therefore composes skin, override and outline in one pass and exposes `SetMaterialOverride`; `PlayerMaterialOverrideController` holds the *requests* and resolves which one wins, because how many callers there are is a question `PlayerVisual` has no business knowing. Split the two whenever several systems want to change one thing: one place decides the final value, another place decides whose turn it is.
- **Anything posing a bone the camera hangs off runs between `PlayerController` (order 0) and the Cinemachine brain (order 100).** The Animator restores bones every frame, so a LateUpdate write after the brain's sample is not a frame late — it is never seen at all.
- **What the view is doing is a state per object, not a row in a list.** States differ in *behaviour*, not configuration — `PlayerCameraFreeflyState` hands the look back to the player and raises nothing, `PlayerCameraLookAtState` turns the head onto whatever its shot is about — so each is a subclass of `PlayerCameraState` on its own child under `Cameras`, and adding one is a new script and a new object rather than another branch in the controller. `Enter`/`Exit` are non-virtual and own the invariants; `OnEnter`/`OnExit` are what a subclass fills in. **A state resolves its own target rather than being handed one**: it knows which beat it belongs to, so it can listen for whose turn it is and swing on its own — a `Transform` passed in with the request would put that knowledge in every caller instead, and each of them would keep a copy of it. `PlayerCameraController` only decides *which*, from a stack of requests — the shape `UIEscapeStack` and the cursor's counted release already take, so a card being picked while a focus is up unwinds in any order. Callers hold a handle rather than a name: a state released by name is released by whoever asked last, not by whoever holds it.
- **Freefly is the absence of a shot, not one of them.** The player is already looking through the camera on whichever rig this client renders, and which rig that is stays `PlayerVisual`'s business — naming it in the camera states would mean picking one of the two, and the owner renders the other. So the base state raises nothing and only hands the look back. A shot is made live by enabling the `CinemachineCamera` **component**, never by switching its GameObject off: the state that has to switch it back on lives on that same object. And it must be disabled rather than left at priority zero, because every enabled vcam is a candidate and the rig's own also sits at the default — a tie the brain may break either way, which reads as the view occasionally starting out pointed at nothing.
- **An aim the rest of the table has to see is the look being pointed, not a camera pointed beside it.** A shot that swings a `CinemachineCamera` onto somebody shows *this* client a turned view and shows everybody else a player staring straight ahead — and if the head is turned as well, that is two things aiming at one point through two different clamps, drifting apart the moment either is limited. `PlayerController.SetLookTarget` steers the same `_lookYaw`/`_pitch` the player's own input steers, so the bone genuinely turns and the view rides it: already clamped, already replicated, already interpolated on the way out, and **nothing new travels** for a player turning to watch somebody else. It is rate limited rather than tweened (`_lookTurnSpeed`, degrees per second) because the point is usually a body that is breathing and animating, so the destination never stops moving and a tween would be killed and rebuilt every frame — the same "genuinely continuous work" the no-polling rule already exempts the look for. The player keeps their view throughout: input wins while they are turning and for `_manualLookReleaseDelay` after, or a stick let go to centre reads as the camera snatching the view mid-gesture.
- **Those two angles are offsets from the pose the clip is holding, so the pair that aims at a point is solved, never taken from `LookRotation`.** `ApplyLookTo` composes `AngleAxis(yaw, frame.up) * AngleAxis(pitch, frame.right)` *onto* the animated `localRotation`, so yaw 0 / pitch 0 means "wherever the clip put the head" — and the seated clips do not hold it level. A `LookRotation` toward the target answers a different question and lands a permanent few degrees off, which reads as a rig that is subtly wrong rather than as maths that is. `PlayerController.SolveLookAngles` inverts the actual composition: pitch first, because turning about the frame's up leaves height alone and so there is exactly one pitch reaching the target's height (`rest.y·cos p − rest.z·sin p = desired.y`, written as one cosine so it inverts, taking whichever of the two roots is nearer the current pitch so the head never flips over on the way); then yaw is the bearing left over. Measured exact — 0.0000° across twelve rest/target pairs including off-level rest poses. Two things it depends on: it is read at the top of `LateUpdate`, while the bone still holds the clip's pose and before the look is written over it, so what comes out is the absolute pair rather than a correction to add to the last one; and it is solved **twice**, because turning the head swings the eye around the bone as well as pointing it, and a hand's breadth of travel against a face a table away is a couple of degrees — enough to land the aim on a shoulder.
- **Who is being asked to move and who the room is looking at are two values.** `PokerGameData.CurrentTurnClientId` says whose answer the table is waiting on; `FocusClientId` says who every head should be pointed at. They are the same player on every street, which is why `PokerGameMode.BeginTurn` writes both and no street carries a line about it — and they come apart the moment a beat is *about* somebody without asking them anything. `PokerItemConsumeStage` walks the seats swallowing caps and deliberately calls `ClearTurn`, so reading the focus off the turn leaves the room staring at nobody through the one beat the round is played for; writing the turn instead would put "X'S TURN" on screen over a player being offered nothing and would have every `HasTurn` gate in the project believe it. The stage machine clears the focus at every handover, so a beat that wants one says so as it opens rather than inheriting whoever the last one was about.
- **Everything leaves before anything arrives.** When one thing replaces another and both write the same slot, the outgoing one's teardown must run *before* the incoming one's setup — otherwise the leaving hook releases what the arriving hook has just taken, and the result is a feature that looks like it never started rather than one that started and was erased. `PlayerCameraController.Apply` ran the other way round for a while, on a reason that had since expired: back when a state released the look flag on its way out, leaving last would have undone what arriving had set. Once states stopped doing that and started holding a *look target* instead, the same order became the bug — `SetLookTarget` on the new shot, then `ClearLookTarget` from the old, and the head stayed pointed at whatever the last beat had been about. Reproduced exactly in edit mode: `Enter(new); Exit(old)` leaves the player with no target, `Exit(old); Enter(new)` leaves them aimed. Worse, *which* order the controller saw depended on which of two binders `Update` happened to run first, so it presented as a camera that was reliably stuck at one particular transition. Two lessons: put the teardown first by default, and **when a paired hook stops releasing something, re-read every ordering rule written for the thing it used to release** — the comment explaining an order is exactly where a stale reason hides.
- **The camera knows about the round; the round knows nothing about the camera.** `PokerStage` briefly carried a `_cameraShot` naming the framing it wanted, and that is the dependency backwards: a rule about what a beat *is* had an opinion about what it *looks like*, and every stage asset in the project would have grown one. The shot is authored on the camera side instead — `PokerStageCameraBinder` sits beside each state on the player and holds the list of `PokerStage` assets that shot belongs to, picked from a dropdown rather than typed, so a stage that is renamed or replaced cannot leave a shot pointing at nothing. Nothing in `Game.Runtime.GameMode.Poker.Stages` references a camera type at all.
- **A shot is a state plus a binder, not a controller with a table.** A single component holding rows of `(stage, state)` is a list somebody keeps in step by hand, and a row left out is a shot that silently never runs. One binder per state means adding a shot is one object carrying two components, and the hierarchy under `Cameras` reads as the round itself. It is composition rather than a base class because the state already has one — `PlayerCameraLookAtState` — and a shot is not a kind of stage watcher. The binders never fight over the handover: each releases and requests inside the same `Update` pass, so whichever order they run in, the stack has settled before anything is drawn.
- **A street's shot branches on whose turn it is, and that branch lives in the state.** `PokerWagerCameraState` looks down at your own seat while it is your turn and turns to whoever is deciding while it is not — one state that re-aims, rather than two swapped in and out on every turn, which would tear a shot down and rebuild it in the middle of itself. A viewer needs no special case there: it is never their turn, so they watch the player like everybody else. Which spot at your own seat it frames is `PokerSeatAnchor`, serialized — the first wager runs *before* the deal, so there is no row of cards yet and what is being decided is the cap about to go down, while the second runs with a hand to decide over. The `_requiresPlaceInMatch` gate on the binder is only for shots about a seat that a viewer has nothing in (`State_OwnCards`), because a shot about the table or about somebody else is exactly what being a viewer is for.
- **Watching somebody else is the one shot that cuts to a virtual camera, and it is that player's camera, not the watcher's.** `PokerFocusPlayerCameraState` (the eating beat) still turns the head, so the room sees who is looking, and on top of that holds the focused player's `PlayerSpectatorCamera` (`Player/SpectatorCamera`, reached through `PlayerRigController.SpectatorCamera`) — a camera on the body it frames follows them into whichever chair they sit in. The eater is never cut away from their own eyes (`player.IsOwner` → no hold). The camera ships disabled at priority 0 and is raised only while held, since every body in the room carries one. The cut is taken where the target resolves, so a body that replicates late is picked up by the same retry that aims the head; a focus cleared between two eaters keeps the cut. **Going under is the one shot even its owner watches from outside.** `PokerDeathCameraState` + `PokerDeathCameraBinder` (`Player_Poker/Cameras/State_Death`, aim delay 0, no manual look) cut *every* screen to the dying player's `PlayerSpectatorCamera`, the owner's included, for `_duration` (4 s) from the moment it happened. Nothing is announced for it: every client already hears `HallucinationRate` cross `MaxHallucination` on each player's own data, so the binder watches the whole registry and starts the shot on that edge — only the edge, so a late join does not replay a body already on the floor, and a rate coming back down ends it. The owner renders only their hands, so for that screen the state turns `PlayerVisual.SetRenderAllBody(true)` while it lasts and back to the hands on exit. **`RenderAllBody` is which rig this client draws for a body, local and settled at spawn** (`!IsOwner`, before the first appearance so the owner never flashes a body); it only switches renderers — `PlayerRigController.RenderedRig` still answers by ownership, so cards, props and cues keep hanging off the rig they were on.

- **Look limits live on `PlayerController` and nowhere else.** `_pitchLimits` (−60, 45), `_yawLimits` (±80, how far the head turns from the body while a seat anchors it) and `_focusYawLimits` (±150, while an aim holds the look — widened to at least the yaw pair in `ActiveYawLimits`, so a focus pair tuned below it cannot freeze the head). A seat used to carry its own set and hand it over on sitting down, which made two answers to one question; `SeatPose` now holds only the animation state, and a seat calls `ResetLook()` on sitting and on standing to square the head with the body. Standing, yaw turns the whole body and is not limited; anchored, it turns the look bone and replicates like pitch, because nothing else carries it.
- **A shot that is not being asked for owns no priority, and it ships disabled.** Every player in the room runs its own `PlayerCameraController`, so the copies on other people's bodies are camera states nobody is watching — and `SetLive(false)` used to leave `Priority` standing at 20 while only switching the component off, so each of those was a shot outranking the one this client looks through the moment anything enabled it. The priority is raised on the way up and dropped on the way down. The `CinemachineCamera`s were also authored **enabled** in `Player`/`Player_Poker`, which makes every instance a live candidate from `Awake` until its `OnNetworkSpawn` runs — the class's own `OnInitialize` says a shot must be off until it is asked for, and that has to be true in the prefab as well, or edit mode and every instant before spawn disagree with it. The brain's `DefaultBlend` is where the transition's length lives (`Bootstrap`, EaseInOut); nothing in code sets it.
- **A shot waits a beat before it swings, and the wait is the shot's own number.** `PlayerCameraLookAtState.Aim` schedules the re-aim on `_aimDelay` (0.5 s) rather than applying it, so entering a shot and every change of target inside one both hold the view on the beat that is ending — a head that leaves the instant `CurrentTurnClientId` moves reads as a cut, where a pause reads as somebody looking up at whoever has started deciding. It belongs on the base rather than on each subclass, because "the answer has moved" is the one event every look-at shot already raises (`PokerWagerCameraState`'s turn, `PokerFocusPlayerCameraState`'s focus). Two things it must not do: the wait counts `Time.unscaledTime`, since a pause menu is exactly when `timeScale` is zero; and the null-target retry spends no delay at all, because that wait is for a beat ending and not for the frames a seat index takes to replicate.
- **A shot at a seated player is never authored at a height.** The first version put the focus cameras on a node placed at the eye's position *in the prefab* — a standing bind pose — and the gnome plays the game sitting down, so the shot framed the floor. The second locked a virtual camera to `PlayerRigController.RenderedCamera`, which starts the shot exactly where the player is already looking from. Both are gone now, because a shot that turns the head has neither problem by construction: the first-person camera turns with the head, so the shot begins wherever the player is already looking and goes wherever the head turns. A transform authored at a fixed local height is a guess about a pose; the head is the pose.
- **The look aims a different bone per mode, not per rig, and composes onto the animation rather than replacing it.** On their feet the look drives `Chest_M`, which parents both the neck chain and the two scapulae — so a player looking down lowers their hands with their gaze instead of craning a head off a body that never moved. Anchored in a seat it drives `Head_M` alone: the chair already decided how the body sits, and swinging the whole torso to read the table throws that pose away. Each rig therefore supplies both bones (`_bodyLookTransform`/`_headLookTransform` and their `_owner*` twins) and `ActiveLookTransform` picks on `_bodyAnchored`. Nothing needs undoing when the answer changes — the Animator rewrites both bones every frame, so the one that stops being driven is back under the clip on the next one (measured: switching modes left zero residue). Both are written as `AngleAxis(yaw) * AngleAxis(pitch) * localRotation`, reading whatever the Animator just put there, because every clip in the set poses the chest and a write that replaced it would leave the gnome bolt upright. The axes are derived from the bone's parent *each frame* for the same reason: that parent is itself animated, so a pair cached at spawn has the aim drift off level as the torso moves under it.
- **Animation moves the body, input moves the view.** `Player/FirstPersonCamera` is a child of the player root at the seated eye (`(0, 0.819, −0.104)`), carrying the one `CinemachineCamera` and `PlayerCameraFollow`, and it faces `root × Euler(pitch, yaw, 0)` — the look's own two angles, written by `PlayerController.LateUpdate` right after it turns the bone (order 0, before the interaction and aim casts at 10 and the brain at 100). It **never reads a bone**: copying the head's rotation was tried first and carried every clip's head shake straight into the view, which is exactly what taking the camera off the rig was meant to stop. The head still turns with the look and still shakes for everyone else. A view that should move on purpose is a look target (`SetLookTarget`) or a Cinemachine impulse — never a key on a bone. **Anything aiming the look solves against `PlayerCameraFollow.RestingRotation`** (the root's facing), never against the camera transform, which still holds last frame's look and would feed each answer back into its own question; one solve is exact. What this gives up, on purpose: a head that is scaled or stretched no longer moves the view, and the neck-stretch peek (`PlayerHeadStretchController`, `PokerPeekController`, `IPlayerLookPoint`, `SetLookSuspended`) was deleted with it.
- **The host holds the button, not a hand.** `PokerGameMode.CanStartMatch` counts the funded players and lets the host's own seat count as company even when they have gone under: nothing revives a player between matches unless the idle stage is told to, so a table whose host is unconscious had no way back at all — the one player who can press start was the one the count refused. Pressing it does not bring them round; the deal marks them out of the running like anybody else and they watch the match they started. Keep it separate from `CanDealAnotherHand`, which is the same count asked about *dealing* and must go on refusing.
- **Every rig sharing a set of clips needs the shared avatar, and the one nobody renders loses it quietly.** `Gnome_HandOnly`'s Animator came out of the rig swap with `m_Avatar` null while `Gnome_rig` kept `Gnome_Model_RigAvatar`, so the owner's own hands could not play a single clip — and with no head and no body on that rig, nothing on screen looked wrong. The giveaway was a first person camera that measured *perfectly* still over fifty seconds of idle: an animation that never moves is not a calm animation, it is one that is not running. Check `avatar` on every Animator after a rig swap, not just the one you can see.
- **"Where does yaw go" and "which bone does the look aim" are two questions, not one bool.** `_bodyAnchored` answered both for as long as there were only two cases, and came apart on the third: an accuser pointing across the table (the deleted accusation) was still held by their chair — yaw still went to the bone rather than swivelling the body out of its pose — and yet aimed from the chest, because the whole torso was in the act. No reading of "anchored" produces that. The anchor stays a bool about the body being held; the bone is a named `PlayerLookMode`, with `SetLookModeOverride`/`ClearLookModeOverride` for an act that wants a say while it lasts. **The override is released, never set back to a remembered value** — what the look should aim at once the arm comes down is the seat's business, and the seat is the one that knows whether there is still a chair. Set on every peer, like the anchor and for the same reason: a pointing player's torso turns on everyone else's screen too.
- **A mode is a branch inside the controller, not a second controller.** Splitting seated and standing into two `NetworkBehaviour`s looks tidy until you notice NGO binds `NetworkVariable`s to the behaviour that declares them: two components means two replicated pitches, and swapping between them snaps every remote head to the other one's last value and throws away the interpolation buffer that was smoothing it. The owner/remote rig choice is rig knowledge, needed by both, so it would be duplicated as well. What actually differs between sitting and standing is one line — where yaw goes.
- **Stages reached by reference rather than by sequence** (module-pushed stages, anything queued with `PokerGameMode.InsertStage`) must be declared in `PokerModule.CollectReferencedStages`, so every peer clones them at build time — clients look running stages up by id. (Overlays were the other case, exiting with `PopOverlay`; the overlay stack is since deleted.)
- **A mode's HUD is a variant of the shared HUD prefab, never a copy of it.** `UI_Poker_AbilityMode` inherited every widget from `UI_Poker` and only switched off the bars its streets never asked for (`ActionBar`, `BetBar`, since deleted with that mode) — a copy would stop receiving fixes made to the original. Switching a bar off rather than deleting it is deliberate: a disabled view never runs `OnEnable`, so it subscribes to nothing, and turning raises back on for a mode is one toggle.
- **A module gated on stage references is a second place the sequence is named.** The deleted `PokerAbilityModule._abilityStages`/`_reportStages` said which stages their windows opened in, and an *empty* list meant every stage — so a list still pointing at the previous preset's stages turned the ability game silently off rather than on. Swapping a mode's sequence means re-pointing every module list in the same change.
- **Numbers the UI offers are the stage's own methods** (`PokerItemWagerStage.IsWagerable`; the deleted betting street's `StakeCeiling`/`ClampBet`): server clamps and bar sliders call the same code, so a client can never offer what the server will refuse. The same goes for *which* actions are offered — a new permission on a stage (the betting street's `AllowRaise` was the case) is read by the bar in the same change that adds it, or the button stays lit on a move the server rejects.
- **A turn on a clock must always end, whatever the rules refuse.** The timeout action is a preference, not a guarantee: a street that forbids checking, an action a short stack cannot make, any rule saying the polite answer is unavailable — and a refused action leaves the turn expired, so the tick fires again next frame and the table waits forever on somebody who has already stopped answering. The deleted `PokerBettingStage` took the refusal and folded, which nothing can refuse, and defaulted silence to **calling** rather than folding: a player who says nothing is usually reading the table, not leaving it, and throwing away a hand they never chose to throw is the harshest reading of a pause.
- **One number decides whether a step is on a clock at all, and a step with no clock draws no bar.** `PokerItemWagerStage._turnDuration` at zero or less runs no countdown and no timeout: the table simply waits, which is what a wager the players are meant to take their time over needs. Set a duration and the timeout and the bar both come back together — two behaviours from one field rather than a visibility toggle beside a hidden deadline that could disagree with it. `PokerGameData.HasTurnClock` is what a view reads to decide, because `TurnRemaining` already answers 0 for an unclocked turn and a bar drawn at 00:00 reads as a hung timer rather than as no timer.
- **An event that changes no rule is a replicated flag on a module, never a stage.** The blackout (`PokerBlackoutModule` + `UIPokerBlackoutScreen`, since deleted) put the lights out once a hand at a moment nobody was given: the turn kept running, the clock kept counting, nothing was asked differently — so it was a `NetworkVariable<bool>` every client drew for itself, and the screen owned entirely what the dark looked like. Push a stage only when the *question* changes. Its schedule is the shape to copy for any chance-driven event: the moment is picked as the stage opens and the odds are not rolled until that moment arrives, so *when* and *whether* stay two questions, and the stages at risk are a list of stage assets with a chance each, picked rather than named. A screen meant to darken everything is a panel over the whole HUD rather than the scene's lights switched off, because half of what a player is reading is drawn on the canvas; and it never takes the pointer while play carries on underneath.
- **"The stage started" is too late for a rule about what a player is carrying.** The old money deal took its ante inside `StartStage` (ante, deal cost and `UpfrontCostPerPlayer` are since deleted with the money game), so a module listening on `OnStageStarted` heard about it after the money was gone — a player down to their last coin paid the ante with it and was put all in on the spot, staked out of a hand before being dealt into it. `PokerStageMachine` raises `OnStageStarting` before `StartStage` for that, and `PokerModule.OnStageStarting` is still the hook; the deleted blood exchange (`PokerBloodExchangeModule`) sold its blood there. What moves with the hook: `CanAct` is always false at that moment, because nobody is `Active` until the hand has started — seated and alive is the question being asked — and a rule about a cost that is about to land has to price the player against that cost, not against what they hold now.
- **A guard copied from a street that bets *after* the deal is wrong on one that wagers *before* it.** `PokerItemWagerStage` opened with `CountInHand(...) <= 1` — the same test the old `PokerBettingStage` used — but the first wager runs before any card is dealt, so nobody is `Active` and the count reads zero: the street declared the hand over and jumped to its `_handOverStage`, which is the reveal. The table then span, because the reveal ends the match and drops back to the waiting room, which starts the wager again. `CanWager` asks the question that is actually being asked here — **seated and conscious**, with folding the only thing that removes somebody afterwards — and it is what opening, advancing, finishing and `HandleAction` all read. This is the same trap already written down for `OnStageStarting`: `CanAct` and `IsInHand` are answers about a hand in progress, and any step that runs outside one has to ask something else.
- **A screen meant to cover the HUD is the *last* sibling, and nothing in the inspector says otherwise.** uGUI draws later siblings on top, so a full-screen panel sitting near the front of the list is drawn *under* every widget added after it — and since it still covers the 3D table, it looks like it is working right up until somebody notices the pot readout shining through the dark. `UI_Poker/DrunkScreen` was placed with `SetAsLastSibling` for that reason, while `BlackoutScreen` sat at sibling index **1 of 19** with a comment claiming it covered the HUD as well as the table — it did not (both screens have since been deleted).
- **A house rule about what a player can answer with hangs off the turn, not the deal.** `PokerModule.OnTurnBegan` is raised from `PokerGameMode.BeginTurn` *after* the turn is on the table, so a module changing what somebody is carrying is answering a question they can already see being asked. The deleted `PokerBloodExchangeModule` sold a broke player a stake in blood there — a rate written as two plain integers (`_bloodSpent`, `_moneyGained`) rather than one float nobody can picture — and skipped an overlay's turns by checking `CurrentOverlay` (since deleted with the overlays), because those were already staked in blood.
- **A rule variant is another asset, not another class.** The deleted `PokerBettingStage` covered a call-or-fold street through `_openingBet` and `_allowRaise` rather than a subclass, so the turn loop, pause/resume, timeout and hand-over handling were written once. Reach for a new `*Stage` class only when the *shape* of the step differs, not its numbers or its permissions.
- **A move made by looking is aimed on the owner's client and named on the server.** Only the aimer's machine can see through their eyes, so the accusation's aim (`PokerReportAimController`, since deleted) read it from the camera in `LateUpdate` after the look had been written, and sent the answer up **only when it changed** — never per frame, and never outside the window the phase said was open. The server decided whether whoever they landed on could be accused at all, and was the one that lit them up, so every seat watched the same finger travel. What is picked is then locked from the server's copy, not from the client's claim at the moment it matters. The cast asked the server's own predicate (`CanBeReported`) about every body it passed through rather than taking the nearest player: anybody not in this hand is free to walk around the room while it is played, and one of them standing between the accuser and the table was stopping the finger on somebody the server would have refused anyway. Size the hit buffer for everyone the cast can pass through, not for everyone it can accuse — a full buffer drops the rest of the list in silence, which reads as the table not being there at all.
- **A server RPC that refuses says which gate refused it.** A request the UI already decided to offer, dropped by a stack of guards that all `return` in silence, is indistinguishable from a button that is not wired, a prefab field left null and a stage that was never pushed — and each of those sends you looking somewhere else. The deleted `PokerAbilityModule.ReportRPC` named its gate (`RefuseReport`), and a setup that cannot possibly work — no action animator, no point controller, an overlay opening with nothing to judge — warns rather than skipping quietly. Reserve the silent skip for things deliberately allowed to be missing, like an animator state the art has not landed yet.
- **A `CharacterController` is not a hit volume — it only exists on the client that drives it.** `PlayerController` enables it for the owner alone (it stays off in the prefab so it cannot overwrite the spawn position the server sent), which means on any given machine *every other player has no collider at all* and no cast can ever find them. Anything that needs to point at a player — an aim, a targeted ability, a hover — needs its own always-present volume: `AimTarget`, a trigger `SphereCollider` hung on the body rig's `Chest_M` so it follows whatever pose the seat put them in, answering casts and pushing nothing. A trigger also stays out of the interaction scan's way, which ignores triggers when testing for obstruction.
- **A cast that finds nothing is diagnosed by drawing it, never by replacing it.** A sphere cast looking for a player fails in several ways that look identical from the outside — the eye sits inside its own `CharacterController` so our own body is always the first hit, the radius may be too small to reach a face across the table, the collider may not cover the seated body, the layer mask may exclude it. Swapping the mechanism for something that cannot miss hides which one it was. The deleted `PokerReportAimController` carried `_drawDebugRays` (green for the aim, yellow for a player that lost, **magenta for our own body**, red for scenery, plus the sphere drawn where it ends up) and `_logAimChanges`, which writes the hit list once per change rather than once per frame. Draw it first; the picture names the cause in one frame.
- **A step whose UI asks a different question is a replicated phase, not something inferred from the turn.** The deleted accusation's `PokerReportPhase` said whether the table was aiming, answering or hearing the verdict; reading that off `CurrentTurnClientId` works right up until a fourth step exists, and then every consumer is subtly wrong at once. The turn still says *who* moves — the phase says *what they are being asked*.
- **Being out of the game is asked at `IsAlive`, and being dealt into the next hand at `PokerGameMode.CanBeDealtIn` — never at the five places that used to ask both by hand.** `IsAlive` is `HallucinationRate < MaxHallucination` and nothing else: blood is still tracked and still drawn on the body, but running out of it is not what ends a player. `CanBeDealtIn` once added the purse where a table played for money; with the money game gone it is `IsAlive` alone, and keeps its own name because "can this player be dealt in" is the question the deal and the start button ask. The deal and `PokerWaitingStage` mark anybody it refuses `Dead`, and `DealablePlayerCount` counts through the same predicate so a table of corpses cannot start a hand. They keep the chair and watch.
- **Hallucination is its own currency and does not touch blood.** `PokerPlayerData.HallucinationRate` climbs 0→100 and reaching the ceiling is elimination; `Health` stays the blood that fingers are drawn from. Mapping one onto the other looks tidy and is the trap — the finger display counts *damage* against `MaxHealth`, so borrowing it would make a player at full blood lose fingers to a mouthful of mushrooms. Both are public, because the round's two real decisions (what to wager, who to feed the Colorful cap) are choices about who is closest to going under.
- **A mushroom effect asset is one object for every kind, because the kind arrives as a parameter.** `PokerItemEffect.ConsumeServer(gameMode, eater, itemType)` hands the kind in, so `PokerItemHallucinationEffect` can ask whether this eater has met it before (`PokerItemConsumeController.HasConsumed`, read off its public `Consumed` list, lasting the whole match) and charge the larger gain if not — one asset, four caps, and the price is data rather than four near-identical assets to keep in step. A kind nobody has recorded (the plain chip included) must read as *never eaten*, so an unconfigured table charges the full gain rather than silently handing out the discount forever.
- **A value with named kinds is an enum, and a list of them is a list of the kinds — never a bitmask.** `PokerItemDatabase` handed out a `byte` that travelled through the pot ledger, the wallet, the wager action and every effect, and at none of those points did anything say what a 4 was; `PokerItemConsumeController` then kept "which kinds have you met" as an `int` with a static `TypeBit` helper, which could only answer about the first thirty-one values and quietly said *never eaten* for anything past its width. `PokerItemType` names them, `Consumed` is a `NetworkList` of them, and each database row **names the kind it describes** instead of taking it from its position — so reordering the list is a tidy-up rather than a silent re-typing of every stake already dealt. Two things this costs. `NetworkList<T>` wants `T : unmanaged, IEquatable<T>` and a bare enum satisfies only the first half, so `PokerItemUnit` wraps it with implicit conversions both ways — the same reason `CardData` is a struct. And **an enum's values are what replicate, so they are fixed for the life of a save**: keep the numbers the database was already handing out (Green stayed 1, Colorful stayed 5, so no ledger changed meaning), renumber nothing, and let a retired kind keep its value rather than passing it to the next one.
- **A record is a fact about a player; what it costs is the business of whatever charged it.** `PokerPlayerItemController.ServerConsume(itemType, newTypeGain, repeatGain)` took two prices as arguments and applied the hallucination itself, which put the one decision the mushroom round is played for inside a class that only exists to remember things — and any second kind wanting to read the same record differently would have had to add a third and fourth argument. `PokerItemHallucinationEffect` now reads `HasConsumed`, writes the record and charges its own price; `PokerItemConsumeController` keeps the list and answers questions about it. Renamed from `PokerPlayerItemController` for the same reason: a stockpile of things a player can choose to use is a different question with a different lifetime, and it will want its own component rather than more verbs on this one. Rename with `AssetDatabase.MoveAsset` so the guid carries and the prefab keeps its component, and put `[FormerlySerializedAs]` on any field that held it.
- **How something ended is one value, and only one ending is allowed to say what was in the hand.** The deleted accusation's `PokerReportResult.Outcome` was `Dropped`/`Conceded`/`Judged` rather than a `Called` bool the UI then read amounts alongside — three states inferred from two fields is how "the accuser backed down" came out on screen as an **INNOCENT** card, publishing the exact thing they had just paid not to find out. `WasCheater` meant nothing unless the outcome was `Judged`, and the feed returned early on `Conceded`: the fold that caused it was the whole announcement. Backing down also skipped the judging pause outright — that pause is the table getting ready to be told something, and holding everyone there only promises a verdict that is never coming.
- **The pot is the ledger, and one class writes it.** `PokerGameData.PotItems` is the whole pot — one `PokerBetItem` (owner, phase, `ItemType`) per cap staked, so "how much" is a count and "whose, and what" is a query on the same list. It used to be the itemised twin of a scalar `PokerGameData.Pot` the money rules computed with; the scalar is deleted, and with it the chance of the two drifting — the seat-release sweep once added to `Pot` from `PokerGameMode` directly, which is exactly the second writer that makes a mirrored value silently wrong. Every write still goes through `PokerTableUtility` (`WagerItem`, `SwapPotToLosers`, `ServerTakePotItem`, `ResetPot`).
- **A settlement nobody selects is a branch that only ages.** `PokerSettlement.LoserEatsPot` was the plate-feeding case and no preset in the project ever chose it: it kept `SettleByEating`, an `_eaters` buffer and `PokerTableUtility.FeedPot` alive in the one place a hand pays out, and `FeedPot` was still calling `ConsumeServer` straight from the settlement — the exact shape the "a round's consequence is a beat" rule replaced everywhere else. So the dead path was also the wrong path, and the only thing keeping it honest would have been a preset that used it. It was deleted (the rest of `PokerSettlement` followed once the mushroom round was the only game left — the showdown now always calls `PokerTableUtility.SwapPotToLosers`). Read the presets before deciding a branch is load-bearing — `FindAssets("t:...")` and print the serialized value, which also proves nothing moved afterwards.
- **A stake with no size still has a size the table sets.** A player wagering chooses only the *kind*; how many caps that puts up is `PokerItemWagerStage._itemsPerWager`, a serialized number. The two are different questions and keeping them apart is what lets the stake be retuned without the pad, the bar or the server learning a new shape — nothing in the UI changes when it moves from one to three.
- **A kind that can be fed to somebody is not necessarily a kind that can be wagered.** `PokerItemDatabase.Entry.Wagerable` is off for the Colorful cap, and both the random draw and `PokerItemWagerStage.IsWagerable` read it — so it can never be drawn at random, offered by the bar, or accepted by the server. One flag on the data rather than a special case at each of the three places that would otherwise have to remember it by index.
- **How a hand pays out was an enum, never a pair of bools.** `PokerSettlement` was `WinnerTakesPot` and `LosersEatWinnersWager` (since deleted — only the mushroom settlement is left, so there is nothing to choose); two bools would have let a preset switch both on and left the order they were read in deciding the game. The settlement today is `PokerTableUtility.SwapPotToLosers`, where every loser ends up holding a **full copy** of what the winner put up rather than a share — aiming a kind at the whole table is the entire point of choosing one — and a player who folded eats only their own opening cap, which is what folding costs. The losers' own caps are simply gone; winning is worth not having lost and nothing more.
- **The winner names the victim, in public, and cannot decline.** `PokerColorfulPickStage` gives a turn to one player and takes a seat index through `PokerActionType.Target` — the amount carries an identity rather than a size, the same trick the wager plays. Declining would be declined whenever they are ahead, which is always, so the mechanism would switch itself off; the timeout feeds it to the winner themselves, because a silence must not be a way to aim it. Naming yourself is allowed on purpose: being fed a cap is not only a punishment, and a card that rewards eating one has somewhere to live. Somebody already at the ceiling cannot be chosen — feeding them is a move with no consequence at all.
- **Going under is written as the ceiling, not as a flag.** `PokerItemColorfulEffect` adds its gain, rolls against the **new** rate, and on a bad roll writes `MaxHallucination` — so `IsAlive` stays the one question anything asks, and a later sobering could still bring them back. Measured in Play mode: from 40% + a 10% gain, 92 of 200 rolls fainted against an expected ~100. **The roll is shown before it is paid.** `PokerHallucinationRollController` (on `Player_Poker/Hallucination`) takes the number the server already rolled, sends it to every client (`RollRPC(leadIn, roll)`), and writes the ceiling only after lead-in + sweep + result hold (2 s) — a death landing in the same frame as the roll is read off the pose before anybody saw the dice, and a result the table is not given time to read might as well not have been shown. `OnRollSettled(roll, fatal)` is raised on every client the moment the skull stops, and is the seam for any feedback on the result: it plays inside the hold, and the hold is what the skull, the death and the eating beat all wait on. The lead-in stretches to the blink when the gain crossed a rung, so the sweep never plays behind closed eyes. **The effect only queues the roll (`ServerQueueRoll`); the eating beat starts it** with its own pacing, and the RPC carries lead-in, sweep and hold to every client, so no client reads a config and the meter keeps no copy of any duration. `PokerItemConsumeStage.OnEndStage` flushes a queued roll that was never started, or leaving the beat would be a way to survive the Colorful cap. **Config is split by what it answers**: *how much* is the effect assets and the tiers ladder; *when* is `PokerConsumePacing` (`Assets/Configs/Poker/ItemRound/PokerConsumePacing.asset`: bite, gap, handover, impact, roll lead-in, sweep, result hold), referenced by the stage that runs the beat so two eating stages may be paced differently; *what it looks like* is the meter prefab. The one timing that stays elsewhere is the blink, `PokerHallucinationController._transitionDuration`: it runs on every rung change whatever caused it, on the owner client where no stage asset is at hand. **Feedback is its own component**: the meter raises `OnRungCrossed(index, climbed)` as the fill starts and `OnRollSettled(roll, fatal)` when the skull stops, and `UIPokerHallucinationMeterFeedback` answers with placeholder flash / punch / shake on the `Bar/Visual` node — never on `Bar`, which the layout group places — so real VFX or sound replaces one component. **One meter, drawn in two places**: `UI_HallucinationMeter` is handed a `PokerPlayer` — `UIPokerHallucinationBar` binds the local one on the HUD, `PokerHallucinationTagVisual` binds the body it hangs on under `Tag` — and reads everything off replicated state: the fill eases to the rate, a mark per rung of the player's own tiers asset is anchored at its threshold, the skull rests at the end and stops on `roll/100` (inside the fill is under), and `PokerItemConsumeController.Consumed` draws the kinds already met in the order they were met, icons from `PokerItemDatabase.Entry.Icon`. The world binder binds from `Start`, not the first `OnEnable`, because a spawned body is enabled before its synced values are applied.
- **A stake with no size rides the action's `amount` as an identity, not a quantity.** A mushroom wager is one cap and never a sum, so `PokerActionType.Wager` carries the kind's database index where a bet would carry chips — `PokerGameMode.SubmitActionRPC(action, amount)` needed no second RPC, and `PokerItemWagerStage.IsWagerable` is what both the bar and the server size the offer through. `PokerColorfulPickStage` rides a seat index through `PokerActionType.Target` the same way.
- **The pot ledger is the record of who staked what; a copy on the player is a copy the deal wipes.** A round that wagers *before* it deals puts `PokerDealStage` in the middle of itself, and the deal calls `ServerResetForHand` on every player — so a `WageredTypes` list on `PokerPlayerData` lost the first wager halfway through every round. `PokerBetItem` already stamps `OwnerClientId` and `ItemType`, so the ledger answers "what did the winner put up" without a second seeder to keep in step. The same ordering is why the deal no longer touches the pot: `PokerDealStage._clearPotOnDeal` (since removed) wiped it where a Hold'em hand started, and in this round that is the middle of a wager.
- **A serialized field added after an asset was created deserializes to its C# initializer, so a new toggle silently gives every existing asset the old behaviour — including assets created earlier in the same session.** `PokerDealStage._clearPotOnDeal = true` (a field since removed with the money game) was what Hold'em needed and exactly wrong for the mushroom deal, which had been written to disk minutes before the field existed. Nothing warns: the asset is valid, the value is plausible, and the failure is a first wager quietly wiped. After adding a field, set it explicitly on every asset that wants the non-default and **grep the `.asset`** — `LoadAssetAtPath` will happily report the initializer as though somebody had chosen it. A field added to a serialized **struct** is the same trap one level down and reaches every prefab holding one: a focus yaw limit added to the seat pose arrived as `(0, 0)` on both chair prefabs, and taken at face value a zero-width limit is a head an aim can never turn at all — a silent freeze on every seat in the project, worse than the behaviour it replaced. Where a new field is a *bound*, fold the old value into it (`PlayerController.ActiveYawLimits` widens the focus pair to at least the yaw pair) so an un-set one degrades to exactly what the code did before, and set it in the prefabs as well.
- **A chair is handed out, not chosen — and the mechanism that seats a player has one entry point whoever decides.** `PokerSeat.CanInteract`/`CanStand` both answer false: the server seats whoever arrives at the lowest free chair (`PokerGameMode.ServerSeatArrivals`) and nobody leaves while they are at the table. Walking up to a chair was once the other caller (the deleted Sandbox), and `SeatInteractable.SeatServer` stayed the one entry point rather than a second copy of the seating kept in step beside it. A player arriving mid-hand is still seated at once and is `Waiting` until the next deal, because every seat-order helper (`NextPlayer`, `CountInHand`) filters on `CanAct`/`IsInHand` rather than on being in the list. The money gate that used to guard the chair went with the choosing: a stake nobody can meet is the deal's question, not the door's.
- **How many chairs the table is laid with is replicated, and the layout is arithmetic every client repeats.** `PokerGameData.ActiveSeatCount` is written once by the server from the lobby size; `PokerSeatRingVisual` spaces that many chairs evenly around the table and switches the rest off. The chairs are **moved, never spawned** — a scene `NetworkObject` created at runtime comes up with `GlobalObjectIdHash = 0` and never spawns at all — and the count is table state rather than each client reading its own copy of the lobby, because chairs standing in different places on different screens is a desync with nothing to warn anyone. Facing still comes from the chair's own position, so the ring cannot reintroduce the hand-typed yaws that once left four seats pointing 12° off. The radius is measured in `Awake` off serialized references, before anything has been moved: measuring later reads chairs this component has already placed.
- **A component that hides objects holds them serialized, and keys on their authored index — never on a spawn-order registry.** `PokerSeat.All` fills in `OnNetworkSpawn`, so it is in *spawn* order, not `SeatIndex` order, and a chair switched off before it spawns never joins it at all. Laying the ring from that registry while `PokerGameMode` handed chairs out from its own `SeatIndex`-sorted list meant the two disagreed about which chairs existed: a table of six came up with four registered seats numbered 1, 2, 4, 5, and players were seated in chairs that had been switched off. Both now read `seat.SeatIndex` and the ring holds its own `_seats` list, so a hidden chair is still reachable and the two answers are the same by construction. **Edit-mode arithmetic cannot catch this** — 45 geometry checks passed on the broken version, and one Play mode run named it in a single log line.
- **Chairs are filled across the table, not around it.** `PokerGameMode.SpreadSeatIndex` interleaves the two halves of the ring — at four chairs the order is 1, 3, 2, 4 — so two players sit opposite rather than elbow to elbow with half the table empty. The formula takes the **larger** half first when the count is odd (`(count + 1) / 2`, not `count / 2`): at three chairs the naive version sends two arrivals to the same seat and never uses the third, which reads as a player who simply fails to sit down. Only even tables ship today, so that case would have hidden until somebody laid a five-chair table — check a fill order by asserting it visits every chair exactly once at every count, not by looking at the one you use.
- **How many chairs a table is laid with belongs to the table, not the lobby.** `PokerRuleSettings.SeatCount` is what `ServerLayTable` reads; how many people a *room* admits and how many can sit at *this* table are different questions and only the second is a rule. The room screen no longer offers either — `UIRoomSetting._fixedMaxPlayers` is a serialized number and the input field that used to set it is switched off in `Awake`, because a control that ignores what you type into it is worse than no control.
- **A device the game invented is not a device the player is holding.** `VirtualMouseInput` creates a real `Mouse`, so every generic binding matches it: `InputSchemeController` read its events and flipped the scheme back to keyboard the instant the right stick moved the pad's own cursor, which then switched that cursor off — a flip-flop with no error and no log. `SchemeFor` now refuses anything whose `InputDevice.native` is false. The same fact bites the look: `Table/Look` binds `<Mouse>/delta` and `Player/Look` binds `<Pointer>/delta`, both of which the virtual mouse satisfies, so the cursor stick turned the view as well as the pointer. `PlayerController.ReadLookInput` checks `action.activeControl.device is Gamepad` against the scheme and drops anything the player is not actually holding. Reach for `native` and for the active control's device whenever a synthetic device shares a class with a real one; the binding paths cannot tell them apart and never will.
- **Being collected into a match commits a player to the match, not to the hand.** Folding is a decision about these cards; if it also let them stand up with the stake still on them, folding would be the way out of the game. `PokerGameMode.IsCommittedToMatch` releases a player only when they are out of the running — the same `CanBeDealtIn` the deal asks — with two cases decided before that: still in the hand holds them, and `Waiting`, which is somebody who took a free chair mid-hand and was never dealt in, releases them.
- **A chair in the room is not a place in the match.** `PokerItemWagerStage.CanWager` and `PokerColorfulPickStage.CanBeFed` asked "seated and conscious", which is every body at the table — so somebody who sat down halfway through was asked to stake, held the street waiting for an answer, and could be fed the Colorful cap in a match that had been scored around them. `PokerPlayerData.InMatch` is stamped once in `PokerGameMode.StartGame` for everyone seated who can be dealt in, and false for anybody arriving after; `IsPlayingThisMatch` adds `CanBeDealtIn` (conscious) for what counts who is still in the running, and the wager and the feeding ask `InMatch` and `IsAlive` directly. It is **not** folded into `CanBeDealtIn`, which is asked *before* a match to decide whether one can begin — at that moment nobody is stamped in, and a gate reading it would leave the start button permanently dead. `CanDealAnotherHand` counts the stamped players, or a table kept alive by spectators deals hands nobody in them is playing. The deal refuses them by name: `Waiting` (seated, never dealt in) rather than `Dead`, which would say they had gone under. **A spectator is only excluded from what the round *does* to them** — camera states, the HUD and anything else about watching stay exactly as they are, because a viewer following the shot that focuses whoever is acting is the point of being one.
- **Folding is putting the cards down, and that is three things that must not come apart** — the status the rules read, the cards themselves, and the pose the holder is in. `PokerPlayer.ServerFold` does all three, because the five paths that folded a player (a street, a simultaneous street, its timeout, a caught cheat, a departure — most since deleted with their modes) each used to do only the first, so a player caught mid-peek went on studying cards they no longer held. **Mucking is the status alone, never a clear**: `PokerPlayerData.IsFolded` takes every card out of `IsHoleCardInHand` and `IsHoleCardVisible` (the holder's included), and `HandleStatusChanged` raises `OnHoleCardPresentationChanged`, so `PokerHandVisual` plays the cards going face down back onto the table from the path it already has — they lie there until the next deal's `ServerResetForHand` clears them. A `HoleCards.Clear()` here destroyed the hand on the spot, which read as cards vanishing rather than being thrown in. The cost is that "has cards" no longer means "still in the hand": anything choosing among players with a hand asks `IsInHand`, never `CardCount > 0`. The **Fold gesture plays inside `ServerFold` too**, so a timeout is seen folding exactly like a button press, and no stage plays it beside the call.
- **A hand ending and a match ending are two different events, and only one of them is worth announcing.** A match runs itself out over as many hands as the table can still deal: `PokerShowdownStage` asks `PokerGameMode.CanDealAnotherHand` — the match-scoped twin of the `DealablePlayerCount` the host's start button is gated on, counting `IsPlayingThisMatch` — and deals straight into `_nextHandStage`, so the ranking *is* the ceremony between hands and nobody presses anything. `EndHand` puts the cards, the turn and the modules' round away; `EndGame` is that plus `Phase = Finished`. Keeping the phase out of `EndHand` is the point: a beat of `Finished` mid-match unlocks every chair and reads on each screen as the match being over. The match ends only when one player is left who can still be dealt in, and `PokerWaitingStage` is where the stats go back — the one stage that is only ever arrived at with the previous match already finished.
- **What a match is played with resets; what a hand is played with resets more often.** Blood and hallucination carry from hand to hand — reaching the hallucination ceiling is exactly how a player stops being dealt in — so `ServerResetForMatch` is separate from `ServerResetForHand`, and each class owns its own half: `PokerPlayerData.ServerResetForMatch` for the vitals (blood through `ServerResetHealthToStart`), `PokerItemConsumeController.ServerResetForMatch` for the record of what was eaten. Reaching across to set another component's starting value from here would be a second place to keep in step. Author the starting amount *and* its ceiling to agree — `_startingHealth` left at the C# default over a prefab whose `_maxHealth` was tuned down shows one number in the inspector and clamps to another at runtime.
- **The idle table is where a *match* ends — a round passing through it is not one.** `PokerWaitingStage` put every match stat and every served item back on arrival, which is right when the table has been played out and wrong the moment a round loops back through it between hands: everything the players spent the round accumulating went to zero the instant the start button appeared. `_resetMatchStats` is the seam, on for a table that only reaches idle when it is over and off for a round that comes back here each time. Whenever a stage is reused for a second meaning, read what it *does* against both.
- **What may be reached for is opened by the beat that asks, and closed when it ends.** `PokerCardVisual.Pickupable` is set across the hand by `PokerHandVisual.SetPickupable` when the look stage opens and cleared when it closes, and a card already up in the hand is never flagged — so a card stops lifting under the cursor the moment it is taken, rather than hovering for a pick the server would refuse. The camera is held the same way: the shot is requested for the **whole stage** aimed at the seat's card anchor, not per pick aimed at a card. A card is a thing that moves, so a shot held on one would be dragged along by the very pickup it is meant to be framing.
- **A handler unsubscribed by the very act it is meant to survive goes deaf after the first one.** `PokerCardPickController` dropped its `StageId` subscription inside `HandlePick` — a stray line that landed there rather than in the despawn hook — so picking up one card stopped the controller ever hearing the stage change again: the beat opened and never closed, the camera never came back to free flight, and picking stayed open. It watches the id in the `Update` it already runs instead, comparing the raw `FixedString32Bytes` and acting only when it moves. That also closes the real hazard the subscription carried: it had to be taken in `OnNetworkSpawn`, and the table's `Data` may not have spawned by then — binding to nothing there is silent, and the symptom is the same beat that opens and never closes.
- **A per-hand reset must not sweep what another system owns, or that system's setting is a lie.** `PokerPlayerData.ServerResetForHand` used to clear `AbilityIds`, so the ability module's `_clearHandEachRound` set to *off* did nothing at all (field, flag and module are all since deleted): the module carried the stockpile forward and the player's own reset emptied it a moment later. Nothing warned — both writes were correct in isolation, and the symptom was an item that vanished between rounds for no visible reason. An inventory belongs to the module that deals it; the hand reset keeps only what a *hand* owns (cards, bets, who has acted), and a stockpile is emptied by the match reset because it belongs to the match it was built up in. Whenever a flag says "keep this", grep for every other place that clears it.
- **A lifecycle hook must be named after the moment that raises it, or every implementer is quietly wrong.** `PokerGameMode.EndHand` raised `OnGameEnded` on every module — so a module that meant to keep something across hands was emptied at the end of each one, and the (since deleted) ability module's `_clearHandEachRound` set to *off* did nothing whatever. The names now say what they mean: `EndHand` raises `OnHandEnded`, `EndGame` raises `OnMatchEnded` after it. Renaming a hook is not cosmetic — it is how the four implementers get to notice which moment they were actually subscribing to. Beware of testing such a fix through the method you happen to know: calling `ServerResetForHand` directly passed while the real `EndHand` path still wiped the stockpile.
- **A stage sequence wraps to its own first entry, so the last stage must name where the round goes.** `PokerStageMachine` resets its index to 0 at the end of the list, and entry 0 is the waiting room — a table whose final stage just calls `FinishStage()` needs the host to press start after every hand. `PokerColorfulPickStage._nextStage` names the first wager instead. `PokerShowdownStage` is the shape to copy: `_nextHandStage` while the match can continue, `_idleStage` when it cannot, and it calls `EndGame` on that second path — which is also why a showdown left with an empty `_nextHandStage` ends the *match* after every hand rather than falling through to the next stage.
- **A deal that sits in the middle of a round must not rotate the button.** `PokerDealStage.RotateDealer` ran where a Hold'em hand starts, which is the right place there and the wrong place in a round that wagers *before* it deals: the mushroom round's two wagers sit either side of the deal, so the button moved between them and the second wager walked the table in a different order from the first — at two players it read as the order simply flipping. It was switched off by `_rotateDealerOnDeal`, and the dealer button is since deleted outright: the wagers and the deal all go in seat order now. Read every "this is where a hand begins" step in a sequence that begins somewhere else.
- **Where a card lies on the table is a transform in the chair, not the chair itself.** `PokerSeat.CardAnchor` fell back to `SitAnchor` — a point on the *floor* at the player's feet, since a player root is at the feet — so five cards were dealt into the gnome's ankles and no raycast could ever reach them. `Seat_PokerChair` now carries a real `CardAnchor` child on the table top, lying flat with the card's face up and its top pointing away from whoever is sitting there. A fallback that resolves to a plausible transform is worse than a null one: nothing warned, and the cards were "dealt" every hand.
- **A row of cards lying flat steps its depth the way the anchor points, not the way a fan does.** `PokerHandVisual.RowPosition` reused the fan's `-slot * _depthStep`, and the table anchor's forward is *up* — so each later card sank a step into the table and three of five ended up under the surface. Positive is also what a hand dealt onto a table looks like: the card put down later rests on the ones already there.
- **Everybody answering at once is a stage, not something bolted onto the turn before it.** `PokerCardLookStage` is the beat where every player turns their own cards over; nobody holds a turn, and the step ends when the last of them has spent their looks. Folding it into the wager that precedes it would leave one turn ending on two unrelated answers — which cap, and which cards. It offers a `_duration` and ships with it off, which is the table's call and worth knowing the hazard of: with no clock, a player who deliberately turns fewer cards than they may holds the whole table forever, so this eventually needs a way to say "done".
- **A change-mask says what to *animate*; it must never be what decides where a thing belongs.** `PokerHandVisual` moved a card between the table and the hand only for the slots its mask said had changed — so a bit set a moment too early was a move that never arrived, and nothing later noticed, because by then the mask agreed with the data and there was no difference left to act on. The card sat wherever it had been spawned while every replicated value said otherwise, on whichever machine lost the race. Membership is re-asserted for **every** card on every presentation change (`HandOver(i, moved & (1 << i))`), and the mask is demoted to deciding which one travels — an animation is a statement that something happened, and a card merely being put right had nothing happen to it. Both halves are no-ops when there is nothing to do, so re-asserting all five costs nothing. The same reasoning gives `HandOver` its other fix: it drops a card from the group it does *not* belong to even when the target already holds it, because the early-out that skipped that left a card counted by both, and the group that does not own it still counts it when it spaces the rest. A mask is a memory of what was drawn, and it can only ever be as right as every event that reached it; the data is the thing that knows.
- **A change-guard covering two questions needs two masks, and what it redraws is the difference — not the whole thing.** `PokerHandVisual.HandleStateChanged` guarded on the face-up mask alone, so turning a card over redrew its face and never re-laid the hand out — the card came up face up and stayed lying on the table, which is the entire pickup nobody could see. Which cards are *face up* and which are *up in the hand* are different questions with different answers (a showdown puts a revealed hand back down), so each has its own mask and either changing re-lays the hand. Then the redraw itself has to be the XOR: re-setting every card played the flip on all five when one was turned. A guard answers "did anything change"; what gets redrawn is "which one". Both masks clear in `ClearCards`, or the first card of the next hand reads as no change at all.
- **The same XOR decides what is redrawn *and* what is animated; a re-layout tweens only what actually moved.** `PokerHandVisual.Layout` took one `animate` flag for the whole hand, so picking a card up re-placed all five with a tween — and `PokerCardVisual.PlaceAt` adds a `sin` arc to whatever it animates, an arc that exists so a card *leaving* the table rises off it rather than grinding through it. The four cards merely closing the gap therefore jumped into the air and settled again every time one was taken. `Layout(int animateMask)` takes the same difference the face redraw already takes (`inHand ^ _shownInHandMask`), so the card that changed hands travels and the rest slide to their new slot with no arc; a late-join rebuild passes `0`, because a hand being shown as it already stands has nothing to travel from. Whenever a view re-places a whole group after one member changed, ask which of them actually moved — an animation is a statement that something happened, and playing it on everything says it about the wrong things.
- **A shot about *you* aims at a fixed point in front of you, never at your own face.** `PlayerRigController.FocusPoint` is where somebody else's head aims — face height on the full body rig, which is the rig they render. Pointing your own eye at your own copy of it aims it at something a hand's breadth away on your own chest: the solver has nothing sane to answer with and the head comes out wrenched round, which reads as a broken rig rather than as a shot pointed at itself. `SelfFocusPoint` is the other half, and it is deliberately **a fixed child of the player root, hung off no model at all** — only the owner ever reads it, and the rig the owner renders is the hand-only one, so a point on the body rig would freeze with it (`Gnome_rig` is `CullUpdateTransforms` and is switched off for its owner, while `Gnome_HandOnly` is `AlwaysAnimate`). A point on the root cannot freeze and cannot be culled. Anything that can be about either you or somebody else needs both points, and asking `IsOwner` is what picks.
- **Which way a sitter faces is a transform on the chair too, and it is what "the wide shot" turned out not to need.** `PokerSeat.AheadAnchor` sits `(0, 0.819, 1.1634)` in seat space — **the seated eye's own height**, the ring radius along the seat's own forward — so every chair's copy resolves to the same world point, the middle of the table, and the shot comes out level. It was authored at `0.5925` and called head height, which is 0.227 below the eye (`Player/FirstPersonCamera` is at `0.819`) and aimed the wager shot **11° down** on your own turn; `SelfFocusPoint` had the same defect at `0.45`, which is **39° down** over its 0.454 of reach and is what made the eating beat read as staring at the table. Neither is guessed: a point meant to be looked at straight is level with the eye, and the check is `-Atan2(dy, dz)` against the camera's own local position, measured 0.00° for both. Raising it keeps the convergence, because every seat still aims at one shared point — only the height moved. A shot that wants "the room from where I sit" is then the ordinary look-at aimed at that, needing no second camera and no scene marker: the camera's own field of view already holds the table from any seat. It is the one seat anchor with **no fallback** — a cap or a card has to land somewhere, so those may resolve to something plausible, but a gaze does not, and a plausible wrong answer here is a head aimed at the floor with nothing to say why, which is exactly what the card anchor's fallback to the feet once did.
- **Everything authored about a place at the table belongs to the chair.** `PokerSeat` holds `CardAnchor` and `ItemAnchor`, both flat transforms on the table in front of that seat, and `PokerItemPotVisual` looks the spot up from the item's own `OwnerClientId` rather than laying the pot out around the table's middle. Two things follow. A stake lands in front of whoever put it up, which is the only thing the table is actually reading during a wager. And retuning where anything sits is one edit to one chair prefab that reaches every seat — the table visual owns none of it, so a second mode with a different table needs no second layout.
- **The plate is an object on the table when a stake has no size.** `PokerItemPotVisual` reads `PotItems` — the ledger `PokerTableUtility` already writes as the whole pot, so there is no second seeder and a late join replicates the plate as it stands — and puts a cap down on an authored spot with a drop tween. Preset spots rather than computed positions, for the same reason the seat ring measures its radius off serialized references: a layout on a table is something to be looked at.
- **A registry of spawned things is one list for the whole kind, never one per spawner.** Caps were put on the table by two visuals — `PokerItemPotVisual` for what is staked and a plate visual for what a player had been served — and `PokerHallucinationItemTarget` knew only the pot's, so the smiling-mushroom effect changed the caps somebody wagered and left everything handed to them at the settlement wearing its plain face. Nothing warned: the effect was running, its target resolved, and the set it resolved was simply half the caps on the table. `PokerItemCapRegistry` is the one list anything spawning a cap feeds, so "what mushrooms can I see" has a single answer whoever put them there — a runtime object cannot be serialized to, so it has to announce itself. (The plate is gone now, folded into the pot by the rule below; the registry stays, because the next thing that puts a cap somewhere will not be either of them.) A cap is also taken off the register **when it is destroyed, not when it leaves the ledger**, or the one being eaten sheds whatever was painted on it halfway to the eater's mouth; and `Remove` compares with `is null` rather than Unity's own null check, since a reference to an already-destroyed object is still the entry sitting in the list. Whenever a second producer of a thing appears, ask what was resolving only the first one.
- **A thing that changes hands changes owner; it is never copied onto a second list.** The mushroom settlement used to *serve* each loser a fresh copy onto `PokerPlayerItemController.Pending`, drawn by a `PokerItemPlateVisual` of its own — so there were two sets of caps in the game, spawned by two code paths, and everything watching the table found only one of them. `PokerTableUtility.SwapPotToLosers` reads what everybody staked, calls `ResetPot` so every cap on the table comes off, and puts them back through the same `AddPotItems` a wager uses, stamped with the new owner. A settled cap is then spawned by exactly the path that spawns a staked one, lands on the same seat anchor, and is caught by every hook already watching. `PokerItemConsumeStage` eats out of the ledger (`ServerTakePotItem`) and clears what is left on the way out, because a pot that is not wiped by the deal would carry an uneaten cap into the next round; `PokerWaitingStage` calls `ResetPot` too, since a match that ends at the showdown never reaches the eating. The plate, its visual and the `PokerItemArrival` assets went with it — losing the fly-across handover is the price, and the drop the wager already plays is what the settlement looks like now.
- **A round's consequence is a beat, not a line in the settlement.** `PokerTableUtility.SwapPotToLosers` and `PokerColorfulPickStage` used to call `ConsumeServer` where they decided who owed what, so every effect in the round landed in the same frame behind the ranking board and the whole point of the game happened where nobody could see it. They leave the cap standing in front of its new owner instead, and `PokerItemConsumeStage` walks the seats swallowing one at a time with a gesture and a bite duration. The ledger is also what the visual draws, so a cap comes off it as it goes down rather than after: a cap still drawn that nobody is going to eat is worse than no cap at all. Deciding a cost and paying it are two moments whenever the paying is worth watching.
- **A beat paced around a change must wait for what that change sets off, and ask the thing that owns it.** `PokerItemConsumeStage` ran one cap into the next on `_biteDuration` alone, so a cap that pushed its eater across a hallucination rung landed the next one inside the blink `PokerHallucinationController` spends changing rooms — the mouthful nobody saw, at exactly the moment worth seeing. It now reads the rate either side of the effect (never predicted from it: what a cap costs depends on whether that eater has met the kind before) and asks the eater's own controller both questions — `CrossesRung` off the ladder it already holds, and `TransitionDuration` off the number the blink already runs on. A copy of either here would be a second place to keep in step, and `_gapBetweenBites` stays a separate field because "how long a mouthful takes" and "how long between mouthfuls" are two things to tune.
- **A `*Data` class owns state; a verb with a decision in it is a controller.** `PokerPlayerData` had grown to 735 lines and 26 server methods, which is every rule the round has piled onto the model. `PokerPlayerItemController` is the first piece off it: the record of what has been met (`ConsumedTypes`) and the one decision that reads it — a kind you have swallowed before costs the smaller gain — because the record is what sets the price and a record kept elsewhere is a second value to keep in step with the eating that writes it. It lands on the `Items` child, and `PokerPlayer.Items` is how everything reaches it, the same way `ActionAnimator` is reached. The clusters still on the data — the hole cards, the vitals — come off the same way.
- **When art has not decided what a moment looks like, the moment is an asset.** `PokerItemArrival` (since deleted with the plate, see above) was a `ScriptableObject` with one method, and `PokerItemDropArrival` / `PokerItemFlyArrival` were two answers to it: put down in front of you, or handed across from whoever staked it. The visual owned *where* an item ends up and the arrival only *how it gets there*, which is what let the layout be retuned without touching the animation and the animation be replaced without touching the layout. The source it travelled from was the last winner's own place, read off `LastWinnerClientId` rather than replicated again — and an arrival handed no source fell back to appearing in place, so "they were already mine" was not drawn as a handover.
- **A flag a rig needs is named after what it means, not after the first thing that set it.** `Animator_Gnome`'s `Sit` / `Sit_FlipUp` / `Sit_Peek` / `Sit_FlipDown` are hands on the table, picking cards up, holding them, putting them down — that is *holding cards*, and `IsPeekingCards` named one caller of it. Renamed to `IsHaveCardOnHand` and driven from the cards themselves (`PokerHandPoseController`), which is why the check button could go: a control asking for a pose the state already answers is a second answer to a settled question, and the two can disagree.
- **Named animator flags replicate through one controller, not one component per pose.** `PlayerAnimatorStateController` holds a server-written `NetworkList<PlayerAnimatorState>` and puts every flag on both rigs, applying the whole set in `OnNetworkSpawn` so a client arriving mid-hand is not waiting for a change that already happened. `ServerSetBool` is idempotent — a caller may write the same answer on every state change without growing the list — and a parameter the controller does not have is skipped in silence, so a pose can be driven before the art lands. What any flag *means* stays with whoever writes it: this piece carries no poker.
- **Before adding a replicated fact, check whether one already implies it.** `PokerPlayerData.HandOnTable` was added so the second wager could put every hand back down while keeping the faces private — and it was wrong twice over. It was a second value covering ground `HandRevealed` already covers (`IsHoleCardInHand` is derived from it, so a revealed hand is by definition not being held), and the moment it was meant to serve turned out not to exist: laying the hands down mid-wager read at the table as *everybody suddenly putting their cards face down*, because the body animation for "no longer holding cards" is exactly that. It is deleted, and `PokerCardRevealStage` does the whole job with one write — `ServerRevealHand` on every hand still in it, which turns the faces up for the room and drops the cards onto the table in the same change. The tell was the bug report: a feature nobody asked for, describing itself in the one animation the rig had for it.
- **Turning the cards over for the room is a beat, and it happens before anybody is told who won.** `PokerCardRevealStage` sits between the last wager and the showdown: every hand still in it goes face up on the table and the table is given `_duration` to read them, because the ranking board answers the question the cards have only just asked. Folding is how a hand leaves before that — a folder's cards stay face down on the table, and the reveal skips them on `IsInHand`, which a folded status already fails.
- **Adding a stage to a sequence is only half the wiring — every `_handOverStage` that jumps past it is the other half.** `PokerCardRevealStage` went in after the second wager and still never ran, because a street that ends early jumps to its own named stage rather than following the list: `PokerItemWagerStage._handOverStage` pointed at the showdown, which reveals nothing when one player is left (`ResolveContenders` skips `ServerRevealHand` at `inHand <= 1`). The cards therefore stayed face down on exactly the path the round takes most often while testing — a solo table, where the wager ends the moment it opens. Whenever a stage is inserted, grep the preset for every reference that names a stage *by hand* and decide which of them should now go through the new one.
- **A step that runs before the cards exist cannot hand over to a showdown.** `PokerItemWagerStage._handOverStage` is where a street goes when fewer than two players can still act, and on the *first* wager — which runs before the deal — that pointed at the reveal: a table that could not raise two wagerers jumped into the showdown of a hand nobody had been dealt, and published a ranking for it. It goes to the waiting room instead, which is what "there is no hand here" actually means. Read every named exit against *when* its stage runs, not only against what the stage is called.
- **A board that a countdown is running on comes down when the countdown does.** `UIPokerRankingPanel` hides on the showdown list emptying, and the only thing that emptied it was the next `PokerDealStage` — fine for Hold'em, wrong for a round whose deal is in the middle of itself, where the board then sat over the settlement, the pick and the eating. `PokerShowdownStage.FinishShowdown` clears `Data.Showdown` as it hands over, so the beat owns its own board.
- **Furniture is measured, not guessed — and "in front of the chair" is a number about the table.** The seats ring at 1.15–1.177 and the table is a circle of radius 0.795 with its top at 0.423, so a card anchor 0.30 in front of the chair put the hand at 0.850: past the rim, floating in the air between the players. Read the table's own `Renderer.bounds` and place against it (cards at 0.45 → 0.718, staked items at 0.65 → 0.50), the same discipline the seat ring already uses for its radius.
- **A sprite is read from its own -Z, so an anchor that lays one face up points its −Z at the ceiling.** `PokerCardVisual` says so in a comment at the top of the file, and the seat's `CardAnchor` was authored pointing +Z up anyway — which laid every hand face **down** against the wood, and then sent the hover lift (which travels −Z for exactly the same reason) straight down into the table. Two bug reports, one rotation: `Quaternion.Euler(90, 0, 0)` in seat space puts the anchor's forward at the floor, so the card's face is up and its top points at the middle of the table, which is the way round the sitter reads it. Prove it by measuring `-pivot.forward` and checking it is world up — `FaceUp == true` is about which *sprite* is assigned and says nothing about which way the card is pointing. An item anchor is the opposite case and stays upright (identity): a prop stands on the table and is dropped along its own +Y.
- **`EndGame` is the cleanup choke point.** It sweeps every registered player's cards, not only the seated — whoever left a seat mid-hand is outside every stage's reset sweep.

## Asset naming conventions

- Prefabs: `UI_` prefix for UI prefabs (`UI_Screen_<Name>` for full-screen panels, `UI_<Name>` for components). No prefix for gameplay prefabs. `Button_` prefix for button prefabs.
- Animation clips: `Animation_<StateName>.anim`. Animator controllers: `Animator_<Context>.controller` / `.overrideController`. Keep these colocated with the prefab they belong to.
- Scenes: short PascalCase purpose names (`Bootstrap.unity`, `Gameplay_Poker.unity`).
- ScriptableObject assets: PascalCase matching the class name.
- **A font family is a folder holding its faces and their TMP assets** (`Fonts/Skranji/Skranji-Regular.ttf` + `Skranji-Regular SDF.asset`). Font assets are **Dynamic** so a glyph nobody pre-baked — an accent in a Steam name — is rasterised on demand instead of drawing a box, and the bold face is wired into the regular asset's weight table so `<b>` uses the real cut. Created by script, the atlas texture and material must be added to the asset with `AddObjectToAsset`; loose, the asset loads with a broken material.
- **A display font carries `LiberationSans SDF - Fallback` in its fallback table**, so a glyph it was never cut for — a Vietnamese accent, a symbol in a Steam name — comes out in the default face instead of a box. Reach for that asset rather than `LiberationSans SDF`: the plain one is Static with 250 baked characters, the `- Fallback` one is Dynamic over the same TTF and rasterises whatever is asked of it. The project's own strings stay English; the fallback is there for names it does not control.
- **A piece of the world that carries behaviour is a prefab — model, components and its authored anchors together** (`Seat_PokerChair.prefab`, `GameMode_Poker.prefab`, `PokerTableVisual.prefab`), never a scene object assembled by hand. Retuning where cards land is then one prefab edit that reaches every seat; the scene only places instances and sets what differs per instance.
- A spawn point sits where the spawned prefab's *root* belongs, not where the character ends up — player roots are at the feet, so a seat's point stays on the floor and the sitting animation supplies the height.
- **A teleport goes through `NetworkTransform.Teleport`, never through the transform alone.** `PlayerController.Teleport` wrote `SetPositionAndRotation` and nothing else, so the jump existed only on the machine that made it: everybody else received it as one more position delta and *interpolated* the whole way, which on the first seating is the distance from the spawn point to the chair — a player gliding across the room into their seat rather than being in it. `NetworkTransform.Teleport(position, rotation, scale)` marks the state as a jump and the receivers snap. Only the authority may say a jump happened (`CanCommitToTransform`, and this project's `OwnerNetworkTransform` puts that on the owner), so anything else falls back to writing the transform and letting the next authority update have the last word. The `CharacterController` still comes off around it, for the same reason as before — it owns the transform while it is enabled.
- **A prop's collider is fitted from its mesh's *local* bounds, never from a world-axis box you compute yourself.** The environment FBXs are Z-up exports and sit in the scene at `rot x=270`, so the mesh's local Y is the world's Z — a `BoxCollider` whose `size` is taken from `Renderer.bounds` is authored in the wrong axis order and comes out lying on its side. `center`/`size` from `MeshFilter.sharedMesh.bounds` are already in the collider's own local space, and the transform's rotation and scale then apply for free. Nothing warns about the wrong one: a box of plausible dimensions in the wrong orientation reads as correct in the inspector and surfaces only as a player walking through one face of a crate and bouncing off thin air beside it. Verify by comparing `Collider.bounds` against `Renderer.bounds` — both are world AABBs, so a correct box matches to within a couple of centimetres (`Gameplay_Poker`'s room props: 36 of 36).
- **An environment prop carries its collider from the model importer, not from a box fitted by hand in the scene.** `addColliders` on the FBX gives every instance a `MeshCollider` that follows the actual geometry, arrives with the model, and needs no scene override — the perimeter `Bounds/Wall_*` boxes and the seat prefabs are the only hand-authored colliders left in `Gameplay_Poker`. Turning that flag on over a scene that was already fitted with primitives is where it bites, in two silent ways found together. Every prop that had a box keeps it **and** gains the mesh one, so the room runs two colliders per object with nothing complaining; and a prop whose auto `MeshCollider` a previous pass had *removed as an override* gains nothing at all, because the flag was already on and the removal outranks it — 13 barrels sat with only their box while the other 23 props sat with both. Fixing it is one pass: revert the removed-component overrides, then delete every `BoxCollider` that is an added-component override on an FBX instance (`PrefabUtility.IsAddedComponentOverride` is what separates those from the walls and the chairs, which are not prefab instances). Two older lessons survive for anything still fitted by hand: a box is built from `MeshFilter.sharedMesh.bounds`, never from `Renderer.bounds` — these FBXs are Z-up exports sitting at `rot x=270`, so a box sized from world bounds comes out lying on its side and reads as correct in the inspector; and what is worth colliding at all is read off the `CharacterController` (`height 0.647`, `stepOffset 0.30`), since a prop whose bottom sits above ~0.70 cannot be reached and one under the step offset is walked over regardless.
- **Measure a seated fit with the Animator running, never with `AnimationClip.SampleAnimation`.** The two disagree, and the difference is the whole answer: `SampleAnimation` writes only the clip's curve paths, so a root node the curves do not name stays at its bind pose, while the Animator also writes the generic avatar's root node from the clip's root motion settings. On the gnome sit clips that is a 17cm lift — `Root_M` local Y `0.2825` under the Animator against `0.1788` sampled — so a chair fitted from a sampled pose leaves the character floating in play. Sample only to read a clip's authoring intent; take every number that furniture is built from out of Play mode.
- **A seat's facing is derived from where it stands, never typed.** `Gameplay_Poker`'s six chairs carried hand-typed yaws off a clean hexagon (0/60/120/180/240/300) while four of them actually sat at ring angles `±47.735°`/`±132.265°` and a radius of `1.1769` rather than `1.15` — so those four faced `12.265°` away from the table and the sitter's hands landed skew on it. The two on the Z axis happened to be right, which is exactly why it survived: half the table looked fine. Compute the yaw as `Atan2(-x, -z)` from the seat's own position and the error cannot be introduced again. The pose itself was never at fault — the wrists measure `(∓0.5290, 0.4232, 0.0249)` in the character's own frame, symmetric to four decimal places, so any skew on the table is the seat's angle and nothing else.
- **A component that recomputes a layout has to be able to stand down, or hand-authoring it is impossible.** `PokerSeatRingVisual.Place` writes every chair's position *and* rotation on `OnEnable`, so a designer who squares the chairs up in the scene and turns the model to taste watches all of it snap back the moment they press Play, with nothing logged and nothing in the inspector to explain it. `_placeSeats` off leaves each chair exactly where the scene put it and keeps only the hide-and-show half, which is the half that answers to a replicated count. The cost is real and is the reason it stays on by default: a table laid for two then seats them at adjacent corners of a square rather than opposite each other, which is the whole reason the ring exists.
- **A model that is turned wrong is fixed in its own prefab, not corrected in whatever code aims it.** The first answer here was a `_facingOffset` on the ring visual, turned onto the derived facing — and it put the same angle in two places, left the seat transform lying about which way the chair looks, and would have gone stale the moment the art was re-exported. The chair's own child carries the correction inside `Seat_PokerChair`, so the seat root goes on meaning "square to the table" everywhere that reads it — the card and item anchors included.
- **Re-authoring the chairs redefines the ring, because the radius is measured off them.** `_radius` at zero averages the distance of every serialized chair, so trimming a six-chair hexagon to four and squaring them up sets the radius to whatever was authored. Carrying the old average across (the four survivors measured `1.1634302`, so the square was laid at exactly that) keeps play mode unmoved by what was meant to be a tidy-up of the scene view; picking a rounder number would have shifted every seat relative to a table nobody re-measured.
- **An Animator on a rig whose renderers are all disabled freezes.** `PlayerVisual` switches off the body rig for the owner and the hand-only rig for everyone else, and the default `CullUpdateTransforms` then stops writing that rig's transforms entirely — its bones hold whatever pose they were last given. It reads as a rig that animates correctly, because the stale pose is a real pose. Set `AlwaysAnimate` on any rig that is hidden but still has to be measured, drive a prop, or feed a bone lookup.
- **Fix "this object is switched off" in the prefab that owns it, never with a scene override.** `Screen_Loading` was inactive inside `UI_Manager.prefab`, and the scene was carrying an `m_IsActive` override to switch it back on — so the loading screen worked only for as long as that one override survived, and it did not. Set it in the prefab and revert the override (`PrefabUtility.RevertPropertyOverride`) so the scene stops disagreeing; an override that merely repairs the prefab is a bug waiting for the next merge.
- **A scene re-serialized by the editor is not automatically noise — read whose prefab the guid belongs to before reverting it.** Discarding `Bootstrap.unity` after a rebase threw away an `m_IsActive: 1` override on the `UI_Manager` instance that was switching `Screen_Loading` on, and the loading screen went dead again with nothing to explain it. Map the guid to its `.meta` first (`grep -rl <guid> Assets --include=*.meta`); a `git checkout` of a scene is a content change, not a cleanup.
- **A scene instance's override beats the prefab, so check the scene before believing a prefab edit landed.** `Gameplay_Poker`'s `GameMode_Poker` instance overrides `_sequence`, which means the preset the match actually runs is the scene's, not the prefab's — change one and the other silently keeps deciding. Same for any serialized value a designer has touched in the scene.
- **`SetDirty` + `AssetDatabase.SaveAssets()` is not a write.** Two `PokerShowdownStage` presets took a `SerializedObject` edit, reported the new value back correctly, and were still unchanged in the `.asset` on disk — `SaveAssets` flushed nothing and said nothing. `AssetDatabase.SaveAssetIfDirty(asset)` wrote them. Same lesson as the prefab saves below, with a different API doing the lying: name the asset you mean, then grep the file.
- **"Read it back from disk" means the file, not `LoadAssetAtPath`.** That returns the *in-memory* asset, so a verification pass built on it happily reports the change you just made even when the write never reached the file — three separate fixes read back green and were all still absent from the `.prefab` on disk. The tell was in the console, not the tool result: `Asset Database is set to Read Only, but it has found out-of-date assets`, with `SaveAsPrefabAsset` returning `false` and `SaveAsPrefabAsset` on an instance returning `null`, neither of them logging a reason. Check `git diff` or `grep` the asset file itself, and treat a `false`/`null` from a save API as a hard stop rather than something to retry through. `PrefabUtility.SavePrefabAsset(go, out var ok)` on the asset loaded in place succeeded where the `LoadPrefabContents`/`SaveAsPrefabAsset` round trip did not. That route is not reliable either — it returned `false` twice in one session on a prefab it had just saved, again with nothing logged. When both save APIs refuse, write the value into the `.prefab` YAML directly and `ImportAsset(ForceUpdate)`, then read it back through `SerializedObject`: the file is the source of truth and the editor will pick up an honest edit to it.
- **A prefab edit is not done until it is read back from disk.** `SaveAsPrefabAsset` returned without complaint on an edit that deleted a child, and the child was still there on the next load — the failure only surfaced later as a missing script on the object that was supposed to be gone. Use the `out bool` overload, then `LoadAssetAtPath` again and check the thing you changed; the same lesson `Screen_Loading` and the button tints already taught, now with the save itself lying.
- **A PNG under `Assets/Textures/**` imports as a Sprite because a Preset says so, not because anyone remembered.** `Assets/Settings/Presets/UISprite.preset` carries the settings the project's UI art already uses — Sprite/Single, no mipmaps, Clamp, Tight, 100 PPU, Uncompressed, alpha as transparency — and it is registered in the Preset Manager against `glob:"Assets/Textures/**"`. The filter is the whole point and must not be widened to all textures: `Assets/Art/**/Texture` is full of 3D material maps that have to keep arriving as Textures with mipmaps and Repeat. Build the preset from a throwaway seed PNG rather than from an existing sprite, or that sprite's own 9-slice border becomes everyone's default. Verify it the only way that means anything — import a fresh PNG into each of the two places and read the importer back.
- **Move assets with `AssetDatabase.MoveAsset`, never by moving files on disk** — it carries the `.meta` and the GUID, so references survive. After a batch move, open the affected prefabs and scenes and check for null materials and missing scripts.
- **Renaming a serialized *field* silently drops its value, even when the guid survives the file rename.** `AssetDatabase.MoveAsset` carried every script's guid through the Mushroom→Item rename, so no prefab lost a component and nothing logged a word — but `_mushroomDatabase`, `_mushroomAnchor` and `_capPrefab` were still the keys in the YAML, and Unity would have deserialized the renamed fields as null the first time each prefab was saved. The failure is a table with no database, chairs with no item spot and a pot that draws nothing, all of them looking like features that were never wired. After renaming a field, grep every `.prefab`, `.unity` and `.asset` for the **old key** and rewrite it in place; the check is that the property reads back non-null through `SerializedObject`, not that the component is still there.
- **A mechanism is renamed when the game outgrows the one thing it was built for, and prose is not part of the rename.** `PokerMushroom*` became `PokerItem*` — database, effect, wager stage, consume stage, pot and plate visuals, `PendingItems`, `ServerQueueItem`, `WagerItem`, `PokerSeat.ItemAnchor` — because a stake is an index into a catalogue and nothing in any of it knows what a mushroom is. The comments still say cap and mushroom where they describe *this* game, which is the same split the naming rule already asks for: domain-agnostic mechanism, concrete domain code. What tells two stakes apart is a prefab per entry (`PokerItemDatabase.Entry.WorldPrefab`), never a tint on one shared model — a colour is how a placeholder distinguishes things, not how a game does.

## Editor settings that affect how you write code

- **Domain Reload is disabled** (Scene Reload only). Static fields, static events, and singleton `Instance` properties survive between Play sessions. Every class holding static state must reset it via `[RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.SubsystemRegistration)]` — see `SteamController`, `GameNetworkManager`, `GameModeController`, `UIManager`. A `static event` is the dangerous one: reset it to `null` there rather than trusting `OnDisable`, or it keeps handlers pointing at objects destroyed two play sessions ago. `static readonly` constants are exempt.
- **Auto Refresh is disabled.** After writing scripts outside the Editor, trigger `AssetDatabase.Refresh()` manually before expecting a recompile.
- **A `ProjectSettings/*.asset` written through an API lives in memory until the project is saved.** `Preset.SetDefaultPresetsForType` reported the new entry back correctly through `GetDefaultPresetsForType` while `PresetManager.asset` on disk still read `m_DefaultPresets: {}` — the same lie `SetDirty` + `SaveAssets` tells about prefabs, with a different API. Follow it with `AssetDatabase.SaveAssets()` **and** `ExecuteMenuItem("File/Save Project")`, then grep the file.
- **Delete through `AssetDatabase.DeleteAssets(paths, failed)`, never from the shell.** The single-asset `AssetDatabase.DeleteAsset` is refused by the tool before the command runs — a command that so much as *contains* the call is rejected whole ("User interactions are not supported"), even when the line would never execute, so nothing earlier in it happens either; empty folders go through the batch call too. The batch call goes through: measured, it removed the file and its `.meta` and `AssetPathToGUID(..., OnlyExistingAssets)` came back empty in the same command. That matters most for scripts — a `.cs` deleted from the shell freezes the compilation graph (see below) and needs a person at the editor, while one deleted through the database recompiles normally. Before deleting, prove the shipping scenes do not reach the asset (`AssetDatabase.GetDependencies(buildScenes, true)`) and refuse the batch if any of it is still reached.
- **A `RunCommand` cannot import a *new* asset, and it reports success either way.** Writing three new `.cs` files and calling `AssetDatabase.Refresh`/`ImportAsset` logged no error, and `AssetPathToGUID` even handed back a fresh guid for each — while no `.meta` reached disk, `LoadAssetAtPath<MonoScript>` stayed null, `FindAssets` returned **0**, and every compile failed with CS0246 against a file sitting right there in the folder. The tell is that pair: a path that resolves to a guid but finds nothing. Editing an *existing* tracked file works fine, which is why this only bites when a feature adds its first new script. `AllowAutoRefresh()` is not the fix and is actively harmful — it decrements a counter the project keeps at zero and the editor then asserts `m_DisallowAutoRefresh >= 0` on every refresh until it is paired back. New files need a real import from the editor itself (focus it, or Ctrl+R with Auto Refresh off), so plan on handing that step to whoever is at the machine rather than reporting the code as compiled.
- **A `.cs.meta` can be written by hand, and Unity adopts the guid in it.** `fileFormatVersion: 2` plus `guid: <32 hex>` is the whole file (that is what every script meta in this project is), so a feature's new scripts can be given their guids from the shell and the prefab and scene work that points at them stops waiting on the editor. Measured: eight metas written with `/dev/urandom` guids, and `AssetDatabase.AssetPathToGUID` handed back exactly those eight after the import. Check the guid appears in no other file first — the odds say it will not, and one collision is a reference silently resolving to the wrong asset.
- **When a script is deleted outside Unity, the compilation graph can freeze holding it, and nothing in a `RunCommand` will unstick it.** The symptom is `error CS2001: Source file '…' could not be found` and, downstream of that, *every* type in `Game.*` failing to resolve because the assembly never builds — which reads as the new code being wrong rather than as the old code not being gone. Diagnose it with the two probes that actually answer: `AssetDatabase.AssetPathToGUID(path, AssetPathToGUIDOptions.OnlyExistingAssets)` — the default overload happily returns a guid for an asset that no longer exists, so it cannot tell you anything — and `CompilationPipeline.GetAssemblies()`'s `sourceFiles`, which is the list the compiler is actually handed. A frozen graph shows both halves at once: the deleted file still in the list, and files added since not in it. None of `ImportAsset` on the file, `ImportAsset` on the folder recursively, `AssetDatabase.Refresh`, `ExecuteMenuItem("Assets/Refresh")`, `RequestScriptCompilation`, `RequestScriptCompilation(CleanBuildCache)`, or clearing every MPPM `Library/Bee` and generated `.csproj` moved it — and `AssetDatabase.DeleteAsset`, which would, is refused inside a `RunCommand`. It needs the editor window focused by a person. Plan a change that deletes a script around that, and delete the script *from the editor* rather than from the shell where there is any choice.
- **Make a folder with `AssetDatabase.CreateFolder`, and never with `Directory.CreateDirectory` + `Refresh`.** The refresh does not take effect inside the `RunCommand` that asked for it, so the folder exists on disk and not in the database — and then every write into it fails *quietly*: `SaveAsPrefabAsset` returned `false` for six prefabs in a row and `CreateAsset` left the object null, which surfaced later as an `ArgumentException` from a `SerializedObject` built on it rather than as anything naming the folder. Materials into the same missing folder appeared to succeed. Create the folder in its own command, check `IsValidFolder` before writing, and reload the asset from its path after `CreateAsset` rather than keeping the instance you passed in.
- **Check which editor the Unity connection is attached to before trusting a single write.** An MPPM virtual player runs with `-readonly`, so through it `SaveAsPrefabAsset` returns `false`, `SaveAssets` flushes nothing, and `AssetDatabase.IsOpenForEdit` is `false` for every asset in the project — the whole session reads as a string of silent no-ops, and the edits look correct right up until the file on disk is checked. `Application.dataPath` names it outright: the main editor answers `<project>/Assets`, a virtual player answers `<project>/Library/VP/mppm*/Assets`. Read that first and re-point the connection at the main editor rather than diagnosing each failed write; the "Asset Database is set to Read Only" console line is the same fact arriving too late.
- **Deleting a script fails the compile with CS2001 against an MPPM mirror until that virtual player's build cache is cleared.** The mirror's `Assets` is a symlink, so the file is already gone there — what is stale is `Library/VP/mppm*/Library/Bee` and the generated `.csproj`, and the main editor's own clean rebuild never reaches them. Delete those two, then `RequestScriptCompilation(CleanBuildCache)`. Closing the virtual player also works but throws away a running test session, so clear the cache first.
- **UI uses TextMeshPro**, never legacy `UnityEngine.UI.Text` — `TextMeshProUGUI`, `TMP_InputField`, `TMP_Dropdown`, and `TMP_Text` in code.
- **Input uses `InputActionReference` serialized fields**, never string lookups like `_playerInput.actions["Look"]` — see `PlayerController`.
- **A mouse reports a delta and a stick reports a position, so they are integrated differently or the pad crawls.** Mouse delta is already a per-frame amount and must never be scaled by `deltaTime`; a stick says how far it is being held, which is a rate and means nothing until multiplied by the frame length and a degrees-per-second speed. Worse, a `Value` action only raises `performed` when its value *changes*, so a stick held at full deflection stops reporting entirely — the view turns about a degree and stops. `PlayerController.ReadLookInput` is therefore polled from `Update` (look is the continuous work the no-polling rule already exempts) and branches on `InputSchemeController.IsGamepad`, with `_lookSensitivityX/Y` for the mouse and `_gamepadLookSpeedX/Y` plus an exponent for the stick. The symptom reads as "controller sensitivity is too low", which sends you tuning a number that was never the problem.
- **Which device is in hand is `InputSchemeController`, driven by `InputSystem.onEvent` and not by `onActionChange`.** `onActionChange` only speaks for actions that are enabled and bound, so a pad button pressed on a street where nothing is listening would never switch the scheme and every badge on screen would keep naming a key nobody is using. Filter events through `EnumerateChangedControls(device, 0.15f)` — a stick at rest still streams state and a mouse reports jitter, so an unfiltered event is not evidence anyone touched anything — and early-out when the device already matches, which is almost every event.
- **Every binding carries its control scheme, or masking silently blanks the UI.** `GetBindingDisplayString(InputBinding.MaskByGroup(...))` is what makes a badge name the device in hand, and a binding whose `groups` is empty matches no mask and comes back as an empty string. The whole `Table` map was authored that way, so adding the mask would have blanked all nine key badges on the action pad at once. Assign the groups in the same change that introduces the mask. Composites are the exception worth knowing: `Move`'s WASD composite returns empty under a keyboard mask, so a "WASD to move" hint cannot be read this way.
- **A "nothing changed" guard has to be told that a rebind is a change.** `PlayerInteractionController.RefreshPrompt` (since deleted with the Sandbox's walk-up interaction) early-outed when the action name matches what is already shown, and the name does not move when the device does — so the prompt would go on naming a keyboard after the player picked up a pad. Clear the remembered value before refreshing, the same defect `UIButton.ResetState` and the old ability wheel's `UIWheelItemView.Bind` were fixed for.
- **Two `RuntimeInitializeOnLoadMethod(SubsystemRegistration)` methods run in an undefined order, so never subscribe to another static's event from one.** `CursorController` listening for `InputSchemeController.OnSchemeChanged` from its own reset would be wiped whenever the other reset ran second and set the event to null. Reset in `SubsystemRegistration`, subscribe in `AfterSceneLoad`, which always runs after every reset.
- **Editing `.inputactions` from script: write `asset.ToJson()` and then prove the action ids did not move.** Prefabs reference `InputActionReference` sub-assets whose fileIDs come from the action ids, so an id that changes silently detaches every serialized reference in the project. Capture `action.id` for every action before the edit, reimport, and compare — 30 of 30 unchanged is the check, not "it looked fine in the inspector".
- **Never call `AssetDatabase.Refresh(ImportAssetOptions.ForceUpdate)`; refresh plainly, or import the one asset you wrote.** A whole-project force reimport re-serializes assets nobody touched, and the damage lands where a serialized value is *resolved* rather than stored — an `InputActionProperty` re-binds itself by name to whichever `InputActionReference` sub-asset the fresh import handed out. `UI_Manager`'s `VirtualMouseInput` came back with its left button moved from `Table/PickCard` to `UI/Click`, and `UI/Click` is bound to the real mouse: every click then pressed the *virtual* mouse's button, `Pointer.current` became the virtual cursor sitting somewhere else, and the press landed on nothing. The report was "clicking the UI does nothing", which points at the UI and not at an import three commands earlier. Two anchor overrides were flattened in the same pass. Plain `AssetDatabase.Refresh()` picks up new scripts perfectly well; when a specific asset needs rereading, name it with `ImportAsset(path)`.
- **`.inputactions` ships two `InputActionReference` sub-assets per action, so a fileID resolves by luck.** Measured on `InputSystem_Actions`: 68 references for 34 actions, every name appearing twice, and a force reimport does not collapse them. So `-5630367516989439448` is `Table/PickCard` in one set and was something else in the other, which is why a prefab pointing at a fileID can silently come to mean a different action. Diagnose by loading every sub-asset and printing name against `TryGetGUIDAndLocalFileIdentifier`, never by reading the fileID in the YAML and assuming it still means what it meant.
- Scene-placed `NetworkObject`s created programmatically get `GlobalObjectIdHash = 0` and fail to spawn. If that happens, remove and re-add the `NetworkObject` component on the saved scene object to regenerate it.

## Rules

1. Keep the two-assembly split (`Game.Runtime`, `Game.Editor`); don't introduce new asmdefs without a real modularity need.
2. Server-authoritative by default — any gameplay state that must be consistent across clients lives in a `NetworkBehaviour`/`NetworkVariable`, not in a locally-mutated field trusted from the client.
3. No XML doc comments or comment blocks; let naming carry the meaning.
4. Follow SOLID, KISS and DRY; prefer industry-standard patterns over bespoke structure, and keep modules loosely coupled and reusable.
5. Extend through `protected virtual OnX` hooks called from a non-virtual base method — never edit a parent class to accommodate a subclass. Never make a Unity message (`Awake`, `Update`, `OnDestroy`) `virtual`: a subclass forgetting `base.Awake()` is a recurring, silent bug.
6. Every system binds and unbinds through explicit paired lifecycle hooks; never poll for a dependency in `Update()`.
7. Animate with DOTween tweens, not hand-rolled `Lerp`/`Slerp` stepped in `Update()`.
8. Never resolve a dependency by searching the scene (`FindFirstObjectByType`, `FindAnyObjectByType`, `Camera.main`) — serialize it, be handed it, or register it.
9. Name a mechanism domain-agnostically and domain code explicitly; the name must state its purpose on sight. Don't abstract until a second real use exists.
10. A serialized value that must match something else is picked from a dropdown, never typed.

## Maintaining this file

**Write the rule down in the same change that establishes it.** A convention agreed only in chat is gone by the next session — these rules are where the project remembers.

A rule earns its place when either is true: **it repeats** (the same correction or the same shape has come up twice — don't wait for a third), or **it matters** (getting it wrong causes a silent failure, a leak, or a bug that is hard to trace back, even if it happened once). A one-off decision with no consequence stays in the code.

When adding one: put it in the section it belongs to instead of appending a new one, cite the file in this repo that demonstrates it, and fix any existing rule it contradicts. A rule that disagrees with the code is worse than no rule, because it will be trusted.
